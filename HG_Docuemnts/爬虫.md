## Dashboard

Dashboard 类似 Kubernetes Dashboard、Airflow Dashboard 和 Prometheus/Grafana，用于集中展示任务、Worker 和实时趋势。

**第一行：核心指标卡**

```text
+----------------+  +----------------+  +----------------+  +----------------+
| 今日采集任务    |  | 成功任务        |  | 失败任务        |  | 当前 Worker     |
| 120000         |  | 119800         |  | 200            |  | 50             |
+----------------+  +----------------+  +----------------+  +----------------+
```

**第二行：实时趋势**

```text
任务数量趋势：折线图
QPS 趋势：折线图
```

**第三行：最近任务**

```text
| 任务 | 网站 | 状态 | 耗时 |
```

### Dashboard.jsx

```jsx
import React from "react";
import { Card, Row, Col, Table } from "antd";

class Dashboard extends React.Component {
  constructor(props) {
    super(props);
    this.state = {
      stats: {},
      tasks: []
    };
  }

  componentDidMount() {
    this.loadData();
  }

  loadData = () => {
    // 调接口
    fetch("/api/dashboard")
      .then((res) => res.json())
      .then((data) => {
        this.setState({
          stats: data.stats,
          tasks: data.tasks
        });
      });
  };

  render() {
    const { stats, tasks } = this.state;
    const columns = [
      { title: "任务", dataIndex: "name" },
      { title: "来源", dataIndex: "source" },
      { title: "状态", dataIndex: "status" },
      { title: "耗时", dataIndex: "cost" }
    ];

    return (
      <div>
        <Row gutter={16}>
          <Col span={6}>
            <Card title="今日任务">{stats.total}</Card>
          </Col>
          <Col span={6}>
            <Card title="成功">{stats.success}</Card>
          </Col>
          <Col span={6}>
            <Card title="失败">{stats.failed}</Card>
          </Col>
          <Col span={6}>
            <Card title="Worker">{stats.worker}</Card>
          </Col>
        </Row>

        <Card title="最近任务" style={{ marginTop: 20 }}>
          <Table rowKey="id" columns={columns} dataSource={tasks} />
        </Card>
      </div>
    );
  }
}

export default Dashboard;
```

## Spider 管理

用于管理 Bilibili Video Spider、Douyin Spider、News Spider 等爬虫实例。

| 字段 | 说明 |
| --- | --- |
| 名称 | Spider 名称 |
| 类型 | 视频等业务类型 |
| 状态 | 运行中、已停止 |
| Worker 数量 | 当前 Worker 数量 |
| QPS 限制 | 例如 `100/s` |
| 最后运行 | 最近运行时间 |

支持新增、启动、停止、编辑、删除和查看日志：

```text

------------------------------------------------

B站视频   RUNNING    20       停止
微博      STOP       0        启动
```

### SpiderManage.jsx

```jsx
import React from "react";
import { Table, Button, Space, Card } from "antd";

class SpiderManage extends React.Component {
  state = {
    data: []
  };

  componentDidMount() {
    this.fetchSpider();
  }

  fetchSpider = () => {
    fetch("/api/spiders")
      .then((res) => res.json())
      .then((data) => {
        this.setState({ data });
      });
  };

  startSpider = (id) => {
    fetch(`/api/spider/${id}/start`, {
      method: "POST"
    });
  };

  render() {
    const columns = [
      { title: "名称", dataIndex: "name" },
      { title: "状态", dataIndex: "status" },
      { title: "Worker", dataIndex: "workers" },
      { title: "QPS", dataIndex: "qps" },
      {
        title: "操作",
        render: (text, row) => (
          <Space>
            <Button type="primary" onClick={() => this.startSpider(row.id)}>
              启动
            </Button>
            <Button>停止</Button>
            <Button>日志</Button>
          </Space>
        )
      }
    ];

    return (
      <Card title="Spider管理">
        <Button>新增Spider</Button>
        <Table
          style={{ marginTop: 20 }}
          rowKey="id"
          columns={columns}
          dataSource={this.state.data}
        />
      </Card>
    );
  }
}

export default SpiderManage;
```

## Spider Engine

Spider Engine 负责 HTTP 请求、Cookie、Header、User-Agent、重试、限流和超时控制。

```go
type Spider struct {
    Name        string
    StartURL    string
    Client      *http.Client
    RateLimiter Limiter
    Parser      Parser
}
```

基础执行流程：

```go
func (s *Spider) Run() {
    resp, err := s.Client.Get(s.StartURL)
    data := s.Parser.Parse(resp)
    Save(data)
}
```

> 示例代码仅表达核心流程；生产实现还需要处理 `err`、关闭响应体、状态码校验、重试和上下文取消。

## 任务调度

生产环境不能依赖 `for + sleep` 循环，应由 Scheduler 投递任务，再由 Worker 集群消费。

```text
Scheduler
    |
Redis Queue
    |
Crawler Worker
```

任务示例：

```json
{
  "type": "VIDEO_DETAIL",
  "url": "xxx",
  "priority": 10
}
```

Redis 队列可使用 `crawler:task:list`，Worker 持续消费：

```go
for {
    task := queue.Pop()
    crawler.Execute(task)
}
```

## Redis

### URL 去重

使用 Redis Set 避免 `BV123` 等 URL 被重复采集：

```text
crawler:url:set
```

```go
exists := redis.SIsMember(
    ctx,
    "crawler:url",
    url,
)
```

### 限流

例如目标站点限制 `100 请求/分钟`，可以通过 Redis Token Bucket 和 `crawler:bilibili:rate` 等 Key 实现分布式限流。

## 数据库设计

大型系统不应只保留最终业务表，建议同时保存原始数据和清洗后的结构化数据，以便重新解析和追溯。

### 原始数据表

```sql
CREATE TABLE crawler_raw_data
(
    id BIGINT PRIMARY KEY,
    source VARCHAR(32),
    url VARCHAR(512),
    content LONGTEXT,
    create_time DATETIME
);
```

`content` 保存原始 HTML/JSON，便于规则变化后重新解析。

### 视频业务表

```sql
CREATE TABLE video
(
    id BIGINT PRIMARY KEY,
    source VARCHAR(32),
    source_video_id VARCHAR(64),
    title VARCHAR(255),
    author VARCHAR(128),
    cover VARCHAR(512),
    play_count BIGINT,
    like_count BIGINT,
    comment_count BIGINT,
    publish_time DATETIME,
    create_time DATETIME,
    UNIQUE KEY uk_source_video
    (
        source,
        source_video_id
    )
);
```

| 字段 | 值 |
| --- | --- |
| `source` | `bilibili` |
| `source_video_id` | `BV1xxx` |
| `title` | `Go微服务` |

### UP 主表

```sql
CREATE TABLE author
(
    id BIGINT PRIMARY KEY,
    source VARCHAR(32),
    uid VARCHAR(64),
    nickname VARCHAR(128),
    fans BIGINT,
    follow BIGINT
);
```

### 标签表

```sql
CREATE TABLE video_tag
(

```

> <h2 id="数据采集平台架构设计">数据采集平台架构设计</h2>

目标不是编写一个简单爬虫脚本，而是建设可扩展的**数据采集平台**。系统不应从 `for + http.Get()` 出发，而应按以下链路设计：

> **采集任务平台 → 调度系统 → URL/API 请求队列 → Crawler Worker → 解析器 → 数据标准化 → Kafka → 存储 → 监控/告警 → Web 管理后台**

针对 B 站等站点，应优先使用开放平台或公开授权接口；B 站提供开放平台和开发者接入能力。([创作中心][1]) 采集公开页面时，必须遵守目标站点的 `robots.txt`、服务条款、访问频率限制以及版权和隐私要求，不得绕过访问控制。Colly 提供 robots.txt、并发/延迟限制、Cookie、缓存和分布式抓取等能力。([Go Packages][2])

> <h2 id="采集任务模型">采集任务模型</h2>

页面采集和接口采集是两类不同的采集任务。

### 页面采集

例如：

```text

```

目标是将页面内容转换为结构化数据：

```json
{
  "video_id": "BVxxxx",
  "title": "...",
  "author": "...",
  "view_count": 123456,
  "like_count": 12345,
  "comment_count": 1000,
  "publish_time": "...",
  "description": "..."
}
```

处理链路：

```text
HTTP
 ↓
HTML
 ↓
DOM
 ↓
Selector
 ↓
字段提取
 ↓
结构化数据
```

---

### 接口采集

例如目标接口返回：

```json
{
    "code": 0,
    "data": {
        "items": [
            {
                "id": "xxx",
                "title": "xxx"
            }
        ]
    }
}
```

处理链路：

```text
HTTP Request
       ↓
JSON Response
       ↓
JSON Decode
       ↓
Schema Mapping
       ↓
标准化
       ↓
Storage
```

**如果合法、公开且稳定地提供了 API，API 采集通常优于 HTML 爬取。**

```text
HTML
  ↓
DOM结构容易变化
  ↓
Selector容易失效
```

```text
JSON
 ↓
字段结构明确
 ↓
更适合机器处理
```

```go
type HTMLParser struct{}
```

```go

    ContentType string
    URL         string
}
```

```text

```

而是：

```text

   ↓

   ↓

   ↓
PAUSED
   ↓

   ↓

```

异常：

```text

   ↓
FAILED
```

人工停止：

```text
RUNNING
   ↓
STOPPING
   ↓
STOPPED
```

## 调度系统

例如用户创建：

```text

```

```text
Scheduler
    │
    ├── Task A → 10min
    ├── Task B → 1hour
    ├── Task C → daily
    └── Task D → manual
```

然后：

```text
Scheduler
   ↓
Kafka
   ↓
CrawlRequest
```

不要让 Scheduler 自己执行 HTTP。

```text

```

> <h2 id="流量治理与可靠性">流量治理与可靠性</h2>

## Redis 的职责

Redis 不应该作为最终事实数据库。

主要用途：

### 去重

```text
crawler:dedup:{task_id}
```

例如：

```text
SHA256(
    method +
    url +
    query +
    body
)
```

得到：

```text
request_hash
```

Redis：

```text
SET crawler:dedup:xxx 1 NX EX 86400
```

如果存在：

```text
跳过
```

---

### 分布式限流

例如：

```text
bilibili.com
```

限制：

```text
10 requests / second
```

所有 Worker 共享：

```text
Redis
```

而不是：

```text
Worker1 10 QPS
Worker2 10 QPS
Worker3 10 QPS
```

最后变成：

```text
30 QPS
```

---

## Host 级别限流

应避免 Worker 数量与并发数叠加后形成失控流量：

```text
Worker = 100
Concurrency = 100
```

然后：

```text
100个Worker
×
100请求
=
10000 QPS
```

应建立分层限流：

```text
Global Limit
      ↓
Domain Limit
      ↓
Task Limit
      ↓
Worker Limit
```

例如：

```text
全局：10000 QPS

bilibili.com：100 QPS

Task A：20 QPS

Worker：5 concurrent
```

最终：

```text
Global
 └── bilibili.com
      ├── Task A
      │    ├── Worker 1
      │    └── Worker 2
      │
      └── Task B
```

Colly 自身也有按域名配置并发和延迟限制的能力。([Go Packages][2])

---

## 代理池

大型系统里代理应该是一个独立服务：

```text
Proxy Manager
```

维护：

```text
proxy_id
ip
port
protocol
region
status
success_rate
latency
last_used_at
failure_count
```

Worker：

```text
Crawler
  ↓
Proxy Manager
  ↓
Proxy
  ↓
Target
```

**代理池应该用于合法的流量治理、区域测试和可靠性，不应该用于绕过目标站点的访问控制、验证码、封禁或其他反爬机制。**

---

## 失败重试

不能：

```go
for i := 0; i < 10; i++ {
    http.Get(...)
}
```

应该：

```text
Request
 ↓
失败
 ↓
Retry Policy
 ↓
是否可重试？
 ├── No → DLQ
 └── Yes
       ↓
Exponential Backoff
       ↓
Retry
```

例如：

```text
1s
2s
4s
8s
16s
```

并且需要：

```text
jitter
```

避免大量 Worker 同时重试。

---

### 错误分类

例如：

```text
429
500
502
503
504
network timeout
connection reset
```

通常可以考虑重试。

而：

```text
400
401
403
404
```

一般不能盲目重试，应检查请求、权限和资源状态。

特别是：

```text
403
```

不要设计成：

```text
403
 ↓
换IP
 ↓
继续打
```

这种思路会规避访问控制。正确设计是：

```text
403
 ↓
Task Error
 ↓
人工检查权限 / API授权 / 配置
```

---

## DLQ

Kafka：

```text
crawler.request
```

失败：

```text
crawler.request.dlq
```

例如：

```json
{
    "request_id": "req_xxx",
    "task_id": "task_xxx",
    "url": "...",
    "error_code": "HTTP_500",
    "error_message": "...",
    "attempt": 3
}
```

UI：

```text
任务详情
   ↓
失败请求
   ↓
DLQ
   ↓
重新执行
```

># <h1 id="MLC_GO-数据采集平台">MLC_GO 数据采集平台</h1>

# MLC_GO 数据采集平台

本文档描述 `MLC_GO` 当前已经实现的 crawler 能力、两种启动方式、Bilibili 推荐接口协议，以及后续接入 Douyin、Xiaohongshu 正式开放平台时的适配器和签名模块设计。

## 一、合规边界

当前实现仅采集第三方公开推荐接口返回的元数据：

- 不下载、解密、转存或代理视频媒体文件。
- 不绕过登录、验证码、设备校验、风控或访问控制。
- 不把第三方内容伪装成本站用户投稿。
- 不把第三方 Cookie、Token、Secret、签名原文写入日志或数据库。
- 不为 Douyin、Xiaohongshu 实现未经授权的逆向签名、私有接口抓取或反爬绕过。

生产使用前必须确认目标平台开放平台协议、服务条款、robots 规则、数据授权范围、存储期限和展示方式。

## 三、Bilibili 推荐采集

### 1. 实际接口

当前已经实际接入：

```text
GET https://api.bilibili.com/x/web-interface/wbi/index/top/feed/rcmd
```

请求参数：

```text
fresh_type=3
ps=<单批数量>
```

请求头：

```text
Accept: application/json
Referer: https://www.bilibili.com/
User-Agent: MLC_GO-HGCrawler/1.0
```

当前环境验证中，匿名请求可以返回 `code=0` 的推荐列表。该结果不代表第三方接口永久稳定，也不代表所有地域、IP 或未来版本都不需要 WBI、Cookie 或正式授权。

### 2. 采集字段

统一模型包含：

| 字段 | Bilibili 来源 | 说明 |
| --- | --- | --- |
| `platform` | 固定 `bilibili` | 平台标识 |
| `contentId` | `bvid` | 第三方内容唯一标识 |
| `title` | `title` | 视频标题 |
| `authorId` | `owner.mid` | 字符串返回，避免前端整数精度丢失 |
| `authorName` | `owner.name` | UP 主名称快照 |
| `coverUrl` | `pic` | 封面地址，HTTP 会升级为 HTTPS |
| `targetUrl` | `uri` | Bilibili 页面地址，不是媒体文件 |
| `durationSeconds` | `duration` | 视频时长，单位秒 |
| `viewCount` | `stat.view` | 播放量快照 |
| `likeCount` | `stat.like` | 点赞量快照 |
| `commentCount` | `stat.danmaku` | 当前实现映射弹幕量快照 |
| `publishedAt` | `pubdate` | Unix 秒转换为 UTC |

推荐流可能混有直播、番剧、广告或其他卡片。当前实现只接受：

```text
goto == "av"
bvid != ""
title != ""
```

同一批数据按 BVID 去重。

### 3. 网络和资源边界

- Endpoint 必须是 `https://api.bilibili.com`，禁止运行时传入任意目标地址形成 SSRF。
- 单次响应最多读取 `2 MiB`。
- 单批最多接收 50 条，默认 12 条。
- 默认请求超时 10 秒。
- 默认进程内限流 `0.2 req/s`，burst 为 1。
- 默认额外重试 2 次，最大允许 3 次。
- 网络错误、读取错误、HTTP 429、502、503、504 可以重试。
- JSON 协议错误、业务拒绝码、固定 4xx 不重试。
- 重试使用指数退避和随机 jitter。
- 错误响应只丢弃最多 4 KiB，不记录完整响应和凭据。

### 4. 任务状态

任务状态单向迁移：

```text
RUNNING -> SUCCESS
RUNNING -> FAILED
```

同一进程内不允许两个抓取任务重叠执行。任务历史最多保留 500 条，推荐数据只保存最近一次成功抓取的内存快照。失败任务不会清空上一份成功数据。

当前内存快照不是持久化数据仓库。服务重启后任务和推荐快照会清空。

## 四、两种启动方式

### 方式一：独立 `cmd/hg_crawler`

#### 单次执行

适合本地验证和 Kubernetes CronJob：

```bash
go run ./cmd/hg_crawler --once --timeout=10s
```

行为：

1. 创建共享 Bilibili crawler manager。
2. 执行一次推荐抓取。
3. 将任务和推荐结果输出到 stdout。
4. 成功以 0 退出，失败以非 0 退出。

#### 常驻独立服务

```bash
go run ./cmd/hg_crawler \
  --addr=:8090 \
  --interval=5m \
  --timeout=10s
```

独立服务提供：

```text
GET  /healthz
GET  /api/v1/crawler/dashboard
GET  /api/v1/crawler/spiders
POST /api/v1/crawler/spiders/bilibili/start
POST /api/v1/crawler/spiders/bilibili/stop
GET  /api/v1/crawler/tasks
POST /api/v1/crawler/tasks
GET  /api/v1/crawler/recommendations
```

如果主业务服务占用 `:8080`，独立 crawler 必须使用其他端口，并由 API Gateway、Ingress 或反向代理转发 `/api/v1/crawler/*`。

### 方式二：随 `main_mlc_project.go` 启动

主应用可以内嵌启动 Bilibili 周期 worker，但默认关闭：

```yaml
crawler:
  bilibili:
    enabled: false
    interval: 5m
    timeout: 10s
    max_items: 12
    retry_count: 2
    rate_per_second: 0.2
    user_agent: "MLC_GO-HGCrawler/1.0"
```

启用方式：

```bash
CRAWLER_BILIBILI_ENABLED=true go run .
```

或在明确的环境配置中设置：

```yaml
crawler:
  bilibili:
    enabled: true
```

主应用生命周期：

```text
loadRuntimeConfig
  -> buildMLCApplication
  -> NewHGBilibiliManager
  -> crawlerManager.Start
  -> app.Serve
  -> app.Close
  -> crawlerManager.Stop
```

主应用模式当前只启动周期 worker，不直接在主业务端口挂载 crawler 管理 API。原因是当前主 API Gateway 尚未配置 crawler 模块的鉴权、限流和舱壁策略。管理 API 由独立 `cmd/hg_crawler` 提供。

### 多副本警告

主应用 Deployment 如果有 3 个副本，启用内嵌 crawler 会产生 3 个独立 worker。HPA 扩容会继续放大请求。

生产环境只能在以下条件之一满足时启用：

1. crawler 所在 Deployment 固定单副本。
2. 仅一个指定实例注入 `CRAWLER_BILIBILI_ENABLED=true`。
3. 实现 Redis lease，确保同一平台同一时间只有一个全局 owner。
4. 使用独立 CronJob，并设置 `concurrencyPolicy: Forbid`。

推荐生产方式仍是独立 CronJob 或独立单副本 worker。

## 六、Douyin 平台适配器设计

### 1. 接入前提

Douyin 适配器只允许接入官方开放平台或已获得书面授权的服务端 API。

需要明确：

- 应用 `client_key`。
- 应用 `client_secret`，仅通过 Secret 环境变量或密钥管理系统注入。
- OAuth 授权范围和 Token 刷新规则。
- API Host 白名单。
- 单应用、单用户和单 IP 限流规则。
- 内容字段授权范围和数据保留期限。

不得实现：

- Web/App 私有接口逆向。
- X-Bogus、a_bogus、设备指纹等未授权反爬参数破解。
- 模拟真实用户设备、伪造 Cookie 或绕过验证码。

### 2. 建议目录

```text
internal/modules/crawler/platform/
├── hg_douyin_platform.go
└── signature/
    ├── hg_signer.go
    └── hg_douyin_openapi_signer.go
```

适配器继续实现统一接口：

```go
type HGDouyinPlatform struct {
    client HTTPDoer
    signer HGRequestSigner
    tokenProvider HGAccessTokenProvider
    limiter *rate.Limiter
}

func (p *HGDouyinPlatform) Name() string
func (p *HGDouyinPlatform) FetchRecommendations(ctx context.Context) ([]HGRecommendation, error)
```

如果开放平台没有“匿名推荐流”接口，应将具体能力命名为授权接口真实语义，例如“授权用户公开视频列表”，而不是伪装成推荐流。

### 3. Token 模块

```go
type HGAccessTokenProvider interface {
    AccessToken(ctx context.Context) (string, error)
}
```

生产要求：

- Token 加密存储。
- 刷新使用 singleflight，避免并发刷新风暴。
- Token 日志完全脱敏。
- 401/Token 过期只允许一次受控刷新重试。
- 不在业务错误中返回 client_secret、access_token、refresh_token。

## 八、通用签名模块设计

签名模块只实现平台官方文档公布的算法。

### 1. 接口

```go
type HGRequestSigner interface {
    Sign(ctx context.Context, req *http.Request, body []byte) error
}
```

职责：

- 添加官方要求的时间戳、nonce、App ID、摘要和签名 Header/Query。
- 统一 canonical request 构造。
- 不发送请求，不管理重试，不解析业务响应。
- 不在错误信息中包含 Secret 或完整签名原文。

### 2. Canonical Request

典型官方签名流程：

```text
HTTP Method
Canonical Path
Sorted Query
Timestamp
Nonce
SHA256(Request Body)
```

然后根据官方协议使用：

```text
HMAC-SHA256(secret, canonical_request)
```

或平台文档指定的其他标准算法。

必须固定：

- Query 排序方式。
- URL 编码方式。
- 空 body 摘要。
- Header 大小写规则。
- 时间戳单位和允许时钟偏差。
- nonce 长度和随机源。

### 3. Secret 管理

- Secret 不写入 YAML 和 Git。
- Secret 通过 Kubernetes Secret、Vault、KMS 或环境变量注入。
- 日志禁止打印请求 Authorization、Cookie、签名和 Token。
- 错误只返回签名阶段，例如 `signing douyin request failed`。
- Secret 轮换需要支持新旧密钥短期并存或原子切换。

### 4. 测试

签名测试必须使用平台官方测试向量：

- 固定 method/path/query/body/timestamp/nonce。
- 校验 canonical request。
- 校验最终摘要。
- 校验 Query 编码和排序。
- 校验 body 被读取后仍能发送。
- 校验错误和日志不包含 Secret。
- 校验时钟偏差和过期请求。

## 九、平台注册与扩展

当平台数量增加后，manager 不应继续硬编码单个平台，可以增加只读注册表：

```go
type HGPlatformRegistry interface {
    Get(name string) (HGPlatform, bool)
    List() []string
}
```

任务请求通过 `platform` 选择已注册适配器，但仍不得接受任意 URL。

```text
Task(platform=douyin)
  -> Registry.Get("douyin")
  -> authorized HGDouyinPlatform
  -> signer/token provider
  -> official API
  -> HGRecommendation
```

每个平台必须拥有独立：

- Endpoint allowlist。
- 连接池。
- 限流器。
- 熔断状态。
- Token/Secret。
- 指标标签。
- 任务并发上限。

不能用一个公共全局限流器或公共 Cookie 混用所有平台。

## 十、持久化建议

当前版本只保存内存快照。生产持久化建议使用独立外部内容表，不复用本站投稿表：

```text
crawler_external_contents
crawler_runs
```

内容唯一键：

```text
UNIQUE(platform, content_id)
```

写入要求：

- 每批 20-100 条。
- 单批短事务。
- `INSERT ... ON DUPLICATE KEY UPDATE` 幂等更新可变统计。
- HTTP 请求必须在事务外执行。
- 不根据一轮推荐样本全量删除历史内容。
- 任务列表使用 ID/时间复合游标，不使用深 offset。

如果未来需要混入本站推荐流，必须先让 candidate、card cache、cursor、repository 和 API DTO 全部支持 `source/platform`，不能只把 BVID 写入现有 Redis Feed ZSET。

## 十一、生产部署建议

优先级从高到低：

1. Kubernetes CronJob 执行 `cmd/hg_crawler --once`，配置 `concurrencyPolicy: Forbid`。
2. 独立单副本 crawler Deployment，管理 API 由内部网关保护。
3. 多副本 crawler + Redis lease。
4. 主业务应用内嵌 worker，仅适用于明确单副本或指定单实例启用场景。

监控指标建议：

```text
crawler_requests_total{platform,status}
crawler_request_duration_seconds{platform}
crawler_items_total{platform,result}
crawler_last_success_timestamp_seconds{platform}
crawler_task_running{platform}
crawler_rate_limited_total{platform}
crawler_token_refresh_total{platform,result}
```

指标标签必须保持低基数，禁止使用 BVID、用户 ID、URL、错误文本作为 Prometheus label。
