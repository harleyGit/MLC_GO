# **MLC_GO 统一业务错误码系统技术规格文档（Tech Spec）**

版本：v1.0 ｜ 技术栈：Go + MySQL + Redis + Kafka + Centrifugo + React ｜ 设计目标：大型互联网平台、多业务模块、高并发、可观测、可扩展

## **一、设计目标与核心结论**

针对你的 MLC_GO 服务端，涵盖即时通信（IM）、商城、电商支付、爬虫、运维管理、视频、评论、弹幕、用户、IAM 权限、通知中心等模块，建议建立一套**平台级统一业务错误码体系**。

参考 B站、字节跳动等大型互联网平台的 API 设计理念，但不直接照搬某个平台的私有错误码。

**最终推荐：HTTP Status + Business Code + Error Key + Trace ID + Structured Details。**

这五个字段各司其职：

| 字段            | 职责             | 示例                      |
| ------------- | -------------- | ----------------------- |
| HTTP Status   | 表示 HTTP 请求处理结果 | `403`                   |
| Business Code | 机器可识别的业务错误码    | `1201003`               |
| Error Key     | 稳定的语义标识        | `IAM_PERMISSION_DENIED` |
| Message       | 给用户看的中文提示      | `没有操作权限`                |
| Trace ID      | 关联服务端日志、链路追踪   | `4bf92f...`             |

其中 `message` 不应该作为 React 判断业务逻辑的依据。

### **1.1 统一响应示例**

成功：

```
{
  "code": 200,
  "message": "Success💯",
  "data": {
    "user_id": "u_10001",
    "nickname": "Harley"

权限不足：

库存不足：

  "message": "商品库存不足",

```

兼容现有的 `HGResultModel` 和 `HGPageResultModel`，不需要推翻你已经开发的响应模型。

### **1.2 必须解决的问题**

1. **全局唯一**：不同业务模块不能出现相同错误码。
2. **模块隔离**：IM、商城、视频、爬虫、运维分别维护自己的错误码。
3. **语义稳定**：发布新版本不能随意改变已有错误码的含义。
4. **协议统一**：HTTP、WebSocket、Kafka 使用同一套业务错误语义，但采用各自的传输协议。
5. **前后端解耦**：React 根据错误码执行登录跳转、Toast、重试、权限提示等操作。
6. **高并发安全**：错误码必须是静态定义，不需要每次请求查询数据库。
7. **可观测性**：支持 Prometheus、OpenTelemetry、结构化日志与告警。
8. **安全性**：不泄漏数据库 SQL、用户隐私、内部服务地址、风控规则。

## **二、B站、字节与 MLC_GO 的设计对比**

需要区分**公开可观察的 API 行为**与**企业内部未公开的错误码规范**。B站部分公开接口可以观察到 `code/message/data` 风格；字节旗下不同产品及开放平台并不共享一套可确认的全局错误码标准。

| 维度       | B站公开接口风格      | 字节系公开 API 风格 | MLC_GO 推荐      |
| -------- | ------------- | ------------ | -------------- |
| 成功码      | 常见 `0`        | 不同 API 存在差异  | 保留现有 `200`     |
| 业务错误码    | 整数码           | 整数或字符串等      | 7 位整数          |
| 错误消息     | `message`     | 常见 `message` | `message`      |
| 数据载荷     | `data`        | `data` 或其他结构 | `data`         |
| 模块化分配    | 内部规范未完整公开     | 内部规范未完整公开    | 固定模块号段         |
| 链路追踪     | 接口实现各异        | 接口实现各异       | `trace_id`     |
| HTTP 状态码 | 部分业务错误仍返回 200 | 依具体 API 而异   | 优先语义化 HTTP 状态码 |
| 国际化      | 依具体产品         | 依具体产品        | `error` + i18n |
| 前端错误处理   | 依具体客户端        | 依具体客户端       | 统一拦截器 + 模块处理器  |

**架构取舍：** 采用统一 JSON Envelope，保留已有成功码 `200`，新增模块化业务错误码，不使用 `HTTP 200` 来掩盖所有失败。

公开资料验证：B站的社区整理接口文档显示成功码 `0`，并存在 `-101`（未登录）、`-400`（请求错误）等错误码。TikTok API v2 官方文档则采用字符串错误码、HTTP 状态码和 `log_id`，例如 `access_token_invalid` 对应 HTTP 401。

因此，MLC_GO 更适合采用**模块化数字错误码 + 稳定字符串标识**的混合方案。

## **三、全局错误码编码规则**

### **3.1 采用 7 位整数编码**

建议格式：

编码结构：M M S S E E E

# **MM**

业务模块

11–99

# **SS**

子模块

00–99

# **EEE**

具体错误

001–999

例如 1402004 = 14（商城）+ 02（库存）+ 004（库存不足）

编码公式：

```
code = module*100000 + submodule*1000 + reason
```

举例：

```
1402004
│ │  └── 004 库存不足
│ └───── 02  库存子模块
└─────── 14  商城模块
```

设计约束：

- `200`：沿用现有成功码，不占用业务错误号段。
- `1000000–9999999`：业务错误码区间。
- `1000001`：通用内部错误。
- `1000002`：请求参数无效。
- `1000003`：请求过于频繁。
- `1000004`：服务暂时不可用。
- `1000005`：请求幂等冲突。
- 已发布错误码永久保留语义，不允许重新分配给其他错误。

| 模块号 | 模块                | 错误码范围           |
| --- | ----------------- | --------------- |

| 12  | IAM 角色/权限/作用域     | 1200000–1299999 |
| 13  | IM 即时通信           | 1300000–1399999 |
| 14  | MALL 商城           | 1400000–1499999 |
| 15  | PAYMENT 支付/钱包     | 1500000–1599999 |
| 16  | VIDEO 视频          | 1600000–1699999 |
| 17  | CRAWLER 爬虫        | 1700000–1799999 |
| 18  | OPS 运维            | 1800000–1899999 |
| 19  | NOTIFICATION 消息通知 | 1900000–1999999 |
| 20  | MEDIA 对象存储        | 2000000–2099999 |
| 21  | REALTIME 实时连接     | 2100000–2199999 |
| 22  | RISK 风控           | 2200000–2299999 |

## **五、Go 工程目录与模块依赖设计**

建议把错误码能力抽象为独立基础设施包，业务模块只能依赖统一错误包，不允许反向依赖业务代码。

## **六、Go 统一错误码核心实现**

下面提供可以直接用于 AI 编码的核心实现。

### **6.1 定义错误码与元数据**

文件：`internal/platform/hgerrors/error.go`

```

package hgerrors

import (
    "errors"
    "fmt"
    "net/http"
)

type Code int32

type Definition struct {
    Code       Code
    Key        string
    Message    string
    HTTPStatus int
    Retryable  bool
}

type AppError struct {
    Def   Definition
    Cause error
}

func (e *AppError) Error() string {
    if e.Cause != nil {
        return fmt.Sprintf("%s: %v", e.Def.Key, e.Cause)
    }
    return e.Def.Key
}

func (e *AppError) Unwrap() error {
    return e.Cause
}

func New(def Definition) *AppError {
    return &AppError{Def: def}
}

func Wrap(def Definition, cause error) *AppError {
    return &AppError{Def: def, Cause: cause}
}

func Resolve(err error) Definition {
    var appErr *AppError
    if errors.As(err, &appErr) {
        return appErr.Def
    }
    return InternalError
}

var InternalError = Definition{
    Code:       1000001,
    Key:        "COMMON_INTERNAL_ERROR",
    Message:    "服务器繁忙，请稍后重试",
    HTTPStatus: http.StatusInternalServerError,
    Retryable:  true,
}

```

其中：

- `Code`：唯一数字错误码。
- `Key`：给 React、日志和监控使用。
- `Message`：面向用户的安全提示。
- `HTTPStatus`：对应 HTTP 状态码。
- `Retryable`：表示错误在适当条件下是否可能重试成功，不代表客户端必须自动重试。
- `Cause`：原始错误，仅用于服务端日志，不返回客户端。

### **6.3 Service 层返回业务错误**

例如，用户购买商品时库存不足。

```

package mall

import (
    "context"

    "your-module/internal/platform/hgerrors"
)

type StockRepository interface {
    Available(ctx context.Context, skuID string) (int64, error)
}

type Service struct {
    repo StockRepository
}

func (s *Service) CheckStock(
    ctx context.Context,
    skuID string,
    quantity int64,
) error {
    available, err := s.repo.Available(ctx, skuID)
    if err != nil {
        return hgerrors.Wrap(
            hgerrors.InternalError, err,
        )
    }

    if available < quantity {
        return hgerrors.New(
            hgerrors.MallStockInsufficient,
        )
    }

    return nil
}

```

`CheckStock` 只负责预检查。真正下单时仍必须通过事务、条件更新或库存预占机制保证原子性，不能仅凭预检查结果扣减库存。

### **6.4 统一 HTTP 响应封装**

文件：`hgresponse/response.go`

```

package hgresponse

import (
    "encoding/json"
    "log/slog"
    "net/http"

    "your-module/internal/platform/hgerrors"
)

type Result struct {
    Code    int32  `json:"code"`
    Error   string `json:"error,omitempty"`
    Message string `json:"message"`
    Data    any    `json:"data"`
    TraceID string `json:"trace_id,omitempty"`
}

func WriteError(
    w http.ResponseWriter,
    r *http.Request,
    err error,
    traceID string,
) {
    def := hgerrors.Resolve(err)

    slog.ErrorContext(
        r.Context(),
        "request failed",
        "error_code", def.Code,
        "error_key", def.Key,
        "trace_id", traceID,
        "cause", err,
    )

    result := Result{
        Code:    int32(def.Code),
        Error:   def.Key,
        Message: def.Message,
        Data:    nil,
        TraceID: traceID,
    }

    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(def.HTTPStatus)

    if encodeErr := json.NewEncoder(w).Encode(result); encodeErr != nil {
        slog.ErrorContext(
            r.Context(),
            "encode error response failed",
            "cause", encodeErr,
        )
    }
}

func WriteSuccess(
    w http.ResponseWriter,
    data any,
    traceID string,
) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusOK)

    _ = json.NewEncoder(w).Encode(Result{
        Code:    200,
        Message: "Success💯",
        Data:    data,
        TraceID: traceID,
    })
}

```

这里的 `traceID` 应来自已有的 OpenTelemetry SpanContext；没有有效 Span 时使用统一请求 ID 作为兜底，并明确区分两者。

正式落地时还需要补充：

- 防止响应头已经写入后重复 `WriteHeader`。
- 使用统一中间件完成请求日志记录。
- 对敏感字段进行日志脱敏。
- 对外部错误进行映射，避免直接输出 `err.Error()`。
- 复用现有 `HGResponsePackage`，避免同一工程同时存在两套响应写入机制。

## **七、业务错误与 HTTP Status 如何映射**

不要把所有业务错误都返回 HTTP 200，也不要简单地把业务错误码当成 HTTP 状态码。

| HTTP | 场景          | MLC_GO 示例       |
| ---- | ----------- | --------------- |
| 200  | 请求成功        | `code=200`      |
| 202  | 异步任务已接受     | 爬虫任务已提交         |
| 400  | 请求参数不正确     | 弹幕超长            |
| 401  | 身份认证失败      | Access Token 失效 |
| 403  | 无权执行操作      | IAM 权限不足        |
| 404  | 资源不存在       | 商品不存在           |
| 409  | 业务状态冲突      | 库存不足、订单状态冲突     |
| 413  | 请求体过大       | 上传文件超限          |
| 415  | 媒体类型不支持     | 不支持的文件格式        |
| 422  | 语法正确但语义校验失败 | 特定复杂业务校验        |
| 429  | 客户端触发限流     | 评论频率超限          |
| 500  | 未预期服务端错误    | 内部程序异常          |
| 502  | 上游响应异常      | 依赖服务错误          |
| 503  | 服务暂不可用      | Redis/Kafka 不可用 |
| 504  | 上游超时        | 调用依赖服务超时        |

HTTP 202 表示**请求已接受，但处理尚未完成**，不是业务失败。

例如：

```
{
  "code": 200,
  "message": "任务已提交",
  "data": {
    "task_id": "crawler_10001",
    "status": "queued"
  }
}
```

该响应的 HTTP Status 为 `202 Accepted`。

### **7.1 重试策略**

| 错误类别            | 自动重试  | 处理方式               |
| --------------- | ----- | ------------------ |
| 参数错误            | 否     | 用户修正参数             |
| 权限不足            | 否     | 提示权限不足             |
| Access Token 过期 | 有条件   | Refresh Token 续签一次 |
| 库存不足            | 否     | 刷新库存               |
| 上游暂时不可用         | 有条件   | 指数退避 + 抖动          |
| 请求限流            | 有条件   | 遵循 Retry-After     |
| 支付结果未知          | 不直接重付 | 查询支付状态             |
| Kafka 临时异常      | 有条件   | 消费端重试              |
| 数据库唯一键冲突        | 依业务   | 幂等查询或冲突处理          |

特别注意：`Retryable=true` 只是错误的潜在可恢复属性，真正执行重试还必须同时检查 HTTP Method、请求幂等性、重试预算和截止时间。

## **八、WebSocket / Centrifugo 的错误码设计**

对于你的 IM、IAM 权限变更、通知中心，不应该把 HTTP 错误响应直接复制成 Centrifugo 协议消息。

建议分为三类：

| 场景        | 使用协议               | 错误处理         |
| --------- | ------------------ | ------------ |
| 发送 IM 消息  | HTTP API           | 统一业务码        |
| IM 消息实时推送 | Centrifugo Publish | 正常事件数据       |
| 连接鉴权失败    | Centrifugo 协议      | 使用其原生错误结构    |
| 订阅频道失败    | Centrifugo 协议      | 原生错误 + 服务端映射 |
| 业务操作失败事件  | 应用层事件              | 业务码          |
| 权限变更通知    | 应用层事件              | 通知重新同步       |

### **8.1 IM 消息发送流程**

```
React 发送消息
      |
      v
POST /api/v1/im/messages
      |
      v
Go 验证 Token、权限、消息内容
      |
      v
MySQL 事务持久化消息 + Outbox
      |
      v
返回 HTTP 200 + message_id
      |
      v
Outbox Worker 发布实时事件
      |
      v
Centrifugo
      |
      v
接收方 React
```

消息持久化成功后，实时推送暂时失败不能把已保存的消息改判为发送失败。应通过 Outbox 重试和客户端断线同步恢复。

### **8.2 WebSocket 业务事件格式**

```
{
  "event": "im.message.created",
  "event_id": "evt_10001",
  "version": 1,
  "data": {
    "message_id": "msg_10001",
    "conversation_id": "conv_10001",
    "content": "你好"
  },
  "trace_id": "4bf92f3577b34da6"
}
```

需要发送应用层错误事件时：

```
{
  "event": "im.operation.failed",
  "event_id": "evt_10002",
  "version": 1,
  "data": {
    "request_id": "req_10001",
    "code": 1301003,
    "error": "IM_CONVERSATION_MUTED",
    "message": "当前会话禁止发言"
  }
}
```

注意：这些是应用层 JSON Payload，不是 Centrifugo 内置的 Reply Error。Centrifugo 原生鉴权、订阅和连接错误仍须遵守其协议定义。

## **九、Kafka 消费者错误码与重试设计**

你的 Go 工程已经有 Kafka、Inbox 去重、事件消费、爬虫流水线，因此必须把**业务错误码**与**消息消费结果**分离。

例如：

```
Kafka Consumer
     |
     v
检查 event_id
     |
     +-- 已成功处理 --------> ACK
     |
     v
执行业务处理
     |
     +-- 成功 --------------> ACK
     |
     +-- 可恢复错误 --------> Retry
     |
     +-- 永久性错误 --------> DLQ
     |
     +-- 未知结果 ----------> 检查幂等状态
```

这里的 ACK 表示消息处理完成并满足提交消费位点的条件，而不是 Kafka 存在一个通用的逐条 ACK API。

### **9.1 建议的消费者处理结果**

```
type ConsumerAction string

const (
    ConsumerAck   ConsumerAction = "ack"
    ConsumerRetry ConsumerAction = "retry"
    ConsumerDLQ   ConsumerAction = "dlq"
)

type ConsumerResult struct {
    Action    ConsumerAction
    ErrorCode int32
    Reason    string
}
```

示例：

| 业务错误         | 消费结果              | 原因                |
| ------------ | ----------------- | ----------------- |
| 1703002 阶段冲突 | ACK / Retry / DLQ | 取决于事件是否乱序、状态是否可恢复 |
| 1703003 清洗失败 | Retry 或 DLQ       | 区分临时故障与永久脏数据      |
| 1703004 存储失败 | Retry             | 数据库临时不可用          |
| 1704002 重复事件 | ACK 或 DLQ         | 相同内容去重；冲突内容隔离     |
| 1000001 未知异常 | 有限 Retry          | 超限进入 DLQ          |

### **9.2 必须遵守的可靠性约束**

- MySQL 业务事务提交成功后，才允许推进对应消息的已处理状态。
- 使用 `event_id` + Inbox 唯一约束进行消费幂等。
- Kafka 位点提交必须考虑分区内连续处理进度，不能因为后一条消息成功就越过前一条未处理消息。
- Retry Topic、DLQ 必须保留原始事件、错误码、重试次数和关联 ID。
- 对于 DLQ，必须先可靠写入 DLQ，再推进原消息位点。
- 消费者必须支持指数退避、最大重试次数和人工重新投递。

不要把 HTTP 500、503 等状态码直接作为 Kafka 消费重试的唯一判断依据。

```

import { HGErrorCodes } from "./hg_error_codes.js";

export function handleBusinessError(
  response,
  { toast, onAuthExpired, refreshStock }
) {
  const code = response?.code;

  switch (code) {
    case HGErrorCodes.AUTH_TOKEN_EXPIRED:
      onAuthExpired?.();
      break;

    case HGErrorCodes.IAM_PERMISSION_DENIED:
    case HGErrorCodes.IAM_SCOPE_DENIED:
      toast("当前账号没有操作权限");
      break;

    case HGErrorCodes.MALL_STOCK_INSUFFICIENT:
      toast("库存不足，请重新选择数量");
      refreshStock?.();
      break;

    default:
      toast(response?.message || "操作失败");
  }
}

```

## **十一、错误码应该存储在 MySQL 吗？**

建议采用 **Go 代码作为错误码的权威来源，MySQL 作为可选的运维管理元数据存储**。

不建议每次业务报错都查询数据库。

### **11.1 推荐架构**

```
Go hgerrors
  |
  +-- 错误码常量
  +-- 错误语义
  +-- HTTP Status
  +-- Retryable
  |
  +------> HTTP / WebSocket / Kafka
  |
  +------> 自动生成 OpenAPI
  |
  +------> 自动生成 React 常量
  |
  +------> 同步 MySQL 错误码目录
                   |
                   v
             运维管理后台
             - 查询错误码
             - 查看错误说明
             - 配置展示文案
             - 查看错误统计
```

### **11.2 MySQL 错误码目录表**

```
CREATE TABLE hg_error_code_catalog (
    code INT NOT NULL PRIMARY KEY,
    error_key VARCHAR(128) NOT NULL,
    module VARCHAR(32) NOT NULL,
    submodule VARCHAR(32) NOT NULL,
    http_status SMALLINT NOT NULL,
    default_message VARCHAR(255) NOT NULL,
    retryable BOOLEAN NOT NULL DEFAULT FALSE,
    description TEXT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'active',
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    KEY idx_module_status (module, status),

        CHECK (status IN ('active', 'deprecated', 'reserved'))

```

使用规则：

- 错误码及语义只允许通过代码变更和审核流程修改。
- 运维后台默认只读，不允许随意修改 `code`、`error_key`。
- 可编辑的国际化文案放入独立的 `hg_error_code_localizations` 表。
- 不允许通过修改数据库来改变 Go 服务运行时的错误码语义。
- 每次 CI 构建验证数据库目录迁移与代码定义是否一致。

## **十二、自动化测试与质量门禁**

错误码系统不能只测试“能不能返回 JSON”，还必须测试编号冲突、协议映射和兼容性。

### **12.1 错误码注册中心**

建议每个 `Definition` 统一注册，启动时检查：

1. Code 是否重复。
2. Error Key 是否重复。
3. Code 是否符合模块编号规则。
4. HTTP Status 是否有效。
5. 是否存在空 Key 或空 Message。
6. 已发布错误码是否被删除或改变语义。

例如：

```

package hgerrors

import "fmt"

func ValidateRegistry(defs []Definition) error {
    codes := make(map[Code]struct{}, len(defs))
    keys := make(map[string]struct{}, len(defs))

    for _, def := range defs {
        if def.Code < 1000000 || def.Code > 9999999 {
            return fmt.Errorf("invalid code: %d", def.Code)
        }

        if def.Key == "" || def.Message == "" {
            return fmt.Errorf("empty key or message: %d", def.Code)
        }

        if def.HTTPStatus < 400 || def.HTTPStatus > 599 {
            return fmt.Errorf("invalid HTTP status: %d", def.Code)
        }

        if _, exists := codes[def.Code]; exists {
            return fmt.Errorf("duplicate code: %d", def.Code)
        }

        if _, exists := keys[def.Key]; exists {
            return fmt.Errorf("duplicate key: %s", def.Key)
        }

        codes[def.Code] = struct{}{}
        keys[def.Key] = struct{}{}
    }

    return nil
}

```

这段校验针对错误定义注册表，因此 HTTP 202 等异步成功状态不应注册为失败型 `Definition`。

### **12.2 必须覆盖的测试**

| 测试场景           | 预期结果               |
| -------------- | ------------------ |
| 重复注册 Code      | 构建失败               |
| 重复注册 Error Key | 构建失败               |
| 错误码跨模块编号       | 构建失败               |
| 数据库内部错误        | 返回通用 500，不泄漏 SQL   |
| Token 过期       | HTTP 401 + 1101002 |
| IAM 权限不足       | HTTP 403 + 1201003 |
| 商城库存不足         | HTTP 409 + 1402004 |
| 重复 IM 消息请求     | 返回已保存消息            |
| Kafka 重复事件     | 幂等处理               |
| Kafka 临时存储失败   | 有限重试               |
| 支付回调重复         | 不重复入账              |
| 未知错误           | 映射 1000001         |
| 错误码升级          | 已发布编号及语义保持兼容       |

CI 执行：

```
go test ./internal/platform/...
go test -race ./internal/platform/...
go vet ./...
```

建议生成一份版本化的 `error-codes.json`，在 CI 中与上一正式发布版本比较，防止误删或重用历史错误码。

## **十三、Prometheus、OpenTelemetry 与日志监控**

错误码不仅是给 React 看的，还应该成为线上运维排查问题的统一维度。

### **13.1 Prometheus 指标**

建议定义：

```
hg_http_requests_total{
  module,
  route,
  method,
  status
}

hg_business_errors_total{
  module,
  error_code
}

hg_kafka_consumer_failures_total{
  topic,
  consumer_group,
  error_code,
  action
}

hg_external_dependency_errors_total{
  dependency,
  error_code
}
```

不要将 `user_id`、`trace_id`、`order_id`、`message_id` 等高基数字段放入 Prometheus Label。

这些信息应该进入日志和 Trace。

### **13.2 结构化日志示例**

```
{
  "level": "ERROR",
  "service": "mlc-go",
  "module": "mall",
  "error_code": 1402004,
  "error_key": "MALL_STOCK_INSUFFICIENT",
  "http_status": 409,
  "trace_id": "4bf92f3577b34da6",
  "route": "/api/v1/mall/orders",
  "duration_ms": 18
}
```

对于库存不足等正常业务冲突，日志级别一般使用 `INFO` 或 `WARN`，不应全部记为 `ERROR`。

建议告警规则：

- 5xx 错误率持续超过阈值。
- 支付确认失败率异常升高。
- Kafka DLQ 消息数量持续增长。
- IAM 权限拒绝次数突然异常。
- 爬虫数据源失败率持续升高。
- IM 消息持久化失败率升高。

告警阈值应根据历史基线、SLO 和流量规模制定，不建议所有模块共用固定阈值。

## **十四、现有 MLC_GO 工程迁移方案**

你已有 `HGResponsePackage`、`HGResultModel`、`HGErrorResult` 等基础设施，建议渐进迁移，而不是一次性替换。

1. **阶段一：统一错误码定义**

   新增 `hgerrors`，盘点当前所有返回码，建立旧码与新码的映射表，冻结新编号规则。
2. **阶段二：改造响应封装**

   保留 `HGResponsePackage` 作为唯一响应出口，在原有模型上增加 `error`、`trace_id`、`details`，支持按业务错误映射 HTTP Status。
3. **阶段三：逐模块迁移**

   推荐顺序：AUTH → IAM → IM → 商城 → 支付 → 视频 → 爬虫 → 运维 → 通知。优先迁移新接口，再迁移旧接口。
4. **阶段四：统一 React 错误处理**

   生成前端常量，接入 HTTP 拦截器和业务模块处理器，确保新旧响应格式在过渡期均可识别。
5. **阶段五：接入 Kafka / Centrifugo**

   将业务错误语义映射到消费者结果和应用层实时事件，保留各自协议原生错误。
6. **阶段六：上线可观测性和兼容性门禁**

   接入日志、Trace、Metrics、CI 错误码校验及历史兼容性测试。通过灰度发布逐步切换。

特别注意：现有客户端可能把 HTTP 200 作为所有业务响应的预期状态。切换语义化 HTTP 状态码之前，必须先检查 React、移动端以及第三方调用方的兼容性。



## **十六、最终架构建议**

对于 MLC_GO，我建议采用以下原则作为长期规范：

**一套错误码字典、一个 Go 错误类型、一套 HTTP 响应出口、多个协议适配器、统一可观测体系。**

这样设计的主要价值是：未来无论商城、IM、视频、爬虫拆分成多少个微服务，错误码都可以保持稳定，React、iOS 和运维系统也不需要为每个服务重新定义错误处理规则。

另外，错误码系统应与现有 IAM 权限体系、Kafka 幂等机制、OpenTelemetry 和通知系统协同，但不应与它们形成强耦合。**错误码是平台基础契约，而不是某个业务模块的私有实现。**
