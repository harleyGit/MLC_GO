# MLC 商家商品发布系统 — 技术规格文档（Tech Spec）

Tech Spec v1.0

Go + React + MySQL + Redis + Kafka

面向 AI 编码实现

本文面向你的 MLC_GO + MLC_React 电商业务模块，参考拼多多的商品发布、商品详情、SKU、优惠券、拼单、店铺管理等电商能力，设计一套支持实物商品、虚拟商品、会员卡、人民币支付、M币抵扣及会员折扣的完整商品发布系统。

设计目标：

- 商家端：发布商品、设置分类、SKU、价格、库存、运费、优惠活动、会员权益、上架和下架。
- 消费者端：浏览商品、选择规格、单独购买、发起拼单、使用优惠券、M币抵扣、会员折扣。
- 平台端：商家资质审核、类目管理、商品审核、违禁商品治理、会员规则和营销规则配置。
- 工程架构：按领域拆分，支持后续扩展到百万商品、亿级订单和高并发交易，但不以首期部署就达到该规模为前提。
- 资金安全：人民币为法定计价单位，M币作为平台内部权益余额使用；支付、库存、订单和权益必须具备幂等与审计能力。

## 一、总体业务架构

MLC 电商业务架构

领域模块可以先部署在同一个 Go 服务中，后续按负载独立拆分。Kafka 用于异步事件，不承担支付与库存强一致性事务。

类目设计约束：

1. 类目最多三级，商品绑定一个叶子类目。
2. 类目 ID 使用 `BIGINT UNSIGNED`，业务中使用字符串传递，避免 JavaScript 大整数精度问题。
3. 属性模板动态配置，支持必填、可选、枚举、数值、文本及单位。
4. `PHYSICAL`、`VIRTUAL`、`MEMBERSHIP`、`SERVICE` 是履约类型，不应简单等同于一级类目。
5. 食品、美妆、健康、出版物等受监管类目必须具备资质校验和审核流程；高风险或禁止销售的商品不允许发布。

## 三、商品模型与 SKU 规格设计

### 3.1 SPU 与 SKU 的区别

参考拼多多、淘宝等电商平台的商品组织方式，采用 SPU + SKU 模型。

- SPU（Standard Product Unit）：商品主体，描述商品是什么。
- SKU（Stock Keeping Unit）：具体可销售规格，决定售价、库存和购买选项。

例如商家发布一款手机：

SPU：某品牌 X Pro 手机

商品名称、描述、品牌、分类、详情图片

黑色 / 256GB

¥3,999

库存：100 件

黑色 / 512GB

¥4,599

库存：60 件

白色 / 256GB

¥3,999

库存：80 件

白色 / 512GB

¥4,599

库存：40 件

商品发布时，商家填写一个 SPU，并通过规格组合生成多个 SKU。

### 3.2 商品字段定义

| 字段                  | 类型       | 说明                                  |
| ------------------- | -------- | ----------------------------------- |
| `productId`         | string   | 商品业务 ID                             |
| `merchantId`        | string   | 商家 ID                               |
| `shopId`            | string   | 店铺 ID                               |
| `categoryId`        | string   | 叶子类目 ID                             |
| `productType`       | enum     | PHYSICAL/VIRTUAL/MEMBERSHIP/SERVICE |
| `title`             | string   | 商品标题，1～120 字                        |
| `subtitle`          | string   | 商品副标题，最多 200 字                      |
| `brandId`           | string?  | 品牌 ID                               |
| `mainImage`         | string   | 商品主图 URL                            |
| `images`            | string[] | 商品轮播图，1～15 张                        |
| `detailContent`     | JSON     | 商品详情富文本结构                           |
| `attributes`        | JSON     | 类目属性                                |
| `skuList`           | array    | 商品规格列表                              |
| `freightTemplateId` | string?  | 运费模板                                |
| `afterSalePolicyId` | string?  | 售后规则                                |
| `status`            | enum     | 商品状态                                |
| `version`           | int      | 乐观锁版本                               |
| `createdAt`         | datetime | 创建时间                                |
| `updatedAt`         | datetime | 更新时间                                |

SKU 结构：

| 字段                  | 类型     | 说明               |
| ------------------- | ------ | ---------------- |
| `skuId`             | string | SKU 业务 ID        |
| `skuCode`           | string | 商家自定义编码          |
| `specs`             | JSON   | 规格键值，例如颜色、容量     |
| `image`             | string | SKU 图片           |
| `priceCent`         | int64  | 单买价格，人民币分        |
| `originalPriceCent` | int64? | 有依据的原价或划线价       |
| `groupPriceCent`    | int64? | 拼单价格             |
| `stock`             | int64  | 可销售总库存           |
| `weightGram`        | int64? | 重量               |
| `status`            | enum   | ENABLED/DISABLED |

金额统一采用人民币分（整数），不能使用 `float64` 保存金额。

例如：

```
{
  "priceCent": 399900,
  "currency": "CNY"
}
```

代表人民币 ¥3,999.00。

### 3.3 SKU 组合生成算法

商家选择：

```
颜色：黑色、白色
容量：256GB、512GB
```

前端自动生成笛卡尔积：

```
颜色 × 容量

黑色 + 256GB
黑色 + 512GB
白色 + 256GB
白色 + 512GB
```

编码约束：

- 最多 3 个销售规格维度。
- 每个 SPU 首期最多 200 个 SKU。
- 同一 SPU 的规格组合必须唯一。
- SKU 删除前检查是否被订单引用；历史订单必须保留规格快照。
- 修改 SKU 价格不得影响已经创建并锁定价格的有效订单。
- SKU 库存由库存领域统一管理，不允许商家直接修改订单预占库存。

## 五、商品状态机

商品状态不建议只使用一个 `status` 字段表达所有情况。采用审核状态和销售状态分离。

| 维度   | 状态        | 说明     |
| ---- | --------- | ------ |
| 审核状态 | DRAFT     | 草稿     |
| 审核状态 | PENDING   | 待审核    |
| 审核状态 | APPROVED  | 审核通过   |
| 审核状态 | REJECTED  | 审核驳回   |
| 销售状态 | OFF_SHELF | 未上架    |
| 销售状态 | ON_SHELF  | 已上架    |
| 销售状态 | SUSPENDED | 平台强制停售 |
| 销售状态 | DELETED   | 逻辑删除   |

关键规则：

1. `PENDING` 的商品不能直接上架。
2. `REJECTED` 商品修改后可重新提交。
3. `APPROVED + ON_SHELF` 且 SKU 有可售库存，才允许正常购买。
4. 商家下架后，已有订单仍按原有交易快照继续履约。
5. 修改商品标题、主图、关键属性等重要字段时，需要根据平台审核策略重新审核。
6. 平台强制停售的商品不能由商家自行恢复。

建议将审核中的版本与线上已发布版本分离。 否则商家修改在售商品时，未审核内容可能提前展示给消费者。

## 六、会员卡与会员折扣系统

会员卡是本系统的重要差异化业务。必须区分：

- 会员卡商品：商家或平台发布并销售的商品。
- 会员权益：购买会员卡后赋予用户的折扣、优惠券、免运费等能力。
- 会员订阅记录：用户持有哪些会员、何时生效、何时到期。

### 6.1 会员类型

| 会员类型 | 作用范围      | 示例         |
| ---- | --------- | ---------- |
| 平台会员 | 平台指定商家和商品 | MLC VIP 年卡 |
| 店铺会员 | 指定店铺      | 某数码店会员     |
| 品类会员 | 指定商品类目    | 数码影音会员     |
| 权益卡  | 指定权益组合    | 95 折卡、免运费卡 |

会员卡可以设置月卡、季卡、年卡或固定有效期。

### 6.2 会员卡配置结构

```
{
  "cardId": "card_10001",
  "name": "MLC VIP 年卡",
  "scopeType": "PLATFORM",
  "durationDays": 365,
  "priceCent": 9900,
  "benefits": [
    {
      "type": "DISCOUNT",
      "discountBps": 9500,
      "categoryIds": ["1001", "1002"]
    },
    {
      "type": "COUPON_PACKAGE",
      "packageId": "pkg_001"
    }
  ],
  "renewable": true,
  "stackPolicy": "EXCLUSIVE"
}
```

`discountBps = 9500` 代表按原价的 95% 支付，即 95 折，而不是减免 95%。

### 6.3 会员权益生效规则

```
用户购买会员卡
       |
       v
创建会员卡订单
       |
       v
人民币支付成功
       |
       v
支付回调验签 + 幂等校验
       |
       v
发放会员权益
       |
       v
写入 user_memberships
       |
       v
发布 MembershipActivated 事件
       |
       v
用户后续购买商品享受会员折扣
```

约束：

- 会员卡权益必须在订单支付成功后发放。
- 会员卡订单不允许使用自身尚未生效的会员折扣。
- 会员有效期由后端判断，前端不能自行认定。
- 同一用户重复购买会员卡，采用明确的续期或并行规则。
- 退款时应按权益使用情况和已公示规则撤销或调整权益。
- 不同店铺会员卡不能默认跨店使用。
- 会员卡不等于支付工具；普通折扣卡不应被设计为可自由转让的储值余额。

## 七、M币抵扣与人民币支付

### 7.1 M币的业务定位

建议沿用已有的钱包、充值订单和交易订单领域，新增电商支付抵扣能力，而不是重新开发一套钱包。

首期建议将 M币定义为平台封闭场景内的积分或权益余额，不支持提现、用户间转账、商家直接收取 M币或兑换法币。若 M币可通过人民币充值取得，则需要单独评估预付资金、退款、税务和监管要求，不能仅按普通积分处理。

建议首期定义：

```
100 M币 = 1 元抵扣额度
```

这是平台可配置的示例规则，不代表 M币具有法定货币兑换属性。

M币与人民币必须使用独立账本，不能混为同一种余额。

### 7.2 支付计算示例

假设用户购买一件商品：

订单金额试算

商品单买价

¥100.00

会员 95 折

-¥5.00

优惠券减 ¥10

-¥10.00

使用 M币抵扣

2000 M币 = ¥20.00

0 M币3,000 M币

最终人民币实付

# ¥65.00

演示规则：会员折扣 → 优惠券 → M币，M币最高抵扣 ¥30。实际结算还应计入运费、税费及平台限制，最终金额由 Go 服务端计算。

### 7.3 价格计算优先级

首期固定以下顺序：

```
SKU 单买价 / 拼单价
          |
          v
商品级促销价（符合条件时）
          |
          v
会员折扣
          |
          v
优惠券抵扣
          |
          v
运费 + 适用税费
          |
          v
M币抵扣（仅限允许抵扣的金额部分）
          |
          v
人民币应付金额
```

服务端必须为每笔订单生成不可变价格明细：

```
{
  "currency": "CNY",
  "skuSubtotalCent": 10000,
  "membershipDiscountCent": 500,
  "couponDiscountCent": 1000,
  "shippingCent": 0,
  "taxCent": 0,
  "mCoinUsed": 2000,
  "mCoinDeductionCent": 2000,
  "cashPayableCent": 6500
}
```

重要约束：

- 不允许客户端上传最终应付金额作为权威值。
- M币抵扣不能超过平台配置上限及当前可抵扣金额。
- 优惠券与会员折扣的叠加规则必须显式配置。
- M币预占、扣减、释放、退款都必须具有独立流水。
- 全额 M币抵扣时，订单仍应走统一结算确认流程，不调用外部人民币支付。
- 支付失败或超时必须释放库存预占、优惠券预占及 M币预占。
- 退款按原支付构成分别退回人民币与 M币，不得擅自将现金退款改为 M币。

SKU 库存表

```

CREATE TABLE product_inventory (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    sku_id VARCHAR(40) NOT NULL,
    total_stock BIGINT NOT NULL DEFAULT 0,
    reserved_stock BIGINT NOT NULL DEFAULT 0,
    sold_stock BIGINT NOT NULL DEFAULT 0,
    version BIGINT UNSIGNED NOT NULL DEFAULT 1,
    updated_at DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_sku_id (sku_id),
    CONSTRAINT chk_inventory CHECK (
        total_stock >= 0
        AND reserved_stock >= 0
        AND sold_stock >= 0
        AND total_stock >= reserved_stock + sold_stock
    )
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

```

库存语义定义：

```
total_stock     当前库存批次的累计可分配数量
reserved_stock  已被未完成订单预占的数量
sold_stock      已确认售出的数量

available_stock =
    total_stock - reserved_stock - sold_stock
```

库存补货增加 `total_stock`；库存扣减或盘亏必须通过库存调整事务处理，不能破坏约束。退款是否回补库存，由实际退货入库流程决定，不能在退款成功时无条件加库存。

### 8.3 并发库存预占 SQL

采用数据库条件更新保证首期不超卖：

```

UPDATE product_inventory
SET
    reserved_stock = reserved_stock + :quantity,
    version = version + 1,
    updated_at = NOW(3)
WHERE sku_id = :sku_id
  AND total_stock - reserved_stock - sold_stock >= :quantity;

```

只有 `RowsAffected() == 1` 才代表预占成功。

库存预占记录必须与订单创建放在同一个数据库事务中，并设置唯一业务预占 ID。支付成功后将预占库存转为已售库存：

```
UPDATE product_inventory
SET
    reserved_stock = reserved_stock - :quantity,
    sold_stock = sold_stock + :quantity,
    version = version + 1,
    updated_at = NOW(3)
WHERE sku_id = :sku_id
  AND reserved_stock >= :quantity;
```

同时以条件更新将预占记录从 `RESERVED` 改为 `COMMITTED`。只有成功完成该状态转移的事务才能提交库存确认，避免重复支付回调重复扣减。

对于订单超时，只有成功将预占状态从 `RESERVED` 转为 `RELEASED` 才允许释放库存。支付回调和超时关闭必须竞争同一个订单状态锁；超时任务不得在支付状态尚未确认时盲目释放库存。

### 9.6 创建商品的 Go 事务逻辑

```

func (s *ProductService) CreateDraft(
    ctx context.Context,
    cmd CreateProductCommand,
) (CreateProductResult, error) {

    // 1. 校验当前登录商家是否有权操作该店铺
    if err := s.authorizeShop(ctx, cmd); err != nil {
        return CreateProductResult{}, err
    }

    // 2. 校验类目、经营资质、属性、SKU 和价格
    if err := s.validator.ValidateCreate(ctx, cmd); err != nil {
        return CreateProductResult{}, err
    }

    // 3. 开启数据库事务
    // 事务中必须完成：
    // - 依据 merchant_id + Idempotency-Key 锁定幂等记录
    // - 校验 request_hash 是否与首次请求一致
    // - 生成商品业务 ID
    // - 插入 SPU、SKU、初始库存
    // - 插入商品草稿版本
    // - 保存幂等结果
    // - 写入 Outbox 事件
    //
    // 任一步骤失败，整体回滚。

    return s.repo.CreateDraftTx(ctx, cmd)
}

```

上述是业务编排骨架，不是可独立编译的完整实现。AI 编码时需要生成命令 DTO、依赖注入、仓储事务实现和测试，并遵守项目已有的数据库封装及错误响应规范。

幂等规则：

```
唯一键：
merchant_id + idempotency_key + operation

request_hash：
SHA256(规范化后的请求业务字段)

相同 key + 相同 hash：
返回首次请求的结果

相同 key + 不同 hash：
409 IDEMPOTENCY_KEY_CONFLICT
```

商家 ID 必须从认证上下文获取，不能信任请求体传入的 `merchantId`。

建议由平台维护营销策略，不允许商家任意定义价格计算公式。

```
promotion_type:

DIRECT_DISCOUNT
PERCENT_DISCOUNT
FULL_REDUCTION
COUPON
GROUP_BUY
MEMBERSHIP_DISCOUNT
FREE_SHIPPING
MCOIN_DEDUCTION
```

每个活动必须具有：

- 活动范围。
- 生效时间。
- 优先级。
- 互斥组。
- 单用户使用次数。
- 总预算或总使用次数。
- 退款返还规则。

首期默认：

拼单价与商品级直接促销互斥；会员折扣与优惠券是否叠加由平台策略决定；M币在其他优惠完成后抵扣。

不能简单地把所有优惠累加，否则容易产生负价、超额优惠和商家亏损。

## 十三、支付、订单与资金安全

商家商品发布只是商品生命周期的起点。为了保证发布后的商品真正能够购买，需要与订单系统形成闭环。

### 13.1 下单链路

```
用户选择商品 SKU
        |
        v
请求结算试算
        |
        v
校验商品、库存、会员、优惠券、M币
        |
        v
生成带有效期的服务端报价
        |
        v
用户提交订单
        |
        v
重新校验报价及业务状态
        |
        v
MySQL 事务：
  创建订单
  预占库存
  预占优惠券
  记录待处理的 M币预占操作
  写入 Outbox
        |
        v
完成 M币预占及结算准备
        |
        v
创建人民币支付单
        |
        v
支付渠道完成支付
        |
        v
支付回调验签 + 幂等
        |
        v
确认订单 / 库存 / M币
        |
        v
触发商品履约
```

跨钱包和订单数据库的操作不能假装是一个 MySQL 本地事务。如果两个领域使用不同数据库，需要使用明确的 Saga 状态、幂等操作和补偿机制。

### 13.2 必须防止的问题

| 风险      | 防护措施         |
| ------- | ------------ |
| 重复提交订单  | 幂等键 + 唯一约束   |
| 商品超卖    | 条件更新 + 库存预占  |
| 客户端篡改价格 | 服务端统一定价      |
| 重复扣 M币  | 钱包流水唯一业务键    |
| 支付回调重复  | 支付事件幂等       |
| 会员重复发放  | 订单权益发放唯一约束   |
| 优惠券重复使用 | 预占状态机        |
| 商家越权编辑  | JWT + 店铺归属校验 |
| 图片恶意上传  | 类型、大小、安全扫描   |
| 商品违规发布  | 类目资质 + 审核    |
| 订单退款重复  | 退款单唯一键 + 状态机 |

### 13.3 M币与商家结算

这里需要特别明确：

假设商品原价 ¥100，会员优惠 ¥5，优惠券 ¥10，M币抵扣 ¥20，用户现金支付 ¥65。

商家最终应结算多少，不等于用户现金支付多少。

必须区分优惠资金的承担方：

| 项目     | 金额   | 承担方示例 |
| ------ | ---- | ----- |
| 商品原价   | ¥100 | —     |
| 会员优惠   | -¥5  | 商家    |
| 优惠券    | -¥10 | 平台    |
| M币抵扣   | -¥20 | 平台    |
| 用户现金支付 | ¥65  | 用户    |

在上述假设下，若平台承担的优惠均需补贴商家，则商家交易结算基数可以是 ¥95，再扣除约定的平台佣金及其他费用。

因此必须新增优惠资金承担明细和商家结算台账。不能直接以现金实付金额计算商家收入，也不能在缺乏资金来源和结算规则的情况下承诺商家足额到账。

## 十四、Redis、Kafka 与高并发设计

### 14.1 Redis 使用范围

建议 Redis 只作为缓存、限流和部分短期状态存储。

```
commerce:product:detail:{productId}
commerce:product:sku:{skuId}
commerce:category:tree:v1
commerce:membership:benefit:{userId}
commerce:promotion:active:{productId}
commerce:rate:merchant:{merchantId}
```

缓存规则：

- 商品详情：可配置 TTL，例如 60～300 秒。
- 类目树：版本化缓存。
- 商品上架、下架、审核变更：主动失效缓存。
- 商品库存：MySQL 为首期权威库存，Redis 可以缓存展示值。
- 会员权益：缓存必须受权益版本和有效期约束。
- 订单最终价格：不能以 Redis 缓存价格作为结算依据。

### 14.2 Kafka Topic 设计

```
commerce.product.created
commerce.product.submitted
commerce.product.approved
commerce.product.published
commerce.product.unpublished

commerce.inventory.reserved
commerce.inventory.released
commerce.inventory.committed

commerce.order.created
commerce.order.paid
commerce.order.cancelled
commerce.order.refunded

commerce.membership.activated
commerce.membership.expired

commerce.promotion.started
commerce.promotion.ended
```

事件统一封装：

```
{
  "eventId": "evt_10001",
  "eventType": "commerce.product.published",
  "aggregateType": "product",
  "aggregateId": "prod_10001",
  "aggregateVersion": 5,
  "occurredAt": "2026-11-07T12:00:00Z",
  "payload": {
    "productId": "prod_10001",
    "shopId": "shop_10001"
  }
}
```

要求：

1. 使用 Transactional Outbox 避免数据库提交成功但消息丢失。
2. 消费者使用 `eventId` 去重。
3. 相同商品的事件使用 `productId` 作为 Kafka Key。
4. 消费者必须支持重复投递、重试和 DLQ。
5. 对商品版本进行校验，避免旧事件覆盖新状态。
6. Kafka 不负责商品发布主事务的强一致性。

## 十五、非功能性要求

以下是建议的首期验收目标，不是现有系统已经达到的性能。

| 指标       | 首期目标                 |

## 十九、正式编码前必须确定的架构决策

本 Tech Spec 已覆盖主要业务，但还有几个需要在代码中固定的策略：
