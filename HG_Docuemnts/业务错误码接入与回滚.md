# 统一业务错误码接入与回滚

## 1. 已实施的协议与权威来源

- Go 定义：`internal/response/hgerrors/hg_codes_*.go`。字典不查询 DB/Redis；重复编号、重复 Key、跨模块编号、空提示、非法 HTTP 状态在包初始化和单测中被拒绝。
- 完整机器字典：`docs/error-codes.v1.json`。`200` 是成功，不在错误字典内。
- 七位编号采用 `module*100000+submodule*1000+reason`。COMMON=10、AUTH=11、IAM=12、IM=13、MALL=14、PAYMENT/WALLET=15、VIDEO/COMMENT/DANMAKU=16、CRAWLER=17、OPS=18、NOTIFICATION=19、MEDIA=20、REALTIME=21、RISK=22。SEARCH=23 和 MEMBERSHIP=24 保留号段，不杜撰尚无业务实现的失败规则。
- `1501004`、`1605001`、`2001005` 保留为处理中状态，不注册为失败定义。
- `Code` 是不可变常量，也实现 `error`。`Wrap(code,cause)` 保留原始错误链，可用 `errors.Is(err,code)`、`errors.Is(err,旧哨兵)` 和 `errors.As`。未知原因只解析为 `1000001`，不会回显 cause。
- 旧码对照：`HG_Docuemnts/业务错误码旧码映射.md`。一个旧码可能被多个模块用于不同状态，不能仅凭数字把所有错误强行归为同一业务原因。

## 2. HTTP 灰度协议

当前客户端尚未在本工作区验收，因而**默认保留旧协议**。准备好的客户端以如下值显式请求新协议：

```http
Accept: application/vnd.mlc.v2+json
```

该精确媒体类型与路由版本 `X-API-Version` 无关。只设置 `application/json` 或 `*/*` 不会开启新协议。JSON 请求的 `Content-Type` 仍为 `application/json`，签名与鉴权规则不变。

新协议示例，HTTP 403：

```json
{
  "code": 1201003,
  "error": "IAM_PERMISSION_DENIED",
  "message": "没有操作权限",
  "data": null,
  "trace_id": "关联标识",
  "details": {"requirement": "由服务端路由生成的公开权限申请条件"}
}
```

新协议成功的 `code` 始终为 `200`，提示为 `Success💯`，对象放在 `data`。HTTP 202 表示已受理，`data.status="accepted"`，不代表异步投影已经完成。

旧协议保留 `code/message/result/tid/timestamp`，分页对象自身的 `result`、游标和 total 等字段保持不变；新协议仅把同一分页对象放在 `data`，不展开或重命名其内部字段。旧隐式 HTTP 200 的失败在新协议下按字典返回合理的非 2xx。

统一出口仍是 `internal/response`：新调用使用 `HGFailError` 和 `HGSuccessStatus`；旧调用可用 `HGFailStatus` 同时提供旧状态与旧结果。**不要先调用 `WriteHeader` 再输出错误**。已开始发送的响应发生 panic 时中止连接，不追加第二个 JSON。

`trace_id` 优先取 context 中已有的有效 OpenTelemetry SpanContext，否则取项目 Trace 适配器，再取请求 TID。没有关联上下文时生成请求 ID；此兜底值不代表已采集分布式 Trace。没有新增 OTel exporter 或伪造 Span，现有自有 Trace 适配器的值/指针不一致问题已修正。

### 安全与兼容性变化

- 登录账号不存在与密码不正确统一返回凭据错误，避免账号枚举。
- SQL、JWT 解析细节、时间诊断和动态底层错误不复制到 HTTP 响应。
- 旧协议也不保证保留不安全的动态错误文案；客户端不能按 message 分支。
- Centrifugo 原生代理、LiveKit Webhook、二进制媒体流和探活无正文状态仍使用各自传输协议，不强行转换成业务 Envelope。

## 3. 各模块已接入的关键失败

| 模块 | 接入点 | 不改变的约束 |
|---|---|---|
| AUTH | JWT 缺失/无效/过期、会话撤销、会话依赖不可用、登录凭据隐藏 | Token 校验、会话与设备身份仍由已有逻辑判定；刷新策略不重写 |
| IAM | 路由声明的权限不足及公开申请提示、MFA 错误、权限依赖不可用 | 对象归属与商家资格仍在业务层校验 |
| IM | 会话拒绝、状态冲突、消息过长/为空、同请求不同内容 | 消息/设备投递/Outbox 同事务；同内容重放返回原回执 |
| MALL | 精确库存不足、广义不可购、钱包余额不足 | 原库存和资金事务及重放分支保留；广义库存哨兵不谎报纯库存不足 |
| PAYMENT | 充值订单缺失/过期、请求幂等冲突、渠道不可用 | 客户端成功不等于付款到账；模拟回调重放不得再次写账 |
| VIDEO | 评论缺失/关闭、弹幕关闭/过长、弹幕幂等冲突、互动 202 | 点赞 true 等已有幂等成功不改成重复操作错误 |
| CRAWLER | 独立服务改用共享出口、任务执行冲突、上游/存储失败 | 原服务同步完成任务仍是 HTTP 200，不假装是异步受理 |
| OPS | 权限拒绝、资产幂等/余额错误、爬虫任务租约冲突 | 高风险操作、审核与审计顺序不改 |
| NOTIFICATION / MEDIA | 模板缺失/冲突、资源不存在 | 发布/引用/审核等权威状态仍由原模块判断 |

还没有精确哨兵的分支使用 COMMON 分类，不从 `err.Error()` 文案猜出库存、角色、资金或重试语义。

## 4. Kafka 与 Centrifugo

`HGConsumerResult` 将 `ack/retry/dlq` 与 `Code` 分开。`Retryable=false` 的业务定义仍不自动跳过 Kafka 消息；只有明确的终止包装且 DLQ 同步确认后才允许推进该失败位点。

DLQ 保留原始 value（base64）、原 topic/partition/offset、key、headers 和时间戳，并增加：

- `error_code`：字典原因；未知错误为 `1000001`；
- `retry_count`：当前进程观察到的同一失败位点的重试次数，首次为零；
- `action`：`retry` 是错误留档，**不表示**可以提交；`dlq` 是终止隔离。

重试计数每分区仅维护一个失败头，最多 4096 槽。进程重启、重平衡或槽淘汰后不是全局持久重试次数，运维不得将它理解为跨进程的精确次数。

单条消费保持分区内连续成功位点；失败分区停止后续处理，其他分区可继续。弹幕批消费发现后续坏消息时，必须先完成有效前缀的 ClickHouse + Redis，再返回失败下标；前缀写入失败会整批重试。

**待确认的生产策略：** 原工程普通错误没有持久重试预算和退避调度，本次没有擅自用“超过次数”将它改成可跳过终态。尤其 Statistic/Danmaku 权威投影失败不能因为错误码为 4xx/5xx 或达到次数就越过源 offset。是否采用保留原位暂停、人工恢复或业务可接受的 DLQ 后继续，必须逐 topic 确认后实施。当前动作分类和重试元数据不等于完成了有界重试调度。

Centrifugo connect/RPC 的原生 `error.code`、`disconnect` 格式不变。新应用层失败事件可携带业务码，但本次不新增不存在的推送事件。IM 实时发布失败不推翻已提交消息，仍由已有 Outbox/Inbox、重试与断线同步恢复。

## 5. React 接入（仅说明，不修改其他仓库）

1. 将 `docs/error-codes.v1.json` 引入前端构建，生成 `{[error_key]:code}` 常量。不要从数据库实时拉取错误语义。
2. 升级请求封装后再附加专用 Accept 值；Fetch 先 `await response.json()`，再检查 `response.ok` 和 `body.code`，Axios 在非 2xx 拦截器读取 `error.response.data`。
3. 过渡期按 `body.data ?? body.result` 读载荷；失败 `data` 固定为 null，不能当成功。
4. 仅 `AUTH_TOKEN_EXPIRED=1101002` 触发现有单飞续签。所有并发请求共享同一续签 Promise，最多续签一次；只有幂等请求或具备稳定幂等键的写请求允许重放。
5. 缺失/无效 Token、已撤销会话与签名错误不盲目续签。503 不能误判为权限不足或自动登出。
6. `1201003` 展示权限提示及可选 `details.requirement`；`1402004` 刷新库存；支付结果不确定时查询状态，不能重付。
7. 模块自定义处理器优先于默认 Toast；重试还必须满足请求幂等性、预算与截止时间，不能只看字典中的 retryable。
8. 不将服务端 `message`、HTTP 200 或实时通知当作付款、授权、持久化完成的唯一依据。

## 6. 迁移、监控与发布

- 迁移文件：`migrations/000090_error_code_catalog.up.sql` 和对应 down。创建小型目录并填充静态元数据，不改业务表，无请求期查询。
- 本次只生成文件，**未连接数据库、未执行迁移**。目录对管理端应只读，不允许编辑编号、Key 和运行时语义。
- 离线导出：`go run ./cmd/hg_error_catalog`；目录 INSERT 导出用 `-format seed`。已发布版本不可覆盖旧迁移；后续新增定义应创建新版本字典和增量迁移，并做历史兼容性审核。
- `cmd/hg_error_catalog/hg_catalog_test.go` 核对当前 Go 字典、JSON 基线和 SQL 种子；CLI 的 `-baseline` 检查历史快照是当前字典的不可变子集。`.github/workflows/business-errors-ci.yml` 从 PR 基线或前一次提交取快照，拒绝删除或改变已发布定义，并执行相关测试、race、vet 与 production 构建。首版没有旧快照时仍执行当前字典/种子一致性测试。
- `hg_business_errors_total{module,error_code}` 是固定字典维度的进程计数，挂入现有管理 metrics 出口。现有 Kafka `mlc_kafka_dlq_*`、`retryable/terminal_failures` 指标保留，修正批处理 retry 留档成功未计数问题。
- HTTP 失败记录安全的结构化分类、状态和关联 ID，不记录 Token、SQL、用户请求正文或完整 cause。完整原始 cause 仍保留于 `AppError.Unwrap`，不把含秘密的底层文本无条件打入日志。
- 客户端灰度前先验收所有签名头、非 2xx JSON、超时续签和分页；无客户端、无压测、无真实外部服务验收，不宣称达到千万并发容量或生产已验证。

### 回滚

1. 先取消客户端的专用 Accept，恢复旧码与 `result` 格式。
2. 确认不再有新协议客户端后再回滚应用；否则新客户端面对旧服务器的非 2xx/字段差异仍需兼容。
3. 错误目录表不参与运行时，回滚应用无需删除它。仅获得数据库回滚授权时才执行 down。
4. 不重置 Kafka offset、不清理 Inbox/Outbox、不回滚已提交订单和资金、不删除历史错误码。
