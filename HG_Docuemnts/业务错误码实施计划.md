# 统一业务错误码：实施与验收计划

| 顺序 | 现状与差异 | 实施与验收点 |
|---|---|---|
| 1. 字典 | `internal/response/hg_err_result.go` 定义六位码，`internal/pkg/hg_response` 是另一套旧标签/文章常量。`idgen` 的时钟、序号等错误属于内部诊断。 | `internal/response/hgerrors` 是七位业务码唯一权威；按领域分文件，校验编号、Key、状态及历史快照。SEARCH/MEMBERSHIP 未有明确失败定义，保留号段。 |
| 2. HTTP | `HGResultModel` 的载荷是 `result`；分页对象自身也有 `result`。多数失败先写 HTTP 状态再调用 `FailResult`，部分旧接口隐式返回 200。 | 由 `internal/response` 一次写状态和响应体；显式协商新格式，保留默认旧格式。未知错误脱敏，跟踪 ID 关联日志；不复制大分页载荷。 |
| 3. AUTH → IAM → IM | Guard、JWT、路由权限与业务拒绝是不同边界；IM HTTP 与 Centrifugo RPC 使用不同协议。 | 区分缺失、无效、过期、依赖故障；登录不枚举账号。保留权限申请提示。IM 重放成功与异内容冲突分别测试。 |
| 4. MALL → PAYMENT | `product`/`commerce` 的库存哨兵还表示商品不可购；钱包、充值和模拟支付有各自的状态判断。 | 仅在能确定库存不足的分支细分错误；沿用已有交易、重放与支付确认逻辑。 |
| 5. VIDEO → CRAWLER → OPS → NOTIFICATION | 评论、弹幕、任务租约、通知模板缺失均曾返回通用参数码。 | 按业务哨兵映射；HTTP 202 保持成功，用状态说明已受理。按实际模块补充 MEDIA 等适配。 |
| 6. 消息协议 | IM 消息、设备投递和 Outbox 同事务，实时发布在事务外；Kafka 已有分区回退、终止标记、同步 DLQ 和监控。 | 业务码只描述原因，不决定提交。DLQ 增加原因码和重试信息；验证分区前缀与 DLQ 写入失败路径。Centrifugo connect/RPC 保留原生协议。 |
| 7. 目录、监控与客户端 | 迁移采用编号 `up/down.sql`，当前最高 000089；项目有手写 Prometheus 出口、请求 TID 和自有 Trace 适配器，无 React 工程。 | 生成 000090 离线目录迁移、版本化 React JSON 和接入说明；指标维度只取静态定义。 |
| 8. 发布 | 旧客户端可能只处理 HTTP 200 和六位码。 | 先发布兼容服务端，再由客户端显式协商；回滚先撤协商。执行无外部服务的契约、业务重放、race、vet 和 production 构建，数据库与真实服务验收单独执行。 |
