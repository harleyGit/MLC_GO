可以。你这个场景已经不是简单的“充值表”了，而是一个**大型交易/支付域的账户资金系统**：

> 用户 → 充值人民币 → 获得平台币 → 平台币作为账户余额 → 购买会员/家电/衣服/化妆品/数码产品 → 扣减平台币 → 形成完整订单、支付、资金流水、退款/冲正记录。

如果目标是按**支付宝/抖音支付/大型电商**的思路设计，并且考虑未来达到**亿级甚至更大数据量**，我建议不要把所有东西塞进一张 `recharge_order` 表，而是拆成：

```text
用户
 │
 ▼
充值商品/充值档位
 │
 ▼
充值订单
 │
 ├── 支付单
 │     └── 支付渠道
 │
 ▼
资金账户
 │
 ├── 账户余额
 │
 └── 资金流水
 │
 ▼
平台币
 │
 ▼
交易订单
 │
 ├── 会员
 ├── 家电
 ├── 衣服
 ├── 化妆品
 └── 数码产品
```

核心思想是：

> **订单负责“买了什么”，支付负责“怎么付”，账户负责“有多少钱”，流水负责“钱为什么发生变化”。**

# 二、第一张表：充值档位

你看到 B 站充值页面里面：

```text
6元
30元
68元
198元
...
```

这些本质上不是订单，而是**充值商品/SKU**。

建议：

```sql
CREATE TABLE payment_recharge_sku (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    
    sku_id          VARCHAR(64) NOT NULL,
    
    sku_code        VARCHAR(64) NOT NULL,
    
    title           VARCHAR(128) NOT NULL,
    
    currency        CHAR(3) NOT NULL DEFAULT 'CNY',
    
    pay_amount      BIGINT UNSIGNED NOT NULL COMMENT '实际支付金额，单位分',
    
    coin_amount     BIGINT UNSIGNED NOT NULL COMMENT '获得平台币数量',
    
    bonus_coin      BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '赠送平台币',
    
    total_coin      BIGINT UNSIGNED NOT NULL,
    
    status          TINYINT NOT NULL DEFAULT 1,
    
    sort_order      INT NOT NULL DEFAULT 0,
    
    start_time      DATETIME(3) NOT NULL,
    
    end_time        DATETIME(3) DEFAULT NULL,
    
    version         INT UNSIGNED NOT NULL DEFAULT 1,
    
    created_at      DATETIME(3) NOT NULL,
    
    updated_at      DATETIME(3) NOT NULL,
    
    PRIMARY KEY (id),
    
    UNIQUE KEY uk_sku_id (sku_id),
    
    UNIQUE KEY uk_sku_code (sku_code),
    
    KEY idx_status_sort (status, sort_order)
) ENGINE=InnoDB;
```

例如：

| sku_id | title | pay_amount | coin_amount | bonus_coin |
|---|---|---:|---:|---:|
| `RSKU_01J...` | 6元充值 | 600 | 600 | 0 |
| `RSKU_01K...` | 30元充值 | 3000 | 3000 | 0 |
| `RSKU_01L...` | 68元充值 | 6800 | 6800 | 200 |
| `RSKU_01M...` | 198元充值 | 19800 | 19800 | 2000 |

这里有一个非常重要的设计：

## 金额不要使用 DECIMAL

不要：

```sql
pay_amount DECIMAL(10,2)
```

而使用：

```sql
pay_amount BIGINT
```

单位：

```text
分
```

例如：

```text
6.00元 → 600
68.00元 → 6800
198.00元 → 19800
```

这样避免浮点/金额计算问题。

# 三、为什么 SKU 需要单独设计？

因为：

```text
充值档位 ≠ 充值订单
```

比如：

```text

```

这是一个商品。

用户点击之后：

```text
用户 A
 ↓
购买 6元充值
 ↓
生成订单 ORD_XXXX
```

订单才是交易事实。

所以：

```text
payment_recharge_sku
```

保存：

> “卖什么”

而：

```text
recharge_order
```

保存：

> “谁买了什么”

对外使用。


# 六、订单号应该怎么生成？

大型系统不建议简单：

```go
time.Now().Unix()
```

也不要：

```text
UUID
```

直接作为所有业务 ID。

可以采用：

```text
业务前缀 + 时间 + Snowflake/UUID/自定义序列
```

例如：

```text
R20260930102543_8F72K92L
```

或者：

```text
R20260930_01K7X8F3A9Y7...
```

不同业务使用不同前缀：

```text
R = Recharge
T = Trade
P = Payment
RF = Refund
L = Ledger
```

例如：

```text
R202609301234...
T202609301234...
P202609301234...
RF202609301234...
```

不过实际大型系统里，我更建议：

> **业务订单号采用 Snowflake/UUIDv7/ULID 类有序 ID + 业务前缀。**

例如：

```text
R01K8M9K2W7H6...
```

这样：

```text
全局唯一
趋势递增
无需中心数据库发号
适合分布式
```

# 七、非常重要：SKU 快照

你会注意到订单里面我没有只保存：

```sql
sku_id
```

还保存：

```sql
sku_snapshot_title
pay_amount
coin_amount
bonus_coin
```

这是非常重要的。

假设：

2026 年：

```text
充值 68元
赠送 200币
```

用户购买以后。

2027 年：

```text
68元
赠送 500币
```

如果订单只保存：

```text
sku_id = xxx
```

那么你以后查询历史订单时：

```text
这个用户当时到底获得了多少币？
```

可能就错了。

所以订单必须保存**交易时快照**：

```text
sku_id
sku_snapshot_title
pay_amount
coin_amount
bonus_coin
total_coin
```

原则：

> 商品可以变化，订单历史事实不能变化。

# 十五、账户流水：整个资金系统的“账本”

这个是最重要的表之一：

```text
account_ledger
```

不要仅仅依靠：

```text
account.available_balance
```

因为：

> 余额告诉你“现在多少钱”，流水告诉你“钱怎么来的、怎么没的”。

设计：

```sql
CREATE TABLE account_ledger (
    id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    ledger_id           VARCHAR(64) NOT NULL,

    account_id          VARCHAR(64) NOT NULL,

    user_id             BIGINT UNSIGNED NOT NULL,

    currency            VARCHAR(16) NOT NULL,

    business_type       VARCHAR(32) NOT NULL,

    business_id         VARCHAR(64) NOT NULL,

    direction            TINYINT NOT NULL,

    amount               BIGINT NOT NULL,

    balance_before       BIGINT NOT NULL,

    balance_after        BIGINT NOT NULL,

    idempotency_key      VARCHAR(128) NOT NULL,

    remark               VARCHAR(256) DEFAULT NULL,

    created_at            DATETIME(3) NOT NULL,

    PRIMARY KEY (id),

    UNIQUE KEY uk_ledger_id (ledger_id),

    UNIQUE KEY uk_idempotency (idempotency_key),

    KEY idx_account_created (
        account_id,
        created_at,
        id
    ),

    KEY idx_user_created (
        user_id,
        created_at,
        id
    ),

    KEY idx_business (
        business_type,
        business_id
    )

) ENGINE=InnoDB;
```

# 十六、流水具体长什么样？

比如：

用户：

```text
user_id = 10001
```

充值：

```text
68元
```

获得：

```text
6800 Coin
```

流水：

```text
balance_before = 0
amount         = +6800
balance_after  = 6800
direction      = CREDIT
business_type  = RECHARGE
business_id    = R20260930xxxx
```

然后用户购买：

```text
会员
```

消耗：

```text
300 Coin
```

产生：

```text
balance_before = 6800
amount         = -300
balance_after  = 6500
direction      = DEBIT
business_type  = MEMBERSHIP
business_id    = T20260930xxxx
```

这就形成完整资金链。

---

# 十七、为什么流水里面一定要保存 before/after？

这个设计非常重要。

例如：

```text
before = 6800
amount = -300
after  = 6500
```

以后审计的时候：

```text
6800 - 300 = 6500
```

可以验证。

如果只有：

```text
amount = -300
```

你只能知道：

> 扣了 300。

不知道：

> 扣之前多少，扣之后多少。

# 十八、千万不要直接这样做

很多初学者会写：

```sql
UPDATE account
SET balance = balance - 300
WHERE user_id = 10001;
```

这在高并发资金系统里面是不够的。

应该至少：

```sql
START TRANSACTION;

SELECT available_balance
FROM account
WHERE account_id = ?
FOR UPDATE;

-- 检查余额

UPDATE account
SET available_balance = available_balance - 300,
    version = version + 1
WHERE account_id = ?;

INSERT INTO account_ledger (...);

COMMIT;
```

核心保证：

```text
余额修改
+
流水记录
```

必须在**同一个事务**里面。

# 二十一、但是 Kafka 不能直接保证资金安全

这一点特别重要。

不能：

```text
Kafka消费成功
↓
直接认为钱到账
```

因为可能：

```text
Kafka消息重复
Kafka消费失败
服务重启
网络超时
数据库提交成功但 ACK 丢失
```

所以必须：

> **幂等消费。**

例如：

```sql
UNIQUE(idempotency_key)
```

```text
RECHARGE:R01K8M9...
```

第一次：

```text

```

第二次：

```text
INSERT duplicate
```

系统知道：

```text
这笔充值已经处理过
```

不会再次增加余额。

# 二十二、推荐采用 Outbox Pattern

这是你以后做大型 Go 后端非常值得掌握的设计。

充值完成：

```text
DB Transaction
│
├── payment_order = SUCCESS
│
├── recharge_order = PAID
│
└── outbox_event = RECHARGE_SUCCESS
```

三个操作：

```text
同一个 MySQL Transaction
```

然后后台：

```text
Outbox Worker
      ↓
Kafka
```

这样避免：

```text
DB成功
Kafka失败
```

导致事件丢失。

# 二十三、Outbox 表

```sql
CREATE TABLE outbox_event (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    event_id        VARCHAR(64) NOT NULL,

    aggregate_type  VARCHAR(64) NOT NULL,

    aggregate_id    VARCHAR(64) NOT NULL,

    event_type      VARCHAR(64) NOT NULL,

    payload         JSON NOT NULL,

    status          TINYINT NOT NULL DEFAULT 0,

    retry_count     INT UNSIGNED NOT NULL DEFAULT 0,

    next_retry_at   DATETIME(3) DEFAULT NULL,

    created_at      DATETIME(3) NOT NULL,

    published_at    DATETIME(3) DEFAULT NULL,

    PRIMARY KEY (id),

    UNIQUE KEY uk_event_id (event_id),

    KEY idx_status_retry (
        status,
        next_retry_at,
        id
    ),

    KEY idx_aggregate (
        aggregate_type,
        aggregate_id
    )

) ENGINE=InnoDB;
```

# 二十六、亿级表索引一定要克制

例如：

```text
account_ledger
```

不要随便：

```text
idx_user
idx_account
idx_order
idx_business
idx_time
idx_status
idx_type
...
```

因为：

> 一个亿级表，每增加一个索引，都可能带来巨大的存储、写入和维护成本。

核心索引应该围绕查询场景设计。

例如用户查询资金流水：

```sql
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 50
```

那么：

```sql
KEY idx_user_created (
    user_id,
    created_at,
    id
)
```

非常重要。

# 二十七、用户订单查询不要 OFFSET

不要：

```sql
LIMIT 100000, 20
```

亿级数据非常痛苦。

应该：

```text
Keyset Pagination
```

例如：

```sql
SELECT *
FROM trade_order
WHERE user_id = ?
  AND (
       created_at < ?
       OR (
           created_at = ?
           AND id < ?
       )
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

这和你之前学习 Go 后端的 **Keyset Paging** 是同一类思想。
