# 商品发布落地设计（基于《商品发布技术方案》）

## 现状与边界

- `internal/modules/product` + `mall_merchant` + `product` / `product_sku` 已提供 **M币单 SKU** 商品发布、审核、补图、编辑、归档；`trade_order`、`payment_order`、`mall_fulfillment`、coin lot 在实物 M币交易中复用同库短事务。保留旧 API、价格单位及历史订单，不将 M币价格自动换算为人民币。
- `internal/modules/mallcny` 与 `hg_mall_cny_*` 仅是显式开启的 debug 沙箱，单 SKU、模拟支付、不支持审核/媒体绑定/正式发货；不可迁移为生产支付事实或与旧商品 ID 混用。
- `internal/modules/trade`、`payment`、`refund` 目前主要是模型和仓储契约；`recharge` 有独立的充值编排，但不代表商品人民币支付渠道已接入。`coin` 可提供既有余额和流水能力，不直接用充值汇率定义购物抵扣比例。
- React 商家中心 `hg_merchant_products_page.jsx`、`hg_merchant_publish_page.jsx`、`hg_merchant_orders_page.jsx` 目前接入 M币接口；`hg_mall_categories.js` 是五个类目的静态白名单；`hg_mall_cny_page.jsx` 为独立 debug 页面。两套金额和身份不可在同一商品卡上混显。

**已确认方向**：新增生产 CNY 商品主链，旧 M币商品与 debug 沙箱继续隔离；正式支付宝/微信支付预留对接，debug 可模拟支付，但模拟记录永不进入生产账本。上线人民币交易以真实渠道回调验签及退款对账完成为门槛。

## 发布模型与状态机

以 `mall_merchant` 的 `merchant_id` 和用户归属复用商家身份；新增 `merchant_shops` 等身份表前须先明确同一商家与店铺的映射，避免两套所有权。类目新增平台管理的三级树与叶子模板，ID 通过字符串传输；先只开放已核实资质/履约规则的普通实物叶子类目。受监管类目、虚拟交付、会员权益和本地服务在资质、退款及履约规则实现前不可上架，不因表单可选择就允许销售。

商品以独立 CNY `product_id` 标识 SPU，销售规格由 1～200 个 SKU 组成，最多三维规格；服务器按标准化规格键值计算哈希、校验维度和值集合与所有 SKU 组合一致，禁止重复组合、负价及超出上限的价格/库存。金额只存人民币整数分，ID 对外为字符串。媒体先登记本人上传资产，再在事务内绑定草稿；上传完成不代表审核通过。既有 M币 `mall_product_image` 的归属/删除安全检查可作为能力参考，但不共用公开商品图片集合。

审核状态 `DRAFT → PENDING → APPROVED/REJECTED`，销售状态 `OFF_SHELF → ON_SHELF`；只有 `APPROVED + ON_SHELF` 且 SKU 可售才进入目录和新订单。驳回后修改可重提；强制停售 `SUSPENDED` 仅平台恢复；归档 `DELETED` 不影响订单快照。线上版本与待审版本分开：商家编辑在售商品只写审核快照，审核通过在短事务内切换 `published_version`；审核操作记录操作者、版本及结论，并禁止审核自己店铺。乐观锁冲突返回 409，创建/提交使用按商家和操作域唯一的幂等键及规范化请求哈希；相同键不同请求拒绝。

### 迁移计划（只编写，未经确认不执行）

新建生产专属 `commerce_category`、`commerce_category_attribute`、`commerce_merchant_qualification`（或对已有商家资质表建立明确映射）、`commerce_product`、`commerce_product_version`、`commerce_sku`、`commerce_media`、`commerce_inventory`、`commerce_inventory_log`、`commerce_audit_log`、`commerce_idempotency`；交易阶段追加 `commerce_order`（关联既有 `trade_order_id`）、`commerce_order_item`、`commerce_inventory_reservation`、`commerce_payment_allocation`、`commerce_settlement_ledger`、`commerce_outbox`/`commerce_inbox`。表名统一 `commerce_` 前缀，避免与既有 `product` 及 debug `hg_mall_cny_*` 含义混淆；同一订单的支付事实仍以 `trade_order`、`payment_order`、`refund_order` 为准，不新建另一套现金账本。完整 DDL 需按每阶段的实际事务、查询和回滚方案分别交付，不能直接复制规格文档示例建表。

大表索引至少覆盖 `product_id` 唯一查找、`(merchant_id,id)` 商家游标、`(category_id,sale_status,id)` 目录游标、`(audit_status,id)` 审核队列、`(product_id,status,id)` SKU，以及订单 `(merchant_id,id)` / `(user_id,id)` 和超时 `(status,expires_at,id)`。列表默认 20 条、服务端固定最大值，使用 `limit+1` 与稳定游标；拒绝深 OFFSET、无界预加载和动态拼接过滤。画像、图片数、SKU 最低价等仅可采用经验证的索引/有界聚合或投影，不能逐商品发 N 次查询。最终索引与 P95 需要实际数据量、EXPLAIN 和压测验证。

## API 与页面规划

生产路由建议单独置于 `/api/v1/commerce/`，保留 `/api/v1/mall/*` 与 `/api/v1/mall/cny/*` 现有语义。新增商家类目/属性、媒体上传确认和未使用清理、草稿创建/修改/详情/游标列表、提交审核、上架/下架、SKU 库存调整/流水及商家订单/发货接口；管理员读取审核队列及审批接口；消费者只读已上架商品目录和 SKU 详情。所有路由复用 JWT、签名和 IAM，服务端在事务内再次校验商家状态、店铺归属、商品/订单归属与版本。请求体有大小上限，图片走格式/魔数/大小校验及本人资产绑定；失败不记录收件信息和支付敏感字段。

商家中心显式按货币分区：原“我的 M币商品/订单”保持既有路径与行为；新增“人民币商品”入口逐步接入新 API。发布页首先加载服务端可经营叶子类目和模板，不把 `hg_mall_categories.js` 的旧白名单当作新业务权威。发布页支持服务端草稿断点续编、多 SKU（限 200）规格表与客户端预校验、人民币分格式化、已绑定/未绑定媒体清理和审核反馈；上架与驳回提示严格对应状态。商品管理页提供唯一 ID 精确查询、审核版本预览、上/下架、归档和库存操作；订单页只展示对应货币和已经支付且本店有权查看的收件快照，登记运单必须再次经服务端确认。当前 M币页面的紫色渐变主按钮、白卡片和语义徽标可继续复用，生产新页面用主题变量保证深浅色及对比度，不把沙箱示例放进正式表单。

首期接口按现有 `RouteSpec` 注册（全部登录、签名、资源授权；公开目录也需遵循当前商城鉴权约定）：

| 请求 | 路径 | 响应或写入约束 |
| --- | --- | --- |
| GET | `/api/v1/commerce/merchant/categories` | 仅返回本店可经营的叶子类目及属性模板版本；空集不可提交 |
| POST | `/api/v1/commerce/merchant/products` | `Idempotency-Key` + 正文哈希，创建 DRAFT；返回字符串 `productId` / `version` |
| PUT | `/api/v1/commerce/merchant/products/{id}` | `expectedVersion`；只更新草稿/待审版本，冲突 409 |
| GET | `/api/v1/commerce/merchant/products` | `cursor`，最多 20+1，返回 `list/nextCursor/hasMore` |
| GET | `/api/v1/commerce/merchant/products/{id}` | 本店唯一商品精确点查及草稿版本，越权不返回待审内容 |
| POST | `/api/v1/commerce/merchant/products/{id}/submit` | 校验图片、模板、资质、SKU 完整性，DRAFT/REJECTED→PENDING |
| POST | `/api/v1/commerce/admin/products/{id}/decision` | 平台 RBAC，拒绝自审；记录版本、原因与操作者 |
| POST | `/api/v1/commerce/merchant/products/{id}/publish` | 仅 APPROVED 可上架；下架/归档另设动作，不让客户端写状态列 |
| GET | `/api/v1/commerce/products`、`/api/v1/commerce/products/{id}` | 仅可见已审已上架版本、标明 `currency: CNY`，库存只是快照 |

商家创建正文建议采用 `{ categoryId: "...", productType: "PHYSICAL", title, subtitle, images: [mediaId], specDimensions: [{name, values}], skus: [{skuCode, specs, priceCent, initialStock}] }`。服务端生成商家/店铺 ID，`mediaId` 来自已确认、未占用的本人图片；`priceCent` 为 int64 整数分，前端文本仅作格式化。标准库 JSON 数字解析、JS 53 位安全整数和 DB 有符号范围需统一限制；与现有 M币 `amount`、沙箱 `priceFen` 不做字段复用或静默转换。错误响应沿用项目 `response` 包，HTTP 400/403/404/409 分开表达验证、归属、缺失、状态冲突。

## 交易、支付与失败恢复

服务端试算与建单重算相同定价规则，订单保留 SKU、金额、折扣承担方、运费及地址快照；客户端金额仅用于发现报价变化。预占库存采用 `available >= quantity` 条件更新与唯一预占 ID，同订单事务写订单、预占、幂等事实及 outbox。超时关闭与支付成功竞争同一订单状态锁；回调晚到时必须记录实收事实、触发原路退款/人工对账，不得无声忽略或二次履约。退款依据原支付构成分别退回现金与 M币，退款后库存是否回补取决于退货入库事实，不能无条件回补。

生产支付预留 `支付宝 / 微信` 渠道适配接口：创建支付尝试、查询支付状态、验签回调、关闭订单、按原渠道退款与退款查询。渠道配置/证书由既有密钥管理或环境注入，不提交、不输出凭据；回调必须验证签名、商户号、订单、币种、实付分额与事件唯一标识，再在同库幂等事务推进 `payment_order`、`trade_order`、预占与 outbox。网络调用不放入 MySQL 事务，结果未知时按幂等键查询渠道并重试/对账。debug 模拟渠道必须由环境 + 配置双重控制，使用独立测试订单命名空间和标识，不把模拟回调声明为支付宝或微信真实回调；pre/prod 禁止模拟成功。没有真实渠道的商户协议、回调/退款文档与可隔离测试账号时，正式支付、发货及结算入口保持不可用，**不宣称 CNY 交易已上线**。

M币抵扣待独立配置比例、钱包预占/确认/释放及原路退款台账完成后开放；不能把币直接算入人民币账本，不能复用 `recharge` 支付成功作为权益发放。会员卡需要权益规则/到期/退款回收；拼团、优惠券和平台补贴需要资金承担方结算台账；这些能力未实现前不可在正式商品页提供可点击入口。

## 分阶段验收

1. 类目/资质与商品：草稿、审核、版本隔离、上架/下架、图片、商家与消费者页面联调；覆盖越权、重复规格、负价、冲突、重复请求、图片归属和历史订单不变。
2. 库存与订单：并发预占、超时释放、订单价格快照和店铺发货；构造 100 人争抢 10 件库存、迟到回调与发货重放。无渠道时只能验收不可支付阶段。
3. 支付与退款：分别接入支付宝/微信官方生产协议及回调和退款对账；隔离 debug 模拟端到端测试；生产准入需真实渠道沙箱验签、幂等及对账证据。
4. 会员/M币/营销：明确平台与商家承担方，接入双账本、预占补偿、权益生效/撤销，再逐项启用 UI。

不执行迁移、不启动有真实写入的后台任务或支付测试；阶段验收须注明执行环境、命令、结果与未覆盖风险。预计亿级订单需评估分库/归档、热 SKU 锁竞争、队列积压与限流降级；本设计不宣称已经达到容量目标。
