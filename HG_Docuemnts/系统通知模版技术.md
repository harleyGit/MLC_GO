# **MLC 系统通知模板管理技术规格文档（Tech Spec）**

版本：v1.0 ｜ 技术栈：Go + React + MySQL + Redis + Kafka + Centrifugo ｜ 适用模块：运维管理、IAM、消息中心、系统通知

## **一、项目目标**

在 MLC 平台的**运维管理后台**新增「系统通知模板管理」功能，由具备权限的管理员统一配置、审核、发布和维护通知模板。

当用户发生注册成功、订单支付、商品审核、账号安全变更等业务事件时，Go 后端根据对应模板生成通知，通过消息中心的「系统通知」展示，并可通过 Centrifugo 实时推送。

设计参考 哔哩哔哩（Bilibili）、抖音 等大型内容平台常见的站内消息体验，但以下为适合 MLC 工程的自主架构设计，不代表这些平台的内部实现。

## **二、整体架构设计**

系统通知业务链路

逻辑架构图：Kafka 负责异步任务，MySQL 保存权威数据，Centrifugo 负责实时通知，不承担永久存储。

### **2.1 组件职责**

| 组件                      | 职责                   |
| ----------------------- | -------------------- |
| React Admin             | 通知模板配置、审批、发布和发送管理    |
| Go Notification Service | 模板管理、渲染、发送编排         |
| MySQL 8.0               | 模板版本、发送任务、通知记录、用户收件箱 |
| Redis                   | 未读数缓存、限流、热点模板缓存      |
| Kafka                   | 业务事件异步消费、批量任务处理      |
| Centrifugo              | 在线用户的新消息提醒、未读数更新     |
| SeaweedFS               | 通知封面、公告图片等媒体资源       |
| IAM                     | 后台权限、业务作用域、操作审计      |

**不建议将通知全文直接放在 Kafka 中作为唯一存储。** Kafka 负责事件传递；消息中心的持久数据以 MySQL 为准。

## **四、通知模板配置协议**

建议使用 JSON 作为前后端传输格式，所有模板均采用统一 Schema。

### **4.1 完整模板示例**

```

{
  "template_code": "order.payment_success",
  "name": "订单支付成功",
  "category": "transaction",
  "title_template": "订单支付成功",
  "body_template": "您的订单 {{order_no}} 已支付成功，实付 ¥{{amount}}。",
  "variables_schema": {
    "order_no": {
      "type": "string",
      "required": true,
      "max_length": 64
    },
    "amount": {
      "type": "string",
      "required": true,
      "pattern": "^[0-9]+\\.[0-9]{2}$"
    }
  },
  "action_type": "order_detail",
  "action_config": {
    "route_name": "order_detail",
    "params": {
      "order_id": "{{order_id}}"
    }
  },
  "priority": 2,
  "channels": ["in_app", "realtime"],
  "scope_type": "platform",
  "scope_id": "",
  "locale": "zh-CN",
  "status": "draft"
}

```

注意：`order_id` 也必须在正式 Schema 中声明为必填字符串。模板发布时必须检查标题、正文及跳转参数中的全部变量，防止遗漏。

### **4.2 变量渲染规范**

推荐使用 `{{variable_name}}`，不引入复杂模板脚本语言。

Go 服务负责：

1. 提取模板中的变量。
2. 验证变量是否存在、类型是否正确。
3. 检查字符串长度和格式。
4. 对正文进行纯文本安全处理。
5. 替换变量，生成最终通知快照。
6. 记录使用的模板版本。

禁止执行模板中的任意代码，禁止使用 `eval`，禁止将用户提供的 HTML 直接渲染为可执行内容。

**建议消息中心 V1 仅支持纯文本与受控图片资源。** 富文本、Markdown、卡片式通知可以在后续版本增加。

### **4.3 跳转协议**

不要允许管理员随意配置任意 URL。推荐使用前端路由白名单：

```
const NOTIFICATION_ROUTES = {
  order_detail: "/mall/orders/:orderId",
  security_center: "/settings/security",
  announcement_detail: "/announcements/:id",
  video_detail: "/video/:videoId",
  product_detail: "/mall/products/:productId"
};
```

后端返回结构化的 `action_type` 与 `action_params`，React 负责解析并导航。

必须验证参数、限制内部路由，并在跳转目标页面重新进行用户身份与资源权限校验。

## **五、MySQL 数据库设计**

采用「模板主表 + 不可变版本表 + 发送任务表 + 通知实例表 + 用户收件箱表」的结构。

### **5.1 数据关系**

```
notification_templates
  模板主表
      │
      └── notification_template_versions
              模板版本表
                    │
                    └── notification_dispatch_tasks
                            发送任务
                                │
                                └── notification_messages
                                        通知内容快照
                                            │
                                            └── notification_inbox
                                                    用户收件箱
                                                    已读/删除状态
```

其中一条通知内容可以关联多个收件人。这样平台公告可以复用内容，避免为每个用户重复存储相同正文。

### **5.2 数据库 DDL**

以下为 MySQL 8.0 可执行的核心建表 SQL。

```

CREATE TABLE notification_templates (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    template_code VARCHAR(100) NOT NULL,
    name VARCHAR(128) NOT NULL,
    category VARCHAR(32) NOT NULL,
    scope_type VARCHAR(32) NOT NULL DEFAULT 'platform',
    scope_id VARCHAR(64) NOT NULL DEFAULT '',
    status VARCHAR(20) NOT NULL DEFAULT 'draft',
    latest_version INT UNSIGNED NOT NULL DEFAULT 0,
    published_version INT UNSIGNED DEFAULT NULL,
    created_by VARCHAR(64) NOT NULL,
    updated_by VARCHAR(64) NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_template_code (template_code),
    KEY idx_template_status (status, category)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE notification_template_versions (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    template_id BIGINT UNSIGNED NOT NULL,
    version INT UNSIGNED NOT NULL,
    title_template VARCHAR(200) NOT NULL,
    body_template TEXT NOT NULL,
    variables_schema JSON NOT NULL,
    action_type VARCHAR(32) NOT NULL DEFAULT 'none',
    action_config JSON DEFAULT NULL,
    channels JSON NOT NULL,
    priority TINYINT UNSIGNED NOT NULL DEFAULT 2,
    locale VARCHAR(16) NOT NULL DEFAULT 'zh-CN',
    status VARCHAR(20) NOT NULL DEFAULT 'draft',
    created_by VARCHAR(64) NOT NULL,
    reviewed_by VARCHAR(64) DEFAULT NULL,
    reviewed_at DATETIME(3) DEFAULT NULL,
    published_at DATETIME(3) DEFAULT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_template_version (template_id, version),
    CONSTRAINT fk_notification_template
        FOREIGN KEY (template_id)
        REFERENCES notification_templates(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE notification_dispatch_tasks (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    request_id VARCHAR(100) NOT NULL,
    template_id BIGINT UNSIGNED NOT NULL,
    template_version INT UNSIGNED NOT NULL,
    target_type VARCHAR(32) NOT NULL,
    target_config JSON NOT NULL,
    variables JSON NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    scheduled_at DATETIME(3) DEFAULT NULL,
    total_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    success_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    failure_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    created_by VARCHAR(64) NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_dispatch_request (request_id),
    KEY idx_dispatch_schedule (status, scheduled_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE notification_messages (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    task_id BIGINT UNSIGNED NOT NULL,
    template_id BIGINT UNSIGNED NOT NULL,
    template_version INT UNSIGNED NOT NULL,
    event_key VARCHAR(160) NOT NULL,
    title VARCHAR(200) NOT NULL,
    body TEXT NOT NULL,
    category VARCHAR(32) NOT NULL,
    action_type VARCHAR(32) NOT NULL DEFAULT 'none',
    action_params JSON DEFAULT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_message_event (event_key),
    KEY idx_message_task (task_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE notification_inbox (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    message_id BIGINT UNSIGNED NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    read_at DATETIME(3) DEFAULT NULL,
    deleted_at DATETIME(3) DEFAULT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_user_message (user_id, message_id),
    KEY idx_user_inbox (
        user_id, deleted_at, created_at DESC, id DESC
    ),
    KEY idx_user_unread (user_id, read_at, deleted_at),
    CONSTRAINT fk_inbox_message
        FOREIGN KEY (message_id)
        REFERENCES notification_messages(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

```

### **5.3 数据库实现补充约束**

上述 DDL 是核心模型，生产实现还必须满足以下规则：

- `notification_templates.status` 表示模板整体是否启用；版本表 `status` 表示具体版本的审批和发布状态。
- 已发布版本禁止原地修改。编辑时创建新版本，审批通过后原子更新 `published_version`。
- `notification_messages.event_key` 必须由可信业务事件生成，确保同一业务事件不会重复创建通知内容。
- 对于相同正文但不同用户的通知，使用同一 `message_id` 配合不同 `user_id`。
- 对于每个用户内容不同的模板，例如含用户名、订单号的通知，必须按用户或相同渲染内容分组生成消息，不得共享包含其他用户数据的内容快照。
- `notification_inbox` 的唯一键阻止同一通知重复进入同一用户收件箱。
- 用户删除通知只更新 `deleted_at`，不直接删除公共消息。
- 所有用户 ID 必须与现有 `users.user_id` 类型一致；上线前检查字符集和排序规则。
- 业务上所有日期使用 UTC 存储，展示时由前端转换时区。

**大规模部署注意：** 亿级收件箱数据不建议直接依赖单张无分区 MySQL 表。第一阶段可以先使用上述模型；达到规模阈值后按 `user_id` 分片，并通过服务层统一查询。跨分片的数据库外键需要移除，由应用维护引用关系。

### **5.4 必须补充的可靠性表**

为了确保数据库提交成功但 Kafka 发送失败时不会丢通知，增加 Transactional Outbox。

```

CREATE TABLE notification_outbox (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    event_id VARCHAR(100) NOT NULL,
    topic VARCHAR(128) NOT NULL,
    event_key VARCHAR(160) NOT NULL,
    payload JSON NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    retry_count INT UNSIGNED NOT NULL DEFAULT 0,
    next_retry_at DATETIME(3) DEFAULT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    published_at DATETIME(3) DEFAULT NULL,
    UNIQUE KEY uk_outbox_event (event_id),
    KEY idx_outbox_pending (status, next_retry_at, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE notification_delivery_outbox (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    inbox_id BIGINT UNSIGNED NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    retry_count INT UNSIGNED NOT NULL DEFAULT 0,
    next_retry_at DATETIME(3) DEFAULT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_delivery_inbox (inbox_id),
    KEY idx_delivery_pending (status, next_retry_at, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

```

`notification_outbox` 用于可靠地发布业务通知任务到 Kafka；`notification_delivery_outbox` 用于收件箱持久化成功后，可靠地触发 Centrifugo 推送。后者只保证尽力通知在线客户端，离线用户仍通过消息中心 API 补拉。

### **6.3 发送系统通知**

管理员手动发送、定时公告以及业务系统自动发送，都统一进入 Notification Service。

```

POST /api/v1/admin/notification/dispatch
Authorization: Bearer <access_token>
Content-Type: application/json
Idempotency-Key: notify-20261120-001

{
  "template_code": "order.payment_success",
  "target": {
    "type": "users",
    "user_ids": ["user_10001"]
  },
  "variables": {
    "order_no": "MLC20261120001",
    "order_id": "order_10001",
    "amount": "129.00"
  },
  "scheduled_at": null
}

```

响应：

```

{
  "code": 0,
  "message": "accepted",
  "data": {
    "task_id": 90001,
    "status": "pending"
  }
}

```

接口返回 `pending` 只表示任务已被持久化接受，**不能代表消息已经成功送达用户**。

对于 `order.payment_success` 等业务通知，普通管理员不应该随意构造订单号和金额发送。生产环境应由订单服务内部触发，通知服务从可信事件获取数据。手动发送主要用于公告、运营消息和经过授权的测试通知。

### **6.4 消息中心接口**

| Method | API                                                  | 作用     |
| ------ | ---------------------------------------------------- | ------ |
| GET    | `/notifications?category=system&cursor=...&limit=20` | 通知列表   |
| GET    | `/notifications/{inboxId}`                           | 通知详情   |
| GET    | `/notifications/unread-count`                        | 未读数量   |
| POST   | `/notifications/{inboxId}/read`                      | 单条已读   |
| POST   | `/notifications/read-all`                            | 全部已读   |
| DELETE | `/notifications/{inboxId}`                           | 删除通知   |
| GET    | `/notification-preferences`                          | 用户通知偏好 |
| PUT    | `/notification-preferences`                          | 修改通知偏好 |

消息中心列表返回示例：

```

{
  "code": 0,
  "message": "success",
  "data": {
    "items": [
      {
        "inbox_id": 88001,
        "message_id": 77001,
        "category": "transaction",
        "title": "订单支付成功",
        "body": "您的订单 MLC20261120001 已支付成功，实付 ¥129.00。",
        "action_type": "order_detail",
        "action_params": {
          "orderId": "order_10001"
        },
        "is_read": false,
        "created_at": "2026-11-20T12:30:00Z"
      }
    ],
    "next_cursor": null,
    "has_more": false
  }
}

```

接口规范：

- 用户 ID 从已验证的 JWT 中获取，不能相信前端传入的 `user_id`。
- 查询时必须添加 `WHERE user_id = ? AND deleted_at IS NULL`。
- 使用 `(created_at, id)` 组合游标分页，禁止深度 OFFSET 分页。
- 单次 `limit` 默认 20，最大 100。
- 已读、删除接口必须具备幂等性。
- `read-all` 应采用数据库批量更新或水位线方案，不能对几十万条消息逐条执行 SQL。
- 未读数优先使用 Redis 投影，缓存失效后从 MySQL 修复。


业务事件通过显式的映射表匹配模板，不允许任意 Kafka 消息直接指定高权限模板发送。

### **7.3 消费幂等**

Kafka 消费端必须处理重复投递。Kafka 的消费语义不能直接保证外部 MySQL 写入天然恰好一次，因此需要数据库唯一约束与幂等处理。

Apache Kafka+1



推荐规则：

```
event_key = "order_paid:" + order_id

收到事件
   |
   v
验证 event_key
   |
   v
查询或插入通知实例
   |
   +-- 已存在 -> 验证事件一致性
   |              补齐缺失收件箱记录
   |
   +-- 不存在 -> 创建消息实例
                  创建收件箱记录
                  创建投递 Outbox
   |
   v
提交数据库事务
   |
   v
提交 Kafka Offset
```

对于已存在的 `event_key`，还要比较事件内容摘要或业务主键，防止不同业务事件错误复用同一个幂等键。

### **7.4 失败重试策略**

| 场景             | 处理方式               |
| -------------- | ------------------ |
| Kafka 临时不可用    | Outbox 延迟重试        |
| MySQL 临时故障     | 不提交消费 Offset       |
| 模板变量缺失         | 标记永久失败并告警          |
| Centrifugo 不可用 | Delivery Outbox 重试 |
| 用户不在线          | 不影响消息持久化           |
| 同一事件重复投递       | 唯一约束去重             |
| 重试次数超限         | 进入失败队列，支持人工处理      |

推荐初始重试间隔：5 秒、30 秒、2 分钟、10 分钟、30 分钟，并添加随机抖动。

对于永久性错误不要无限重试。

例如：

```

```

该频道必须由后端授权订阅，禁止用户自行订阅其他用户的频道。

### **8.1 推送新通知**

```

{
  "type": "notification.created",
  "event_id": "evt_notify_77001",
  "data": {
    "inbox_id": 88001,
    "category": "transaction",
    "created_at": "2026-11-20T12:30:00Z"
  }

```

建议推送轻量事件，而不是完整通知正文。React 收到事件后通过 API 拉取通知，减少敏感信息暴露和消息协议耦合。

### **8.2 React 处理流程**

```
function handleNotificationEvent(event, queryClient) {
  if (event.type === "notification.created") {
    queryClient.invalidateQueries({
      queryKey: ["notifications"]
    });

    queryClient.invalidateQueries({
      queryKey: ["notification-unread-count"]
    });
  }
}
```

上述代码假设工程使用 TanStack Query；如果现有项目没有使用，可用原生 `fetch` 加自定义状态管理替代。

必须支持：

- WebSocket 断线自动重连。
- 页面重新获得焦点后主动同步。
- 多标签页状态一致性。
- 收到重复事件时不重复插入 UI。
- 首次登录、重新登录时从 API 加载通知。
- 用户退出登录后清理频道订阅与通知缓存。

实时推送只是提醒，**数据库 API 才是通知的权威查询入口**。

## **九、IAM 权限与审批流程**

通知管理涉及全平台用户，必须限制管理员发送权限，尤其是批量公告和安全通知。

### **9.1 权限矩阵**

| 操作     | super_admin | security_admin | ops_admin | operator |
| ------ | ----------- | -------------- | --------- | -------- |
| 查看模板   | ✓           | ✓              | ✓         | ✓        |
| 创建模板   | ✓           | 安全类            | ✓         | 授权后      |
| 编辑草稿   | ✓           | 安全类            | ✓         | 授权后      |
| 审核模板   | ✓           | 安全类            | ✓         | —        |
| 发布模板   | ✓           | 安全类            | ✓         | —        |
| 全平台群发  | ✓           | —              | 授权后       | —        |
| 查看发送记录 | ✓           | 安全类            | ✓         | 授权后      |
| 停用模板   | ✓           | 安全类            | ✓         | —        |

此表是推荐的初始授权策略，不应将角色名称硬编码为最终权限判定依据。实际权限来自 IAM 数据库。

### **9.2 与现有 IAM 结合**

使用已有的：

```
Role + Permission + Scope + ABAC
```

例如：

```
{
  "permission": "notification:template:publish",
  "scope_type": "platform",
  "scope_id": "",
  "resource": {
    "category": "transaction"
  }
}
```

Go 服务应同时验证：

1. 当前用户是否具有 `notification:template:publish` 权限。
2. 用户的 `scope_type/scope_id` 是否覆盖目标模板。
3. ABAC 规则是否允许操作对应通知分类。
4. 当前版本是否处于可发布状态。
5. 审批人与提交人是否满足职责分离要求。

React 仅负责根据权限隐藏或禁用按钮，最终权限必须由 Go 后端再次校验。

### **9.3 模板状态机**

建议状态：

`draft → reviewing → approved → published`

审核驳回转为 `rejected`，修改后重新提交。发布版本停用后状态变为 `disabled`。

关键规则：**历史通知不受模板更新影响。** 用户已经收到的通知始终使用发送时生成的内容快照。

## **十、平台公告与批量通知**

除业务事件通知外，还应支持管理员主动创建公告。

### **10.1 目标人群**

| target_type | 说明        |
| ----------- | --------- |
| `users`     | 指定用户      |
| `all`       | 全平台用户     |
| `role`      | 指定 IAM 角色 |
| `segment`   | 指定用户分群    |
| `merchant`  | 指定商家或商家成员 |
| `creator`   | 指定创作者     |

对于 `role`、`segment`、`merchant` 等动态目标，必须在任务创建时定义目标快照语义，避免任务运行过程中因用户角色变化导致不可预期的收件人范围。

### **10.2 全平台群发方案**

不建议管理员点击「发送」后同步向千万用户逐条写入 MySQL。

建议两种模式：

**模式 A：逐用户物化通知**

适用于订单、账号安全、审核结果等个性化通知。

每个收件人创建独立收件箱记录，支持独立已读、删除状态。

**模式 B：公告公共存储 + 用户状态延迟物化**

适用于全平台统一公告。

```
系统公告
   |
   v
notification_announcements
   |
   | 记录公告、受众、发布时间
   v
用户访问消息中心
   |
   +--> 查询个人通知
   |
   +--> 查询当前有效公告
   |
   v
合并排序返回
```

模式 B 还需要增加：

- `notification_announcements`：公告主体、版本、受众快照、发布时间、过期时间。
- `notification_announcement_user_state`：`announcement_id`、`user_id`、`read_at`、`deleted_at`，唯一键为 `(announcement_id,user_id)`。
- 全局公告未读数计算规则和缓存失效机制。

对于千万级用户，全局公告建议优先采用模式 B，避免一次公告产生千万条重复的消息内容和收件箱记录。

公告受众必须经过服务端 IAM 和分群规则过滤；不能仅依靠 React 判断用户是否属于目标人群。

### **12.1 核心接口定义**

```

package notification

import "context"

type RenderRequest struct {
    TemplateCode string
    Version      uint32
    Variables    map[string]string
}

type RenderResult struct {
    Title        string
    Body         string
    ActionType   string
    ActionParams map[string]string
}

type TemplateRenderer interface {
    Render(
        ctx context.Context,
        req RenderRequest,
    ) (RenderResult, error)
}

type DispatchCommand struct {
    RequestID    string
    TemplateCode string
    RecipientIDs []string
    Variables    map[string]string
}

type NotificationService interface {
    Dispatch(
        ctx context.Context,
        cmd DispatchCommand,
    ) (uint64, error)

    MarkRead(
        ctx context.Context,
        userID string,
        inboxID uint64,
    ) error
}

```

这里的 `RenderRequest.Version` 在业务发送时必须解析为确定的已发布版本，并持久化版本号。不得在 Kafka 消费重试时重新选择最新版本，否则同一个事件可能产生不同内容。

对于批量公告，不能把全部用户 ID 装进 `RecipientIDs`。需要另外实现基于受众分片、游标和批次的 Dispatch Worker。

## **十三、安全、性能和监控要求**

### **13.1 安全规范**

1. 通知模板编辑、审批、发布和发送均需要 IAM 校验。
2. 安全、交易类通知禁止普通运营人员随意群发。
3. 发送前验证目标用户与业务资源的归属关系。
4. 禁止模板变量中携带明文密码、Access Token、Refresh Token、TOTP 密钥。
5. 模板内容只支持安全的纯文本渲染。
6. 所有管理操作写入不可篡改或受保护的审计记录。
7. 批量发送需要人数预估、二次确认、频控和发送上限。
8. 防止通过通知中的链接进行开放重定向或钓鱼攻击。
9. 通知日志中的个人信息应脱敏。
10. 模板预览不得触发真实通知发送。

### **13.2 监控指标**

建议使用现有 `/metrics` 导出机制。

| 指标                                       | 说明            |
| ---------------------------------------- | ------------- |
| `notification_dispatch_total`            | 创建发送任务总数      |
| `notification_dispatch_failed_total`     | 发送任务失败数       |
| `notification_render_failed_total`       | 模板渲染失败数       |
| `notification_inbox_write_total`         | 收件箱写入数        |
| `notification_inbox_write_failed_total`  | 收件箱写入失败数      |
| `notification_outbox_pending`            | 待发布 Outbox 数量 |
| `notification_delivery_lag_seconds`      | 实时投递延迟        |
| `notification_kafka_consumer_lag`        | Kafka 消费积压    |
| `notification_unread_reconcile_mismatch` | 未读数对账异常       |

### **13.3 性能目标**

以下是建议的工程验收目标，不是现有系统的实测性能：

| 指标           | 建议目标              |
| ------------ | ----------------- |
| 通知列表 API P95 | 200ms 以内          |
| 单用户通知写入      | 幂等、可恢复            |
| 实时通知延迟 P95   | 2 秒以内             |
| 消息列表分页       | 默认 20 条           |
| 大规模公告        | 异步、分批或延迟物化        |
| 重复事件         | 不产生重复收件箱记录        |
| Kafka 故障     | 业务事件可通过 Outbox 恢复 |

千万并发与亿级数据需要通过分库分片、Kafka 分区扩容、Redis 集群、批量写入和容量压测逐步实现，不能仅凭该逻辑架构保证。

## **十六、最终实施建议**

建议优先实现下面这条完整闭环：

第一阶段

**模板管理 + 单用户通知 + 消息中心**

管理员创建「订单支付成功」模板 → 审核发布 → Go 订单支付事件触发 → Kafka 异步处理 → MySQL 保存 → Centrifugo 推送 → React 消息中心展示。

第二阶段

**平台公告 + 定时发送 + 用户分群**

补充公告管理、批量任务、频控、用户通知偏好及发送审计。

第三阶段

**大规模分发与性能优化**

根据真实负载引入收件箱分片、公告延迟物化、未读数投影对账、Kafka 扩容与性能压测。

这样设计可以让 MLC 的系统通知同时服务于商城、视频、账号安全、创作者、商家和平台运维模块，后续增加新的业务通知时，通常只需增加模板和业务事件映射，而不需要重新开发整套消息中心。

**最重要的三个设计约束：模板版本不可变、业务事件发送必须幂等、通知持久化不能依赖 WebSocket 是否在线。** 这三个约束决定了系统能否长期稳定扩展。
