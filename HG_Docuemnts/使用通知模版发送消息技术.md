# **MLC 通知模板管理与消息发送系统 — 技术规格文档（Tech Spec V1.0）**

技术栈：Go + React (JavaScript) + MySQL 8.0 + Redis + Kafka + Centrifugo + SeaweedFS

## **一、系统目标**

在你的 MLC_GO + React 工程中，实现一套对标 B站、字节跳动等大型互联网平台的**通知模板创建、管理、发布、发送、实时推送、消息中心展示、已读管理及发送记录追踪系统**。

核心设计原则：

**模板负责定义消息内容，发送任务负责选择接收人，消息实例负责保存实际通知，Kafka 负责异步处理，Centrifugo 负责实时推送。**

例如，在运维管理后台创建一个模板：

系统维护通知

已发布

**系统维护公告**

尊敬的 {{nickname}}，平台将于 {{maintenance_time}} 进行系统维护，预计持续 {{duration}} 分钟。维护期间部分功能可能无法使用。

模板编码：system_maintenance_notice · 站内信 + WebSocket

运营人员使用该模板，填写实际变量：

```
{
  "nickname": "用户A",
  "maintenance_time": "2026-11-22 02:00",
  "duration": 30
}
```

用户在消息中心收到：

**系统通知**

2026-11-21 21:00

未读

**系统维护公告**

尊敬的用户A，平台将于 2026-11-22 02:00 进行系统维护，预计持续 30 分钟。维护期间部分功能可能无法使用。

MLC 平台官方通知

查看详情

这里要区分两个业务动作：

- **创建模板**：只保存通知的结构、文案、变量、渠道和展示规则，不会发送给用户。
- **发送通知**：选择已发布的模板、接收用户和变量，生成通知任务并执行投递。

## **二、整体系统架构**

```
             React 运维管理后台
                     |
          +----------+----------+
          |                     |
      模板管理               通知发送
   创建/编辑/审核          选模板/选用户
   预览/发布/停用          预览/确认发送
          |                     |
          v                     v
      Template API          Send API
          |                     |
          v                     v
      MySQL 模板库         MySQL 发送任务
                                |
                         Transactional
                            Outbox
                                |
                                v
                              Kafka
                                |
                      Notification Worker
                                |
                +---------------+--------------+
                |               |              |
             模板渲染        接收人展开       发送策略
                |               |              |
                +---------------+--------------+
                                |
                       消息实例持久化
                                |
                +---------------+--------------+
                |               |              |
             MySQL           Centrifugo     其他渠道
           消息中心持久化     WebSocket      短信/邮件
                |               |              |
                v               v              v
           历史消息查询      React 实时更新   渠道回执
                |
           已读/删除/分页
```

架构要点：

1. MySQL 是通知及已读状态的权威数据源。
2. Kafka 用于异步分发、削峰、重试和解耦。
3. Centrifugo 只负责实时通知，不承担消息永久存储。
4. Redis 用于频率限制、短期去重和缓存，不作为唯一持久化存储。
5. SeaweedFS 存储通知图片、封面等媒体资源。
6. 每个接收人的消息独立管理已读状态，支持多端同步。

以下方案按可直接交给 AI 编码工具实施的规格组织。

## **三、完整业务流程**

建议把通知系统分为五个阶段。

1. **创建通知模板**

   运维人员填写模板编码、标题、内容、变量、消息类型、跳转地址和发送渠道。保存为 `draft`。
2. **审核并发布模板**

   有审核权限的管理员审核内容。发布后生成不可变版本，只有 `published` 模板可用于正式发送。
3. **创建发送任务**

   选择模板版本，指定接收人（单用户、多个用户、用户群组或全站），填写变量，选择立即发送或定时发送。
4. **异步发送与实时推送**

   Go 保存任务，Outbox 投递 Kafka，Worker 分批生成用户通知，写入 MySQL 后通过 Centrifugo 推送。
5. **消息中心展示与状态管理**

   React 收到实时事件，更新未读数和通知列表。用户可以查看、标记已读、删除、点击跳转。运维后台可查看任务结果。

### **3.1 模板类型**

| 模板类型          | 业务触发场景        | 展示位置  |
| ------------- | ------------- | ----- |
| `system`      | 系统维护、升级、平台公告  | 系统通知  |
| `security`    | 异地登录、密码修改、MFA | 安全通知  |
| `transaction` | 下单、支付、退款、物流   | 交易通知  |
| `interaction` | 点赞、评论、关注、收藏   | 互动消息  |
| `merchant`    | 店铺审核、商品违规、结算  | 商家通知  |
| `operation`   | 活动邀请、优惠券、福利   | 活动通知  |
| `creator`     | 视频审核、内容下架、收益  | 创作者通知 |

这些是建议的业务分类，不是发送渠道。一个 `transaction` 类型的通知可以同时通过站内信、WebSocket 和邮件发送。

### **3.2 发送方式**

| 方式   | 接收人选择        | 示例            |
| ---- | ------------ | ------------- |
| 单用户  | 一个 `user_id` | 账号安全提醒        |
| 批量用户 | `user_ids[]` | 给 500 名商家发通知  |
| 角色用户 | IAM 角色及作用域   | 通知所有审核人员      |
| 条件人群 | 用户标签、状态、分群   | 通知最近 30 天活跃用户 |
| 全站广播 | 全体符合条件的用户    | 平台维护公告        |
| 业务事件 | 由 Go 业务模块触发  | 用户支付成功        |

**重要：全站公告与逐用户通知必须采用不同的存储策略。**

对于千万级用户，全站公告不应该默认复制千万条完全相同的通知。可以采用公告主体单条存储 + 用户已读游标或状态记录的方式，降低写入和存储成本。

## **四、数据库设计（MySQL 8.0）**

以下表结构是 V1 核心设计。使用 `VARCHAR(64)` 表示业务 ID，与你现有的字符串用户 ID 风格兼容。时间统一保存为 UTC，展示时转换到用户时区。

### **4.1 模板主表**

```
CREATE TABLE notification_templates (
    id VARCHAR(64) PRIMARY KEY,
    template_code VARCHAR(128) NOT NULL UNIQUE,
    template_name VARCHAR(128) NOT NULL,
    category VARCHAR(32) NOT NULL,
    status VARCHAR(24) NOT NULL DEFAULT 'draft',
    current_version INT NOT NULL DEFAULT 0,
    created_by VARCHAR(64) NOT NULL,
    updated_by VARCHAR(64) NOT NULL,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,

    INDEX idx_status_category(status, category)
);
```

状态约定：

```
draft -> pending_review -> published
  ^           |
  |           v
  +-------- rejected

published -> disabled
disabled  -> published (重新审核后)
```

### **4.2 模板版本表**

```
CREATE TABLE notification_template_versions (
    id VARCHAR(64) PRIMARY KEY,
    template_id VARCHAR(64) NOT NULL,
    version INT NOT NULL,
    title_template VARCHAR(255) NOT NULL,
    body_template TEXT NOT NULL,
    variables_schema JSON NOT NULL,
    channels JSON NOT NULL,
    display_config JSON NOT NULL,
    content_hash CHAR(64) NOT NULL,
    created_by VARCHAR(64) NOT NULL,
    created_at DATETIME(3) NOT NULL,

    UNIQUE KEY uk_template_version(template_id, version),
    FOREIGN KEY (template_id)
        REFERENCES notification_templates(id)
);
```

版本规则：

- 已发布版本内容不可修改。
- 修改模板时创建新版本。
- 发送任务绑定具体版本，避免模板更新后历史通知内容变化。
- 审核应绑定版本号及内容哈希，避免审核后内容被替换。
- `variables_schema` 使用白名单声明变量类型、必填项和默认值。

### **4.3 发送任务表**

```
CREATE TABLE notification_send_tasks (
    id VARCHAR(64) PRIMARY KEY,
    request_id VARCHAR(128) NOT NULL UNIQUE,
    request_hash CHAR(64) NOT NULL,
    template_id VARCHAR(64) NOT NULL,
    template_version INT NOT NULL,
    audience_type VARCHAR(32) NOT NULL,
    audience_snapshot JSON NOT NULL,
    variables JSON NOT NULL,
    status VARCHAR(24) NOT NULL DEFAULT 'pending',
    scheduled_at DATETIME(3) NULL,
    total_count BIGINT NOT NULL DEFAULT 0,
    success_count BIGINT NOT NULL DEFAULT 0,
    failure_count BIGINT NOT NULL DEFAULT 0,
    created_by VARCHAR(64) NOT NULL,
    approved_by VARCHAR(64) NULL,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,

    INDEX idx_schedule(status, scheduled_at)
);
```

`request_id` 防止重复提交。同一个 `request_id` 携带不同 `request_hash` 时，返回幂等冲突。

### **4.4 用户通知实例表**

```
CREATE TABLE user_notifications (
    id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    task_id VARCHAR(64) NOT NULL,
    category VARCHAR(32) NOT NULL,
    title VARCHAR(255) NOT NULL,
    content TEXT NOT NULL,
    payload JSON NOT NULL,
    created_at DATETIME(3) NOT NULL,
    read_at DATETIME(3) NULL,
    deleted_at DATETIME(3) NULL,

    PRIMARY KEY (id, user_id),
    UNIQUE KEY uk_task_user(task_id, user_id),
    INDEX idx_user_list(
        user_id, deleted_at, created_at DESC, id DESC
    )
);
```

注意：`uk_task_user` 适用于每个任务每用户最多一条站内通知的语义。对于同一个业务事件可重复触发的情况，应创建不同任务或引入 `event_id` 作为实例幂等维度。

### **4.5 发送任务接收人表**

```
CREATE TABLE notification_task_recipients (
    task_id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    status VARCHAR(24) NOT NULL DEFAULT 'pending',
    attempts INT NOT NULL DEFAULT 0,
    last_error VARCHAR(512) NULL,
    updated_at DATETIME(3) NOT NULL,

    PRIMARY KEY (task_id, user_id),
    INDEX idx_status_task(status, task_id)
);
```

建议再补充以下表：

| 表名                                | 职责            |
| --------------------------------- | ------------- |
| `notification_outbox`             | 可靠事件投递        |
| `notification_channel_deliveries` | 各渠道发送状态、回执、重试 |
| `notification_audit_logs`         | 模板和发送任务审核审计   |
| `notification_user_preferences`   | 用户通知偏好        |
| `notification_announcements`      | 全站公告主体        |
| `notification_announcement_reads` | 公告用户已读状态      |
| `notification_task_batches`       | 大批量发送的分片进度    |

其中 `notification_outbox` 必须包含 `event_id`、`event_type`、`aggregate_id`、`payload`、`status`、`attempts`、`next_retry_at` 和创建时间。

**生产级补充约束：** 千万级数据量不能只依靠上述单表索引。需要根据用户 ID 进行水平分片或分区设计，并将 `user_notifications` 的唯一约束、游标分页及跨分片查询一起调整。以上 DDL 是可落地的单库基础版，不应直接视为千万并发的最终物理模型。

### **6.1 模板渲染**

不建议将用户输入直接传入 Go 的 `text/template` 并开放任意表达式。

V1 使用受限变量语法：

```
{{nickname}}
{{maintenance_time}}
{{duration}}
```

渲染规则：

- 仅允许 `{{[a-zA-Z_][a-zA-Z0-9_]*}}`。
- 不支持执行函数、循环或任意表达式。
- 必须校验变量是否存在、类型是否正确、长度是否超限。
- 禁止渲染未声明变量。
- 缺少必填变量直接返回错误。
- HTML 通知需要使用安全 HTML 渲染及净化策略，React 默认以文本形式显示。
- 限制模板大小、渲染耗时和最终输出长度。

核心接口：

```
type TemplateRenderer interface {
    Render(
        ctx context.Context,
        version TemplateVersion,
        variables map[string]any,
    ) (RenderedNotification, error)
}

type RenderedNotification struct {
    Title   string
    Content string
}
```

### **6.2 发送任务事务**

关键原则：**任务创建与 Outbox 写入必须处于同一个 MySQL 事务。**

```
func (s *SendService) CreateTask(
    ctx context.Context,
    cmd CreateTaskCommand,
) (string, error) {
    // 1. IAM 权限和 Scope 校验
    // 2. 校验模板版本及发布状态
    // 3. 校验接收人范围和发送策略
    // 4. 计算 request_hash

    // 5. 开启 MySQL 事务
    // 6. 插入 notification_send_tasks
    // 7. 插入 notification_outbox
    // 8. 提交事务

    // 9. 返回 taskID
    // 不在 HTTP 请求中同步发送全部通知
    return "", nil
}
```

以上是接口骨架，不是完整实现。AI 编码时必须补齐事务、错误处理、幂等冲突及单元测试，不得将 `return "", nil` 当成可交付代码。

### **6.3 Kafka 消费与可靠投递**

建议 Topic：

```
notification.task.created.v1
notification.audience.batch.v1
notification.delivery.requested.v1
notification.delivery.retry.v1
notification.delivery.dlq.v1
```

推荐处理语义：

```
MySQL 事务提交
       |
       v
Outbox Relay
       |
       v
Kafka 事件
       |
       v
Worker 消费
       |
       v
幂等写入消息实例
       |
       v
写入实时推送 Outbox
       |
       v
提交 Kafka Offset
```

必须实现：

1. Kafka 至少一次投递，消费者通过数据库唯一键实现业务幂等。
2. 消息实例与推送 Outbox 在同一事务写入。
3. 推送失败不得删除已经持久化的消息。
4. 可重试错误使用指数退避和随机抖动。
5. 永久失败进入 DLQ，并支持人工排查和重放。
6. Worker 重启后能够从数据库状态恢复。
7. 任务取消只阻止尚未开始的批次，不承诺撤回已经投递的通知。
8. 定时任务使用数据库抢占租约或 `FOR UPDATE SKIP LOCKED`，避免多个 Scheduler 重复执行。

对于 `notification.delivery.requested.v1`，建议使用 `user_id` 作为 Kafka Key，以利于同一用户相关事件的分区局部有序处理，但不能把这种局部有序误认为跨 Topic 或跨分区的全局顺序保证。

## **七、Centrifugo 实时通知实现**

你现有的工程已经使用 `/api/v1/iam/me/realtime` 获取 Centrifugo JWT，因此建议**复用现有 Centrifugo 连接，而不是为通知模块重新创建一个 WebSocket 连接**。

### **7.1 频道设计**

| Channel                       | 用途        | 订阅权限       |
| ----------------------------- | --------- | ---------- |
| `notification:user:{userId}`  | 个人通知      | 仅本人        |
| `notification:admin:{userId}` | 管理后台任务进度  | 具备对应权限的管理员 |
| `notification:system`         | 非敏感公共公告事件 | 按平台策略授权    |

对于私人消息，后端必须验证 JWT 中的 `sub` 与频道所属用户一致。不能仅依靠前端隐藏频道名称。

Centrifugo 支持后端通过 HTTP API 发布事件，客户端通过授权频道实时接收。

### **7.2 Go 发布通知**

可以直接使用 Go 标准库 `net/http` 调用 Centrifugo，暂时不需要引入额外 SDK。

```
type RealtimePublisher struct {
    BaseURL string
    APIKey  string
    Client  *http.Client
}

func (p *RealtimePublisher) Publish(
    ctx context.Context,
    userID string,
    notificationID string,
) error {
    payload := map[string]any{
        "channel": "notification:user:" + userID,
        "data": map[string]any{
            "event":          "notification.created",
            "notificationId": notificationID,
        },
        "idempotency_key": notificationID,
    }

    body, err := json.Marshal(payload)
    if err != nil {
        return err
    }

    req, err := http.NewRequestWithContext(
        ctx,
        http.MethodPost,
        strings.TrimRight(p.BaseURL, "/")+"/api/publish",
        bytes.NewReader(body),
    )
    if err != nil {
        return err
    }

    req.Header.Set("Content-Type", "application/json")
    req.Header.Set("X-API-Key", p.APIKey)

    resp, err := p.Client.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        return fmt.Errorf(
            "centrifugo publish HTTP status: %d",
            resp.StatusCode,
        )
    }

    var result struct {
        Error *struct {
            Code    int    `json:"code"`
            Message string `json:"message"`
        } `json:"error"`
    }

    if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
        return err
    }

    if result.Error != nil {
        return fmt.Errorf(
            "centrifugo publish: %d %s",
            result.Error.Code,
            result.Error.Message,
        )
    }

    return nil
}
```

生产环境必须给 `http.Client` 设置超时，并对连接错误、5xx 和可重试 API 错误进行分类处理。`idempotency_key` 只能提供 Centrifugo 支持范围内的短期去重，不能替代数据库持久化幂等。

建议将以下权限加入现有 IAM 权限字典。

权限判定遵循现有设计：

```
User
  |
  v
Role
  |
  v
Permission
  |
  v
Scope
  |
  v
ABAC Policy
  |
  v
允许 / 拒绝
```

例如，普通 `operator` 可以创建面向指定用户的通知任务，但向全站用户发送系统公告必须满足更高权限和审批策略。

建议采用以下安全约束：

- 创建人与审核人分离，禁止自行审批自己的高风险群发任务。
- `security` 类通知由安全服务触发，普通运营人员不能伪造账号安全事件。
- 全站、跨租户或大规模群发必须设置人数阈值与二次确认。
- 接收人展开时必须再次校验 IAM Scope，不能只在创建任务时检查。
- 模板跳转 URL 仅允许受控站内路由或已审核域名，防止钓鱼链接。
- 验证码、密码、Access Token、Refresh Token、TOTP 密钥禁止写入普通通知正文和日志。
- 审核、发送、取消、重试操作均记录操作人、时间、IP、请求 ID 和内容版本。
- 不同业务通知遵循不同的用户偏好规则，营销通知支持退订，必要的安全通知不能被普通营销退订规则屏蔽。

## **十、千万级用户的性能设计**

大规模通知系统的瓶颈不只在 Kafka，也包括接收人展开、MySQL 写入、未读计数和实时推送。

建议按发送规模分级处理：

| 发送规模         | 建议方案                  |
| ------------ | --------------------- |
| 1–100 人      | 普通异步任务                |
| 101–10 万人    | Kafka 分批投递            |
| 10 万–1000 万人 | 分片 Worker + 限速 + 分库分表 |
| 全站公告         | 公告共享存储 + 用户已读状态       |

这些数值是初始工程分级建议，不是经压测验证的容量上限。

对于用户消息中心，推荐使用：

```
MySQL
  |
  +-- 持久化通知
  |
  +-- 用户已读状态
  |
  +-- 通知实例唯一约束

Redis
  |
  +-- 未读计数缓存
  |
  +-- 发送频控
  |
  +-- 短期去重
```

未读数需要支持缓存失效后的数据库重建或对账，避免重复消费导致计数永久偏移。

### **10.1 性能指标**

以下为建议的初期验收目标，最终需要通过压测调整。

| 指标           | 初期目标              |
| ------------ | ----------------- |
| 单用户通知列表 P95  | 小于 200ms          |
| 未读数查询 P95    | 小于 100ms          |
| 在线通知实时可见 P95 | 小于 2 秒            |
| 消费者重复事件      | 不产生重复通知           |
| Worker 重启    | 未完成任务可恢复          |
| 任务创建幂等       | 相同请求只创建一个任务       |
| 消息持久化        | 不因 WebSocket 失败丢失 |

实时延迟目标应在指定负载、网络环境和集群规模下测量，不能作为无条件 SLA。

## **十二、最终架构建议**

对于你的 MLC 工程，建议将通知系统建设为**统一通知服务**，让 IAM、商城、支付、视频、评论、创作者、运维等模块通过统一的业务事件或内部服务接口触发通知。

业务模块不应该自行拼接通知文案、直接写消息中心表或直接调用 Centrifugo。这样才能实现统一模板、审核、频控、幂等、审计和用户偏好管理。

实施优先级建议是：**模板版本管理 → 可靠发送任务 → 消息持久化 → 实时推送 → 运维统计 → 大规模群发优化**。

这样既能满足当前系统通知的实际使用，又可以逐步扩展到订单消息、评论点赞、商家通知、安全提醒等业务，而不需要为每个模块重新开发一套通知发送机制。
