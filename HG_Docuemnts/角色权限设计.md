># <h2 id="角色权限设计">角色权限设计</h2>

# Go 后端工程：商城 + 视频 + 爬虫 + 运维的统一角色权限系统设计

针对你的 Go 工程，建议采用 RBAC（基于角色的访问控制）+ ABAC（基于属性的访问控制）+ 数据权限 + 审批机制 的组合架构。

这套方案适合商城、视频平台、创作者中心、商家后台、爬虫管理平台和运维管理后台，设计目标参考字节跳动、B站这类大型互联网平台的工程实践，但不意味着完全复制其内部实现。

核心原则：

用户身份、角色、权限、资源归属、业务状态必须分开设计。

例如，一个用户可以同时是普通用户、视频创作者和商家，但不能因为拥有商家身份，就能操作其他商家的商品。

## 一、首先设计哪些角色？

建议不要只定义 `admin`、`user` 两种角色，而是根据业务域划分。

### 1. 平台角色设计

| 角色    | 角色编码               | 核心职责           |
| ----- | ------------------ | -------------- |
| 游客    | `guest`            | 浏览公开商品、公开视频    |
| 普通用户  | `user`             | 购买、点赞、评论、收藏、关注 |
| 视频创作者 | `creator`          | 发布、修改、删除自己的视频  |
| 商家    | `merchant`         | 管理自己店铺的商品和订单   |
| 商家员工  | `merchant_staff`   | 根据授权管理店铺部分业务   |
| 内容审核员 | `content_reviewer` | 审核视频、评论、弹幕     |
| 商品审核员 | `product_reviewer` | 审核商品发布及变更      |
| 爬虫操作员 | `crawler_operator` | 创建、启动、停止爬虫任务   |
| 运营人员  | `operator`         | 管理活动、推荐位、内容运营  |
| 客服    | `customer_service` | 处理用户咨询、售后      |
| 运维人员  | `ops_engineer`     | 查看系统监控、执行授权操作  |
| 安全管理员 | `security_admin`   | 管理角色授权和安全策略    |
| 超级管理员 | `super_admin`      | 极少数平台级管理操作     |

这里有两个重要区别：

- 游客不是必须存入数据库的角色：游客一般是未登录的请求主体，可使用 `anonymous` 身份访问公开资源。
- 商家、创作者不一定是全局角色：更准确地说，它们往往是业务身份或某个组织下的成员身份。

例如，用户 A 可以同时是创作者和店铺 B 的管理员，但在店铺 C 没有任何管理权限。

## 二、整体权限系统架构

建议采用以下分层结构：

```
                    客户端
                       |
       +---------------+---------------+
       |               |               |
     Web/App        创作者中心        管理后台
       |               |               |
       +---------------+---------------+
                       |
                 API Gateway
                       |
              身份认证 Authentication
                       |
           +-----------+-----------+
           |                       |
        游客访问                 JWT 登录
           |                       |
           +-----------+-----------+
                       |
               Authorization
                  权限引擎
                       |
       +---------------+---------------+
       |               |               |
     RBAC             ABAC           数据权限
   角色权限          条件策略         资源归属
       |               |               |
       +---------------+---------------+
                       |
                   业务服务
                       |
       +---------------+---------------+
       |               |               |
     视频服务         商城服务        爬虫服务
       |               |               |
    创作者服务       订单服务         运维服务
       |               |               |
       +---------------+---------------+
                       |
                MySQL / Redis
                       |
               Kafka / ClickHouse
```

四个核心概念：

| 概念         | 解释       | 示例             |
| ---------- | -------- | -------------- |
| Subject    | 谁在操作     | 用户 `U1001`     |
| Role       | 拥有什么角色   | `creator`      |
| Permission | 允许执行什么操作 | `video:update` |
| Resource   | 操作哪个具体对象 | 视频 `V2001`     |

实际授权需要判断：

```
用户是否登录？
    ↓
是否具备 video:update 权限？
    ↓
该视频是否属于当前用户？
    ↓
视频当前状态是否允许修改？
    ↓
全部通过 → 执行操作
```

这比单纯判断 `role == "admin"` 更安全，也更容易扩展。

## 三、业务权限矩阵设计

权限建议统一采用：

`业务域:资源:操作`

例如：

```
video:submission:create
video:submission:update
video:submission:delete
video:submission:publish

mall:product:create
mall:product:update
mall:product:publish

crawler:task:create
crawler:task:execute
crawler:task:stop

ops:metrics:read
ops:deployment:execute

iam:role:grant
```

这样新增直播、广告、支付等业务时，不需要重构原有权限模型。

### 1. 前台业务权限

| 功能        | 游客 | 普通用户 | 创作者 | 商家 |
| --------- | -- | ---- | --- | -- |
| 浏览公开视频    | ✓  | ✓    | ✓   | ✓  |
| 浏览公开商品    | ✓  | ✓    | ✓   | ✓  |
| 点赞、评论、收藏  | —  | ✓    | ✓   | ✓  |
| 购买商品      | —  | ✓    | ✓   | ✓  |
| 发布视频      | —  | —    | ✓   | —  |
| 修改自己的视频   | —  | —    | ✓   | —  |
| 发布商品      | —  | —    | —   | ✓  |
| 修改自己的商品   | —  | —    | —   | ✓  |
| 查看自己的订单   | —  | ✓    | ✓   | ✓  |
| 查看自己店铺的订单 | —  | —    | —   | ✓  |

注意：这里是各业务身份的基础授权。实际用户拥有多个身份时，权限可以组合，但仍要校验具体资源的归属。

### 2. 后台业务权限

| 功能     | 审核员 | 运营  | 爬虫操作员 | 运维  | 安全管理员 |
| ------ | --- | --- | ----- | --- | ----- |
| 审核内容   | ✓   | 按授权 | —     | —   | —     |
| 推荐位管理  | —   | ✓   | —     | —   | —     |
| 启动爬虫   | —   | —   | ✓     | —   | —     |
| 查看爬虫任务 | —   | 按授权 | ✓     | 按授权 | —     |
| 查看系统指标 | —   | 按授权 | —     | ✓   | —     |
| 部署和回滚  | —   | —   | —     | 按授权 | —     |
| 分配角色   | —   | —   | —     | —   | ✓     |
| 查看安全审计 | —   | —   | —     | 按授权 | ✓     |

不要让运营人员默认拥有运维权限，也不要让运维人员默认拥有订单退款、商品审核等业务权限。

## 四、MySQL 数据库设计

建议采用 6 张核心权限表，再配合业务表实现资源归属控制。

### 1. 核心表关系

### 2. 核心建表 SQL

以下是可以作为第一版数据库迁移的核心结构。假设你现有 `users.id` 是字符串型用户 ID，采用 `VARCHAR(64)`。

```
CREATE TABLE iam_roles (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    role_code VARCHAR(64) NOT NULL,
    role_name VARCHAR(100) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_role_code (role_code)
);

CREATE TABLE iam_permissions (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    permission_code VARCHAR(128) NOT NULL,
    description VARCHAR(255) NOT NULL DEFAULT '',

    UNIQUE KEY uk_permission_code (permission_code)
);

CREATE TABLE iam_role_permissions (
    role_id BIGINT UNSIGNED NOT NULL,
    permission_id BIGINT UNSIGNED NOT NULL,

    PRIMARY KEY (role_id, permission_id),
    KEY idx_permission_id (permission_id)
);

CREATE TABLE iam_user_role_bindings (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    role_id BIGINT UNSIGNED NOT NULL,

    scope_type VARCHAR(32) NOT NULL,
    scope_id VARCHAR(64) NOT NULL DEFAULT '',

    status TINYINT NOT NULL DEFAULT 1,
    expires_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_user_role_scope (
        user_id, role_id, scope_type, scope_id
    ),
    KEY idx_role_scope (role_id, scope_type, scope_id)
);

CREATE TABLE iam_organizations (
    id VARCHAR(64) PRIMARY KEY,
    org_type VARCHAR(32) NOT NULL,
    org_name VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
);

CREATE TABLE iam_audit_logs (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    actor_user_id VARCHAR(64) NOT NULL,
    action VARCHAR(128) NOT NULL,
    target_type VARCHAR(64) NOT NULL,
    target_id VARCHAR(64) NOT NULL,
    request_id VARCHAR(64) NOT NULL,
    detail JSON,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    KEY idx_actor_time (actor_user_id, created_at),
    KEY idx_target_time (target_type, target_id, created_at)
);
```

生产环境还需要增加外键或等效的应用层引用完整性校验、审计结果、授权人、撤销时间、策略版本及必要的索引。审计日志建议仅追加写入，并异步归档。

### 3. 为什么需要 scope_type 和 scope_id？

这是整个方案中最重要的设计之一。

假设用户 `U1001`：

- 是普通用户。
- 是视频创作者。
- 是商家 `SHOP100` 的管理员。
- 是商家 `SHOP200` 的普通员工。

数据库可以保存：

| user_id | role           | scope_type | scope_id |
| ------- | -------------- | ---------- | -------- |
| U1001   | user           | global     | 空字符串     |
| U1001   | creator        | global     | 空字符串     |
| U1001   | merchant_admin | shop       | SHOP100  |
| U1001   | merchant_staff | shop       | SHOP200  |

当用户修改 `SHOP100` 的商品时，权限引擎检查其在 `SHOP100` 下的角色。

当用户修改 `SHOP300` 的商品时，即使拥有 `merchant_admin`，也不能通过授权。

这叫做作用域授权，是多商家、多组织业务的基础。

### 1. 定义权限常量

```
package domain

type Permission string

const (
    VideoRead    Permission = "video:submission:read"
    VideoCreate  Permission = "video:submission:create"
    VideoUpdate  Permission = "video:submission:update"
    VideoPublish Permission = "video:submission:publish"

    ProductCreate  Permission = "mall:product:create"
    ProductUpdate  Permission = "mall:product:update"
    ProductPublish Permission = "mall:product:publish"

    CrawlerExecute Permission = "crawler:task:execute"
    OpsMetricsRead Permission = "ops:metrics:read"
)
```

### 2. 定义当前请求主体

```
type Principal struct {
    UserID        string
    Authenticated bool
    SessionID     string
}

type Resource struct {
    Type       string
    ID         string
    OwnerID    string
    ScopeType  string
    ScopeID    string
    Status     string
}

type Decision struct {
    Allowed bool
    Reason  string
}

type Authorizer interface {
    Authorize(
        ctx context.Context,
        principal Principal,
        permission Permission,
        resource Resource,
    ) (Decision, error)
}
```

其中：

- `Principal`：当前操作用户。
- `Permission`：想执行什么操作。
- `Resource`：想操作哪个具体资源。
- `Decision`：最终是否允许。

特别注意，`OwnerID`、`ScopeID`、`Status` 等敏感属性必须从可信数据库或服务端上下文读取，不能直接相信前端传来的值。

### 3. 视频修改接口：具体如何校验？

假设用户请求：

```
PUT /api/videos/V1001
Authorization: Bearer <access_token>
```

Go Service 参考代码：

```
func (s *VideoService) UpdateVideo(
    ctx context.Context,
    principal iam.Principal,
    videoID string,
    input UpdateVideoInput,
) error {

    // 1. 从数据库读取视频
    video, err := s.repo.FindByID(ctx, videoID)
    if err != nil {
        return err
    }

    // 2. 权限校验
    decision, err := s.authz.Authorize(
        ctx,
        principal,
        iam.VideoUpdate,
        iam.Resource{
            Type:    "video",
            ID:      video.ID,
            OwnerID: video.CreatorID,
            Status:  video.Status,
        },
    )
    if err != nil {
        return err
    }

    if !decision.Allowed {
        return ErrForbidden
    }

    // 3. 修改自己的视频
    // SQL 必须再次约束 owner 和可修改状态
    return s.repo.UpdateOwnedVideo(
        ctx,
        videoID,
        principal.UserID,
        input,
    )
}
```

这里有两个层次：

第一层：权限引擎判断用户是否具有修改资格。

第二层：SQL 约束资源归属，防止并发情况下视频所有权或状态发生变化。

例如：

```
UPDATE video_submissions
SET title = ?
WHERE id = ?
  AND creator_id = ?
  AND status = 'draft';
```

还要检查 `RowsAffected()`。如果返回 0，可能是视频不存在、归属不符、状态变化或数据未发生实际变化，需要按业务规则处理。

对于审核、转移归属、退款等复杂操作，建议使用事务、条件更新或 `SELECT ... FOR UPDATE`，保证权限判断与状态变更的一致性。

## 六、JWT + Redis 权限缓存设计

你现有工程已经使用 JWT、Redis、MySQL，因此不需要重新构建登录系统。

建议 JWT 主要保存身份和会话信息，不要把所有角色权限写进去。

```
{
  "sub": "U1001",
  "sid": "SESSION1001",
  "iss": "mlc-auth",
  "aud": "mlc-api",
  "exp": 1790000000
}
```

权限获取流程：

```
客户端请求
    |
    v
JWT 验证签名、有效期、会话
    |
    v
获取 user_id
    |
    v
Redis 查询用户角色和权限
    |
    +--- 缓存命中 ---> 校验作用域和资源
    |
    +--- 缓存未命中
              |
              v
         MySQL 查询角色权限
              |
              v
         写入 Redis 缓存
              |
              v
         校验作用域和资源
              |
              v
          允许 / 拒绝
```

Redis Key 可以设计为：

```
iam:roles:user:U1001
iam:permissions:user:U1001
iam:roles:user:U1001:shop:SHOP100
iam:policy:version
```

对于普通权限，可以缓存角色和权限映射；对于高风险权限，例如退款、授权管理员、生产环境部署，不应仅依赖可能过期的缓存。

推荐措施：

- 角色变更后主动失效相关缓存。
- 通过 Kafka 通知其他服务更新本地权限缓存。
- 缓存设置合理 TTL 和版本号。
- 权限服务异常时，敏感操作默认拒绝。
- 高危操作重新验证最新授权、MFA 和审批状态。

这是因为缓存提升性能，但不能牺牲权限撤销的及时性。

## 七、视频、商品、爬虫的特殊权限

### 1. 视频发布

创作者有 `video:submission:publish` 权限，不代表视频可以直接公开。

```
创作者提交视频
      |
      v
验证创作者资格
      |
      v
验证视频归属
      |
      v
视频进入 pending_review
      |
      v
内容审核
      |
      +--- 通过 ---> published
      |
      +--- 拒绝 ---> rejected
```

这里权限和业务状态必须分开。

创作者具备提交发布申请的权限，审核系统决定视频是否真正公开。

### 2. 商品发布

商家有 `mall:product:create`，还必须满足：

- 店铺正常营业。
- 用户在当前店铺具有有效授权。
- 商品类目符合商家经营资格。
- 商品通过必要审核。
- 商品状态允许上架。

尤其是商品价格、库存、结算账户等敏感字段，建议采用字段级权限。

例如：

```
mall:product:update_basic
mall:product:update_price
mall:product:update_stock
mall:product:publish
mall:product:delete
```

这样商家客服可以修改商品描述，但不能擅自修改商品价格。

### 3. 爬虫管理

爬虫权限要分为两类：

人类操作权限

```
crawler:task:create
crawler:task:execute
crawler:task:stop
crawler:task:read
crawler:task:delete
```

机器服务权限

```
crawler:video:discover
crawler:video:clean
crawler:video:store
```

你现有的 Kafka 爬虫流水线：

```
discovered
    |
    v
raw
    |
    v
cleaned
    |
    v
stored
```

不应该给 Kafka Consumer 分配一个普通的 `super_admin` 用户角色。

建议为爬虫 Worker 创建独立的服务身份（Service Principal），通过服务凭证、mTLS 或工作负载身份进行认证，并只允许它执行对应阶段的操作。

同时，爬虫任务要增加目标站点授权、抓取范围、速率限制和任务审批，避免权限系统允许了操作，却违反目标平台的访问规则。

## 八、运维后台：采用更严格的权限控制

运维不应该拥有所有业务数据的访问权。

建议将运维权限划分为：

| 权限                        | 用途               | 风险 |
| ------------------------- | ---------------- | -- |
| `ops:metrics:read`        | 查看 Prometheus 指标 | 低  |
| `ops:logs:read`           | 查看脱敏日志           | 中  |
| `ops:config:read`         | 查看非敏感配置          | 中  |
| `ops:deployment:execute`  | 部署应用             | 高  |
| `ops:database:migrate`    | 执行数据库迁移          | 高  |
| `ops:production:rollback` | 生产环境回滚           | 高  |
| `iam:role:grant`          | 分配权限             | 极高 |

生产环境的部署、数据库迁移、角色授权等操作，建议增加审批和短期授权。

即使是 `super_admin`，也不建议默认绕过所有安全控制。资金转账、退款、审计日志修改等能力应有独立约束。

## 九、千万并发、亿级数据下如何扩展？

首先要明确：千万级用户、千万级并发请求、亿级业务数据是三个不同的规模指标。不能仅凭使用 Redis 或 Kafka 就认为系统能够承载千万并发。

建议分阶段实施：

| 阶段   | 权限架构                      | 适用情况           |
| ---- | ------------------------- | -------------- |
| 第一阶段 | MySQL + Redis + Go IAM 模块 | 当前工程，优先落地      |
| 第二阶段 | 独立 IAM 服务 + 权限事件同步        | 多业务服务、多团队      |
| 第三阶段 | 分布式细粒度权限引擎                | 海量资源关系、多租户复杂授权 |

当资源关系非常复杂时，可以评估 OpenFGA。它支持关系型授权模型，并提供 Go SDK，适合处理用户、组织、店铺和资源之间的复杂授权关系。

[image](https://www.google.com/s2/favicons?domain=https://openfga.dev\&sz=32)

OpenFGA+1



但对于你当前的工程，不建议一开始就引入独立 OpenFGA 集群。先把统一授权接口和权限模型设计好，后续替换底层实现即可。

高并发下还有一个容易忽略的问题：公开视频列表和公开商品列表通常不需要每次查询都读取用户角色。它们应使用公开内容的状态过滤、缓存和 CDN，避免将权限系统变成所有流量的瓶颈。

对于需要权限的数据列表，必须在 SQL 查询层增加作用域过滤，而不是先查出全部数据，再由 Go 代码过滤。OWASP 也建议默认拒绝、最小权限以及对每个受保护请求执行授权校验。

## 十、建议你的工程按以下顺序落地

第一阶段：权限基础设施

完成角色表、权限表、用户角色绑定表、作用域授权表和初始化数据。优先建立 `Authorize()` 统一接口。

第二阶段：接入现有业务

先接入视频发布、商品发布、爬虫管理三个模块。分别验证资源归属、组织作用域和任务操作权限。

第三阶段：完善后台安全

增加管理端角色授权、审计日志、敏感操作审批、MFA、权限撤销与缓存同步。

第四阶段：性能与可靠性验证

增加权限单元测试、跨店铺越权测试、缓存失效测试、权限服务故障测试及压测。

## 十一、最终技术选型

| 技术模块    | 推荐方案                             |
| ------- | -------------------------------- |
| 身份认证    | JWT Access Token + Refresh Token |
| 权限模型    | RBAC + ABAC + 资源关系               |
| 权限持久化   | MySQL 8.0                        |
| 权限缓存    | Redis                            |
| 权限校验    | Go IAM Authorizer                |
| 资源归属    | MySQL 条件查询和事务                    |
| 跨服务通知   | Kafka                            |
| 运维安全    | MFA + 审批 + 最小权限                  |
| 安全审计    | MySQL + 异步归档                     |
| 后期细粒度授权 | 按需引入 OpenFGA                     |

最终建议：你的 Go 工程应采用“一套用户身份体系、多角色、多作用域、细粒度权限、业务资源归属校验”的统一 IAM 架构。

这套架构最关键的不是创建多少个角色，而是确保：

用户可以拥有多个角色，但每个角色只能在被授权的业务范围内操作指定资源。

这样未来增加直播、广告投放、会员、钱包支付、商家结算、创作者收益等模块时，都可以复用同一套权限体系，而不需要重新设计用户和角色系统。

># <h2 id="RBAC和ABAC">RBAC和ABAC</h2>

RBAC 和 ABAC 都是权限控制模型，用于判断：一个用户能不能执行某个操作。

核心区别：

- RBAC：根据用户的角色判断权限。
- ABAC：根据用户、资源、环境等属性判断权限。

## 一、RBAC：基于角色的访问控制

RBAC = Role-Based Access Control。

简单理解：先给用户分配角色，再给角色分配权限。

例如，你的 Go 工程有视频发布、商城和运维功能。

| 用户 | 角色    | 拥有的权限     |
| -- | ----- | --------- |
| 张三 | 普通用户  | 浏览、点赞、评论  |
| 李四 | 视频创作者 | 发布视频、修改视频 |
| 王五 | 商家    | 发布商品、修改商品 |
| 赵六 | 运维人员  | 查看系统日志、监控 |

关系如下：

```
用户：李四
   |
   v
角色：creator（视频创作者）
   |
   +-- video:create
   |
   +-- video:update
   |
   +-- video:delete
```

Go 代码示例：

```
func CanPublishVideo(role string) bool {
    return role == "creator"
}
```

只要用户拥有 `creator` 角色，就允许执行视频发布操作。

问题： 如果李四拥有 `creator` 角色，是否就可以修改张三发布的视频？

仅靠上面这种 RBAC 判断，无法区分视频属于谁。

这就需要 ABAC。

## 二、ABAC：基于属性的访问控制

ABAC = Attribute-Based Access Control。

简单理解：不仅看用户是什么角色，还要根据相关属性和条件判断是否允许操作。

例如：

- 用户 ID 是什么？
- 视频属于谁？
- 视频处于什么状态？
- 用户属于哪个店铺？
- 当前是否满足操作条件？

假设数据库有以下视频：

| 视频 ID | 创建者 ID | 状态        |
| ----- | ------ | --------- |
| V001  | U1001  | draft     |
| V002  | U1002  | published |
| V003  | U1001  | draft     |

当前用户是 `U1001`。

业务规定：用户只能修改自己创建的、处于草稿状态的视频。

Go 代码：

```
func CanUpdateVideo(
    userID string,
    videoOwnerID string,
    videoStatus string,
) bool {
    return userID == videoOwnerID &&
        videoStatus == "draft"
}
```

判断结果：

| 视频   | 是否允许修改   | 原因         |
| ---- | -------- | ---------- |
| V001 | &#x20;允许 | 自己的视频，草稿状态 |
| V002 | &#x20;拒绝 | 不是自己的视频    |
| V003 | &#x20;允许 | 自己的视频，草稿状态 |

这就是 ABAC：根据资源属性和用户属性进行权限判断。

## 三、RBAC + ABAC 结合使用

对于你的 Go 工程，建议两个一起使用。

```
用户 U1001 请求修改视频 V001
              |
              v
       1. JWT 身份认证
              |
              v
       2. RBAC 角色权限判断
              |
       是否有 video:update？
              |
          +---+---+
          |       |
         否       是
          |       |
         拒绝     v
              3. ABAC 属性判断
                    |
             视频属于 U1001？
             视频状态是 draft？
                    |
                +---+---+
                |       |
               否       是
                |       |
               拒绝    允许修改
```

对应 Go 代码：

```
func CanUpdateVideo(
    role string,
    userID string,
    ownerID string,
    status string,
) bool {

    // RBAC：检查角色
    if role != "creator" {
        return false
    }

    // ABAC：检查资源属性
    if userID != ownerID {
        return false
    }

    if status != "draft" {
        return false
    }

    return true
}
```

这只是用于理解原理的简化代码。生产环境应该支持一个用户拥有多个角色，并从数据库读取可信的资源属性。

## 四、两者的区别总结

| 对比   | RBAC         | ABAC           |
| ---- | ------------ | -------------- |
| 中文   | 基于角色的访问控制    | 基于属性的访问控制      |
| 判断依据 | 用户拥有的角色及其权限  | 用户、资源、环境等属性    |
| 典型问题 | 你有没有修改视频的权限？ | 你能不能修改这个具体视频？  |
| 优点   | 简单、容易维护      | 灵活、控制更精细       |
| 缺点   | 难以单独处理复杂条件   | 规则较复杂          |
| 适用场景 | 管理员、创作者、商家   | 视频归属、店铺归属、状态限制 |

一句话记住：

- RBAC：你是什么角色，能做什么？
- ABAC：在当前条件下，你能不能操作这个具体资源？

对于你正在开发的商城、视频发布、商品发布、爬虫和运维系统，使用 RBAC 管理功能权限，ABAC 管理具体资源和业务条件，是比较合理且可扩展的技术方案。

># <h2 id="平台超级管理员">平台超级管理员</h2>

有。在你的 Go 后端工程中，建议设置一个平台超级管理员（Super Admin），作为权限体系的初始管理者，可以创建角色、分配权限、授权其他管理员。

但要注意：超级管理员不等于可以绕过所有业务安全规则。

## 一、最高权限角色叫什么？

常见命名如下：

| 名称    | 代码               | 用途       |
| ----- | ---------------- | -------- |
| 超级管理员 | `super_admin`    | 平台最高管理角色 |
| 安全管理员 | `security_admin` | 管理角色和权限  |
| 普通管理员 | `admin`          | 日常后台管理   |
| 运维管理员 | `ops_admin`      | 管理系统运维   |
| 商家管理员 | `merchant_admin` | 管理指定店铺   |

你的工程建议使用：

```
type RoleCode string

const (
    RoleSuperAdmin     RoleCode = "super_admin"
    RoleSecurityAdmin  RoleCode = "security_admin"
    RoleAdmin          RoleCode = "admin"
    RoleMerchantAdmin  RoleCode = "merchant_admin"
)
```

超级管理员的权限包括：

```
super_admin
    |
    +-- iam:role:create       创建角色
    +-- iam:role:update       修改角色
    +-- iam:role:grant        分配角色
    +-- iam:role:revoke       撤销角色
    +-- iam:permission:grant  为角色配置权限
    +-- iam:user:disable     禁用用户
    +-- iam:audit:read       查看授权审计
```

## 二、第一个超级管理员从哪里来？

这是一个经典的 Bootstrap（初始化引导）问题。

因为系统刚部署时，没有管理员，也就没有人能给其他用户授予管理员角色。

解决方案：在首次部署时，通过受控的初始化程序创建第一个超级管理员。

不建议在普通用户注册接口中加入类似以下逻辑：

```
// 错误示例：第一个注册用户自动成为超级管理员
if userCount == 0 {
    role = "super_admin"
}
```

因为任何抢先调用注册接口的人，都可能获得最高权限。

### 推荐初始化流程

```
首次部署 Go 服务
        |
        v
执行 MySQL Migration
        |
        v
初始化系统角色与权限
        |
        v
创建首个管理员账号
        |
        v
执行 Bootstrap 管理命令
        |
        v
将 super_admin 绑定到该用户
        |
        v
记录授权审计
        |
        v
关闭 Bootstrap 入口
        |
        v
后续管理员通过 IAM 授权
```

## 三、MySQL 如何初始化超级管理员？

假设已经创建了 `iam_roles` 和 `iam_user_role_bindings` 两张表。

第一步：初始化角色。

```
INSERT INTO iam_roles (
    role_code,
    role_name,
    status
)
VALUES (
    'super_admin',
    '平台超级管理员',
    1
)
ON DUPLICATE KEY UPDATE
    role_code = role_code;
```

第二步：给已有用户 `U1001` 授权。

```
INSERT INTO iam_user_role_bindings (
    user_id,
    role_id,
    scope_type,
    scope_id,
    status
)
SELECT
    'U1001',
    id,
    'global',
    '',
    1
FROM iam_roles
WHERE role_code = 'super_admin';
```

这样，`U1001` 就拥有了平台级超级管理员角色。

但以上 SQL 只是原理演示。生产环境应该由受控的 Bootstrap 命令执行，并验证账号、角色、授权状态和审计结果，而不是让业务人员直接执行 SQL。

## 四、Go 后端如何实现首次授权？

建议增加一个管理命令：

```
./mlc-server iam bootstrap --user-id U1001
```

Go 核心逻辑：

```
func BootstrapSuperAdmin(
    ctx context.Context,
    db *sql.DB,
    userID string,
) error {

    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // 1. 验证目标用户存在且状态正常
    // 2. 锁定 IAM Bootstrap 状态记录
    // 3. 检查系统是否已经完成初始化
    // 4. 查询 super_admin 角色
    // 5. 插入用户角色绑定
    // 6. 写入不可随意修改的授权审计
    // 7. 标记 Bootstrap 已完成

    return tx.Commit()
}
```

这里建议专门建立一条 Bootstrap 状态记录，在同一个事务中加锁检查和更新，保证即使多个进程同时初始化，也只有一个能成功。

另外，首次授权命令必须满足：

- 只能由可信部署环境中的管理员执行。
- 不能暴露为公开 HTTP API。
- 必须验证目标账号身份。
- 初始化完成后不能再次执行。
- 不允许通过修改普通注册参数获得最高权限。

## 五、超级管理员如何给其他用户授权？

例如，`U1001` 是超级管理员，要把 `U2002` 设置为视频审核员。

```
超级管理员 U1001
        |
        v
POST /admin/iam/role-grants
        |
        v
验证 JWT 身份
        |
        v
检查 iam:role:grant 权限
        |
        v
检查是否允许授予目标角色
        |
        v
验证 U2002 账号状态
        |
        v
MySQL 事务写入角色绑定
        |
        +-- 写入授权审计
        |
        v
Redis 权限缓存失效
        |
        v
U2002 获得 content_reviewer 角色
```

请求示例：

```
{
  "userId": "U2002",
  "roleCode": "content_reviewer",
  "scopeType": "global",
  "scopeId": ""
}
```

实际接口还应验证授权者是否具有授予该角色的资格，避免普通管理员把自己或别人提升为 `super_admin`。

## 六、生产环境建议增加三项保护

1. 最高角色保护：`super_admin` 只能通过专门的高风险授权流程授予，普通 `iam:role:grant` 权限不能授予该角色。
2. 防止最后一个超级管理员被删除：撤销、禁用或删除管理员时，必须在事务中确保仍保留可用的恢复管理路径。
3. 敏感授权审计：记录操作人、被授权人、角色、作用域、操作时间、审批单和请求 ID。最高权限变更建议采用 MFA 和双人审批。

## 七、最终建议

对于你的 Go 商城 + 视频 + 爬虫 + 运维工程，推荐采用以下角色层次：

```
               super_admin
               平台超级管理员
                      |
          +-----------+-----------+
          |           |           |
     security_admin  admin     ops_admin
       安全管理员   平台管理员   运维管理员
                      |
           +----------+----------+
           |          |          |
       operator   reviewer   crawler_operator
        运营人员    审核人员     爬虫操作员


       creator    merchant     user
        创作者       商家       普通用户
```

这张图表示管理职责的划分，不表示下层角色自动继承上层角色的全部权限。具体权限仍然由角色与权限的绑定关系决定。

最推荐的实现：

- 初始超级管理员通过 `iam bootstrap` 命令创建。
- 日常角色分配通过 IAM API 完成。
- 使用 MySQL 保存授权关系，Redis 缓存权限。
- 所有授权操作记录审计日志。
- 对超级管理员授予、撤销等高风险操作使用独立审批机制。

这样既能解决第一个超级管理员从哪里来的问题，也能支持后续成千上万名运营、商家、创作者和管理员的权限管理。
