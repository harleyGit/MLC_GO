># <h2 id="角色权限设计">角色权限设计</h2>

# Go 后端工程：商城 + 视频 + 爬虫 + 运维的统一角色权限系统设计

针对你的 Go 工程，建议采用 RBAC（基于角色的访问控制）+ ABAC（基于属性的访问控制）+ 数据权限 + 审批机制 的组合架构。

这套方案适合商城、视频平台、创作者中心、商家后台、爬虫管理平台和运维管理后台，设计目标参考字节跳动、B站这类大型互联网平台的工程实践，但不意味着完全复制其内部实现。

核心原则：

用户身份、角色、权限、资源归属、业务状态必须分开设计。

例如，一个用户可以同时是普通用户、视频创作者和商家，但不能因为拥有商家身份，就能操作其他商家的商品。

## 一、首先设计哪些角色？

建议不要只定义 `admin`、`user` 两种角色，而是根据业务域划分。

### 1. 平台角色设计

| 角色    | 角色编码               | 核心职责           |
| ----- | ------------------ | -------------- |
| 游客    | `guest`            | 浏览公开商品、公开视频    |
| 普通用户  | `user`             | 购买、点赞、评论、收藏、关注 |
| 视频创作者 | `creator`          | 发布、修改、删除自己的视频  |
| 商家    | `merchant`         | 管理自己店铺的商品和订单   |
| 商家员工  | `merchant_staff`   | 根据授权管理店铺部分业务   |
| 内容审核员 | `content_reviewer` | 审核视频、评论、弹幕     |
| 商品审核员 | `product_reviewer` | 审核商品发布及变更      |
| 爬虫操作员 | `crawler_operator` | 创建、启动、停止爬虫任务   |
| 运营人员  | `operator`         | 管理活动、推荐位、内容运营  |
| 客服    | `customer_service` | 处理用户咨询、售后      |
| 运维人员  | `ops_engineer`     | 查看系统监控、执行授权操作  |
| 安全管理员 | `security_admin`   | 管理角色授权和安全策略    |
| 超级管理员 | `super_admin`      | 极少数平台级管理操作     |

这里有两个重要区别：

- 游客不是必须存入数据库的角色：游客一般是未登录的请求主体，可使用 `anonymous` 身份访问公开资源。
- 商家、创作者不一定是全局角色：更准确地说，它们往往是业务身份或某个组织下的成员身份。

例如，用户 A 可以同时是创作者和店铺 B 的管理员，但在店铺 C 没有任何管理权限。

## 二、整体权限系统架构

建议采用以下分层结构：

```
                    客户端
                       |
       +---------------+---------------+
       |               |               |
     Web/App        创作者中心        管理后台
       |               |               |
       +---------------+---------------+
                       |
                 API Gateway
                       |
              身份认证 Authentication
                       |
           +-----------+-----------+
           |                       |
        游客访问                 JWT 登录
           |                       |
           +-----------+-----------+
                       |
               Authorization
                  权限引擎
                       |
       +---------------+---------------+
       |               |               |
     RBAC             ABAC           数据权限
   角色权限          条件策略         资源归属
       |               |               |
       +---------------+---------------+
                       |
                   业务服务
                       |
       +---------------+---------------+
       |               |               |
     视频服务         商城服务        爬虫服务
       |               |               |
    创作者服务       订单服务         运维服务
       |               |               |
       +---------------+---------------+
                       |
                MySQL / Redis
                       |
               Kafka / ClickHouse
```

四个核心概念：

| 概念         | 解释       | 示例             |
| ---------- | -------- | -------------- |
| Subject    | 谁在操作     | 用户 `U1001`     |
| Role       | 拥有什么角色   | `creator`      |
| Permission | 允许执行什么操作 | `video:update` |
| Resource   | 操作哪个具体对象 | 视频 `V2001`     |

实际授权需要判断：

```
用户是否登录？
    ↓
是否具备 video:update 权限？
    ↓
该视频是否属于当前用户？
    ↓
视频当前状态是否允许修改？
    ↓
全部通过 → 执行操作
```

这比单纯判断 `role == "admin"` 更安全，也更容易扩展。

## 三、业务权限矩阵设计

权限建议统一采用：

`业务域:资源:操作`

例如：

```
video:submission:create
video:submission:update
video:submission:delete
video:submission:publish

mall:product:create
mall:product:update
mall:product:publish

crawler:task:create
crawler:task:execute
crawler:task:stop

ops:metrics:read
ops:deployment:execute

iam:role:grant
```

这样新增直播、广告、支付等业务时，不需要重构原有权限模型。

### 1. 前台业务权限

| 功能        | 游客 | 普通用户 | 创作者 | 商家 |
| --------- | -- | ---- | --- | -- |
| 浏览公开视频    | ✓  | ✓    | ✓   | ✓  |
| 浏览公开商品    | ✓  | ✓    | ✓   | ✓  |
| 点赞、评论、收藏  | —  | ✓    | ✓   | ✓  |
| 购买商品      | —  | ✓    | ✓   | ✓  |
| 发布视频      | —  | —    | ✓   | —  |
| 修改自己的视频   | —  | —    | ✓   | —  |
| 发布商品      | —  | —    | —   | ✓  |
| 修改自己的商品   | —  | —    | —   | ✓  |
| 查看自己的订单   | —  | ✓    | ✓   | ✓  |
| 查看自己店铺的订单 | —  | —    | —   | ✓  |

注意：这里是各业务身份的基础授权。实际用户拥有多个身份时，权限可以组合，但仍要校验具体资源的归属。

### 2. 后台业务权限

| 功能     | 审核员 | 运营  | 爬虫操作员 | 运维  | 安全管理员 |
| ------ | --- | --- | ----- | --- | ----- |
| 审核内容   | ✓   | 按授权 | —     | —   | —     |

| 启动爬虫   | —   | —   | ✓     | —   | —     |

| 查看系统指标 | —   | 按授权 | —     | ✓   | —     |
| 部署和回滚  | —   | —   | —     | 按授权 | —     |
| 分配角色   | —   | —   | —     | —   | ✓     |
| 查看安全审计 | —   | —   | —     | 按授权 | ✓     |

不要让运营人员默认拥有运维权限，也不要让运维人员默认拥有订单退款、商品审核等业务权限。

## 四、MySQL 数据库设计

建议采用 6 张核心权限表，再配合业务表实现资源归属控制。

### 2. 核心建表 SQL

以下是可以作为第一版数据库迁移的核心结构。假设你现有 `users.id` 是字符串型用户 ID，采用 `VARCHAR(64)`。

```
CREATE TABLE iam_roles (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    role_code VARCHAR(64) NOT NULL,
    role_name VARCHAR(100) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_role_code (role_code)
);

CREATE TABLE iam_permissions (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    permission_code VARCHAR(128) NOT NULL,
    description VARCHAR(255) NOT NULL DEFAULT '',

    UNIQUE KEY uk_permission_code (permission_code)
);

CREATE TABLE iam_role_permissions (
    role_id BIGINT UNSIGNED NOT NULL,
    permission_id BIGINT UNSIGNED NOT NULL,

    PRIMARY KEY (role_id, permission_id),
    KEY idx_permission_id (permission_id)
);

CREATE TABLE iam_user_role_bindings (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    role_id BIGINT UNSIGNED NOT NULL,

    scope_type VARCHAR(32) NOT NULL,
    scope_id VARCHAR(64) NOT NULL DEFAULT '',

    status TINYINT NOT NULL DEFAULT 1,
    expires_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_user_role_scope (
        user_id, role_id, scope_type, scope_id
    ),
    KEY idx_role_scope (role_id, scope_type, scope_id)
);

CREATE TABLE iam_organizations (
    id VARCHAR(64) PRIMARY KEY,
    org_type VARCHAR(32) NOT NULL,
    org_name VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
);

CREATE TABLE iam_audit_logs (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    actor_user_id VARCHAR(64) NOT NULL,
    action VARCHAR(128) NOT NULL,
    target_type VARCHAR(64) NOT NULL,
    target_id VARCHAR(64) NOT NULL,
    request_id VARCHAR(64) NOT NULL,
    detail JSON,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    KEY idx_actor_time (actor_user_id, created_at),
    KEY idx_target_time (target_type, target_id, created_at)
);
```

生产环境还需要增加外键或等效的应用层引用完整性校验、审计结果、授权人、撤销时间、策略版本及必要的索引。审计日志建议仅追加写入，并异步归档。

### 3. 为什么需要 scope_type 和 scope_id？

这是整个方案中最重要的设计之一。

假设用户 `U1001`：

- 是普通用户。
- 是视频创作者。
- 是商家 `SHOP100` 的管理员。
- 是商家 `SHOP200` 的普通员工。

数据库可以保存：

| user_id | role           | scope_type | scope_id |
| ------- | -------------- | ---------- | -------- |
| U1001   | user           | global     | 空字符串     |
| U1001   | creator        | global     | 空字符串     |
| U1001   | merchant_admin | shop       | SHOP100  |
| U1001   | merchant_staff | shop       | SHOP200  |

当用户修改 `SHOP100` 的商品时，权限引擎检查其在 `SHOP100` 下的角色。

当用户修改 `SHOP300` 的商品时，即使拥有 `merchant_admin`，也不能通过授权。

这叫做作用域授权，是多商家、多组织业务的基础。

### 1. 定义权限常量

```
package domain

type Permission string

const (
    VideoRead    Permission = "video:submission:read"
    VideoCreate  Permission = "video:submission:create"
    VideoUpdate  Permission = "video:submission:update"
    VideoPublish Permission = "video:submission:publish"

    ProductCreate  Permission = "mall:product:create"
    ProductUpdate  Permission = "mall:product:update"
    ProductPublish Permission = "mall:product:publish"

    CrawlerExecute Permission = "crawler:task:execute"
    OpsMetricsRead Permission = "ops:metrics:read"

```

### 2. 定义当前请求主体

```
type Principal struct {
    UserID        string
    Authenticated bool
    SessionID     string
}

type Resource struct {
    Type       string
    ID         string
    OwnerID    string
    ScopeType  string
    ScopeID    string
    Status     string
}

type Decision struct {
    Allowed bool
    Reason  string
}

type Authorizer interface {
    Authorize(
        ctx context.Context,
        principal Principal,
        permission Permission,
        resource Resource,
    ) (Decision, error)
}
```

其中：

- `Principal`：当前操作用户。
- `Permission`：想执行什么操作。
- `Resource`：想操作哪个具体资源。
- `Decision`：最终是否允许。

特别注意，`OwnerID`、`ScopeID`、`Status` 等敏感属性必须从可信数据库或服务端上下文读取，不能直接相信前端传来的值。

### 3. 视频修改接口：具体如何校验？

假设用户请求：

```
PUT /api/videos/V1001
Authorization: Bearer <access_token>
```

Go Service 参考代码：

```
func (s *VideoService) UpdateVideo(
    ctx context.Context,
    principal iam.Principal,
    videoID string,
    input UpdateVideoInput,
) error {

    // 1. 从数据库读取视频
    video, err := s.repo.FindByID(ctx, videoID)
    if err != nil {
        return err
    }

    // 2. 权限校验
    decision, err := s.authz.Authorize(
        ctx,
        principal,
        iam.VideoUpdate,
        iam.Resource{
            Type:    "video",
            ID:      video.ID,
            OwnerID: video.CreatorID,
            Status:  video.Status,
        },
    )
    if err != nil {
        return err
    }

    if !decision.Allowed {
        return ErrForbidden
    }

    // 3. 修改自己的视频
    // SQL 必须再次约束 owner 和可修改状态
    return s.repo.UpdateOwnedVideo(
        ctx,
        videoID,
        principal.UserID,
        input,
    )
}
```

这里有两个层次：

第一层：权限引擎判断用户是否具有修改资格。

第二层：SQL 约束资源归属，防止并发情况下视频所有权或状态发生变化。

例如：

```
UPDATE video_submissions
SET title = ?
WHERE id = ?
  AND creator_id = ?
  AND status = 'draft';
```

还要检查 `RowsAffected()`。如果返回 0，可能是视频不存在、归属不符、状态变化或数据未发生实际变化，需要按业务规则处理。

对于审核、转移归属、退款等复杂操作，建议使用事务、条件更新或 `SELECT ... FOR UPDATE`，保证权限判断与状态变更的一致性。

## 六、JWT + Redis 权限缓存设计

你现有工程已经使用 JWT、Redis、MySQL，因此不需要重新构建登录系统。

建议 JWT 主要保存身份和会话信息，不要把所有角色权限写进去。

```
{
  "sub": "U1001",
  "sid": "SESSION1001",
  "iss": "mlc-auth",
  "aud": "mlc-api",
  "exp": 1790000000
}
```

权限获取流程：

```
客户端请求
    |
    v
JWT 验证签名、有效期、会话
    |
    v
获取 user_id
    |
    v
Redis 查询用户角色和权限
    |
    +--- 缓存命中 ---> 校验作用域和资源
    |
    +--- 缓存未命中
              |
              v
         MySQL 查询角色权限
              |
              v
         写入 Redis 缓存
              |
              v
         校验作用域和资源
              |
              v
          允许 / 拒绝
```

Redis Key 可以设计为：

```
iam:roles:user:U1001
iam:permissions:user:U1001
iam:roles:user:U1001:shop:SHOP100
iam:policy:version
```

对于普通权限，可以缓存角色和权限映射；对于高风险权限，例如退款、授权管理员、生产环境部署，不应仅依赖可能过期的缓存。

推荐措施：

- 角色变更后主动失效相关缓存。
- 通过 Kafka 通知其他服务更新本地权限缓存。
- 缓存设置合理 TTL 和版本号。
- 权限服务异常时，敏感操作默认拒绝。
- 高危操作重新验证最新授权、MFA 和审批状态。

这是因为缓存提升性能，但不能牺牲权限撤销的及时性。

## 七、视频、商品、爬虫的特殊权限

### 1. 视频发布

创作者有 `video:submission:publish` 权限，不代表视频可以直接公开。

```
创作者提交视频
      |
      v
验证创作者资格
      |
      v
验证视频归属
      |
      v
视频进入 pending_review
      |
      v
内容审核
      |
      +--- 通过 ---> published
      |
      +--- 拒绝 ---> rejected
```

这里权限和业务状态必须分开。

创作者具备提交发布申请的权限，审核系统决定视频是否真正公开。

### 2. 商品发布

商家有 `mall:product:create`，还必须满足：

- 店铺正常营业。
- 用户在当前店铺具有有效授权。
- 商品类目符合商家经营资格。
- 商品通过必要审核。
- 商品状态允许上架。

尤其是商品价格、库存、结算账户等敏感字段，建议采用字段级权限。

例如：

```
mall:product:update_basic
mall:product:update_price
mall:product:update_stock
mall:product:publish
mall:product:delete
```

这样商家客服可以修改商品描述，但不能擅自修改商品价格。

### 3. 爬虫管理

爬虫权限要分为两类：

人类操作权限

```
crawler:task:create
crawler:task:execute
crawler:task:stop
crawler:task:read
crawler:task:delete
```

机器服务权限

```
crawler:video:discover
crawler:video:clean
crawler:video:store
```

你现有的 Kafka 爬虫流水线：

```
discovered
    |
    v
raw
    |
    v
cleaned
    |
    v
stored
```

不应该给 Kafka Consumer 分配一个普通的 `super_admin` 用户角色。

建议为爬虫 Worker 创建独立的服务身份（Service Principal），通过服务凭证、mTLS 或工作负载身份进行认证，并只允许它执行对应阶段的操作。

同时，爬虫任务要增加目标站点授权、抓取范围、速率限制和任务审批，避免权限系统允许了操作，却违反目标平台的访问规则。

## 八、运维后台：采用更严格的权限控制

运维不应该拥有所有业务数据的访问权。

建议将运维权限划分为：

| 权限                        | 用途               | 风险 |
| ------------------------- | ---------------- | -- |
| `ops:metrics:read`        | 查看 Prometheus 指标 | 低  |
| `ops:logs:read`           | 查看脱敏日志           | 中  |
| `ops:config:read`         | 查看非敏感配置          | 中  |
| `ops:deployment:execute`  | 部署应用             | 高  |
| `ops:database:migrate`    | 执行数据库迁移          | 高  |
| `ops:production:rollback` | 生产环境回滚           | 高  |
| `iam:role:grant`          | 分配权限             | 极高 |

生产环境的部署、数据库迁移、角色授权等操作，建议增加审批和短期授权。

即使是 `super_admin`，也不建议默认绕过所有安全控制。资金转账、退款、审计日志修改等能力应有独立约束。

## 九、千万并发、亿级数据下如何扩展？

首先要明确：千万级用户、千万级并发请求、亿级业务数据是三个不同的规模指标。不能仅凭使用 Redis 或 Kafka 就认为系统能够承载千万并发。

建议分阶段实施：

| 阶段   | 权限架构                      | 适用情况           |
| ---- | ------------------------- | -------------- |
| 第一阶段 | MySQL + Redis + Go IAM 模块 | 当前工程，优先落地      |
| 第二阶段 | 独立 IAM 服务 + 权限事件同步        | 多业务服务、多团队      |
| 第三阶段 | 分布式细粒度权限引擎                | 海量资源关系、多租户复杂授权 |

当资源关系非常复杂时，可以评估 OpenFGA。它支持关系型授权模型，并提供 Go SDK，适合处理用户、组织、店铺和资源之间的复杂授权关系。

OpenFGA+1



但对于你当前的工程，不建议一开始就引入独立 OpenFGA 集群。先把统一授权接口和权限模型设计好，后续替换底层实现即可。

高并发下还有一个容易忽略的问题：公开视频列表和公开商品列表通常不需要每次查询都读取用户角色。它们应使用公开内容的状态过滤、缓存和 CDN，避免将权限系统变成所有流量的瓶颈。

## 十、建议你的工程按以下顺序落地

第一阶段：权限基础设施

完成角色表、权限表、用户角色绑定表、作用域授权表和初始化数据。优先建立 `Authorize()` 统一接口。

第二阶段：接入现有业务

先接入视频发布、商品发布、爬虫管理三个模块。分别验证资源归属、组织作用域和任务操作权限。

第三阶段：完善后台安全

增加管理端角色授权、审计日志、敏感操作审批、MFA、权限撤销与缓存同步。

第四阶段：性能与可靠性验证

增加权限单元测试、跨店铺越权测试、缓存失效测试、权限服务故障测试及压测。

## 十一、最终技术选型

| 技术模块    | 推荐方案                             |
| ------- | -------------------------------- |
| 身份认证    | JWT Access Token + Refresh Token |

这套架构最关键的不是创建多少个角色，而是确保：

这样未来增加直播、广告投放、会员、钱包支付、商家结算、创作者收益等模块时，都可以复用同一套权限体系，而不需要重新设计用户和角色系统。

># <h2 id="RBAC和ABAC">RBAC和ABAC</h2>

RBAC 和 ABAC 都是权限控制模型，用于判断：一个用户能不能执行某个操作。

核心区别：

- RBAC：根据用户的角色判断权限。
- ABAC：根据用户、资源、环境等属性判断权限。

## 一、RBAC：基于角色的访问控制

RBAC = Role-Based Access Control。

简单理解：先给用户分配角色，再给角色分配权限。

例如，你的 Go 工程有视频发布、商城和运维功能。

| 用户 | 角色    | 拥有的权限     |
| -- | ----- | --------- |
| 张三 | 普通用户  | 浏览、点赞、评论  |
| 李四 | 视频创作者 | 发布视频、修改视频 |
| 王五 | 商家    | 发布商品、修改商品 |
| 赵六 | 运维人员  | 查看系统日志、监控 |

关系如下：

```
用户：李四
   |
   v
角色：creator（视频创作者）
   |
   +-- video:create
   |
   +-- video:update
   |
   +-- video:delete
```

Go 代码示例：

```
func CanPublishVideo(role string) bool {
    return role == "creator"
}
```

只要用户拥有 `creator` 角色，就允许执行视频发布操作。

问题： 如果李四拥有 `creator` 角色，是否就可以修改张三发布的视频？

仅靠上面这种 RBAC 判断，无法区分视频属于谁。

这就需要 ABAC。

## 二、ABAC：基于属性的访问控制

ABAC = Attribute-Based Access Control。

简单理解：不仅看用户是什么角色，还要根据相关属性和条件判断是否允许操作。

例如：

- 用户 ID 是什么？
- 视频属于谁？
- 视频处于什么状态？
- 用户属于哪个店铺？
- 当前是否满足操作条件？

假设数据库有以下视频：

| 视频 ID | 创建者 ID | 状态        |
| ----- | ------ | --------- |
| V001  | U1001  | draft     |
| V002  | U1002  | published |
| V003  | U1001  | draft     |

当前用户是 `U1001`。

业务规定：用户只能修改自己创建的、处于草稿状态的视频。

Go 代码：

```
func CanUpdateVideo(
    userID string,
    videoOwnerID string,
    videoStatus string,
) bool {
    return userID == videoOwnerID &&
        videoStatus == "draft"
}
```

判断结果：

| 视频   | 是否允许修改   | 原因         |
| ---- | -------- | ---------- |
| V001 | &#x20;允许 | 自己的视频，草稿状态 |
| V002 | &#x20;拒绝 | 不是自己的视频    |
| V003 | &#x20;允许 | 自己的视频，草稿状态 |

这就是 ABAC：根据资源属性和用户属性进行权限判断。

## 三、RBAC + ABAC 结合使用

对于你的 Go 工程，建议两个一起使用。

```
用户 U1001 请求修改视频 V001
              |
              v
       1. JWT 身份认证
              |
              v
       2. RBAC 角色权限判断
              |
       是否有 video:update？
              |
          +---+---+
          |       |
         否       是
          |       |
         拒绝     v
              3. ABAC 属性判断
                    |
             视频属于 U1001？
             视频状态是 draft？
                    |
                +---+---+
                |       |
               否       是
                |       |
               拒绝    允许修改
```

对应 Go 代码：

```
func CanUpdateVideo(
    role string,
    userID string,
    ownerID string,
    status string,
) bool {

    // RBAC：检查角色
    if role != "creator" {
        return false
    }

    // ABAC：检查资源属性
    if userID != ownerID {
        return false
    }

    if status != "draft" {
        return false
    }

    return true
}
```

这只是用于理解原理的简化代码。生产环境应该支持一个用户拥有多个角色，并从数据库读取可信的资源属性。

## 四、两者的区别总结

| 对比   | RBAC         | ABAC           |
| ---- | ------------ | -------------- |
| 中文   | 基于角色的访问控制    | 基于属性的访问控制      |
| 判断依据 | 用户拥有的角色及其权限  | 用户、资源、环境等属性    |
| 典型问题 | 你有没有修改视频的权限？ | 你能不能修改这个具体视频？  |
| 优点   | 简单、容易维护      | 灵活、控制更精细       |
| 缺点   | 难以单独处理复杂条件   | 规则较复杂          |
| 适用场景 | 管理员、创作者、商家   | 视频归属、店铺归属、状态限制 |

一句话记住：

- RBAC：你是什么角色，能做什么？
- ABAC：在当前条件下，你能不能操作这个具体资源？

对于你正在开发的商城、视频发布、商品发布、爬虫和运维系统，使用 RBAC 管理功能权限，ABAC 管理具体资源和业务条件，是比较合理且可扩展的技术方案。

># <h2 id="平台超级管理员">平台超级管理员</h2>

有。在你的 Go 后端工程中，建议设置一个平台超级管理员（Super Admin），作为权限体系的初始管理者，可以创建角色、分配权限、授权其他管理员。

但要注意：超级管理员不等于可以绕过所有业务安全规则。

## 一、最高权限角色叫什么？

常见命名如下：

| 名称    | 代码               | 用途       |
| ----- | ---------------- | -------- |
| 超级管理员 | `super_admin`    | 平台最高管理角色 |
| 安全管理员 | `security_admin` | 管理角色和权限  |
| 普通管理员 | `admin`          | 日常后台管理   |
| 运维管理员 | `ops_admin`      | 管理系统运维   |
| 商家管理员 | `merchant_admin` | 管理指定店铺   |

你的工程建议使用：

```
type RoleCode string

const (
    RoleSuperAdmin     RoleCode = "super_admin"
    RoleSecurityAdmin  RoleCode = "security_admin"
    RoleAdmin          RoleCode = "admin"
    RoleMerchantAdmin  RoleCode = "merchant_admin"
)
```

超级管理员的权限包括：

```
super_admin
    |
    +-- iam:role:create       创建角色
    +-- iam:role:update       修改角色
    +-- iam:role:grant        分配角色
    +-- iam:role:revoke       撤销角色
    +-- iam:permission:grant  为角色配置权限
    +-- iam:user:disable     禁用用户
    +-- iam:audit:read       查看授权审计
```

## 二、第一个超级管理员从哪里来？

这是一个经典的 Bootstrap（初始化引导）问题。

因为系统刚部署时，没有管理员，也就没有人能给其他用户授予管理员角色。

解决方案：在首次部署时，通过受控的初始化程序创建第一个超级管理员。

不建议在普通用户注册接口中加入类似以下逻辑：

```
// 错误示例：第一个注册用户自动成为超级管理员
if userCount == 0 {
    role = "super_admin"
}
```

因为任何抢先调用注册接口的人，都可能获得最高权限。

### 推荐初始化流程

```
首次部署 Go 服务
        |
        v
执行 MySQL Migration
        |
        v
初始化系统角色与权限
        |
        v
创建首个管理员账号
        |
        v
执行 Bootstrap 管理命令
        |
        v
将 super_admin 绑定到该用户
        |
        v
记录授权审计
        |
        v
关闭 Bootstrap 入口
        |
        v
后续管理员通过 IAM 授权
```

## 三、MySQL 如何初始化超级管理员？

假设已经创建了 `iam_roles` 和 `iam_user_role_bindings` 两张表。

第一步：初始化角色。

```
INSERT INTO iam_roles (
    role_code,
    role_name,
    status
)
VALUES (
    'super_admin',
    '平台超级管理员',
    1
)
ON DUPLICATE KEY UPDATE
    role_code = role_code;
```

第二步：给已有用户 `U1001` 授权。

```
INSERT INTO iam_user_role_bindings (
    user_id,
    role_id,
    scope_type,
    scope_id,
    status
)
SELECT
    'U1001',
    id,
    'global',
    '',
    1
FROM iam_roles
WHERE role_code = 'super_admin';
```

这样，`U1001` 就拥有了平台级超级管理员角色。

但以上 SQL 只是原理演示。生产环境应该由受控的 Bootstrap 命令执行，并验证账号、角色、授权状态和审计结果，而不是让业务人员直接执行 SQL。

## 四、Go 后端如何实现首次授权？

建议增加一个管理命令：

```
./mlc-server iam bootstrap --user-id U1001
```

Go 核心逻辑：

```
func BootstrapSuperAdmin(
    ctx context.Context,
    db *sql.DB,
    userID string,
) error {

    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // 1. 验证目标用户存在且状态正常
    // 2. 锁定 IAM Bootstrap 状态记录
    // 3. 检查系统是否已经完成初始化
    // 4. 查询 super_admin 角色
    // 5. 插入用户角色绑定
    // 6. 写入不可随意修改的授权审计
    // 7. 标记 Bootstrap 已完成

    return tx.Commit()
}
```

这里建议专门建立一条 Bootstrap 状态记录，在同一个事务中加锁检查和更新，保证即使多个进程同时初始化，也只有一个能成功。

另外，首次授权命令必须满足：

- 只能由可信部署环境中的管理员执行。
- 不能暴露为公开 HTTP API。
- 必须验证目标账号身份。
- 初始化完成后不能再次执行。
- 不允许通过修改普通注册参数获得最高权限。

## 五、超级管理员如何给其他用户授权？

例如，`U1001` 是超级管理员，要把 `U2002` 设置为视频审核员。

```
超级管理员 U1001
        |
        v
POST /admin/iam/role-grants
        |
        v
验证 JWT 身份
        |
        v
检查 iam:role:grant 权限
        |
        v
检查是否允许授予目标角色
        |
        v
验证 U2002 账号状态
        |
        v
MySQL 事务写入角色绑定
        |
        +-- 写入授权审计
        |
        v
Redis 权限缓存失效
        |
        v
U2002 获得 content_reviewer 角色
```

请求示例：

```
{
  "userId": "U2002",
  "roleCode": "content_reviewer",
  "scopeType": "global",
  "scopeId": ""
}
```

实际接口还应验证授权者是否具有授予该角色的资格，避免普通管理员把自己或别人提升为 `super_admin`。

## 六、生产环境建议增加三项保护

1. 最高角色保护：`super_admin` 只能通过专门的高风险授权流程授予，普通 `iam:role:grant` 权限不能授予该角色。
2. 防止最后一个超级管理员被删除：撤销、禁用或删除管理员时，必须在事务中确保仍保留可用的恢复管理路径。
3. 敏感授权审计：记录操作人、被授权人、角色、作用域、操作时间、审批单和请求 ID。最高权限变更建议采用 MFA 和双人审批。

## 七、最终建议

对于你的 Go 商城 + 视频 + 爬虫 + 运维工程，推荐采用以下角色层次：

```
               super_admin
               平台超级管理员
                      |
          +-----------+-----------+
          |           |           |
     security_admin  admin     ops_admin
       安全管理员   平台管理员   运维管理员
                      |
           +----------+----------+
           |          |          |
       operator   reviewer   crawler_operator
        运营人员    审核人员     爬虫操作员


       creator    merchant     user
        创作者       商家       普通用户
```

这张图表示管理职责的划分，不表示下层角色自动继承上层角色的全部权限。具体权限仍然由角色与权限的绑定关系决定。

最推荐的实现：

- 初始超级管理员通过 `iam bootstrap` 命令创建。
- 日常角色分配通过 IAM API 完成。
- 使用 MySQL 保存授权关系，Redis 缓存权限。
- 所有授权操作记录审计日志。
- 对超级管理员授予、撤销等高风险操作使用独立审批机制。

这样既能解决第一个超级管理员从哪里来的问题，也能支持后续成千上万名运营、商家、创作者和管理员的权限管理。

># <h2 id="完整需求设计与可编码实施方案">完整需求设计与可编码实施方案</h2>

# Go 后端统一角色权限系统：完整需求设计与可编码实施方案

针对你的 Go 后端工程（商城、视频、创作者中心、商品发布、爬虫、运维、钱包、评论、弹幕等），建议建设一个统一的 IAM（Identity and Access Management，身份与访问管理）系统。

目标是形成一套可以直接交给 Codex / OpenCode CLI 编码实现的方案，包括业务需求、角色结构、权限矩阵、数据库设计、Go 接口、业务流程、权限安全和验收标准。

技术架构采用：

RBAC + ABAC + Scope（作用域）+ Resource Ownership（资源归属）+ Audit（审计）

## 一、完整角色组织结构

首先明确：平台管理员、业务管理员、普通用户、创作者、商家之间，不应该设计成简单的上下级继承关系。

推荐采用四个相互独立的权限域。

```
                      MLC 平台 IAM
                           |
                     super_admin
                      超级管理员
                           |
          +----------------+----------------+
          |                |                |
     平台治理域          业务管理域        业务使用域
          |                |                |
    +-----+-----+    +-----+------+    +----+------+
    |           |    |            |    |           |
security_admin admin user_admin  creator_admin user  creator
安全管理员      平台管理员 用户管理员 创作者管理员 用户  创作者
    |                |            |               |
    |          +-----+------+     |            merchant
    |          |            |     |              商家
    |     merchant_admin  content_reviewer
    |     平台商家管理员     内容审核员
    |
    +------------- 技术运营域 -------------+
                     |
          +----------+-----------+
          |          |           |
       ops_admin  operator  crawler_admin
       运维管理员  运营人员    爬虫管理员
          |                      |
     ops_engineer          crawler_operator
      运维工程师              爬虫操作员
```

说明：这是职责组织图，不是自动继承的权限树。各角色的实际权限由 IAM 策略决定。`super_admin` 拥有最高管理权限，但仍受资金安全、审批和审计等强制规则约束。

### 1. 角色完整清单

| 角色编码                      | 中文名称    | 核心职责          |
| ------------------------- | ------- | ------------- |
| `super_admin`             | 超级管理员   | 平台最高管理、关键角色授权 |
| `security_admin`          | 安全管理员   | 角色权限、安全策略、审计  |
| `admin`                   | 平台管理员   | 日常平台后台管理      |
| `user_admin`              | 用户管理员   | 用户状态、封禁、申诉    |
| `creator_admin`           | 创作者管理员  | 创作者资格、创作者管理   |
| `merchant_admin_platform` | 平台商家管理员 | 商家入驻、店铺资质     |
| `content_reviewer`        | 内容审核员   | 视频、评论、弹幕审核    |

| `operator`                | 平台运营人员  | 推荐、活动、内容运营    |
| `ops_admin`               | 运维管理员   | 运维团队和生产操作授权   |
| `ops_engineer`            | 运维工程师   | 监控、日志、授权部署    |
| `crawler_admin`           | 爬虫管理员   | 爬虫任务、策略和调度    |
| `crawler_operator`        | 爬虫操作员   | 执行、停止、查看任务    |
| `user`                    | 普通用户    | 购买、点赞、评论、收藏   |
| `creator`                 | 视频创作者   | 发布、维护自己的视频    |
| `merchant_owner`          | 店铺所有者   | 店铺管理及成员授权     |
| `merchant_staff`          | 商家员工    | 店铺内授权的商品、订单操作 |
| `customer_service`        | 客服      | 售后、工单、用户咨询    |

另外还需要两个不属于普通用户角色的主体：

- `anonymous`：未登录游客，不需要写入 `iam_user_roles`。
- `service_account`：Kafka Consumer、爬虫 Worker、定时任务等机器身份，不使用普通用户 JWT。

特别注意： `merchant_admin_platform` 是平台商家管理员；`merchant_owner` 是某个店铺的所有者。这两个角色的权限完全不同。

## 三、权限模型详细设计

### 1. 统一授权模型

所有授权请求都抽象成五个元素：

```
Subject     谁在操作
Action      执行什么操作
Resource    操作什么资源
Scope       在什么业务范围内
Context     当前业务环境
```

例如，用户 `U1001` 修改视频 `V2001`：

```
{
  "subject": {
    "type": "user",
    "id": "U1001"
  },
  "action": "video:submission:update",
  "resource": {
    "type": "video",
    "id": "V2001"
  },
  "scope": {
    "type": "global",
    "id": ""
  },
  "context": {
    "operation": "edit_draft"
  }
}
```

后端根据视频数据库记录查询 `creator_id` 和 `status`，不能信任客户端提供的归属、店铺或状态属性。

最终判断公式：

\\[ Allow = RolePermission \land ScopeMatch \land ResourcePolicy \land BusinessPolicy \\]

只要其中一项不满足，就拒绝操作。

### 2. 权限编码规范

统一采用：

```
domain:resource:action
```

具体权限清单：

| 业务域 | 权限编码                       | 用途     |
| --- | -------------------------- | ------ |
| 用户  | `user:profile:read`        | 查看用户资料 |
| 用户  | `user:account:disable`     | 封禁用户   |
| 视频  | `video:submission:create`  | 创建视频   |
| 视频  | `video:submission:update`  | 修改视频   |
| 视频  | `video:submission:publish` | 提交视频发布 |
| 视频  | `video:submission:delete`  | 删除视频   |
| 视频  | `video:review:approve`     | 视频审核通过 |
| 评论  | `video:comment:create`     | 发表评论   |
| 评论  | `video:comment:moderate`   | 管理评论   |
| 弹幕  | `video:danmaku:create`     | 发送弹幕   |
| 商城  | `mall:product:create`      | 创建商品   |
| 商城  | `mall:product:update`      | 修改商品   |
| 商城  | `mall:product:publish`     | 商品上架   |
| 商城  | `mall:product:review`      | 商品审核   |
| 订单  | `mall:order:read`          | 查看订单   |
| 订单  | `mall:order:refund`        | 执行授权退款 |
| 钱包  | `wallet:recharge:read`     | 查看充值订单 |
| 爬虫  | `crawler:task:create`      | 创建任务   |
| 爬虫  | `crawler:task:execute`     | 执行任务   |
| 爬虫  | `crawler:task:stop`        | 停止任务   |
| 运维  | `ops:metrics:read`         | 查看监控   |
| 运维  | `ops:deployment:execute`   | 执行部署   |
| IAM | `iam:role:create`          | 创建角色   |
| IAM | `iam:role:grant`           | 分配角色   |
| IAM | `iam:role:revoke`          | 撤销角色   |
| IAM | `iam:permission:grant`     | 配置角色权限 |
| IAM | `iam:audit:read`           | 查看授权审计 |

权限编码必须由后端统一维护，不能让前端任意生成。

### 3. 作用域设计

建议至少支持四种作用域：

| scope_type    | 含义        | 示例                 |
| ------------- | --------- | ------------------ |
| `global`      | 平台全局      | 平台管理员              |
| `shop`        | 指定店铺      | SHOP100            |
| `creator`     | 指定创作者工作空间 | CREATOR100         |
| `environment` | 指定运行环境    | staging、production |

例如：

```
用户 U1001
   |
   +-- user @ global
   |
   +-- creator @ creator:CREATOR100
   |
   +-- merchant_owner @ shop:SHOP100
   |
   +-- merchant_staff @ shop:SHOP200
   |
   +-- ops_engineer @ environment:staging
```

这里的 `@` 表示角色在指定作用域内生效。

同一用户可以拥有多个角色，也可以在不同作用域内拥有不同角色。

## 四、数据库设计：MySQL 8.0

建议将 IAM 的核心关系拆成 8 张表。

```
users（现有用户表）
   |
   +------ iam_user_role_bindings
                 |
                 +------ iam_roles
                            |
                            +------ iam_role_permissions
                                          |
                                          +------ iam_permissions

iam_organizations
   |
   +------ iam_organization_members

iam_service_accounts

iam_bootstrap_state

iam_audit_logs
```

### 1. 角色表

```
CREATE TABLE iam_roles (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    role_code VARCHAR(64) NOT NULL,
    role_name VARCHAR(100) NOT NULL,
    role_type VARCHAR(32) NOT NULL,
    is_system TINYINT NOT NULL DEFAULT 0,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_role_code (role_code)
);
```

`role_type` 建议区分 `platform`、`business`、`tenant`，方便管理后台分类展示。`is_system=1` 表示内置角色，不能随意删除。

### 2. 权限表

```
CREATE TABLE iam_permissions (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    permission_code VARCHAR(128) NOT NULL,
    permission_name VARCHAR(100) NOT NULL,
    domain VARCHAR(32) NOT NULL,
    description VARCHAR(255) NOT NULL DEFAULT '',

    UNIQUE KEY uk_permission_code (permission_code),
    KEY idx_domain (domain)
);
```

### 3. 角色与权限关联表

```
CREATE TABLE iam_role_permissions (
    role_id BIGINT UNSIGNED NOT NULL,
    permission_id BIGINT UNSIGNED NOT NULL,

    PRIMARY KEY (role_id, permission_id),
    KEY idx_permission_id (permission_id),

    FOREIGN KEY (role_id) REFERENCES iam_roles(id),
    FOREIGN KEY (permission_id) REFERENCES iam_permissions(id)
);
```

### 4. 用户角色绑定表

```
CREATE TABLE iam_user_role_bindings (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    role_id BIGINT UNSIGNED NOT NULL,
    scope_type VARCHAR(32) NOT NULL,
    scope_id VARCHAR(64) NOT NULL DEFAULT '',
    status TINYINT NOT NULL DEFAULT 1,
    granted_by VARCHAR(64) NOT NULL,
    expires_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_user_role_scope (
        user_id, role_id, scope_type, scope_id
    ),
    KEY idx_user_active (user_id, status),
    KEY idx_scope_role (scope_type, scope_id, role_id),

    FOREIGN KEY (role_id) REFERENCES iam_roles(id)
);
```

生产代码中必须校验：

- `scope_type=global` 时，`scope_id` 必须为空。
- `scope_type=shop` 时，店铺必须存在。
- 角色允许的作用域必须匹配绑定作用域。
- `expires_at` 过期后授权立即失效。
- 禁用角色后，其所有绑定不再生效。

### 5. 组织表和组织成员表

```
CREATE TABLE iam_organizations (
    id VARCHAR(64) PRIMARY KEY,
    org_type VARCHAR(32) NOT NULL,
    org_name VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
);

CREATE TABLE iam_organization_members (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    organization_id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    joined_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_org_user (organization_id, user_id),
    KEY idx_user (user_id),

    FOREIGN KEY (organization_id)
        REFERENCES iam_organizations(id)
);
```

组织成员关系与角色授权是两件事：加入店铺并不自动意味着拥有修改商品、退款或成员管理权限。

### 6. 服务身份表

```
CREATE TABLE iam_service_accounts (
    id VARCHAR(64) PRIMARY KEY,
    service_name VARCHAR(100) NOT NULL,
    service_type VARCHAR(32) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE KEY uk_service_name (service_name)
);
```

该表保存服务身份元数据。机器凭证建议由专门的密钥管理系统管理，避免将明文密钥存入 MySQL。

服务身份的权限绑定需要独立的 `iam_service_role_bindings`，或把用户角色绑定表泛化为包含 `principal_type`、`principal_id` 的主体授权表。推荐后者作为最终统一模型，但迁移时必须先处理现有数据和唯一索引。

### 7. Bootstrap 状态表

```
CREATE TABLE iam_bootstrap_state (
    id TINYINT UNSIGNED PRIMARY KEY,
    completed TINYINT NOT NULL DEFAULT 0,
    completed_by VARCHAR(64) NULL,
    completed_at DATETIME(3) NULL
);

INSERT INTO iam_bootstrap_state (id, completed)
VALUES (1, 0);
```

首次超级管理员授权时：

```
SELECT completed
FROM iam_bootstrap_state
WHERE id = 1
FOR UPDATE;
```

在同一个事务中检查状态、绑定超级管理员、写审计并标记完成。

### 8. 审计表

```
CREATE TABLE iam_audit_logs (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    actor_id VARCHAR(64) NOT NULL,
    action VARCHAR(128) NOT NULL,
    target_type VARCHAR(64) NOT NULL,
    target_id VARCHAR(64) NOT NULL,
    result VARCHAR(32) NOT NULL,
    request_id VARCHAR(64) NOT NULL,
    details JSON,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    KEY idx_actor_time (actor_id, created_at),
    KEY idx_target_time (target_type, target_id, created_at)
);
```

建议角色授权、撤销和审计写入同一个事务。对重要审计日志再异步发送到独立、受保护的存储系统，避免数据库管理员随意篡改历史记录。

以上 DDL 是核心结构，不是全部生产迁移文件。实施时还需要补充角色作用域约束、机器身份授权、审批表、版本管理和索引性能验证。

### 1. 核心接口

```
package iam

import "context"

type Principal struct {
    Type          string
    ID            string
    SessionID     string
    Authenticated bool
}

type Resource struct {
    Type string
    ID   string
}

type Scope struct {
    Type string
    ID   string
}

type Decision struct {
    Allowed bool
    Reason  string
}

type AuthorizeRequest struct {
    Principal  Principal
    Permission string
    Resource   Resource
    Scope      Scope
}

type Authorizer interface {
    Authorize(
        ctx context.Context,
        req AuthorizeRequest,
    ) (Decision, error)
}
```

`Authorize` 的核心执行步骤：

```
Authorize(request)
       |
       v
1. 验证主体身份
       |
       v
2. 查询有效角色绑定
       |
       v
3. 查询角色拥有的权限
       |
       v
4. 验证 Scope
       |
       v
5. 从业务仓储加载资源属性
       |
       v
6. 执行 ABAC 规则
       |
       v
7. 检查业务状态和强制安全策略
       |
       v
8. 返回 Allow / Deny
```

### 2. API 接口清单

| 方法     | API                                 | 功能       |
| ------ | ----------------------------------- | -------- |
| GET    | `/admin/iam/roles`                  | 角色列表     |
| POST   | `/admin/iam/roles`                  | 创建角色     |
| PATCH  | `/admin/iam/roles/{id}`             | 修改角色     |
| GET    | `/admin/iam/permissions`            | 权限列表     |
| PUT    | `/admin/iam/roles/{id}/permissions` | 配置角色权限   |
| POST   | `/admin/iam/role-grants`            | 授予用户角色   |
| DELETE | `/admin/iam/role-grants/{id}`       | 撤销授权     |
| GET    | `/admin/iam/users/{id}/roles`       | 用户角色列表   |
| GET    | `/admin/iam/audit-logs`             | 审计查询     |
| GET    | `/api/me/permissions`               | 当前用户有效权限 |

对于 `PUT` 修改角色权限的接口，必须禁止普通管理员为自己增加权限，或者通过创建新角色间接获取更高权限。

所有写接口应校验操作人权限、目标角色是否可授予、作用域、版本和必要的审批状态。

## 六、业务场景与权限实现

### 场景一：普通用户申请成为创作者

```
普通用户 U1001
      |
      v
POST /api/creator/applications
      |
      v
验证登录和申请条件
      |
      v
创建申请 pending
      |
      v
creator_admin 审核
      |
      +---- 拒绝 → rejected
      |
      +---- 通过 → approved
                       |
                       v
              授予 creator 角色
                       |
                       v
              记录授权审计
                       |
                       v
              用户可提交视频发布
```

必须保证审核通过与角色授予的状态一致，推荐在同一个 MySQL 事务中处理。如果审核和 IAM 分属不同服务，则通过 Outbox + Kafka 事件实现可靠的最终一致性。

### 场景二：商家员工管理商品

用户 `U1002` 是 `SHOP100` 的商品编辑员。

```
U1002
  |
  +-- merchant_staff @ SHOP100
             |
             +-- mall:product:create
             +-- mall:product:update
             |
             +-- 不具有 mall:order:refund
```

假设数据库中：

| 商品 ID | 店铺 ID   | 是否可修改 |
| ----- | ------- | ----- |
| P001  | SHOP100 | 是     |
| P002  | SHOP200 | 否     |
| P003  | SHOP100 | 是     |

修改商品的 SQL 需要包含店铺约束：

```
UPDATE mall_products
SET title = ?
WHERE product_id = ?
  AND shop_id = ?
  AND status = 'draft';
```

`shop_id` 必须从已验证的资源关系取得，不能直接使用未经验证的客户端参数。

### 场景三：爬虫操作员执行任务

```
crawler_operator
       |
       v
crawler:task:execute
       |
       v
检查任务作用域
       |
       v
检查任务状态和执行配额
       |
       v
创建执行记录
       |
       v
Kafka 发布任务事件
       |
       v
Crawler Worker 消费执行
```

爬虫操作员只能启动被授权的任务。Worker 使用独立机器身份运行，不能继承操作员的全部管理权限。

对于你的 `discovered → raw → cleaned → stored` 流水线，建议在任务创建和启动阶段做用户授权，在 Worker 阶段验证机器身份、任务来源和允许执行的阶段。

### 场景四：超级管理员授权

```
super_admin U0001
       |
       v
授予 U0002 security_admin
       |
       v
验证 U0001 当前权限
       |
       v
检查目标角色是否允许授予
       |
       v
检查 MFA 和审批状态
       |
       v
MySQL 事务
       |
       +-- 创建角色绑定
       +-- 写入授权审计
       +-- 更新权限版本
       |
       v
提交事务
       |
       v
失效 Redis 权限缓存
       |
       v
U0002 获得安全管理员权限
```

这里要防止并发授权、重复提交、缓存未及时失效，以及管理员通过修改自身角色实现权限提升。

## 七、Redis + Kafka 权限缓存设计

结合你现有的 Redis 和 Kafka，推荐：

```
                    IAM MySQL
                       |
                权限变更事务
                       |
                 Outbox Event
                       |
                       v
                      Kafka
                       |
           +-----------+-----------+
           |                       |
      IAM Consumer             其他服务
           |                       |
           v                       v
      Redis 版本更新          本地缓存失效
```

Redis Key：

```
iam:user:U1001:roles
iam:user:U1001:permissions
iam:user:U1001:version

iam:role:creator:permissions
iam:role:merchant_staff:permissions
```

缓存策略：

| 内容      | 建议策略                 |
| ------- | -------------------- |
| 角色权限定义  | Redis 缓存，版本化         |
| 用户角色绑定  | Redis 缓存，变更主动失效      |
| 视频、商品归属 | 优先查询可信业务数据           |
| 高危授权    | 查询最新权威状态             |
| 权限变更通知  | MySQL Outbox + Kafka |
| 缓存不可用   | 敏感操作默认拒绝             |

Kafka 消息可以设计为：

```
{
  "eventId": "EVT10001",
  "eventName": "iam.role_binding.changed",
  "userId": "U1001",
  "roleCode": "creator",
  "scopeType": "global",
  "scopeId": "",
  "version": 12
}
```

Consumer 必须支持事件去重、重复投递和乱序处理。版本号只允许向前更新，不能被旧消息覆盖。

对于需要立即生效的封禁、权限撤销和生产环境高危授权，不应依赖 Kafka 最终一致性作为唯一安全保障。应增加权威状态校验或可验证的版本失效机制。

## 八、测试与验收标准

权限系统最重要的测试不是“管理员能否访问”，而是“没有权限的人能否越权”。

建议至少覆盖以下测试：

| 测试场景               | 预期结果      |
| ------------------ | --------- |
| 游客访问公开视频           | 允许        |
| 游客发布评论             | 拒绝，401    |
| 普通用户发布视频           | 拒绝，403    |
| 创作者修改自己的草稿视频       | 允许        |
| 创作者修改他人的视频         | 拒绝，403    |
| 商家修改其他店铺商品         | 拒绝，403    |
| 商家员工执行未授权退款        | 拒绝，403    |
| 运维人员授予自己超级管理员      | 拒绝，403    |
| 已撤销角色的用户继续访问       | 拒绝        |
| 角色过期后继续访问          | 拒绝        |
| 多次重复授权             | 不产生重复有效绑定 |
| 两个进程同时执行 Bootstrap | 仅一个成功     |
| Kafka 重复消费权限事件     | 最终权限状态正确  |
| Redis 故障时执行高危授权    | 默认拒绝      |
| 最后一个超级管理员被撤销       | 阻止操作      |

HTTP 状态建议统一：

- `401 Unauthorized`：未登录、凭证无效。
- `403 Forbidden`：身份有效，但没有操作权限。
- `404 Not Found`：资源不存在，或出于防枚举要求隐藏其存在。
- `409 Conflict`：授权状态、资源版本或业务状态冲突。

性能验收需要先建立实际业务流量模型，再确定 P95/P99 延迟、缓存命中率和峰值吞吐目标，不能直接假设这套设计能够支撑千万并发。

# MLC_GO 统一 IAM 权限系统实施任务书

## 1. 项目目标

在现有 Go 后端工程中新增统一 IAM 权限模块，实现 RBAC + ABAC + Scope + Resource Ownership + Audit。

业务覆盖：

- 普通用户和游客
- 视频创作者、视频发布、评论和弹幕
- 商家、商品发布、订单和钱包
- 爬虫管理和 Kafka Worker
- 平台运营、内容审核和运维
- 超级管理员及角色权限分配

## 2. 工程约束

1. 优先复用现有 JWT、Redis、MySQL、Kafka、HTTP 中间件和统一响应结构。
2. 不重构现有用户注册、登录和 Refresh Token 流程。
3. 新增 `internal/iam` 模块，避免循环依赖。
4. 所有 SQL 必须参数化，使用 `context.Context`。
5. 授权、撤销、审计必须具备事务一致性。
6. 机器身份与普通用户身份分离。
7. 默认拒绝未授权操作，不能仅依赖前端隐藏按钮。
8. 不允许普通管理员为自己提升权限。
9. 生产环境不得硬编码超级管理员账号或密码。
10. 数据库迁移必须考虑现有数据兼容性。

## 3. 第一阶段：工程分析

在编码前完成：

- 分析现有用户表、主键类型和登录流程。
- 分析 JWT Claims、中间件、路由注册方式。
- 分析 MySQL Migration 机制和 Redis 封装。
- 分析视频、商品、爬虫等业务表的资源归属字段。
- 检查现有角色或管理员逻辑，避免重复实现。

输出实际工程适配方案，不要假设目录、表名和函数已经存在。

## 4. 第二阶段：IAM 基础模块

实现：

- Principal、Role、Permission、Scope、Resource、Decision。
- IAM Repository 接口。
- MySQL 角色和权限仓储。
- Authorizer 统一授权接口。
- RBAC 角色权限校验。
- ABAC 资源属性校验。
- 作用域匹配和过期判断。
- 统一的权限错误类型。

## 5. 第三阶段：数据库

创建迁移文件：

- iam_organizations

## 6. 第四阶段：超级管理员初始化

`iam bootstrap --user-id <ID>`

每个阶段输出：

## 十、最终推荐的落地顺序

阶段 1：IAM 基础 + Bootstrap

优先实现

角色、权限、作用域、数据库迁移、超级管理员初始化。

阶段 2：用户授权 + 业务接入

角色分配、视频归属、店铺归属、爬虫操作权限。

阶段 3：Redis + Kafka + 审计

权限缓存、授权事件、版本失效、完整审计。

阶段 4：审批 + 管理后台 + 性能验证

高危授权审批、MFA、管理界面、压测和故障测试。

最终架构决策： 当前优先采用 Go 单体工程内的模块化 IAM，而不是直接拆成独立微服务。数据库采用 MySQL 作为权限权威数据源，Redis 负责加速，Kafka 负责跨模块事件传播，业务服务负责资源归属和业务状态校验。

这样既能支持你现在的商城、视频、爬虫和运维模块，也为后续扩展直播、广告、会员、商家结算及更复杂的多租户权限模型保留空间。
