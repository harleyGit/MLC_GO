> <h2 id="大型视频社区评论系统设计">大型视频社区评论系统设计</h2>

**普通视频评论区主要使用 HTTP REST API，而不是 WebSocket：**

- 加载评论列表：HTTP GET
- 发布、点赞、删除评论：HTTP POST
- 直播弹幕、礼物、在线人数等实时互动：WebSocket 长连接

评论区通常是“打开视频 → 请求评论 → 浏览或翻页”的按需读取场景，没有必要为大量用户持续保持长连接。B站直播消息系统则属于典型的 WebSocket 场景。参考：[直播间消息 WebSocket 协议][1]。

本文以类 B站的大型视频社区为例，讨论海量评论场景下的数据模型、缓存、消息队列与分片方案。文中的规模和架构属于系统设计假设，不代表 B站官方实现。

***
<br/>

> <h3 id="整体架构">整体架构</h3>

假设系统规模如下：

- 视频数量：10 亿
- 评论数量：100 亿以上
- 日活用户：1 亿
- 热门视频评论并发：千万级

```text
                 用户浏览器
                      |
                      |
                 CDN / Gateway
                      |
              ----------------
              |              |
        Comment API       Comment Write
              |              |
              |
       ------------------
       |                |
    Redis Cache       MySQL/TiDB
       |
       |
    Kafka MQ
       |
       |
 异步处理服务
       |
 -------------------------
 |          |             |
点赞服务  搜索服务    推荐服务
```

**核心思路：**读取请求优先命中缓存，写入请求通过消息队列削峰，持久化数据按业务规模进行分片，点赞、搜索、通知和推荐等能力异步处理。

> <h3 id="评论请求与分页">评论请求与分页</h3>

## 获取评论列表

用户打开视频页面：

```text
https://www.bilibili.com/video/BVxxx
```

前端评论组件按需请求评论列表：

```text
CommentList
      |
      |
GET /api/comment/list
```

请求示例：

```text
GET /api/v1/comment/list

{
 video_id:"BV1xxx",
 cursor:"abc123",
 size:20
}
```

返回示例：

```json
{
 "comments":[
    {
       "id":10001,
       "user":"张三",
       "content":"这个视频不错",
       "like":200,
       "reply_count":30
    }
 ]
}
```

<br/>

## 为什么使用 Cursor 分页

大偏移量的 `offset` 分页需要扫描并丢弃前面的大量记录：

```sql
select *
from comments
where video_id=100
limit 20 offset 100000;
```

当偏移量达到 `10000000` 时，数据库可能需要处理前面 1000 万条记录，越往后翻页成本越高。

Cursor 分页通过上一页末尾记录的位置继续查询。第一次请求：

```text
GET

video_id=100
cursor=null
limit=20
```

返回下一页游标：

```json
{
 comments:[
 ],
 next_cursor:"169123123123"
}
```

下一次请求：

```text
GET

video_id=100
cursor=169123123123
```

对应 SQL：

```sql
SELECT *
FROM comments
WHERE video_id=100
AND comment_id < 169123123123
ORDER BY comment_id DESC
LIMIT 20;
```

配合联合索引 `idx_video_comment`，可以直接从游标位置继续扫描，索引定位复杂度约为 `O(logN)`。

> <h3 id="评论数据模型">评论数据模型</h3>

基础评论表至少需要描述评论本身、所属视频、发布用户、评论树根节点、直接回复目标和计数字段。原文给出的示例结构如下：

```sql
CREATE TABLE comment
(
 `id` BIGINT UNSIGNED PRIMARY KEY NOT NULL AUTO_INCREMENT,
 `comment_id` VARCHAR(255) NULL UNIQUE COMMENT '评论ID',
 video_id VARCHAR(255) NULL UNIQUE COMMENT '视频ID',

 `user_id` VARCHAR(255) NULL UNIQUE COMMENT '用户ID',

 -- 一级评论
 root_comment_id VARCHAR(255) NULL UNIQUE COMMENT '一级评论ID',

 -- 回复谁
 parent_comment_id VARCHAR(255) NULL UNIQUE COMMENT '回复评论ID',

 -- 回复目标用户
 reply_user_id VARCHAR(255) NULL UNIQUE COMMENT '回复目标用户ID',

 content VARCHAR(1000),

 like_count BIGINT DEFAULT 0,

 reply_count BIGINT DEFAULT 0,

 status TINYINT,

 created_at DATETIME,

 INDEX idx_video_root(
    video_id,
    root_id,
    id DESC
 ),

 INDEX idx_parent(
    parent_id
 )
);
```

> 注意：该 SQL 是原文中的结构示例。字段声明使用了 `root_comment_id`、`parent_comment_id`，索引却使用 `root_id`、`parent_id`；同时多个业务字段设置了 `UNIQUE`。实际建表时必须统一字段名，并根据“一条视频、多条评论”和“一名用户、多条评论”的基数关系重新确认唯一约束。

只有 `id`、`video_id`、`content`、`parent_id` 的简单结构难以支持高效的评论树查询、回复目标定位、热点缓存和计数维护，因此需要显式保存根评论、父评论、回复用户及冗余计数。

> <h3 id="评论树与回复设计">评论树与回复设计</h3>

## `root_id` 与 `parent_id`

假设评论关系如下：

```text
用户A:
这个视频很好
```

评论 ID 为 `100`。用户 B 回复 A，评论 ID 为 `200`；用户 C 再回复 B，评论 ID 为 `300`：

```text
用户B 回复 A:
确实很好

用户C 回复 B:
哈哈
```

评论树：

```text
100
 |
 +---200
       |
       +----300
```

数据库记录：

| id  | root_id | parent_id |
| --- | ------- | --------- |
| 100 | 100     | 0         |
| 200 | 100     | 100       |
| 300 | 100     | 200       |

- `root_id`：表示评论属于哪棵评论树，便于一次查询某条一级评论下的全部回复。
- `parent_id`：表示当前评论直接回复哪条评论，用于恢复回复关系。

---
<br/>

## 为什么不返回无限嵌套结构

不推荐直接返回无限递归的 `children`：

```text
comment
{
 children:[
    {
       children:[
       ]
    }
 ]
}
```

大型评论区通常分两步加载：先显示一级评论及回复数量，用户点击“查看 xx 条回复”后，再加载该评论树下的二级回复。

```text
一级评论：

A:
这个视频不错
    100条回复

点击：

展开回复
```

请求：

```text
GET

/comment/reply/list

root_id=100
```

返回扁平回复列表，再通过 `parent_id` 和 `reply_user_id` 展示回复目标：

```text
B 回复 A

C 回复 B

D 回复 C
```

这种方式避免一次构造深层递归结构，也便于分页加载热门评论树。

> <h3 id="用户提及设计">用户提及设计</h3>

评论中的 `@张三` 不应只作为普通字符串保存，否则难以可靠地完成消息通知和反向查询。可以单独建立提及关系表：

```sql
CREATE TABLE comment_mention
(
 id BIGINT,

 comment_id BIGINT,

 mention_user_id BIGINT,

 INDEX idx_user(
    mention_user_id
 )
);
```

例如评论 `500` 的内容为：

```text
id=500

content:
@10086 你的观点不错
```

评论主表保存评论 `500`，提及表保存关联关系：

| comment_id | mention_user |
| ---------- | ------------ |
| 500        | 10086        |

用户 `10086` 打开消息中心时，可按用户 ID 查询被提及记录：

```sql
select *
from comment_mention
where mention_user_id=10086;
```

> <h3 id="高并发写入">高并发写入</h3>

用户发表评论：

```text
POST /comment/create
```

高并发场景下，如果每个 HTTP 请求都同步写入 MySQL，数据库容易成为瓶颈：

```text
HTTP
 |
MySQL insert
```

可以使用 Kafka 对突发写入削峰：

```text
User

 |
 |
Comment API

 |
 |
Kafka

 |
 |
Comment Consumer

 |
 |
MySQL
```

生产消息示例：

```go
func CreateComment(){

    msg:=CommentMessage{
        VideoID:100,
        UserID:200,
        Content:"hello",
    }

    kafka.Send(msg)

    return
}
```

接口立即返回受理结果：

```json
{
 success:true
}
```

消费者异步持久化：

```go
func Consume(){

 for msg:=range kafka{

     db.Insert(comment)

 }
}
```

异步写入需要额外处理消息唯一 ID、幂等消费、失败重试、顺序性和“接口成功但数据暂未可见”的最终一致性问题。

> <h3 id="Redis缓存设计">Redis缓存设计</h3>

Redis 不负责保存全部 100 亿条评论，而是缓存热点列表、热门评论详情和高频计数。

## 热门视频评论列表

Key：

```text
comment:list:{video_id}
```

Value 可以保存热门评论 ID 列表：

```text
comment:list:10001

[
 100,
 200,
 300
]
```

评论完整内容仍以数据库为持久化来源。

---
<br/>

## 评论详情

评论详情可使用 Redis Hash：

```text
comment:10001
```

```text
{
content:"xxx",
like:100,
user:123
}
```

---
<br/>

## 回复数量

不要在每次读取时执行大范围实时统计：

```sql
select count(*)
from comment
where root_id=100
```

可维护独立计数 Key：

```text
comment:reply_count:100
```

新增回复时通过 `INCR` 更新，并异步同步到持久化存储。实际系统还需要处理缓存丢失后的重建及重复消息导致的计数偏差。

<br/>

> <h3 id="评论点赞设计">评论点赞设计</h3>

如果大量用户同时执行以下 SQL，会竞争同一评论记录的行锁：

```sql
update comment
set like_count=like_count+1
```

高并发方案可以先在 Redis 中更新点赞计数：

```text
comment_like_count:{comment_id}

INCR
```

同时向 Kafka 发送点赞事件，再由后台任务聚合并同步到 MySQL：

```text
Redis
 |
Kafka
 |
MySQL
```

```text
like event
```

除总数外，还需要用用户与评论的关联记录防止重复点赞，并保证取消点赞、消息重试和数据库落盘具有幂等性。

> <h3 id="分库分表设计">分库分表设计</h3>

100 亿级评论无法长期依赖单个 MySQL 实例，可以按 `video_id` 的哈希结果路由到不同数据库：

```text
comment_db_00

comment_db_01

...

comment_db_63
```

```go
dbIndex :=
hash(videoID)%64
```

每个库内再拆分数据表：

```text
comment_00

comment_01

...

comment_127
```

最终规模：

```text
64库
*
128表

=8192张表
```

以 `video_id` 作为分片键，可以让同一视频的评论落在固定分片，便于按视频查询。实际分片数量应根据容量评估、扩容策略、热点视频倾斜和运维成本确定，而不是固定采用 `64 × 128`。

> <h3 id="核心方案总结">核心方案总结</h3>

| 问题 | 方案 |
| --- | --- |
| 评论读取 | Redis 热点缓存 |
| 评论写入 | Kafka 削峰与异步持久化 |
| 深度分页 | Cursor 分页 |
| 海量数据 | 分库分表 |
| 点赞 | Redis 计数 + MQ 异步落库 |
| 回复关系 | `root_id` + `parent_id` |
| `@` 用户 | `comment_mention` 关系表 |
| 热点视频 | 多级缓存与热点隔离 |
| 评论搜索 | Elasticsearch |
| 消息通知 | Kafka 异步事件 |

大型视频社区的评论系统不只是 CRUD，其核心能力是：

```text
读多写少
+
热点隔离
+
异步化
+
缓存
+
分片
+
消息队列
```

**整体原则：缓存承担高频读取，消息队列吸收突发写入，数据库负责可靠持久化，分片解决容量问题，独立异步服务处理点赞、搜索、通知和推荐。**
