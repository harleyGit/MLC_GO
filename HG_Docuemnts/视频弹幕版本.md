> <h2 id="B站级弹幕系统设计V1">B站级弹幕系统设计V1</h2>

目标：使用 Go 实现仿 B 站、斗鱼、虎牙的弹幕系统，支撑**千万并发连接和亿级弹幕数据**。

核心不在于单个 WebSocket 库，而在于：**连接模型、房间广播模型、消息削峰、冷热数据分离**。

---

<br/>

> <h3 id="Redis的用途">Redis 的用途</h3>

Redis 不保存全部弹幕，主要用于热门房间状态和最近弹幕等热数据。

## 热门房间状态

例如，使用 `room:10001` 保存房间在线人数和最后消费位置：

```text
room:10001

{
 online:5000000,
 last_cursor:123456
}
```

## 最近弹幕

可使用 `ZSET` 保存最近一段时间的弹幕：

```text
danmaku:10001

score=time
value=json
```

写入示例：

```text
ZADD danmaku:10001 1720000000 msg
```

只保留最近 5 分钟的数据，历史弹幕交给持久化存储。

---

<br/>

> <h3 id="亿级弹幕存储">亿级弹幕存储</h3>

不要使用 MySQL 单表保存十亿级弹幕。例如：

```text
danmaku

id
danmu_id // 字符串
video_id
user_id
content

10亿行
```

单表达到该规模后，查询和维护成本会非常高。推荐进行冷热数据分离：

- **热数据：** Redis。
- **历史数据：** ClickHouse。

ClickHouse 历史表：

```text
danmaku_history
```

主要字段：

```text
video_id
user_id
content
create_time
```

按月份分区：

```sql
PARTITION BY month(create_time)
```

按视频和创建时间排序：

```sql
ORDER BY
(
 video_id,
 create_time
)
```

该结构适合查询视频回放弹幕。

> <h3 id="网络模型">网络模型</h3>

B 站级弹幕系统可采用以下网络与消息链路：

```text

 |
gnet
 |
gobwas/ws
 |
Room Engine
 |
Kafka
```

Go WebSocket 接入层选择：

```text

```

- `gnet` 提供基于 Reactor 模型的高性能事件驱动网络能力。
- `gobwas/ws` 负责 WebSocket 协议处理。
- `Room Engine` 负责房间管理和广播。
- `Kafka` 负责消息削峰和异步解耦。

---

<br/>

> <h3 id="千万连接的机器规模">千万连接的机器规模</h3>

单机经过系统参数和程序优化后，可承载约 `10万~50万` WebSocket 连接，实际容量取决于消息频率、内存占用、广播模型和硬件配置。

千万连接需要 Gateway 集群。例如使用 100 台 Gateway，每台承载 10 万连接：

```text
10,000,000 users

        |

100 gateway

每台:
100,000 connections
```

> <h2 id="gobwasws-与-gnet-构建高性能-websocket-网关">gobwas/ws 与 gnet 构建高性能 WebSocket 网关</h2>

`gobwas/ws` 是 Go 的高性能 WebSocket 协议库。它不像 `gorilla/websocket` 那样强调完整、易用的连接封装，而是提供更接近底层 TCP 的协议升级、帧解析和读写能力。

在弹幕、直播间聊天和大规模长连接网关中，各层职责通常是：

- **`gnet`：**负责高性能网络事件循环和 TCP 连接管理。
- **`gobwas/ws`：**负责 WebSocket Upgrade、Frame、Mask、Ping/Pong 和 Close 等协议处理。
- **业务层：**负责用户、房间、消息路由、弹幕广播和数据存储。

```text
TCP 连接
   |
WebSocket 协议解析
   |
业务消息
```

完整链路示意：

```text
                 APP
                  |
             WebSocket
                  |
        +----------------+
        | Load Balancer  |
        +----------------+
                  |
        +----------------+
        | gnet Gateway   |
        +----------------+
                  |
             gobwas/ws
                  |
            Room Manager
                  |
               Kafka
                  |
          Danmaku Service
                  |
       Redis + ClickHouse
```

> <h3 id="gobwasws-的定位">gobwas/ws 的定位</h3>

## WebSocket 协议流程

客户端首先发送 HTTP Upgrade 请求：

```http
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: xxx
```

服务器返回 `101 Switching Protocols`：

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: xxx
```

升级完成后，连接不再传输普通 HTTP 消息，而是在 TCP 长连接上持续传输 WebSocket Frame：

```text
TCP 长连接

client
  |
server

frame frame frame
```

例如一条弹幕：

```json
{
  "userid": 10001,
  "text": "666"
}
```

实际会封装为：

```text
WebSocket Frame

+---------+
| header  |
+---------+
| payload |
+---------+
```

`gobwas/ws` 主要处理：

- HTTP Upgrade。
- WebSocket Frame 编解码。
- 客户端 Mask 解码。
- Ping/Pong 心跳帧。
- Close 控制帧。

仓库中的常用模块：

```text
gobwas/ws
├── ws
│   └── Upgrade
├── wsutil
│   ├── ReadClientData
│   └── WriteServerMessage
└── wsflate
    └── compression
```

## 性能特点

在百万级连接和高频消息场景中，关键目标是**减少内存分配、数据复制和 GC 压力**。传统处理过程可能经过多次复制：

```text
socket buffer
    ↓ copy
byte[]
    ↓ copy
message
```

底层协议库允许应用更直接地管理缓冲区和解析过程：

```text
socket buffer
      |
   直接解析
```

这不代表所有操作都会自动“零拷贝”，而是 `gobwas/ws` 提供了更低层的 API，便于调用方减少不必要的分配和复制。

---

<br/>

> <h3 id="gobwasws-与-gorillawebsocket">gobwas/ws 与 gorilla/websocket</h3>

| 对比项   | `gorilla/websocket`         | `gobwas/ws`                        |
| -------- | --------------------------- | ---------------------------------- |
| 定位     | 完整、易用的 WebSocket 封装 | 偏底层的协议工具库                 |
| 使用成本 | 较低                        | 较高                               |
| 控制能力 | 常规连接读写                | 可细粒度控制读写、缓冲区和并发模型 |
| 适用场景 | 中小型服务、快速开发        | 自定义网络栈、高性能网关           |

`gorilla/websocket` 的典型代码：

```go
conn, err := websocket.Upgrade(
	w,
	r,
	nil,
	1024,
	1024,
)
if err != nil {
	return
}

for {
	_, msg, err := conn.ReadMessage()
	if err != nil {
		return
	}
	_ = msg
}
```

常见连接模型：

```text
一个连接
   |
goroutine
   |
read loop
   |
write loop
```

该模式简单稳定，但如果每个连接都绑定独立 goroutine 和较大的缓冲区，百万连接下会带来明显的调度与内存压力。具体压力取决于实现方式，并非 `gorilla/websocket` 强制要求固定的“一连接一 goroutine”。

`gobwas/ws` 的常见使用方式：

```go
conn, _, _, err := ws.UpgradeHTTP(r, w)
if err != nil {
	return
}

msg, op, err := wsutil.ReadClientData(conn)
if err != nil {
	return
}

_ = msg
_ = op
```

应用可以自行控制：

```text
什么时候读
什么时候写
buffer 怎么管理
goroutine 怎么分配
```

**选择原则：**优先根据连接规模、团队维护成本和自定义网络模型决定，不要仅因“性能更高”就直接选择更底层的库。

> <h3 id="gnet-与-gobwasws-的分工">gnet 与 gobwas/ws 的分工</h3>

`gnet` 处理 TCP 事件，但不会自动理解 WebSocket Frame。例如收到以下字节：

```text
81 85 37 fa 21 ...
```

`gobwas/ws` 可以将其解析为：

```text
Frame
opcode = text
payload = "hello"
```

组合关系：

```text
                 Client
                   |
              WebSocket
                   |
                  TCP
                   |
                 gnet
                   |
              gobwas/ws
                   |
             Danmaku Logic
```

这类似 Java 网络栈中的：

```text
Netty
  +
WebSocket Codec
```

## 不要直接混用 `gnet` 与 `ws.UpgradeHTTP`

`ws.UpgradeHTTP()` 面向 `net/http` 的 `http.Request`、`http.ResponseWriter` 和劫持后的 `net.Conn`；`gnet.Conn` 则属于事件驱动连接抽象，二者不能仅靠类型转换直接拼接。

下面的代码只能表达意图，不是完整可运行实现：

```go
// 示意代码：gnet 不是 net/http，不能直接这样调用。
func Upgrade(raw net.Conn) {
	conn, _, _, err := ws.UpgradeHTTP(request, response)
	_ = raw
	_ = conn
	_ = err
}
```

在 `gnet` 中通常需要维护连接状态，并在事件回调里完成以下流程：

```text
TCP 连接建立
      |
读取并缓存 HTTP Header
      |
验证 Upgrade: websocket
      |
计算并返回 101 响应
      |
连接切换为 WebSocket 模式
      |
增量解析 WebSocket Frame
```

`wsutil.ReadClientData()` 适合阻塞式 `io.Reader` 场景；在 `gnet` 的事件循环中直接调用阻塞式读取会破坏事件驱动模型。生产实现应使用适合增量数据的握手与 Frame 解析方式，或选择已经完成 `gnet` 集成的 WebSocket Codec。

## 最小 gnet TCP 服务器

```go
package main

import (
	"log"

	"github.com/panjf2000/gnet/v2"
)

type DanmakuServer struct {
	gnet.BuiltinEventEngine
}

func (s *DanmakuServer) OnBoot(eng gnet.Engine) gnet.Action {
	log.Println("server started")
	return gnet.None
}

func (s *DanmakuServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	log.Println(string(buf))
	return gnet.None
}

func main() {
	server := &DanmakuServer{}

	err := gnet.Run(
		server,
		"tcp://:9000",
		gnet.WithMulticore(true),
	)
	if err != nil {
		panic(err)
	}
}
```

```text

```

注意：这段代码尚未实现 HTTP Upgrade 和 WebSocket Frame 解析。

## 独立 `net/http` Echo 示例

如果不使用 `gnet`，可通过 `net/http + gobwas/ws` 快速构建 WebSocket Echo 服务：

```go
package main

import (
	"net/http"

	"github.com/gobwas/ws"
	"github.com/gobwas/ws/wsutil"
)

func handler(w http.ResponseWriter, r *http.Request) {
	conn, _, _, err := ws.UpgradeHTTP(r, w)
	if err != nil {
		return
	}
	defer conn.Close()

	for {
		msg, err := wsutil.ReadClientText(conn)
		if err != nil {
			return
		}

		println(string(msg))

		if err := wsutil.WriteServerText(conn, msg); err != nil {
			return
		}
	}
}

func main() {
	http.HandleFunc("/ws", handler)
	if err := http.ListenAndServe(":8080", nil); err != nil {
		panic(err)
	}
}
```

客户端发送：

```text
hello
```

服务器返回：

```text
hello
```

> <h3 id="连接与广播设计">连接与广播设计</h3>

## 连接与房间模型

大规模长连接系统不应只依赖一个无分片的全局 `map[string]*websocket.Conn`。连接对象通常至少记录业务标识、底层连接、房间和待发送队列：

```go
type Client struct {
	ID        int64
	Conn      gnet.Conn
	RoomID    int64
	SendQueue chan []byte
}
```

房间模型示意：

```go
type Room struct {
	ID      int64
	Clients sync.Map
}
```

```text
Room: 10001
  |
  +-- Client
  |
  +-- Client
  |
  +-- Client
```

`sync.Map` 只是示例，不一定是高并发房间管理的最优方案。生产环境通常还需要分片、事件循环归属、背压、慢连接淘汰和连接生命周期管理。

## 弹幕消息模型

不要只传递无结构字符串，应定义明确的协议模型：

```go
type Danmaku struct {
	UserID  int64  `json:"uid"`
	RoomID  int64  `json:"room_id"`
	Content string `json:"content"`
	Time    int64  `json:"time"`
}
```

消息示例：

```json
{
  "uid": 10001,
  "room_id": 888,
  "content": "666"
}
```

## 广播模型

直接同步遍历所有连接并写入消息：

```go
for _, client := range clients {
	client.Write(msg)
}
```

在超大房间中容易被慢连接拖住，也缺少背压与批处理机制。更合理的方向是将接收、路由和广播解耦：

```text
Receive
   |
 Kafka
   |
Room Worker
   |
Batch Broadcast
```

房间广播队列示意：

```go
type Room struct {
	Broadcast chan []byte
}
```

```go
func broadcast(room *Room) {
	for msg := range room.Broadcast {
		room.Clients.Range(func(k, v any) bool {
			client := v.(*Client)
			client.Send(msg)
			return true
		})
	}
}
```

该代码只展示队列化思路。生产实现还需处理批量编码、写缓冲复用、队列上限、慢消费者、失败重试、跨节点房间路由和消息有序性。

## 规模估算

假设热门直播间存在 `300 万`在线连接、每秒产生 `10 万`条弹幕，不能简单按 `10 万 × 300 万`逐条同步广播。真实系统通常会采用：

- 房间分片与多级扇出。
- 网关本地广播，避免每条消息重复跨网络传输。
- 批量写入与共享编码结果。
- 热门房间拆分、慢连接治理和背压。
- Kafka 等消息系统进行服务解耦，而不是直接承担每个客户端的最终投递。

> <h3 id="技术选型">技术选型</h3>

## WebSocket 库选择

- **中小项目、快速开发：**优先使用 `gorilla/websocket` 或 `coder/websocket` 等高层库。
- **需要自定义事件循环、缓冲区和协议处理：**考虑 `gobwas/ws`。
- **大规模连接网关：**可采用 `gnet + WebSocket Codec`，但必须正确处理增量握手、Frame 解析、背压和连接状态，不能把阻塞式 API 直接塞进事件循环。

`gobwas/ws` 不是必选项。它的价值在于提供更底层的控制能力，同时也意味着更高的实现和维护成本。

## `gnet` 与 `netpoll`

二者解决的问题不同，不应简单二选一：

- **`gnet`：**适合实现事件驱动的 TCP/WebSocket 长连接网关。
- **`netpoll`：**常作为高性能 RPC/网络库的底层能力，例如与 Kitex 组合用于内部服务通信。

网关链路：

```text
用户
 |
WebSocket
 |
Gateway
```

内部 RPC 链路：

```text
Video Service
      |
User Service
```

```text
Kitex
  |
netpoll
  |
 RPC
```

## 推荐技术栈

| 层级       | 技术方向                                            |
| ---------- | --------------------------------------------------- |
| Gateway    | `gnet/v2 + gobwas/ws` 或成熟的 gnet WebSocket Codec |
| RPC        | `Kitex + netpoll`                                   |
| MQ         | Kafka                                               |
| Cache      | Redis Cluster                                       |
| 分析存储   | ClickHouse                                          |
| 业务数据库 | MySQL，用于用户和视频元数据                         |

最终架构：

```text
gnet
  |
TCP 事件循环
  ↓
gobwas/ws
  |
WebSocket 协议
  ↓
Room Manager
  ↓
Kafka
  ↓
Redis + ClickHouse
```

**核心结论：**`gnet` 负责连接与事件循环，`gobwas/ws` 负责 WebSocket 协议，房间和消息系统负责业务广播；`netpoll` 更适合内部 RPC 网络层。大型实时系统可以同时使用这些组件，但必须按职责分层，而不是将 API 直接硬拼。

> <h2 id="Go实时消息平台架构设计">Go 实时消息平台架构设计</h2>

面向 B 站弹幕、直播聊天室、游戏实时消息、IM 群聊和点赞通知等场景，如果目标包括**千万级 WebSocket 长连接、亿级弹幕数据、毫秒级广播和持续扩展能力**，就不应只设计一个 WebSocket Server，而应建设完整的**实时消息平台（Realtime Messaging Platform）**。

**核心原则：** Gateway 只维护连接和转发消息；Room Worker 负责本地实时广播；Kafka 承担异步解耦和持久化链路；Redis 保存热点状态；ClickHouse 存储海量历史消息。

这套架构将实时广播与异步数据处理分离：消息进入 Gateway 后由 Room Worker 直接广播，同时投递 Kafka，供存储、分析等消费者异步处理。

> <h3 id="Gateway与连接模型">Gateway 与连接模型</h3>

### Gateway 职责

Gateway 只负责：

1. TCP 连接。
2. WebSocket 协议处理。
3. 心跳检测。
4. 登录鉴权。
5. 加入或退出房间。
6. 消息转发。

Gateway 不应直接写数据库、操作 Kafka 或查询完整用户资料，避免连接层被业务逻辑阻塞。可参考以下目录：

```text
gateway/
├── main.go
├── server.go
├── connection.go
├── websocket.go
├── heartbeat.go
├── router.go
└── middleware/
```

### Connection 模型

千万级连接不适合集中存放在一个全局 `map[userID]*Conn` 中，应按 Gateway 实例、房间或分片组织连接，降低锁竞争和单点内存压力。

```go
type Connection struct {
    ID            int64
    UserID        int64
    RoomID        int64
    Conn          gnet.Conn
    SendQueue     chan []byte
    LastHeartbeat int64
}
```

连接管理器可维护房间分片：

```go
type ConnectionManager struct {
    rooms sync.Map
}
```

```text
RoomManager

room:10001
       |
       |
       +-- conn
       |
       +-- conn
       |
       +-- conn
```

实际生产中还需限制 `SendQueue` 容量，并通过连接分片、事件循环归属或单线程房间 Worker 控制并发访问。

> <h3 id="RoomManager与广播模型">Room Manager 与广播模型</h3>

一个视频或直播间对应一个 `room_id`。例如视频 `BV1xxxx` 可映射到 `room:888888`：

```go
type Room struct {
    ID           int64
    Clients      sync.Map
    MessageQueue chan *Message
}
```

热门房间可分配独立 Worker，由单独的 goroutine 处理广播、限流和排序：

```text
热门直播

room worker

goroutine

负责:
- 广播
- 限流
- 排序
```

<br/>

### 广播模型

不要在广播主路径中同步向所有客户端写数据：

```go
for client := range clients {
    client.Write(msg)
}
```

任意慢客户端都可能阻塞整个房间。正确方式是为每个连接维护独立的有界发送队列，广播过程只执行非阻塞投递：

```go
type Connection struct {
    SendQueue chan []byte
}
```

```go
func Broadcast(msg []byte) {
    room.Clients.Range(func(_, v any) bool {
        conn := v.(*Connection)

        select {
        case conn.SendQueue <- msg:
        default:
            // 丢弃慢客户端
        }

        return true
    })
}
```

队列满时可按业务要求丢弃消息、合并消息或断开慢客户端，避免单个连接拖垮整个房间。百万级热门房间还需进一步采用房间分片、广播树或多级 Fan-out，单机遍历所有连接并不足以支撑跨节点广播。

> <h3 id="消息协议与发送流程">消息协议与发送流程</h3>

### Protobuf 二进制协议

大规模实时消息不建议使用 JSON 作为核心传输格式，因为字段名和文本解析会增加带宽及 CPU 消耗。可使用 Protobuf：

```protobuf
message Danmaku {
  int64 user_id = 1;
  int64 room_id = 2;
  string content = 3;
  int64 timestamp = 4;
}
```

```text
protobuf
      |
      |
Go struct
```

客户端通过 WebSocket Binary Frame 发送 Protobuf 字节：

```text
Binary Frame

protobuf bytes
```

而不是发送以下 JSON：

```json
{
  "text": "666"
}
```

实际协议还应包含消息类型、协议版本、请求 ID、压缩标记和载荷长度等信封字段。

### 发送链路

用户发送弹幕后的异步数据链路：

```text
APP
 |
 |
WebSocket
 |
 |
Gateway
 |
 |
Room Worker
 |
 |
Kafka
 |
 |
Consumer
 |
 |
Redis
```

**广播不要经过 Kafka。** Kafka 会增加实时广播延迟，应由 Room Worker 在本地或实时 Fan-out 网络中直接广播；Kafka 负责异步存储、分析和事件分发。

```text
              send

              |
              |

Gateway

              |

Room Worker

              |

100万人连接
```

典型处理顺序：

1. Gateway 完成鉴权、协议解析和基础校验。
2. Room Worker 执行限流、排序并实时广播。
3. 消息异步投递 Kafka。
4. 消费者分别更新热点数据、持久化历史消息和生成分析指标。

> <h3 id="KafkaRedis与ClickHouse">Kafka、Redis 与 ClickHouse</h3>

### Kafka：异步消息总线

Topic：

```text
danmaku_message
```

按照 `room_id` 计算 Partition：

```text
partition = hash(roomID) % N
```

同一个房间的消息进入同一 Partition，可在 Kafka Partition 范围内保持顺序。

```go
type KafkaMessage struct {
    RoomID   int64
    UserID   int64
    Content  string
    Timestamp int64
}
```

---

### Redis：热点状态

亿级弹幕历史数据不宜全部写入 MySQL，可使用 ClickHouse：

CREATE TABLE danmaku_history
(

    user_id UInt64,

ENGINE = MergeTree

为防止刷屏，可使用本地令牌桶与 Redis 分布式限流组合控制：

至少监控以下指标：

- 当前连接数、连接建立和断开速率。
- 各房间消息吞吐量与广播延迟。
- 发送队列长度、队列满次数和慢客户端数量。
- Kafka Producer 延迟、积压量和消费失败率。
- Redis、ClickHouse 的写入延迟与错误率。
- Goroutine 数量、GC、内存和网络流量。

使用 Prometheus 采集指标，OpenTelemetry 记录跨服务链路，并支持优雅关闭和连接迁移。

3. 为什么这样改
原有实现存在两个主要扩展瓶颈：
- 每个 Gateway 都订阅全平台广播频道，实例越多，Redis 流量和反序列化工作量越大。
- MySQL 单表不能作为亿万至百亿级弹幕历史的长期唯一存储。
新链路形成以下职责边界：
实时广播：
Client -> gnet Gateway -> local room broadcast
                       -> Redis room channel -> other subscribed gateways

可靠历史：
MySQL transaction -> Outbox -> Kafka
                           -> ClickHouse complete history
                           -> Redis recent Stream
这样可以通过增加 Gateway Pod 横向扩展连接数，通过 Kafka partition 和 Consumer 扩展历史写入吞吐，并将大规模时间线查询转移到 ClickHouse。

> <h3 id="连接与房间广播">连接与房间广播</h3>

### Connection

连接对象保存业务身份、底层连接、最后活跃时间和发送队列：

```go
package connection

import (
	"sync/atomic"

	"github.com/panjf2000/gnet/v2"
)

var counter uint64

type Connection struct {
	ID         uint64
	UserID     int64
	RoomID     int64
	Conn       gnet.Conn
	SendQueue  chan []byte
	LastActive int64
	Close      chan struct{}
}

func New(c gnet.Conn) *Connection {
	return &Connection{
		ID:        atomic.AddUint64(&counter, 1),
		Conn:      c,
		SendQueue: make(chan []byte, 1024),
		Close:     make(chan struct{}),
	}
}
```

不应在房间广播路径中对每个慢客户端直接执行同步写：

```go
conn.Write(msg)
```

若用户 A 的网络写入耗时 `100ms`，同步广播可能拖慢整个房间。推荐链路：

```text
Room
  |
SendQueue
  |
write loop
  |
socket
```

发送队列必须有界，并定义慢客户端策略，例如丢弃消息、断开连接或按优先级降级，否则积压最终会转化为内存问题。

### Connection Manager

```go
package connection

import "sync"

type Manager struct {
	conns sync.Map
}

func NewManager() *Manager {
	return &Manager{}
}

func (m *Manager) Add(c *Connection) {
	m.conns.Store(c.ID, c)
}

func (m *Manager) Remove(id uint64) {
	m.conns.Delete(id)
}

func (m *Manager) Range(fn func(*Connection)) {
	m.conns.Range(func(_, value any) bool {
		fn(value.(*Connection))
		return true
	})
}
```

### Room 与 Room Manager

一个视频或直播间映射为一个 `Room`，例如 `BV1xxx -> roomID=10001`。

```go
package room

import "sync"

type Client interface {
	Send([]byte) error
}

type Room struct {
	ID      int64
	clients sync.Map
}

func NewRoom(id int64) *Room {
	return &Room{ID: id}
}

func (r *Room) Join(id uint64, client Client) {
	r.clients.Store(id, client)
}

func (r *Room) Leave(id uint64) {
	r.clients.Delete(id)
}

func (r *Room) Broadcast(data []byte) {
	r.clients.Range(func(_, value any) bool {
		client := value.(Client)
		if err := client.Send(data); err != nil {
			// TODO remove
		}
		return true
	})
}

type Manager struct {
	rooms sync.Map
}

func NewManager() *Manager {
	return &Manager{}
}

func (m *Manager) Get(id int64) *Room {
	value, _ := m.rooms.LoadOrStore(id, NewRoom(id))
	return value.(*Room)
}
```

若 `Room` 直接保存 `*connection.Connection`，使用有界 `SendQueue` 时可采用非阻塞写入：

```go
func (r *Room) Broadcast(msg []byte) {
	r.Clients.Range(func(_, value any) bool {
		conn := value.(*connection.Connection)

		select {
		case conn.SendQueue <- msg:
		default:
			// 慢客户端丢弃
		}

		return true
	})
}
```

### WebSocket Upgrade 状态

`gobwas/ws` 常见接口基于 `net/http` 或 `net.Conn`，而 `gnet` 的入口是 TCP EventLoop：

```text
TCP EventLoop
  |
OnTraffic()
```

因此需要在事件回调中自行维护协议状态：

```text
HTTP Upgrade
      ↓
101 Switching Protocols
      ↓
WebSocket Frame
```

```go
type ConnState int

const (
	HTTPUpgrade ConnState = iota
	WebSocketConnected
)

type Client struct {
	State  ConnState
	Conn   gnet.Conn
	UserID int64
	RoomID int64
}
```

### Upgrade Accept Key

```go
package websocket

import (
	"crypto/sha1"
	"encoding/base64"
)

func AcceptKey(key string) string {
	h := sha1.New()
	h.Write([]byte(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))
	return base64.StdEncoding.EncodeToString(h.Sum(nil))
}
```

响应格式：

```go
func BuildUpgradeResponse(key string) []byte {
	accept := AcceptKey(key)

	return []byte(fmt.Sprintf(
		"HTTP/1.1 101 Switching Protocols\r\n"+
			"Upgrade: websocket\r\n"+
			"Connection: Upgrade\r\n"+
			"Sec-WebSocket-Accept: %s\r\n\r\n",
		accept,
	))
}
```

生产实现还必须处理 HTTP 请求分片、Header 大小限制、大小写、协议版本、超时和非法请求，不能只用 `bytes.Contains(data, []byte("Upgrade: websocket"))` 判断。

### WebSocket Frame

Upgrade 后的数据是 WebSocket Frame，而不是裸 protobuf：

```text
WebSocket Frame
      |
Frame 解码、反掩码、分片聚合
      |
protobuf payload
```

原示例中的：

```go
func ReadMessage(conn net.Conn) ([]byte, error) {
	return wsutil.ReadClientData(conn)
}
```

不能直接套用到所有 `gnet.Conn` 处理流程；实际接入需要适配 `gnet` 的缓冲区和事件驱动模型，并正确处理半包、粘包、控制帧、分片帧、客户端掩码和最大消息长度。

### OnTraffic 数据链路

```go
func (s *Server) OnTraffic(c gnet.Conn) error {
	data, err := c.Next(-1)
	if err != nil {
		return err
	}

	// TODO websocket upgrade 与 frame 解析
	payload, err := parseFrame(data)
	if err != nil {
		return err
	}

	msg, err := DecodeMessage(payload)
	if err != nil {
		return err
	}

	room := s.Rooms.Get(int64(msg.RoomId))
	room.Broadcast(data)

	// Kafka 写入需要移出 EventLoop，避免阻塞网络事件处理。
	return nil
}
```

> <h3 id="心跳关闭与性能优化">心跳、关闭与性能优化</h3>

### 心跳检测

不能为百万连接分别创建 `time.After()` 或独立 Timer。原始骨架使用全量扫描：

```text
Ticker
  |
每 5 秒扫描
  |
connection.LastActive
```

```go
func Check(manager *connection.Manager) {
	now := time.Now().Unix()

	manager.Range(func(c *connection.Connection) {
		if now-c.LastActive > 60 {
			close(c.Close)
		}
	})
}
```

全量扫描实现简单，但连接规模较大时会形成周期性 CPU 峰值。生产环境可使用分桶扫描或时间轮，例如 `github.com/RussellLuo/timingwheel`。

### 优雅关闭

```text
SIGTERM
  |
停止 accept
  |
标记 Gateway draining
  |
等待写队列和连接退出
  |
关闭 Kafka Producer
  |
退出
```

```go
ctx, cancel := signal.NotifyContext(
	context.Background(),
	os.Interrupt,
	syscall.SIGTERM,
)
defer cancel()

<-ctx.Done()
gateway.Shutdown()
```

实际关闭流程需要设置最大等待时间，避免慢连接或外部依赖导致进程无法退出。

### 百万连接优化原则

**1. 避免每连接一个常驻 goroutine**

```go
go read(conn)
```

百万连接对应百万级 goroutine，会带来栈内存和调度压力。`gnet` 使用 EventLoop 管理大量连接：

```text
CPU Core
  |
EventLoop
  |
Connections
```

**2. 使用对象池时明确所有权**

```go
var pool = sync.Pool{
	New: func() any {
		return make([]byte, 4096)
	},
}
```

对象池可减少部分分配和 GC，但广播数据异步写入时不能提前复用底层字节切片，否则会产生数据竞争或内容污染。

**3. Room 分片**

单个 `sync.Map` 只是骨架。高并发场景可按 `roomID` 将房间分散到多个 shard：

```text
RoomShard[1024]
      |
 roomID hash
      ↓
    shard
      ↓
     room
```

**4. 处理广播放大效应**

房间广播复杂度与本节点订阅人数近似成正比。热门房间需要批量编码、共享只读 payload、分层 fan-out、背压和慢消费者治理。

> <h3 id="Kafka-与多-Gateway-路由">Kafka 与多 Gateway 路由</h3>

Gateway 不应在网络事件循环中直接写数据库，也不应同步等待 Kafka：

```text
Client
  |
Gateway
  +-----------------+
  |                 |
Local Broadcast   Producer Queue
                    |
               Kafka Worker
                    |
             Danmaku Service
```

### Kafka Producer 骨架

```go
package kafka

import (
	"context"

	"github.com/segmentio/kafka-go"
)

type Producer struct {
	writer *kafka.Writer
}

func NewProducer() *Producer {
	return &Producer{
		writer: &kafka.Writer{
			Addr:     kafka.TCP("localhost:9092"),
			Topic:    "danmaku-message",
			Balancer: &kafka.Hash{},
		},
	}
}

func (p *Producer) Send(ctx context.Context, key, value []byte) error {
	return p.writer.WriteMessages(ctx, kafka.Message{
		Key:   key,
		Value: value,
	})
}

func (p *Producer) Close() error {
	return p.writer.Close()
}
```

若在 `OnTraffic` 中直接调用 `Send()`，网络 EventLoop 可能被 Broker 延迟阻塞。生产链路应使用有界队列和 Producer Worker，并定义队列满、重试、超时和失败降级策略：

```text
Gateway
  |
bounded channel
  |
Kafka Producer Worker
```

### Partition 与房间顺序

同一房间的消息需要进入同一 partition，才能利用 Kafka partition 内有序的特性：

```text
partition = hash(room_id) % partition_count
```

```go
func Partition(roomID int64, partitionCount uint32) int {
	h := fnv.New32a()
	_ = binary.Write(h, binary.LittleEndian, roomID)
	return int(h.Sum32() % partitionCount)
}
```

Producer 也可以将 `roomID` 作为 Key，由 `Hash` Balancer 选择 partition：

```go
err := writer.WriteMessages(ctx, kafka.Message{
	Key:   []byte(strconv.FormatInt(roomID, 10)),
	Value: data,
})
```

```text
partition 1
  room100
  room200

partition 2
  room300
```

Kafka 只保证 partition 内的记录顺序。Consumer 若对同一 partition 再并发处理，仍需自行保证同一房间的处理顺序。

### 多 Gateway 广播

```text
          LB
           |
 +---------+---------+
 |         |         |
GW1       GW2       GW3
```

用户 A 连接 `GW1`、用户 B 连接 `GW3` 时，`GW1` 的本地 Room 无法直接触达 `GW3` 上的连接，因此需要跨节点消息分发。

一种思路是计算 Room Owner：

```text
owner = hash(roomID) % gateway_count

room888
   |
  hash
   ↓
  GW3
```

```go
func Owner(roomID int64) string {
	index := hash(roomID) % len(gateways)
	return gateways[index]
}
```

Gateway 注册信息可存放在 Redis：

```text
gateway:list

gw1 -> 10.0.0.1
gw2 -> 10.0.0.2
gw3 -> 10.0.0.3
```

跨节点广播链路：

```text
Client
  |
GW1
  |
Room Router
  |
Kafka broadcast topic
  |
相关 Gateway Consumer
  |
Local Room
  |
WebSocket Clients
```

> **关键修正：** 若某房间的客户端同时分布在多个 Gateway，仅让单一 Owner Gateway 做本地广播并不能触达其他节点。还需要维护房间到 Gateway 的订阅关系，或让所有订阅该房间的 Gateway 消费对应广播事件。

动态 Gateway 列表直接使用 `hash(roomID) % gateway_count` 会在节点增减时造成大规模重映射，生产环境通常使用一致性哈希、固定虚拟分片或独立路由表。

### WebSocket 压测

`wrk` 主要面向 HTTP request/response，不适合直接模拟大量长期 WebSocket 连接。可编写 Go 压测客户端：

```go
package main

import (
	"log"
	"net/url"
	"sync"

	"github.com/gorilla/websocket"
)

func main() {
	var wg sync.WaitGroup

	for i := 0; i < 100000; i++ {
		wg.Add(1)

		go func() {
			defer wg.Done()

			u := url.URL{
				Scheme: "ws",
				Host:   "127.0.0.1:9000",
				Path:   "/ws",
			}

			conn, _, err := websocket.DefaultDialer.Dial(u.String(), nil)
			if err != nil {
				log.Printf("dial: %v", err)
				return
			}
			defer conn.Close()

			for {
				if _, _, err = conn.ReadMessage(); err != nil {
					return
				}
			}
		}()
	}

	wg.Wait()
}
```

```bash
go run stress/main.go
```

单台压测机通常会先受本机端口、文件描述符、内存、CPU 和网卡限制，百万连接压测需要多台压测机并校验服务端和客户端两侧瓶颈。

### 关注指标

- **连接：** 当前连接数、建连成功率、断连率、握手延迟。
- **资源：** CPU、RSS、每连接内存、GC、goroutine、文件描述符。
- **消息：** 入站/出站吞吐、广播 fan-out、队列长度、丢弃数。
- **延迟：** P50/P95/P99 端到端延迟。
- **依赖：** Kafka 发送耗时、失败率、重试数和积压量。

```bash
ss -ant | grep ':9000' | wc -l

free -m
```

消息中可加入 `send_time`，通过 `receive_time - send_time` 计算端到端延迟。跨机器测试前必须同步时钟。

WebSocket 应用层心跳

实现内容：
- 服务端每隔 20s 向已升级连接发送 WebSocket Ping。
- 连接每次收到有效入站流量时更新最后活动时间。
- 连续 60s 没有任何入站帧的连接将被关闭。
- Ping 发送失败的连接也会被关闭。

准确的连接容量计数
修复了关闭期间连接计数可能变为负数的问题。
现在每个连接具有独立的 counted 原子状态：
- OnOpen 时只计数一次。
- OnClose 通过 CompareAndSwap 只释放一次。
- 即使连接在网关未就绪、超过连接上限或关闭过程中被拒绝，也不会重复减计数。
Redis 房间订阅状态机
原有逻辑存在以下竞态：
最后一个连接离开
    -> 将 unsubscribe 放入异步队列
    -> 新连接重新加入并订阅
    -> 旧 unsubscribe 延迟执行
    -> 活跃房间被错误退订
现已改成带 generation 的房间订阅状态机：
- 每次订阅状态变化都会推进代次。
- 异步退订命令携带对应代次。
- 执行退订前重新检查：
- 代次是否仍然匹配。
- 本地引用是否仍为零。
- 房间是否处于已订阅状态。
- 旧退订命令不能再移除已经重新加入的房间。
- 退订队列满时保留多余订阅，不阻塞 gnet event-loop。
移除 Redis I/O 全局锁阻塞
原有首连接订阅操作在持有全局 refsMu 时执行 Redis 网络 I/O，可能导致：
- 某个房间订阅变慢。
- 所有其他新房间握手一起等待。
- 重连突刺时 WebSocket 握手尾延迟扩大。
现在：
- Redis Subscribe 不再持有全局引用锁。
- 同一个房间的并发首连接共享一次订阅结果。
- 不同房间可以并行完成订阅。
- 等待订阅结果的连接支持 context 取消。
- Redis 订阅失败不会将房间误标记为成功。
房间路由就绪状态
Redis Pub/Sub 循环不再静默退出：
- 路由器记录运行状态和退出错误。
- Server.Ready() 同时检查 gnet 和房间路由器。
- Pub/Sub 消息通道异常关闭时，网关会转为未就绪。
- Redis 退订失败时，路由器会记录错误并退出。
- Kubernetes readiness probe 可据此摘除失去跨节点广播能力的实例。
Kafka 毒消息处理

部署文档
部署文档增加心跳约束：
- 默认 Ping 间隔为 20s。
- 默认活动超时为 60s。
- Ingress/LB 空闲超时建议设置为 90s 以上。
- heartbeat_timeout 必须至少是 heartbeat_interval 的两倍。
- 明确心跳扫描不采用每连接 timer/goroutine。
3. 修改原因
本轮处理的是三个可能直接形成生产事故的问题：
1. 没有应用层心跳时，半开连接可能长期占用文件描述符、房间成员、内存和连接额度。
2. 延迟执行的旧退订可能导致活跃网关失去某个房间的跨实例弹幕。
3. 一条永久损坏的 Kafka 消息可能让整个 partition 的 ClickHouse 和 Redis 投影停止推进。
这些问题都无法仅靠增加服务器数量解决，必须在应用层修复正确性和失败处理。
4. 准确性检查
已确认：
- 心跳使用固定 ticker，不产生每连接 timer。
- 心跳扫描不会在房间锁内关闭连接。
- Pong、Ping、文本和其他入站流量都会刷新活动时间。
- 未完成 WebSocket Upgrade 的连接不会进入房间心跳扫描。
- 连接计数通过原子状态保证只释放一次。
- Redis 网络 I/O 不再持有全局房间引用锁。
- 同房间并发首连接不会重复独立维护订阅状态。
- 旧退订代次不能匹配重新加入后的房间。
- 房间仍有本地连接时不会执行退订。
- Pub/Sub 循环异常退出会影响网关 readiness。
- Kafka JSON 和稳定字段错误被标记为终止错误。
- ClickHouse、Redis 等基础设施错误没有被错误标记为终止错误。
- git diff --check 通过。
- 未新增密钥、令牌、连接密码或临时构建产物。
5. 潜在影响
- 网关现在会主动关闭连续 60s 没有入站流量的客户端。
- 标准 WebSocket 客户端通常会自动回复 Pong；自定义客户端必须正确响应服务端 Ping。
- Ingress 或负载均衡器的 WebSocket 空闲超时必须高于应用心跳超时。
- Redis Pub/Sub 循环异常后，网关会变为未就绪，需要 Kubernetes readiness probe 正确配置才能自动摘流。
- Kafka 永久数据错误将进入 DLQ 并推进 offset，生产必须为 DLQ 配置告警和人工处理流程。
- 当前心跳扫描的复杂度仍为每个周期遍历本实例所有房间成员。它避免了百万 timer，但在真实百万连接环境中仍需通过压测确定合理扫描周期和单 Pod 连接上限。
- 本轮没有实现 WebSocket 分片帧重组、完整 Close ACK 等待、Redis recent TTL 或 ClickHouse 显式查询去重，这些仍是后续改进项。
- 当前只能说明完成了高并发架构和故障处理优化，不能声称已经通过百万或千万连接实测。
