> <h2 id="B站级弹幕系统设计V1">B站级弹幕系统设计V1</h2>

目标：使用 Go 实现仿 B 站、斗鱼、虎牙的弹幕系统，支撑**千万并发连接和亿级弹幕数据**。

核心不在于单个 WebSocket 库，而在于：**连接模型、房间广播模型、消息削峰、冷热数据分离**。

---

<br/>

> <h3 id="Redis的用途">Redis 的用途</h3>

Redis 不保存全部弹幕，主要用于热门房间状态和最近弹幕等热数据。

## 热门房间状态

例如，使用 `room:10001` 保存房间在线人数和最后消费位置：

```text
room:10001

{
 online:5000000,
 last_cursor:123456
}
```

## 最近弹幕

可使用 `ZSET` 保存最近一段时间的弹幕：

```text
danmaku:10001

score=time
value=json
```

写入示例：

```text
ZADD danmaku:10001 1720000000 msg
```

只保留最近 5 分钟的数据，历史弹幕交给持久化存储。

---

<br/>

> <h3 id="亿级弹幕存储">亿级弹幕存储</h3>

不要使用 MySQL 单表保存十亿级弹幕。例如：

```text
danmaku

id
danmu_id // 字符串
video_id
user_id
content

10亿行
```

单表达到该规模后，查询和维护成本会非常高。推荐进行冷热数据分离：

- **热数据：** Redis。
- **历史数据：** ClickHouse。

ClickHouse 历史表：

```text
danmaku_history
```

主要字段：

```text
video_id
user_id
content
create_time
```

按月份分区：

```sql
PARTITION BY month(create_time)
```

按视频和创建时间排序：

```sql
ORDER BY
(
 video_id,
 create_time
)
```

该结构适合查询视频回放弹幕。

---

<br/>

> <h3 id="网络模型">网络模型</h3>

B 站级弹幕系统可采用以下网络与消息链路：

```text
Linux

epoll
 |
gnet
 |
gobwas/ws
 |
Room Engine
 |
Kafka
```

Go WebSocket 接入层选择：

```text
gnet + gobwas/ws
```

- `gnet` 提供基于 Reactor 模型的高性能事件驱动网络能力。
- `gobwas/ws` 负责 WebSocket 协议处理。
- `Room Engine` 负责房间管理和广播。
- `Kafka` 负责消息削峰和异步解耦。

---

<br/>

> <h3 id="千万连接的机器规模">千万连接的机器规模</h3>

单机经过系统参数和程序优化后，可承载约 `10万~50万` WebSocket 连接，实际容量取决于消息频率、内存占用、广播模型和硬件配置。

千万连接需要 Gateway 集群。例如使用 100 台 Gateway，每台承载 10 万连接：

```text
10,000,000 users

        |

100 gateway

每台:
100,000 connections
```

> <h3 id="推荐方案">推荐方案</h3>

| 模块         | 技术选型           |
| ------------ | ------------------ |
| WebSocket 层 | `gobwas/ws`        |

| 消息队列     | `Kafka`            |

| 历史弹幕     | `ClickHouse`       |
| 服务发现     | `Nacos` / `Consul` |

```text
                  |
          +---------------+

          +---------------+

                  |

                  |
```

```text
                   |
```

> <h2 id="gobwasws-与-gnet-构建高性能-websocket-网关">gobwas/ws 与 gnet 构建高性能 WebSocket 网关</h2>

`gobwas/ws` 是 Go 的高性能 WebSocket 协议库。它不像 `gorilla/websocket` 那样强调完整、易用的连接封装，而是提供更接近底层 TCP 的协议升级、帧解析和读写能力。

在弹幕、直播间聊天和大规模长连接网关中，各层职责通常是：

- **`gnet`：**负责高性能网络事件循环和 TCP 连接管理。
- **`gobwas/ws`：**负责 WebSocket Upgrade、Frame、Mask、Ping/Pong 和 Close 等协议处理。
- **业务层：**负责用户、房间、消息路由、弹幕广播和数据存储。

```text
TCP 连接
   |
WebSocket 协议解析
   |
业务消息
```

完整链路示意：

```text
                 APP
                  |
             WebSocket
                  |
        +----------------+
        | Load Balancer  |
        +----------------+
                  |
        +----------------+
        | gnet Gateway   |
        +----------------+
                  |
             gobwas/ws
                  |
            Room Manager
                  |
               Kafka
                  |
          Danmaku Service
                  |
       Redis + ClickHouse
```

<br/>

> <h3 id="gobwasws-的定位">gobwas/ws 的定位</h3>

## WebSocket 协议流程

客户端首先发送 HTTP Upgrade 请求：

```http
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: xxx
```

服务器返回 `101 Switching Protocols`：

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: xxx
```

升级完成后，连接不再传输普通 HTTP 消息，而是在 TCP 长连接上持续传输 WebSocket Frame：

```text
TCP 长连接

client
  |
server

frame frame frame
```

例如一条弹幕：

```json
{
  "userid": 10001,
  "text": "666"
}
```

实际会封装为：

```text
WebSocket Frame

+---------+
| header  |
+---------+
| payload |
+---------+
```

`gobwas/ws` 主要处理：

- HTTP Upgrade。
- WebSocket Frame 编解码。
- 客户端 Mask 解码。
- Ping/Pong 心跳帧。
- Close 控制帧。

仓库中的常用模块：

```text
gobwas/ws
├── ws
│   └── Upgrade
├── wsutil
│   ├── ReadClientData
│   └── WriteServerMessage
└── wsflate
    └── compression
```

## 性能特点

在百万级连接和高频消息场景中，关键目标是**减少内存分配、数据复制和 GC 压力**。传统处理过程可能经过多次复制：

```text
socket buffer
    ↓ copy
byte[]
    ↓ copy
message
```

底层协议库允许应用更直接地管理缓冲区和解析过程：

```text
socket buffer
      |
   直接解析
```

这不代表所有操作都会自动“零拷贝”，而是 `gobwas/ws` 提供了更低层的 API，便于调用方减少不必要的分配和复制。

---

<br/>

> <h3 id="gobwasws-与-gorillawebsocket">gobwas/ws 与 gorilla/websocket</h3>

| 对比项   | `gorilla/websocket`         | `gobwas/ws`                        |
| -------- | --------------------------- | ---------------------------------- |
| 定位     | 完整、易用的 WebSocket 封装 | 偏底层的协议工具库                 |
| 使用成本 | 较低                        | 较高                               |
| 控制能力 | 常规连接读写                | 可细粒度控制读写、缓冲区和并发模型 |
| 适用场景 | 中小型服务、快速开发        | 自定义网络栈、高性能网关           |

`gorilla/websocket` 的典型代码：

```go
conn, err := websocket.Upgrade(
	w,
	r,
	nil,
	1024,
	1024,
)
if err != nil {
	return
}

for {
	_, msg, err := conn.ReadMessage()
	if err != nil {
		return
	}
	_ = msg
}
```

常见连接模型：

```text
一个连接
   |
goroutine
   |
read loop
   |
write loop
```

该模式简单稳定，但如果每个连接都绑定独立 goroutine 和较大的缓冲区，百万连接下会带来明显的调度与内存压力。具体压力取决于实现方式，并非 `gorilla/websocket` 强制要求固定的“一连接一 goroutine”。

`gobwas/ws` 的常见使用方式：

```go
conn, _, _, err := ws.UpgradeHTTP(r, w)
if err != nil {
	return
}

msg, op, err := wsutil.ReadClientData(conn)
if err != nil {
	return
}

_ = msg
_ = op
```

应用可以自行控制：

```text
什么时候读
什么时候写
buffer 怎么管理
goroutine 怎么分配
```

**选择原则：**优先根据连接规模、团队维护成本和自定义网络模型决定，不要仅因“性能更高”就直接选择更底层的库。

> <h3 id="gnet-与-gobwasws-的分工">gnet 与 gobwas/ws 的分工</h3>

`gnet` 处理 TCP 事件，但不会自动理解 WebSocket Frame。例如收到以下字节：

```text
81 85 37 fa 21 ...
```

`gobwas/ws` 可以将其解析为：

```text
Frame
opcode = text
payload = "hello"
```

组合关系：

```text
                 Client
                   |
              WebSocket
                   |
                  TCP
                   |
                 gnet
                   |
              gobwas/ws
                   |
             Danmaku Logic
```

这类似 Java 网络栈中的：

```text
Netty
  +
WebSocket Codec
```

## 不要直接混用 `gnet` 与 `ws.UpgradeHTTP`

`ws.UpgradeHTTP()` 面向 `net/http` 的 `http.Request`、`http.ResponseWriter` 和劫持后的 `net.Conn`；`gnet.Conn` 则属于事件驱动连接抽象，二者不能仅靠类型转换直接拼接。

下面的代码只能表达意图，不是完整可运行实现：

```go
// 示意代码：gnet 不是 net/http，不能直接这样调用。
func Upgrade(raw net.Conn) {
	conn, _, _, err := ws.UpgradeHTTP(request, response)
	_ = raw
	_ = conn
	_ = err
}
```

在 `gnet` 中通常需要维护连接状态，并在事件回调里完成以下流程：

```text
TCP 连接建立
      |
读取并缓存 HTTP Header
      |
验证 Upgrade: websocket
      |
计算并返回 101 响应
      |
连接切换为 WebSocket 模式
      |
增量解析 WebSocket Frame
```

`wsutil.ReadClientData()` 适合阻塞式 `io.Reader` 场景；在 `gnet` 的事件循环中直接调用阻塞式读取会破坏事件驱动模型。生产实现应使用适合增量数据的握手与 Frame 解析方式，或选择已经完成 `gnet` 集成的 WebSocket Codec。

```go
	}

}
```

> <h3 id="连接与广播设计">连接与广播设计</h3>

## 连接与房间模型

大规模长连接系统不应只依赖一个无分片的全局 `map[string]*websocket.Conn`。连接对象通常至少记录业务标识、底层连接、房间和待发送队列：

```go
type Client struct {
	ID        int64
	Conn      gnet.Conn
	RoomID    int64
	SendQueue chan []byte
}
```

房间模型示意：

```go
type Room struct {
	ID      int64
	Clients sync.Map
}
```

```text
Room: 10001
  |
  +-- Client
  |
  +-- Client
  |
  +-- Client
```

`sync.Map` 只是示例，不一定是高并发房间管理的最优方案。生产环境通常还需要分片、事件循环归属、背压、慢连接淘汰和连接生命周期管理。

## 弹幕消息模型

不要只传递无结构字符串，应定义明确的协议模型：

```go
type Danmaku struct {
	UserID  int64  `json:"uid"`
	RoomID  int64  `json:"room_id"`
	Content string `json:"content"`
	Time    int64  `json:"time"`
}
```

消息示例：

```json
{
  "uid": 10001,
  "room_id": 888,
  "content": "666"
}
```

## 广播模型

直接同步遍历所有连接并写入消息：

```go
for _, client := range clients {
	client.Write(msg)
}
```

在超大房间中容易被慢连接拖住，也缺少背压与批处理机制。更合理的方向是将接收、路由和广播解耦：

```text
Receive
   |
 Kafka
   |
Room Worker
   |
Batch Broadcast
```

房间广播队列示意：

```go
type Room struct {
	Broadcast chan []byte
}
```

```go
func broadcast(room *Room) {
	for msg := range room.Broadcast {
		room.Clients.Range(func(k, v any) bool {
			client := v.(*Client)
			client.Send(msg)
			return true
		})
	}
}
```

该代码只展示队列化思路。生产实现还需处理批量编码、写缓冲复用、队列上限、慢消费者、失败重试、跨节点房间路由和消息有序性。

## 规模估算

假设热门直播间存在 `300 万`在线连接、每秒产生 `10 万`条弹幕，不能简单按 `10 万 × 300 万`逐条同步广播。真实系统通常会采用：

- 房间分片与多级扇出。
- 网关本地广播，避免每条消息重复跨网络传输。
- 批量写入与共享编码结果。
- 热门房间拆分、慢连接治理和背压。
- Kafka 等消息系统进行服务解耦，而不是直接承担每个客户端的最终投递。

> <h3 id="技术选型">技术选型</h3>

## WebSocket 库选择

- **中小项目、快速开发：**优先使用 `gorilla/websocket` 或 `coder/websocket` 等高层库。
- **需要自定义事件循环、缓冲区和协议处理：**考虑 `gobwas/ws`。
- **大规模连接网关：**可采用 `gnet + WebSocket Codec`，但必须正确处理增量握手、Frame 解析、背压和连接状态，不能把阻塞式 API 直接塞进事件循环。

`gobwas/ws` 不是必选项。它的价值在于提供更底层的控制能力，同时也意味着更高的实现和维护成本。

## `gnet` 与 `netpoll`

二者解决的问题不同，不应简单二选一：

- **`gnet`：**适合实现事件驱动的 TCP/WebSocket 长连接网关。
- **`netpoll`：**常作为高性能 RPC/网络库的底层能力，例如与 Kitex 组合用于内部服务通信。

网关链路：

```text
用户
 |
WebSocket
 |
Gateway
```

内部 RPC 链路：

```text
Video Service
      |
User Service
```

```text
Kitex
  |
netpoll
  |
 RPC
```

## 推荐技术栈

| 层级       | 技术方向                                            |
| ---------- | --------------------------------------------------- |
| Gateway    | `gnet/v2 + gobwas/ws` 或成熟的 gnet WebSocket Codec |
| RPC        | `Kitex + netpoll`                                   |
| MQ         | Kafka                                               |
| Cache      | Redis Cluster                                       |
| 分析存储   | ClickHouse                                          |
| 业务数据库 | MySQL，用于用户和视频元数据                         |

最终架构：

```text
gnet
  |
TCP 事件循环
  ↓
gobwas/ws
  |
WebSocket 协议
  ↓
Room Manager
  ↓
Kafka
  ↓
Redis + ClickHouse
```

**核心结论：**`gnet` 负责连接与事件循环，`gobwas/ws` 负责 WebSocket 协议，房间和消息系统负责业务广播；`netpoll` 更适合内部 RPC 网络层。大型实时系统可以同时使用这些组件，但必须按职责分层，而不是将 API 直接硬拼。

**3. 为什么这样改**

原实现的主要风险是：

- 所有视频共享一把 `roomsMu`。
- 热门房间每次广播都会遍历房间并复制完整目标列表。
- 百万连接房间会产生与在线人数线性增长的短命切片。
- 热门房间广播会阻塞其他视频的加入和离开。
- 慢客户端的积压预算不可配置。
- 单个恶意或异常客户端可以持续占用共享命令队列和数据库连接。
- 新记录插入后还需要经过宽字符串二级索引回读。

修改后：

- 不同视频大概率落入不同目录锁，跨视频竞争显著降低。
- 广播不再创建 O(N) 目标快照，降低大房间的 GC 和内存带宽压力。
- 长尾视频不会因每房间预分配大量分片对象产生反向内存放大。
- 限流在 gnet event-loop 内完成，不访问 Redis、MySQL，也不创建额外 goroutine。
- 过载压力不会无条件传导到 worker 队列和 MySQL。
- `LastInsertId()` 回读命中 InnoDB 聚簇主键，更适合亿级热表。

8. 亿级以上历史数据采用 MySQL 热数据分片、ClickHouse 冷历史和有界归档，不依赖单张 InnoDB 表无限增长。
9. 使用 10 万、50 万、100 万连接分阶段压测，采集单连接内存、广播 P99、GC、mutex/block profile、Redis 带宽和 MySQL 锁等待，再决定单机安全连接上限。

> <h2 id="Go实时消息平台架构设计">Go 实时消息平台架构设计</h2>

面向 B 站弹幕、直播聊天室、游戏实时消息、IM 群聊和点赞通知等场景，如果目标包括**千万级 WebSocket 长连接、亿级弹幕数据、毫秒级广播和持续扩展能力**，就不应只设计一个 WebSocket Server，而应建设完整的**实时消息平台（Realtime Messaging Platform）**。

**核心原则：** Gateway 只维护连接和转发消息；Room Worker 负责本地实时广播；Kafka 承担异步解耦和持久化链路；Redis 保存热点状态；ClickHouse 存储海量历史消息。

```text
                         Client
```

这套架构将实时广播与异步数据处理分离：消息进入 Gateway 后由 Room Worker 直接广播，同时投递 Kafka，供存储、分析等消费者异步处理。

> <h3 id="工程与服务拆分">工程与服务拆分</h3>

生产环境不建议使用单体架构，可按业务职责拆分：

```text
├── danmaku-service

├── online-service
├── analytics-service
├── common
└── deploy
```

- **Gateway：** 基于 `gnet`、`gobwas/ws` 维护海量长连接。
- **Room Service：** 基于 `goroutine + channel` 管理房间状态、消息排序和广播。
- **Danmaku Service：** 消费 Kafka 消息并写入 ClickHouse 等存储。
- **User Service：** 提供用户、鉴权及相关业务能力。
- **Online Service：** 统计在线连接数或近似去重用户数。
- **Analytics Service：** 异步消费消息并完成指标分析。

> <h3 id="Gateway与连接模型">Gateway 与连接模型</h3>

### Gateway 职责

Gateway 只负责：

1. TCP 连接。
2. WebSocket 协议处理。
3. 心跳检测。
4. 登录鉴权。
5. 加入或退出房间。
6. 消息转发。

Gateway 不应直接写数据库、操作 Kafka 或查询完整用户资料，避免连接层被业务逻辑阻塞。可参考以下目录：

```text
gateway/
├── main.go
├── server.go
├── connection.go
├── websocket.go
├── heartbeat.go
├── router.go
└── middleware/
```

---
<br/>

### Connection 模型

千万级连接不适合集中存放在一个全局 `map[userID]*Conn` 中，应按 Gateway 实例、房间或分片组织连接，降低锁竞争和单点内存压力。

```go
type Connection struct {
    ID            int64
    UserID        int64
    RoomID        int64
    Conn          gnet.Conn
    SendQueue     chan []byte
    LastHeartbeat int64
}
```

连接管理器可维护房间分片：

```go
type ConnectionManager struct {
    rooms sync.Map
}
```

```text
RoomManager

room:10001
       |
       |
       +-- conn
       |
       +-- conn
       |
       +-- conn
```

实际生产中还需限制 `SendQueue` 容量，并通过连接分片、事件循环归属或单线程房间 Worker 控制并发访问。

***
<br/>

> <h3 id="RoomManager与广播模型">Room Manager 与广播模型</h3>

一个视频或直播间对应一个 `room_id`。例如视频 `BV1xxxx` 可映射到 `room:888888`：

```go
type Room struct {
    ID           int64
    Clients      sync.Map
    MessageQueue chan *Message
}
```

热门房间可分配独立 Worker，由单独的 goroutine 处理广播、限流和排序：

```text
热门直播

room worker

goroutine

负责:
- 广播
- 限流
- 排序
```

---
<br/>

### 广播模型

不要在广播主路径中同步向所有客户端写数据：

```go
for client := range clients {
    client.Write(msg)
}
```

任意慢客户端都可能阻塞整个房间。正确方式是为每个连接维护独立的有界发送队列，广播过程只执行非阻塞投递：

```go
type Connection struct {
    SendQueue chan []byte
}
```

```go
func Broadcast(msg []byte) {
    room.Clients.Range(func(_, v any) bool {
        conn := v.(*Connection)

        select {
        case conn.SendQueue <- msg:
        default:
            // 丢弃慢客户端
        }

        return true
    })
}
```

队列满时可按业务要求丢弃消息、合并消息或断开慢客户端，避免单个连接拖垮整个房间。百万级热门房间还需进一步采用房间分片、广播树或多级 Fan-out，单机遍历所有连接并不足以支撑跨节点广播。

***
<br/>

> <h3 id="消息协议与发送流程">消息协议与发送流程</h3>

### Protobuf 二进制协议

大规模实时消息不建议使用 JSON 作为核心传输格式，因为字段名和文本解析会增加带宽及 CPU 消耗。可使用 Protobuf：

```protobuf
message Danmaku {
  int64 user_id = 1;
  int64 room_id = 2;
  string content = 3;
  int64 timestamp = 4;
}
```

```text
protobuf
      |
      |
Go struct
```

客户端通过 WebSocket Binary Frame 发送 Protobuf 字节：

```text
Binary Frame

protobuf bytes
```

而不是发送以下 JSON：

```json
{
  "text": "666"
}
```

实际协议还应包含消息类型、协议版本、请求 ID、压缩标记和载荷长度等信封字段。

---
<br/>

### 发送链路

用户发送弹幕后的异步数据链路：

```text
APP
 |
 |
WebSocket
 |
 |
Gateway
 |
 |
Room Worker
 |
 |
Kafka
 |
 |
Consumer
 |
 |
Redis
```

**广播不要经过 Kafka。** Kafka 会增加实时广播延迟，应由 Room Worker 在本地或实时 Fan-out 网络中直接广播；Kafka 负责异步存储、分析和事件分发。

```text
              send

              |
              |

Gateway

              |

Room Worker

              |

100万人连接
```

典型处理顺序：

1. Gateway 完成鉴权、协议解析和基础校验。
2. Room Worker 执行限流、排序并实时广播。
3. 消息异步投递 Kafka。
4. 消费者分别更新热点数据、持久化历史消息和生成分析指标。

> <h3 id="KafkaRedis与ClickHouse">Kafka、Redis 与 ClickHouse</h3>

### Kafka：异步消息总线

Topic：

```text
danmaku_message
```

按照 `room_id` 计算 Partition：

```text
partition = hash(roomID) % N
```

同一个房间的消息进入同一 Partition，可在 Kafka Partition 范围内保持顺序。

```go
type KafkaMessage struct {
    RoomID   int64
    UserID   int64
    Content  string
    Timestamp int64
}
```

---
<br/>

### Redis：热点状态

Redis 不保存所有历史弹幕，只保存热点数据。

**在线人数：**

```text
Key:   room:online:{roomID}
Value: 500000
```

连接建立和断开时可使用计数器维护在线连接数。`HyperLogLog` 适合统计近似去重用户数，但不适合要求精确增减的实时在线人数。

**最近弹幕：**

使用 Redis Stream 保存房间最近的 `1000` 条弹幕：

```text
room:danmaku:{roomID}
```

```sh
XADD room:danmaku:888 *
```

写入后可结合 `MAXLEN` 或定期裁剪控制 Stream 长度。

---
<br/>

### ClickHouse：历史消息

亿级弹幕历史数据不宜全部写入 MySQL，可使用 ClickHouse：

```sql
CREATE TABLE danmaku_history
(
    id UInt64,
    room_id UInt64,
    user_id UInt64,
    content String,
    create_time DateTime
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(create_time)
ORDER BY
(
    room_id,
    create_time
);
```

按房间和时间查询视频回放弹幕：

```sql
SELECT *
FROM danmaku_history
WHERE room_id = 888
ORDER BY create_time;
```

生产环境通常由 Kafka Consumer 聚合批量写入 ClickHouse，避免逐条插入。

> <h3 id="限流与可观测性">限流与可观测性</h3>

### 多级限流

为防止刷屏，可使用本地令牌桶与 Redis 分布式限流组合控制：

```text
danmaku:rate:{userID}
```

- **用户级：** 例如每个用户 `5 条/秒`。
- **房间级：** 例如每个房间 `10 万条/秒`。
- **连接级：** 限制单连接消息频率、帧大小和发送队列长度。
- **系统级：** 过载时执行降级、采样、丢弃低优先级消息或拒绝新连接。

### 可观测性

至少监控以下指标：

- 当前连接数、连接建立和断开速率。
- 各房间消息吞吐量与广播延迟。
- 发送队列长度、队列满次数和慢客户端数量。
- Kafka Producer 延迟、积压量和消费失败率。
- Redis、ClickHouse 的写入延迟与错误率。
- Goroutine 数量、GC、内存和网络流量。

使用 Prometheus 采集指标，OpenTelemetry 记录跨服务链路，并支持优雅关闭和连接迁移。

2. 做了什么改动
- 将 Redis 全局广播频道改为按视频动态频道：video:danmaku:broadcast:{videoID}:v2。
- 本实例首个房间连接建立时订阅，最后一个连接离开时异步退订。
- Redis 订阅线程不再直接遍历热门房间，而是投递到固定 64 个广播分片 worker。
- 同一视频稳定进入同一个广播 worker，保持单实例内广播顺序。
- 广播队列有容量上限，过载时丢弃可恢复的实时副本，不阻塞 Redis 订阅和 gnet event-loop。
- 保留现有房间目录、成员分片、慢客户端字节预算及 JSON WebSocket 协议。
- MySQL 弹幕记录和 Outbox 事件现在可以在同一事务中提交。
- 新增稳定事件 video.danmaku.created，Kafka partition key 为 video_id。
- 新增专用 Kafka Topic mlc.video.danmaku.created.v1，默认 96 partitions、3 replicas。
- Kafka Consumer 按同一 partition 的有界批次写入 ClickHouse。
- 新增 ClickHouse 表 video_danmaku_history，按月分区，排序键为：
(video_id, progress_ms, created_at, danmaku_id)。
- ClickHouse 使用 ReplacingMergeTree(ingested_at)，支持 Kafka 至少一次投递和历史重放。
- 新增 ClickHouse 历史查询能力，限制为最大 5 分钟窗口、1000 条、复合游标分页，禁止深度 OFFSET。
- Kafka 消费成功后，将最近弹幕投影到 Redis Stream。
- Redis Stream 默认仅保留最近约 1000 条，避免将完整历史堆入 Redis。
- Redis Lua 使用 topic:partition -> offset 水位实现永久幂等投影。
- Stream key 和 offset key 使用相同 {videoID} hash tag，兼容 Redis Cluster slot 约束。
- Outbox dispatcher 从 8 worker 提升到固定 64 worker。
- Outbox 有积压时持续排空，只有领取不到事件时才等待轮询间隔。
- 新增完整部署、灰度、回滚、房间亲和、容量计算和压测说明。
3. 为什么这样改
原有实现存在两个主要扩展瓶颈：
- 每个 Gateway 都订阅全平台广播频道，实例越多，Redis 流量和反序列化工作量越大。
- MySQL 单表不能作为亿万至百亿级弹幕历史的长期唯一存储。
新链路形成以下职责边界：
实时广播：
Client -> gnet Gateway -> local room broadcast
                       -> Redis room channel -> other subscribed gateways

可靠历史：
MySQL transaction -> Outbox -> Kafka
                           -> ClickHouse complete history
                           -> Redis recent Stream
这样可以通过增加 Gateway Pod 横向扩展连接数，通过 Kafka partition 和 Consumer 扩展历史写入吞吐，并将大规模时间线查询转移到 ClickHouse。
4. 准确性检查结果
已确认：
- 同一视频的 Redis 广播、Stream 和 offset key 具有一致的 Cluster hash tag。
- 首个连接只有在 Redis 房间订阅成功后才完成 WebSocket 加入。
- 并发第二个连接不会提前绕过首个订阅确认。
- gnet event-loop 不执行退订 Redis I/O。
- Redis 收包不会同步阻塞在百万连接房间广播上。
- MySQL 数据与 Outbox 事件处于同一事务。
- 幂等重放不会重复生成 Outbox 事件。
- Kafka Consumer 先写 ClickHouse，再推进 Redis offset 投影，失败时不提交 Kafka offset。
- ClickHouse 使用批量 JSONEachRow，不是逐条 HTTP 请求。
- ClickHouse 查询使用稳定复合游标，不使用深分页。
- 现有 HTTP、JSON WebSocket、ACK 和 MySQL 幂等语义未改变。
- git diff --check 通过。
- 未发现密钥、密码或临时编译产物写入仓库。
5. 潜在影响
- 弹幕历史 Kafka Consumer 在 debug、pre、prod 中默认保持 enabled: false。
- 启用消费者前必须先执行 deployments/clickhouse/002_video_danmaku_history.sql。
- 当前 HTTP 时间窗查询仍读取 MySQL 热数据，ClickHouse 查询能力已经实现，但尚未强制切换外部查询路径。
- Redis Pub/Sub 仍是实时非可靠传输；断线恢复依赖 MySQL、Redis recent 或 ClickHouse。
- 当前仍保持同步 MySQL 权威创建语义，以兼容现有 ACK。Kafka 和 ClickHouse承担异步历史归档，而不是将旧客户端 ACK 改成“Kafka 已接收”。
- 96 partitions 是默认部署值，最终数量必须根据 Kafka broker 数、写入量和 Consumer 并发确定。

> <h3 id="连接与房间广播">连接与房间广播</h3>

### Connection

连接对象保存业务身份、底层连接、最后活跃时间和发送队列：

```go
package connection

import (
	"sync/atomic"

	"github.com/panjf2000/gnet/v2"
)

var counter uint64

type Connection struct {
	ID         uint64
	UserID     int64
	RoomID     int64
	Conn       gnet.Conn
	SendQueue  chan []byte
	LastActive int64
	Close      chan struct{}
}

func New(c gnet.Conn) *Connection {
	return &Connection{
		ID:        atomic.AddUint64(&counter, 1),
		Conn:      c,
		SendQueue: make(chan []byte, 1024),
		Close:     make(chan struct{}),
	}
}
```

不应在房间广播路径中对每个慢客户端直接执行同步写：

```go
conn.Write(msg)
```

若用户 A 的网络写入耗时 `100ms`，同步广播可能拖慢整个房间。推荐链路：

```text
Room
  |
SendQueue
  |
write loop
  |
socket
```

发送队列必须有界，并定义慢客户端策略，例如丢弃消息、断开连接或按优先级降级，否则积压最终会转化为内存问题。

### Connection Manager

```go
package connection

import "sync"

type Manager struct {
	conns sync.Map
}

func NewManager() *Manager {
	return &Manager{}
}

func (m *Manager) Add(c *Connection) {
	m.conns.Store(c.ID, c)
}

func (m *Manager) Remove(id uint64) {
	m.conns.Delete(id)
}

func (m *Manager) Range(fn func(*Connection)) {
	m.conns.Range(func(_, value any) bool {
		fn(value.(*Connection))
		return true
	})
}
```

### Room 与 Room Manager

一个视频或直播间映射为一个 `Room`，例如 `BV1xxx -> roomID=10001`。

```go
package room

import "sync"

type Client interface {
	Send([]byte) error
}

type Room struct {
	ID      int64
	clients sync.Map
}

func NewRoom(id int64) *Room {
	return &Room{ID: id}
}

func (r *Room) Join(id uint64, client Client) {
	r.clients.Store(id, client)
}

func (r *Room) Leave(id uint64) {
	r.clients.Delete(id)
}

func (r *Room) Broadcast(data []byte) {
	r.clients.Range(func(_, value any) bool {
		client := value.(Client)
		if err := client.Send(data); err != nil {
			// TODO remove
		}
		return true
	})
}

type Manager struct {
	rooms sync.Map
}

func NewManager() *Manager {
	return &Manager{}
}

func (m *Manager) Get(id int64) *Room {
	value, _ := m.rooms.LoadOrStore(id, NewRoom(id))
	return value.(*Room)
}
```

若 `Room` 直接保存 `*connection.Connection`，使用有界 `SendQueue` 时可采用非阻塞写入：

```go
func (r *Room) Broadcast(msg []byte) {
	r.Clients.Range(func(_, value any) bool {
		conn := value.(*connection.Connection)

		select {
		case conn.SendQueue <- msg:
		default:
			// 慢客户端丢弃
		}

		return true
	})
}
```

> <h3 id="WebSocket-与-protobuf">WebSocket 与 protobuf</h3>

### WebSocket Upgrade 状态

`gobwas/ws` 常见接口基于 `net/http` 或 `net.Conn`，而 `gnet` 的入口是 TCP EventLoop：

```text
TCP EventLoop
  |
OnTraffic()
```

因此需要在事件回调中自行维护协议状态：

```text
HTTP Upgrade
      ↓
101 Switching Protocols
      ↓
WebSocket Frame
```

```go
type ConnState int

const (
	HTTPUpgrade ConnState = iota
	WebSocketConnected
)

type Client struct {
	State  ConnState
	Conn   gnet.Conn
	UserID int64
	RoomID int64
}
```

### Upgrade Accept Key

```go
package websocket

import (
	"crypto/sha1"
	"encoding/base64"
)

func AcceptKey(key string) string {
	h := sha1.New()
	h.Write([]byte(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))
	return base64.StdEncoding.EncodeToString(h.Sum(nil))
}
```

响应格式：

```go
func BuildUpgradeResponse(key string) []byte {
	accept := AcceptKey(key)

	return []byte(fmt.Sprintf(
		"HTTP/1.1 101 Switching Protocols\r\n"+
			"Upgrade: websocket\r\n"+
			"Connection: Upgrade\r\n"+
			"Sec-WebSocket-Accept: %s\r\n\r\n",
		accept,
	))
}
```

生产实现还必须处理 HTTP 请求分片、Header 大小限制、大小写、协议版本、超时和非法请求，不能只用 `bytes.Contains(data, []byte("Upgrade: websocket"))` 判断。

### WebSocket Frame

Upgrade 后的数据是 WebSocket Frame，而不是裸 protobuf：

```text
WebSocket Frame
      |
Frame 解码、反掩码、分片聚合
      |
protobuf payload
```

原示例中的：

```go
func ReadMessage(conn net.Conn) ([]byte, error) {
	return wsutil.ReadClientData(conn)
}
```

不能直接套用到所有 `gnet.Conn` 处理流程；实际接入需要适配 `gnet` 的缓冲区和事件驱动模型，并正确处理半包、粘包、控制帧、分片帧、客户端掩码和最大消息长度。

### protobuf 协议

相较 JSON，protobuf 通常具有更小的消息体和更低的解析开销，但具体大小必须以真实字段和编码结果为准。

`proto/danmaku.proto`：

```protobuf
syntax = "proto3";

package danmaku;

option go_package = "./proto";

message DanmakuMessage {
  uint64 user_id = 1;
  uint64 room_id = 2;
  string content = 3;
  uint64 timestamp = 4;
  MessageType type = 5;
}

enum MessageType {
  TEXT = 0;
  LIKE = 1;
  GIFT = 2;
}
```

生成 Go 代码：

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
protoc --go_out=. proto/danmaku.proto
```

编码与解码：

```go
msg := &danmaku.DanmakuMessage{
	UserId:    10001,
	RoomId:    888,
	Content:   "666",
	Timestamp: uint64(time.Now().Unix()),
}

data, err := proto.Marshal(msg)
```

```go
package gateway

import (
	pb "github.com/company/danmaku/proto"
	"google.golang.org/protobuf/proto"
)

func DecodeMessage(data []byte) (*pb.DanmakuMessage, error) {
	msg := &pb.DanmakuMessage{}
	err := proto.Unmarshal(data, msg)
	return msg, err
}
```

### OnTraffic 数据链路

```go
func (s *Server) OnTraffic(c gnet.Conn) error {
	data, err := c.Next(-1)
	if err != nil {
		return err
	}

	// TODO websocket upgrade 与 frame 解析
	payload, err := parseFrame(data)
	if err != nil {
		return err
	}

	msg, err := DecodeMessage(payload)
	if err != nil {
		return err
	}

	room := s.Rooms.Get(int64(msg.RoomId))
	room.Broadcast(data)

	// Kafka 写入需要移出 EventLoop，避免阻塞网络事件处理。
	return nil
}
```

**注意：** `c.Next(-1)` 返回的是当前缓冲区数据，不等于“一次完整 HTTP 请求”或“一条完整 WebSocket 消息”。协议解析器必须支持增量解析。

> <h3 id="心跳关闭与性能优化">心跳、关闭与性能优化</h3>

### 心跳检测

不能为百万连接分别创建 `time.After()` 或独立 Timer。原始骨架使用全量扫描：

```text
Ticker
  |
每 5 秒扫描
  |
connection.LastActive
```

```go
func Check(manager *connection.Manager) {
	now := time.Now().Unix()

	manager.Range(func(c *connection.Connection) {
		if now-c.LastActive > 60 {
			close(c.Close)
		}
	})
}
```

全量扫描实现简单，但连接规模较大时会形成周期性 CPU 峰值。生产环境可使用分桶扫描或时间轮，例如 `github.com/RussellLuo/timingwheel`。

### 优雅关闭

```text
SIGTERM
  |
停止 accept
  |
标记 Gateway draining
  |
等待写队列和连接退出
  |
关闭 Kafka Producer
  |
退出
```

```go
ctx, cancel := signal.NotifyContext(
	context.Background(),
	os.Interrupt,
	syscall.SIGTERM,
)
defer cancel()

<-ctx.Done()
gateway.Shutdown()
```

实际关闭流程需要设置最大等待时间，避免慢连接或外部依赖导致进程无法退出。

### 百万连接优化原则

**1. 避免每连接一个常驻 goroutine**

```go
go read(conn)
```

百万连接对应百万级 goroutine，会带来栈内存和调度压力。`gnet` 使用 EventLoop 管理大量连接：

```text
CPU Core
  |
EventLoop
  |
Connections
```

**2. 使用对象池时明确所有权**

```go
var pool = sync.Pool{
	New: func() any {
		return make([]byte, 4096)
	},
}
```

对象池可减少部分分配和 GC，但广播数据异步写入时不能提前复用底层字节切片，否则会产生数据竞争或内容污染。

**3. Room 分片**

单个 `sync.Map` 只是骨架。高并发场景可按 `roomID` 将房间分散到多个 shard：

```text
RoomShard[1024]
      |
 roomID hash
      ↓
    shard
      ↓
     room
```

**4. 处理广播放大效应**

房间广播复杂度与本节点订阅人数近似成正比。热门房间需要批量编码、共享只读 payload、分层 fan-out、背压和慢消费者治理。

> <h3 id="Kafka-与多-Gateway-路由">Kafka 与多 Gateway 路由</h3>

Gateway 不应在网络事件循环中直接写数据库，也不应同步等待 Kafka：

```text
Client
  |
Gateway
  +-----------------+
  |                 |
Local Broadcast   Producer Queue
                    |
               Kafka Worker
                    |
             Danmaku Service
```

### Kafka Producer 骨架

```go
package kafka

import (
	"context"

	"github.com/segmentio/kafka-go"
)

type Producer struct {
	writer *kafka.Writer
}

func NewProducer() *Producer {
	return &Producer{
		writer: &kafka.Writer{
			Addr:     kafka.TCP("localhost:9092"),
			Topic:    "danmaku-message",
			Balancer: &kafka.Hash{},
		},
	}
}

func (p *Producer) Send(ctx context.Context, key, value []byte) error {
	return p.writer.WriteMessages(ctx, kafka.Message{
		Key:   key,
		Value: value,
	})
}

func (p *Producer) Close() error {
	return p.writer.Close()
}
```

若在 `OnTraffic` 中直接调用 `Send()`，网络 EventLoop 可能被 Broker 延迟阻塞。生产链路应使用有界队列和 Producer Worker，并定义队列满、重试、超时和失败降级策略：

```text
Gateway
  |
bounded channel
  |
Kafka Producer Worker
```

### Partition 与房间顺序

同一房间的消息需要进入同一 partition，才能利用 Kafka partition 内有序的特性：

```text
partition = hash(room_id) % partition_count
```

```go
func Partition(roomID int64, partitionCount uint32) int {
	h := fnv.New32a()
	_ = binary.Write(h, binary.LittleEndian, roomID)
	return int(h.Sum32() % partitionCount)
}
```

Producer 也可以将 `roomID` 作为 Key，由 `Hash` Balancer 选择 partition：

```go
err := writer.WriteMessages(ctx, kafka.Message{
	Key:   []byte(strconv.FormatInt(roomID, 10)),
	Value: data,
})
```

```text
partition 1
  room100
  room200

partition 2
  room300
```

Kafka 只保证 partition 内的记录顺序。Consumer 若对同一 partition 再并发处理，仍需自行保证同一房间的处理顺序。

### 多 Gateway 广播

```text
          LB
           |
 +---------+---------+
 |         |         |
GW1       GW2       GW3
```

用户 A 连接 `GW1`、用户 B 连接 `GW3` 时，`GW1` 的本地 Room 无法直接触达 `GW3` 上的连接，因此需要跨节点消息分发。

一种思路是计算 Room Owner：

```text
owner = hash(roomID) % gateway_count

room888
   |
  hash
   ↓
  GW3
```

```go
func Owner(roomID int64) string {
	index := hash(roomID) % len(gateways)
	return gateways[index]
}
```

Gateway 注册信息可存放在 Redis：

```text
gateway:list

gw1 -> 10.0.0.1
gw2 -> 10.0.0.2
gw3 -> 10.0.0.3
```

跨节点广播链路：

```text
Client
  |
GW1
  |
Room Router
  |
Kafka broadcast topic
  |
相关 Gateway Consumer
  |
Local Room
  |
WebSocket Clients
```

> **关键修正：** 若某房间的客户端同时分布在多个 Gateway，仅让单一 Owner Gateway 做本地广播并不能触达其他节点。还需要维护房间到 Gateway 的订阅关系，或让所有订阅该房间的 Gateway 消费对应广播事件。

动态 Gateway 列表直接使用 `hash(roomID) % gateway_count` 会在节点增减时造成大规模重映射，生产环境通常使用一致性哈希、固定虚拟分片或独立路由表。

### WebSocket 压测

`wrk` 主要面向 HTTP request/response，不适合直接模拟大量长期 WebSocket 连接。可编写 Go 压测客户端：

```go
package main

import (
	"log"
	"net/url"
	"sync"

	"github.com/gorilla/websocket"
)

func main() {
	var wg sync.WaitGroup

	for i := 0; i < 100000; i++ {
		wg.Add(1)

		go func() {
			defer wg.Done()

			u := url.URL{
				Scheme: "ws",
				Host:   "127.0.0.1:9000",
				Path:   "/ws",
			}

			conn, _, err := websocket.DefaultDialer.Dial(u.String(), nil)
			if err != nil {
				log.Printf("dial: %v", err)
				return
			}
			defer conn.Close()

			for {
				if _, _, err = conn.ReadMessage(); err != nil {
					return
				}
			}
		}()
	}

	wg.Wait()
}
```

## HTTP Upgrade 状态机

WebSocket 连接首先收到 HTTP Upgrade 请求，此时连接还不是 WebSocket：

```http

```

```text

      |

```

```go
package connection

type State uint8

const (
	StateHandshake State = iota
	StateWebsocket
	StateClosed

```

连接对象保存状态、用户、房间和发送队列：

```go
type Connection struct {
	ID uint64

	State State
	Conn  gnet.Conn

	RoomID int64

}
```

## HTTP Upgrade 实现

`websocket/upgrade.go`：

```go
package websocket

import (
	"bytes"
	"fmt"
)

func IsWebsocketRequest(data []byte) bool {
	return bytes.Contains(data, []byte("Upgrade: websocket"))
}

func ParseKey(data []byte) string {
	lines := bytes.Split(data, []byte("\r\n"))

	for _, line := range lines {
		if bytes.HasPrefix(line, []byte("Sec-WebSocket-Key")) {
			parts := bytes.Split(line, []byte(":"))
			return string(bytes.TrimSpace(parts[1]))
		}
	}

	return ""
}

func Response(key string) []byte {
	accept := AcceptKey(key)

	return []byte(fmt.Sprintf(
		`HTTP/1.1 101 Switching Protocols\r
Upgrade: websocket\r
Connection: Upgrade\r
Sec-WebSocket-Accept: %s\r
\r
`, accept))
}
```

`ParseKey()` 提取 `Sec-WebSocket-Key`，`Response()` 计算 `Sec-WebSocket-Accept` 并返回 `101 Switching Protocols`。

## gnet 连接与流量处理

连接建立时创建业务连接对象并加入连接管理器：

```go
func (s *Server) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	client := connection.New(c)
	s.connections.Add(client)
	return
}
```

`OnTraffic()` 根据连接状态分派 HTTP Handshake 或 WebSocket 数据：

```go
func (s *Server) OnTraffic(c gnet.Conn) error {
	client := s.connections.Get(c)

	data, err := c.Next(-1)
	if err != nil {
		return err
	}

	switch client.State {
	case connection.StateHandshake:
		return s.handleHandshake(client, data)

	case connection.StateWebsocket:
		return s.handleWebsocket(client, data)
	}

	return nil
}
```

Handshake 完成后异步写入响应，并将状态切换为 `StateWebsocket`：

```go
func (s *Server) handleHandshake(c *Connection, data []byte) error {
	key := websocket.ParseKey(data)
	if key == "" {
		return nil
	}

	resp := websocket.Response(key)
	c.Conn.AsyncWrite(resp)
	c.State = connection.StateWebsocket

	return nil
}
```

## WebSocket Frame 编解码

```go
type GnetConn struct {
```

## 每连接 SendQueue

百万连接场景不能简单地为每个连接常驻一个写 goroutine。连接只维护有界发送队列，慢用户队列写满后按策略丢弃消息：

```go
type Connection struct {
	SendQueue chan []byte
}

func New(c gnet.Conn) *Connection {
	return &Connection{
		Conn:      c,
		SendQueue: make(chan []byte, 1024),
	}
}

func (c *Connection) Push(data []byte) {
	select {
	case c.SendQueue <- data:
	default:
		// 慢用户丢弃
	}
}
```

这里的 `SendQueue` 是简化模型，生产版本应由少量 gnet EventLoop 统一刷新，而不是每连接启动一个 goroutine。

## Room 1024 分片与广播

如果所有房间共用一个容器，千万房间下会形成明显竞争：

```go
sync.Map rooms
```

将房间按 `roomID % 1024` 分片：

```go
const ShardCount = 1024

type RoomManager struct {
	shards [ShardCount]*RoomShard
}

type RoomShard struct {
	rooms sync.Map
}

func shardID(roomID int64) int {
	return int(roomID % ShardCount)
}

func (m *RoomManager) Get(id int64) *Room {
	shard := m.shards[shardID(id)]

	v, _ := shard.rooms.LoadOrStore(id, NewRoom(id))
	return v.(*Room)
}
```

房间广播只遍历本房间连接，并调用 `Push()` 放入发送队列：

```go
func (r *Room) Broadcast(msg []byte) {
	r.clients.Range(func(_, v any) bool {
		client := v.(*Connection)
		client.Push(msg)
		return true
	})
}
```

## Kafka 异步 Worker

Gateway 的网络事件循环中不能同步执行 `SendKafka()`，因为 Kafka 延迟会阻塞连接处理。使用大容量队列将消息交给异步 Worker：

```go
type Producer struct {
	queue chan *Message
}

func NewProducer() *Producer {
	p := &Producer{
		queue: make(chan *Message, 100000),
	}

	go p.worker()
	return p
}

func (p *Producer) worker() {
	for msg := range p.queue {
		data, _ := proto.Marshal(msg)

		kafka.WriteMessages(
			context.Background(),
			kafka.Message{
				Key: []byte(strconv.FormatInt(msg.RoomID, 10)),
				Value: data,
			},
		)
	}
}
```

Gateway 只执行：

```go
producer.Push(msg)
```

消息进入队列后立即返回，Kafka 写入不再阻塞当前连接事件。

## 百万连接无 goroutine 写模型

以下写法会导致百万连接对应大量 goroutine，并增加调度器和 GC 压力：

```go
for {
	go conn.Write(msg)
}
```

```text
1,000,000 goroutine
+
scheduler 压力
+
GC 压力
```

gnet Reactor 的核心原则是：**谁负责读，谁负责写。**

```text
CPU Core 0
 EventLoop
   |
 connection1
 connection2

CPU Core 1
 EventLoop
   |
 connection3
```

连接只保存出站缓冲：

```go
type Connection struct {
	ID   uint64
	Conn gnet.Conn

	// 写缓冲
	Outbound chan []byte
}
```

广播不能直接 `client.Conn.Write(data)`，而是将数据推入有界队列：

```go
func (c *Connection) Push(data []byte) {
	select {
	case c.Outbound <- data:
	default:
		// 丢弃慢用户
	}
}
```

由 EventLoop 批量取出消息并异步发送：

```go
func flush(c *Connection) {
	for {
		select {
		case msg := <-c.Outbound:
			c.Conn.AsyncWrite(msg)
		default:
			return
		}
	}
}
```

```text
100 万连接
    ↓
少量 EventLoop
    ↓
异步写
```

## 千万连接时间轮心跳

不能为每个连接创建一个 `time.Timer`：

```go
for conn {
	time.After()
}
```

千万连接会产生千万个 Timer。Timing Wheel 用固定数量的槽和一个 Ticker 管理连接超时：

```text
                slot
              0 1 2 3
             /       \
      connection  connection
```

数据结构与基础流程：

```go
type Wheel struct {
	slots   []map[uint64]*Connection
	current int
}

func NewWheel() *Wheel {
	return &Wheel{
		slots: make([]map[uint64]*Connection, 360),
	}
}

func (w *Wheel) Add(c *Connection) {
	index := (c.LastActive + 60) % 360
	w.slots[index][c.ID] = c
}

func (w *Wheel) Tick() {
	w.current++
	expired := w.slots[w.current]

	for _, c := range expired {
		if time.Now().Unix()-c.LastActive > 60 {
			c.Conn.Close()
		}
	}
}
```

```text
1000 万连接
一个 Ticker
解决
```

这套架构适用于弹幕、直播聊天室、游戏实时服务器和 IM 群聊等高并发实时消息系统。核心原则是：**Gateway 专注连接，Room 专注广播，业务异步处理，状态外置，存储批量化，服务可水平扩展。**


## <span id="方案实现后的V5目标与结论">方案实现后的V5 目标与结论</span>

V5 在 V4 已有的 gnet Reactor、WebSocket 应用层心跳、动态 Redis 房间订阅、慢客户端隔离、Kafka 毒消息处理和 ClickHouse 异步历史链路基础上，继续优化网关心跳模型。

V4 已经避免“每连接一个 timer 或 goroutine”，但心跳仍由固定 ticker 周期性遍历本实例全部房间成员。单实例连接数增长到数十万或百万后，这种全量扫描会产生：

- 周期性 `O(N)` 连接遍历。
- 所有房间成员分片锁的集中读取。
- 海量 WebSocket Ping 在同一时刻进入 gnet 异步写队列。
- 心跳扫描与热门房间广播争用相同成员锁域。
- 重连风暴后连接心跳相位高度一致，形成周期性 CPU 和网络峰值。

V5 将该模型替换为**固定 ticker 推进的独立分片时间轮**：

```text
V4:

每 20s
   |
   +--> 扫描全部房间
            |
            +--> 扫描全部成员
                     |
                     +--> Ping / Close


V5:

每 1s
   |
   +--> 推进 64 个时间轮分片
            |
            +--> 仅取每个分片当前到期槽
                     |
                     +--> 锁外 Ping / Close
                              |
                              +--> 活跃连接惰性续期
```

V5 的核心收益不是宣称单机已实测支撑千万连接，而是将常规心跳工作量从“周期性扫描本实例所有连接”调整为“每秒仅处理当前到期槽中的连接”，并隔离心跳与房间广播的锁竞争。

千万连接仍必须依赖多 Gateway Pod 水平扩展。单 Pod 安全连接数必须通过真实机器、内核、网卡和客户端压测得到，不能仅根据代码结构推断。

## <span id="V5时间轮架构">V5 时间轮架构</span>

### 总体结构

```text
                         WebSocket Client
                                |
                                v
                      gnet EventLoop / OnTraffic
                                |
                     atomic lastActive.Store()
                                |
                                v
                    不移动时间轮，不获取轮锁


固定 1s ticker
       |
       v
+-------------------------------+
|     Heartbeat Wheel           |
|                               |
|  shard 0  shard 1 ... shard63 |
|     |        |          |     |
|   slots    slots      slots    |
+-------------------------------+
       |
       v
分离当前到期槽，立即释放 shard lock
       |
       +--> 已超时：Close
       |
       +--> Ping 失败：Close
       |
       +--> 活跃：AsyncWrite(Ping) 后重新调度
```

实现文件：

```text
internal/modules/video_danmaku/realtime/hg_heartbeat_wheel.go
internal/modules/video_danmaku/realtime/hg_gnet_server.go
```

时间轮由以下结构组成：

```go
type hgHeartbeatWheelShard struct {
    mu      sync.Mutex
    cursor  uint64
    buckets []map[*hgConnection]struct{}
}

type hgHeartbeatWheel struct {
    tick      time.Duration
    interval  time.Duration
    timeout   time.Duration
    shards    []hgHeartbeatWheelShard
    nextShard atomic.Uint32
    sequence  atomic.Uint64
}
```

设计约束：

- `tick` 固定为 `1s`，不暴露成易误配的部署参数。
- 默认使用 `64` 个独立心跳分片。
- 每个分片有独立 mutex 和 cursor。
- 时间槽切片在初始化时创建，但槽内 map 按需创建。
- 初始化成本与分片数和槽指针数量相关，不与最大连接数相关。
- 每条连接同时最多存在于一个时间槽。
- 时间轮不复用房间 member shard，避免两个不同热点锁域相互耦合。

### 为什么不使用每连接 timer

禁止以下实现：

```go
time.AfterFunc(timeout, func() {
    conn.Close()
})
```

也禁止：

```go
go heartbeatForConnection(conn)
```

百万连接下，每连接 timer 或 goroutine 会放大：

- Go runtime timer heap 压力。
- goroutine 栈和调度成本。
- GC 扫描对象数量。
- 关闭、取消和重连时的生命周期竞态。

V5 始终只使用固定数量的后台 goroutine：现有网关只增加一个时间轮推进 loop，不随连接数增长。

### 为什么入站流量不移动时间轮节点

客户端每次发送 Ping、Pong 或弹幕时，若都执行以下操作：

```text
删除旧时间槽节点
        +
计算新 deadline
        +
插入新时间槽
```

会把 event-loop 上原本极轻的活动更新变成分片锁、map 删除和 map 插入。热门连接或高频 Pong 会持续竞争时间轮锁。

V5 保持入站热路径只有一次原子写：

```go
state.lastActive.Store(time.Now().UnixNano())
```

时间轮节点到期时才读取最新活动时间，并决定关闭或重新安排。这是惰性续期模型，调度成本与心跳检查次数相关，而不是与全部入站帧数量相关。

## <span id="连接生命周期与并发边界">连接生命周期与并发边界</span>

### OnOpen

TCP 连接建立时只执行：

- 创建 `hgConnection`。
- 初始化 `lastActive`。
- 原子增加连接计数。
- 检查 Gateway readiness 和最大连接数。

此时连接尚未完成票据校验和 WebSocket Upgrade，因此不会注册进时间轮。

### Upgrade 成功

连接只有在以下步骤全部成功后才注册心跳：

```text
HTTP Upgrade 请求完整
        |
Origin 校验通过
        |
一次性 ticket 校验通过
        |
Redis 房间订阅成功
        |
gobwas/ws Upgrade 成功
        |
加入本地房间
        |
注册 Heartbeat Wheel
```

失败握手、非法 Origin、无效 ticket 和房间订阅失败连接不会占用时间轮节点。

### OnTraffic

`OnTraffic` 中的活动刷新仍发生在协议处理之前，因此以下有效入站流量都会刷新活动时间：

- WebSocket Ping。
- WebSocket Pong。
- 文本弹幕命令。
- Close 帧。
- 完整到达后被协议逻辑处理的其他帧。

V5 没有擅自改成“只有 Pong 才刷新”，以保持 V4 的连接存活语义兼容。

### OnClose

关闭顺序为：

```text
CAS 释放连接计数
        |
heartbeatClosed = true
        |
从时间轮槽中删除节点
        |
离开本地房间
        |
释放 Redis 房间订阅引用
```

`heartbeatClosed` 必须在删除时间轮节点前生效，因为时间轮线程可能已经把节点从槽内取到本地切片。即使节点已经不在 bucket 中，关闭标志仍可阻止其处理完成后重新插入。

### gnet 并发安全边界

gnet 明确规定 `Conn.Context()` 不能在 EventHandler 外并发调用。因此时间轮不会在后台线程执行：

```go
state := conn.Context().(*hgConnection)
```

Upgrade 成功时直接保存：

```go
state.heartbeatConn = conn
```

后台心跳只使用 gnet 并发安全的操作：

- `Conn.AsyncWrite`。
- `Conn.Close`。

不在后台线程使用：

- `Conn.Context`。
- `Conn.SetContext`。
- `Conn.Peek`、`Conn.Next` 等输入缓冲 API。
- 非并发安全的同步 `Conn.Write`。

### 锁边界

时间轮 shard lock 内只做：

- 推进 cursor。
- 获取当前 bucket。
- 清空当前 bucket 指针。
- 修改 `heartbeatScheduled`。
- 安排连接到未来 bucket。

时间轮锁内禁止：

- `AsyncWrite`。
- `Close`。
- 房间 Join/Leave。
- Redis、MySQL、Kafka 或 ClickHouse I/O。
- 获取 room directory/member lock。

因此时间轮锁和房间广播锁之间不存在嵌套锁顺序。

## <span id="时间轮调度算法">时间轮调度算法</span>

### 首次调度相位打散

滚动发布、机房网络恢复或 Ingress 切流后，可能在短时间建立大量连接。如果所有连接统一安排为 `now + 20s`，即使采用时间轮，仍会在同一个槽产生 Ping 峰值。

V5 使用原子 sequence 将首次调度分散到一个 heartbeat interval 内：

```go
intervalTicks := hgHeartbeatDurationTicks(w.interval, w.tick)
delayTicks := uint64(1)
if intervalTicks > 1 {
    delayTicks += (w.sequence.Add(1) - 1) % uint64(intervalTicks)
}
```

默认配置下，首个 Ping 被分散到连接建立后的约 `1s-20s`。后续检查仍以 `heartbeat_interval` 为上限。

### 分片选择

连接使用独立的全局轮询计数分配到心跳 shard：

```go
state.heartbeatShard =
    (w.nextShard.Add(1) - 1) & uint32(len(w.shards)-1)
```

由于 `heartbeat_shard_count` 必须为 2 的幂，可使用位掩码代替取模。独立轮询避免复用 `memberShard` 时长尾房间首连接集中到相同心跳分片。

### Tick 推进

每秒推进一次全部 shard，但每个 shard 只取当前槽：

```go
shard.cursor++
slot := int(shard.cursor % uint64(len(shard.buckets)))
bucket := shard.buckets[slot]
shard.buckets[slot] = nil
```

随后立刻释放 shard lock，再处理 bucket 中的连接。

### 超时判断

```go
deadline := now.Add(-heartbeatTimeout).UnixNano()

if state.lastActive.Load() <= deadline {
    conn.Close()
}
```

默认 `heartbeat_timeout = 60s`。连接连续 60 秒没有任何有效入站活动时关闭。

### Ping 与续期

活跃连接执行：

```go
if err := conn.AsyncWrite(heartbeatPing, nil); err != nil {
    conn.Close()
    return
}

heartbeatWheel.hgReschedule(state, now)
```

`AsyncWrite` 成功只代表帧进入 gnet 异步写路径，不代表客户端已经收到或已经回复。因此发送 Ping 不会更新 `lastActive`。只有客户端后续 Pong 或其他有效入站流量才刷新活动时间。

下一次检查延迟取：

```text
min(heartbeat_interval, last_active + heartbeat_timeout - now)
```

这保证：

- 活跃连接不会比配置间隔更频繁地收到 Ping。
- 静默连接会在 timeout 附近再次被检查。
- 无需每次入站流量移动时间轮节点。

### 取消与重新调度竞态

重点防护以下时序：

```text
Tick 从 bucket 取出连接
        |
OnClose 标记连接关闭
        |
Tick 完成 Ping
        |
尝试重新插入未来 bucket
```

V5 使用双重检查：

1. `hgReschedule` 前检查 `heartbeatClosed`。
2. 获取 shard lock 后再次检查 `heartbeatClosed`。

因此关闭连接不会重新挂回时间轮，也不会形成长期内存滞留。

## <span id="配置与容量边界">配置与容量边界</span>

默认配置：

```yaml
video_danmaku:
  heartbeat_interval: 20s
  heartbeat_timeout: 60s
  heartbeat_shard_count: 64
```

约束：

| 配置 | 默认值 | 约束 | 说明 |
| --- | ---: | --- | --- |
| `heartbeat_interval` | `20s` | `5s-1m` | 活跃连接 Ping 周期上限 |
| `heartbeat_timeout` | `60s` | 至少为 interval 的 2 倍，最大 `5m` | 静默连接清理时间 |
| `heartbeat_shard_count` | `64` | `4-256` 且为 2 的幂 | 时间轮独立锁分片数量 |
| 内部 wheel tick | `1s` | 固定 | 时间轮推进精度，不暴露为配置 |

Ingress/LB 空闲超时必须高于应用心跳超时，默认建议至少 `90s`。

### 复杂度

V4 常规心跳扫描：

```text
每个 heartbeat interval: O(本实例全部连接)
```

V5 常规时间轮推进：

```text
每个 1s tick: O(heartbeat shard 数 + 当前到期连接数)
```

需要注意，连接最终仍会按配置周期执行 Ping，因此整体长期 Ping 数量仍与连接数成正比。时间轮消除的是集中全量扫描和锁遍历，不可能消除维持 WebSocket 存活所需的网络工作。

### 内存边界

每条已升级连接新增保存：

- `heartbeatConn` 接口引用。
- shard 和 slot 索引。
- scheduled 状态。
- closed 原子状态。
- bucket map 中的一个连接指针 key。

时间槽 map 按需创建，避免为所有 `shard × slot` 预创建空 map。但实际每连接内存仍必须通过真实构建、Go 版本和目标架构下的 RSS 压测测量，不能仅按字段大小相加得出生产容量。

### 千万连接部署结论

V5 仅是单 Gateway 节点的心跳调度优化。千万连接部署仍遵循：

```text
required_pods =
    ceil(target_connections / verified_connections_per_pod)
    * safety_factor
```

安全系数建议不低于 `1.3`，并预留：

- 滚动发布容量。
- 单 AZ 故障容量。
- 热门视频倾斜。
- Redis/Kafka 故障期间的降级余量。
- 网卡和 CPU 突刺余量。

> <h3 id="room-service-实现">Room Service 实现</h3>

## gRPC Server

**`room-service/internal/grpc/server.go`：**

```go
package grpcserver

import (
	"context"

	"google.golang.org/grpc"

	pb "github.com/company/project/api/roompb"
	"github.com/company/project/internal/room"
)

type Server struct {
	pb.UnimplementedRoomServiceServer

	Manager *room.Manager
}

func NewServer(m *room.Manager) *Server {
	return &Server{
		Manager: m,
	}
}

func (s *Server) JoinRoom(
	ctx context.Context,
	req *pb.JoinRoomRequest,
) (*pb.JoinRoomResponse, error) {
	r := s.Manager.Get(int64(req.RoomId))
	r.Join(req.UserId)

	return &pb.JoinRoomResponse{
		Success: true,
	}, nil
}

func (s *Server) Broadcast(
	ctx context.Context,
	req *pb.BroadcastRequest,
) (*pb.Empty, error) {
	r := s.Manager.Get(int64(req.RoomId))
	r.Broadcast(req.Payload)

	return &pb.Empty{}, nil
}

func (s *Server) LeaveRoom(
	ctx context.Context,
	req *pb.LeaveRoomRequest,
) (*pb.Empty, error) {
	r := s.Manager.Get(int64(req.RoomId))
	r.Leave(req.UserId)

	return &pb.Empty{}, nil
}
```

## Room 对象

**`room.go`：**

```go
package room

import "sync"

type Room struct {
	ID    int64
	Users sync.Map
}

func NewRoom(id int64) *Room {
	return &Room{
		ID: id,
	}
}

func (r *Room) Join(uid uint64) {
	r.Users.Store(uid, true)
}

func (r *Room) Leave(uid uint64) {
	r.Users.Delete(uid)
}

func (r *Room) Broadcast(data []byte) {
	r.Users.Range(func(uid, _ any) bool {
		// 实际生产:
		// 推入Gateway连接队列
		println(
			"send user",
			uid,
			string(data),
		)

		return true
	})
}
```

> <h2 id="room-service-做到千万连接广播">Room Service 做到千万连接广播</h2>

对于**千万级连接广播系统**，`Gateway -> Room Service -> Gateway` 的同步 gRPC 模型只能用于小规模方案。假设有 `1000 万` WebSocket 在线、热门直播间 `100 万人`、每秒 `10 万条弹幕`：

```text
Gateway
   |
 gRPC
   |
Room Service
```

每条弹幕都走 gRPC：

```text
100000 msg/s
↓
100000 gRPC calls/s
```

Room Service 很快会成为瓶颈。生产级设计需要把**实时广播路径从 RPC 改成消息总线 + 本地广播**。

> <h3 id="连接归属与控制面">连接归属与控制面</h3>

## 为什么不能让 Room Service 直接管理连接

错误模型：

```text
Room Service
    |
100万个WebSocket连接
```

这会导致 Room Service 的 CPU 和网络 IO 消耗巨大，连接迁移也很困难。正确做法是让连接属于 Gateway：

```text
Gateway-1
 user1
 user2
 user3

Gateway-2
 user100
 user200
```

Room Service 只保存 `room_id -> gateway 列表`：

```text
room_id
↓
gateway列表
```

例如：

```json
{
  "room": 8888,
  "gateways": [
    "gw1",
    "gw7",
    "gw9"
  ]
}
```

## gRPC 变成控制面

gRPC 不消失，但不再用于实时消息。错误做法是每条弹幕都调用：

```go
Broadcast()
```

gRPC 应用于低频管理操作，例如加入房间、查询和配置：

```protobuf
rpc JoinRoom()
```

```protobuf
rpc GetRoomOwner()
```

```protobuf
rpc UpdateRoomConfig()
```

即：

```text
                 Control Plane

Gateway  ---------------- Room Service
        gRPC
```

**千万连接广播的核心原则：**

> **不要让 Gateway 调 Room Service 做广播。**

## <span id="代码实现后的-V6目标与结论">代码实现后的-V6 目标与结论</span>

V6 继续遵循参考设计中的核心数据面原则：Gateway 持有 WebSocket 连接，本地 Room 执行广播，跨实例消息通过消息系统传播，不能让每条弹幕同步调用 Room RPC。当前工程使用按视频动态订阅的 Redis Pub/Sub 作为实时跨实例数据面，Kafka Outbox 和 ClickHouse 负责可靠异步历史链路。

本轮没有引入新的 Room 微服务或同步 gRPC 广播，因为这会扩大工程边界，并在热门房间中增加每消息 RPC 瓶颈。实际检查发现当前 Redis 房间路由存在两个更直接的生产风险：

1. 退订命令通过代次校验后、真正执行 Redis `Unsubscribe` 前，房间可能重新加入。新连接会复用内存中的 `subscribed=true`，但旧命令随后仍会取消底层订阅，导致该实例上的活跃房间静默丢失跨实例弹幕。
2. V5 使用有界 channel 保存退订命令，队列满时直接丢弃。突发大量临时房间同时清空时，被丢弃的房间不会再次触发退订，Redis Pub/Sub 订阅和本地引用状态可能长期残留。

V6 将房间订阅生命周期补全为显式状态机，并把可丢命令队列替换为按房间合并的待退订集合：

```text
subscribed
    |
最后一个本地连接离开
    |
pending unsubscribe（按 videoID 合并）
    |
Run 获取 refsMu 并校验 generation
    |
unsubscribing = true
    |
锁外执行 Redis Unsubscribe
    |
成功：删除空闲房间状态
失败：撤销 Gateway readiness，等待编排重启
```

准确结论是：**V6 修复了 Redis 房间退订与立即重连之间的时间窗竞态，并消除了退订 channel 满时永久丢命令的问题；已通过单元测试、20 次 race 检查和 vet，但尚未在真实 Redis Cluster 上执行 Pub/Sub 故障注入。**

## <span id="Redis房间退订状态机">Redis 房间退订状态机</span>

### V5 竞态时序

V5 的 generation 可以拒绝尚未开始执行的旧命令，但无法覆盖“校验已经通过，Redis I/O 尚未发生”的窗口：

```text
Router Run                         New Connection
    |                                   |
hgShouldUnsubscribe() = true            |
    |                                   |
    |                              Join(videoID)
    |                              看到 subscribed=true
    |                              refs: 0 -> 1
    |                                   |
Redis Unsubscribe(videoID)               |
    |                                   |
底层订阅被取消，但本地仍认为房间已订阅且有连接
```

此后 Redis 发布到该视频频道的弹幕不会再到达当前 Gateway，直到房间引用完全清空并重新建立订阅，或者进程重启。

### V6 状态字段

`hgRoomSubscriptionState` 新增：

```go
unsubscribing bool
```

并复用已有 `ready chan struct{}` 作为订阅和退订状态切换的等待通知。状态字段全部由 `refsMu` 保护。

### Redis I/O 前原子标记

`hgBeginUnsubscribe` 在持有 `refsMu` 时一次性校验：

- 房间状态仍存在。
- command generation 与当前 generation 相同。
- 本地引用数为零。
- 当前确实已订阅。
- 不在订阅中。
- 不在退订中。

校验通过后，在释放锁和调用 Redis 之前设置：

```go
state.unsubscribing = true
state.ready = make(chan struct{})
state.err = nil
```

因此 Redis `Unsubscribe` 开始前，内存状态已经不再允许新连接直接复用旧订阅。

### 退订期间重新加入

`Join` 遇到 `unsubscribing=true` 时不会增加 refs，也不会返回成功，而是：

```text
读取 ready channel
      |
释放 refsMu
      |
等待退订结束或上游 context 取消
      |
重新进入 Join 状态机
      |
创建新的 Redis Subscribe
```

等待期间不持有 `refsMu`，因此不会阻塞 `hgFinishUnsubscribe` 完成状态切换，也不会把 Redis I/O 放入全局锁临界区。

### 退订完成

`hgFinishUnsubscribe` 再次验证 generation 和 `unsubscribing` 状态：

- 成功时设置 `subscribed=false`、关闭 `ready`，并删除 refs 为零的房间状态。
- 失败时保存错误并关闭 `ready`，等待中的 Join 得到失败。
- `Run` 收到 Redis 退订错误后保存运行错误并退出。
- Gateway readiness 由既有后台监控撤销，交给编排系统摘流重启。

这种错误策略优先保证路由正确性，不允许 Redis Pub/Sub 状态未知的实例继续接收新连接。

## <span id="不可丢退订调度">不可丢退订调度</span>

### 为什么不能使用满时丢弃的 channel

退订不是实时弹幕副本。实时广播在过载时允许丢弃，因为历史链路可以恢复；退订命令被永久丢弃则会留下资源和状态泄漏，二者不能使用相同降级语义。

V5：

```go
select {
case commands <- command:
default:
    // 命令永久丢失
}
```

V6 使用：

```go
pending map[string]hgRoomSubscriptionCommand
wake    chan struct{} // capacity = 1
```

### 按房间合并

`hgQueueUnsubscribe` 在 `pendingMu` 下执行：

```go
pending[videoID] = latestCommand
```

同一个房间连续离开、重新加入、再次离开时，只保留最新 generation。这样同时保证：

- 不丢失不同房间的退订请求。
- 不为同一房间累积无意义的旧命令。
- 待处理集合上限受本实例已见房间数约束，而不是受退房事件总次数约束。
- `Leave` 不等待 Redis，不阻塞 gnet event-loop。

### 单信号唤醒

`wake` 容量固定为 1，仅表示“pending 集合中可能有工作”，不承载每条业务命令。发送采用非阻塞方式：

```go
select {
case wake <- struct{}{}:
default:
}
```

信号已存在时无需重复发送，因为 pending map 保存了真实工作。`hgPopUnsubscribe` 每次取出一个房间；若集合仍非空，会再次补充 wake 信号，使 `Run` 继续处理。

### 并发与容量边界

锁边界如下：

| 锁 | 保护内容 | 锁内禁止操作 |
| --- | --- | --- |
| `refsMu` | refs、generation、订阅状态、ready、err | Redis I/O、网络写、房间广播 |
| `pendingMu` | 待退订房间到最新命令的映射 | Redis I/O、等待 channel、获取 refsMu |

V6 不嵌套获取 `refsMu` 和 `pendingMu`，避免形成锁顺序环。

Redis `Unsubscribe` 仍由单个 router Run goroutine 串行执行。这样不产生无界 goroutine，也符合 go-redis PubSub 控制操作的顺序化模型。代价是大量房间同时清空时退订会排队，但 pending 会按房间合并，且连接 event-loop 不会被阻塞。

> <h2 id="Room-Service-如何使用-Kafka-实现跨节点广播">Room Service 如何使用 Kafka 实现跨节点广播</h2>

在千万连接规模下，**Room Service 不应通过逐个调用 Gateway 的 gRPC 接口完成广播**。

假设系统有 `1000` 个 Gateway 节点、`1` 亿用户连接，某热门房间有 `500` 万在线用户。若采用以下调用方式：

```text
Gateway A
    |
 gRPC Broadcast
    |
Gateway B/C/D/E...
```

将产生大量 RPC 连接、广播风暴、节点耦合，并使热点房间压力过度集中。

生产系统通常采用：**Kafka 作为跨节点消息总线，Room Service 负责房间路由，Gateway 负责最终推送。**

***
<br/>

> <h3 id="整体架构">整体架构</h3>

```text
                         Client
                           |
                       WebSocket
                           |
                 Gateway Cluster
                           |
                      Kafka Topic
                   room-broadcast
                           |
             +-------------+-------------+
             |                           |
        Room Service A             Room Service B
             |                           |
        Gateway Group A            Gateway Group B
             |                           |
          Local Room                Local Room
             |
        WebSocket Push
```

消息先写入 Kafka，再由 Room Service 消费并完成房间路由，最后交给相关 Gateway 向本地 WebSocket 连接推送。

***
<br/>

> <h3 id="控制面与数据面">控制面与数据面</h3>

整个系统分为**控制面**与**数据面**。

## 控制面（Control Plane）

控制面负责房间归属、Gateway 注册以及用户进入和退出，通常使用 `gRPC + Redis`：

```text
Gateway
  |
JoinRoom(room=100)
  |
Room Service
```

## 数据面（Data Plane）

数据面负责实时弹幕等高频消息，使用 Kafka 承载跨节点消息流：

```text
用户发送：666
    ↓
  Kafka
    ↓
所有相关 Gateway
    ↓
 用户收到
```

***
<br/>

> <h3 id="Kafka-Topic-与分区设计">Kafka Topic 与分区设计</h3>

创建 `room-broadcast` Topic，并配置多个 Partition，例如：

```text
room-broadcast
├── partition-0
├── partition-1
├── partition-2
└── ...
    partition-255
```

## 为什么使用 `room_id` 作为 Partition Key

Kafka 保证**同一个 Partition 内的消息有序**。发送消息示例：

```json
{
  "room_id": 10001,
  "content": "hello"
}
```

Producer 使用 `room_id` 作为 Key：

```go
kafka.Message{
    Key:   []byte("10001"),
    Value: data,
}
```

Kafka 根据以下公式选择 Partition：

```text
hash(room_id) % partition数量
```

例如：

```text
hash(10001) % 256
        =
   partition 88
```

映射结果：

```text
room10001
    |
partition88
```

同一房间的消息都会进入 `partition 88`，因此弹幕 `A → B → C` 的顺序不会被打乱。

***
<br/>

> <h3 id="Room-Service-消费与广播">Room Service 消费与广播</h3>

假设启动 `10` 个 Room Service 实例：

```text
room-service-1
room-service-2
room-service-3
...
```

所有实例加入同一个 Consumer Group：

```text
room-service-group
```

Kafka 自动为组内实例分配 Partition：

```text
partition 0-20
        |
room-service-1

partition 21-40
        |
room-service-2
```

Reader 配置：

```go
reader := kafka.NewReader(
    kafka.ReaderConfig{
        Brokers: []string{
            "kafka1:9092",
        },
        Topic:   "room-broadcast",
        GroupID: "room-service-group",
    },
)
```

持续消费消息：

```go
for {
    msg, err := reader.ReadMessage(ctx)
    if err != nil {
        continue
    }

    handle(msg)
}
```

## 消费后执行广播

Kafka 消息示例：

```json
{
  "room_id": 888,
  "payload": "666"
}
```

Room Service 解析消息：

```go
type BroadcastMessage struct {
    RoomID  int64
    Payload []byte
}
```

根据 `room_id` 查询房间并广播：

```go
room := roomManager.Get(msg.RoomID)
room.Broadcast(msg.Payload)
```

`Room` 保存本地连接：

```go
type Room struct {
    ID          int64
    Connections sync.Map
}
```

遍历连接并发送消息：

```go
func (r *Room) Broadcast(data []byte) {
    r.Connections.Range(func(_, v any) bool {
        conn := v.(*Connection)
        conn.Send(data)
        return true
    })
}
```

> <h3 id="房间与-Gateway-路由方案">房间与 Gateway 路由方案</h3>

关键问题是：**Room Service 如何知道哪些 Gateway 上存在目标房间的用户？**

假设 `room=888` 的用户分布在三个 Gateway：

```text
Gateway-A
  user1
  user2

Gateway-B
  user100

Gateway-C
  user500
```

对应关系为：

```text
room=888
├── Gateway-A
├── Gateway-B
└── Gateway-C
```

Kafka 消息被消费后，系统必须通知 `Gateway-A/B/C`。常见方案有三种。

---
<br/>

## 方案一：Room Owner

这是最常用、实现最简单的方案。通过哈希计算房间 Owner：

```go
owner = hash(roomID) % gateway数量
```

例如：

```text
room=888
   |
 hash
   |
Gateway-B
```

`room888` 的消息只由 `Gateway-B` 处理：

```text
Client
  |
Gateway-A
  |
Kafka
  |
Gateway-B
  |
Broadcast
  |
Local User
```

- **优点：**简单。
- **缺点：**热点房间的压力会集中到单个 Owner。

---
<br/>

## 方案二：Gateway 订阅 Room

在 Redis 中保存房间与 Gateway 的订阅关系：

```text
room:888:gateways

[
  gw1,
  gw2,
  gw5
]
```

用户进入时，Gateway 注册订阅关系：

```go
SADD room:888:gateways gw1
```

用户离开时执行：

```text
SREM
```

Room Service 消费 Kafka 消息后查询：

```go
SMEMBERS room:888:gateways
```

然后向对应节点发送：

```text
gw1
gw2
gw5
```

- **优点：**路由精准。
- **缺点：**热门房间会产生较大的 Redis 查询与状态维护压力。

---
<br/>

## 方案三：Kafka Partition 绑定 Gateway

这是大型直播系统的常见方案。假设 Topic 有 `256` 个 Partition、Gateway 集群有 `100` 个节点，Consumer Group 自动完成分配：

```text
Gateway-1
  partition 0-2

Gateway-2
  partition 3-5
```

完整路由关系：

```text
room_id
   |
 hash
   |
partition
   |
consumer
   |
gateway
   |
local room
```

该方案通过 Partition 与消费者的绑定完成路由，不需要查询 Redis。

> <h3 id="推荐生产方案：混合模型">推荐生产方案：混合模型</h3>

大型生产系统通常不会只使用一种方案，而是根据房间规模选择不同策略。

## 普通房间

普通房间使用 Owner 模式，例如在线人数少于 `10` 万：

```text

      ↓
```

热门房间需要拆分 Shard：

```text

  ↓

   ↓

```

房间结构：

```text

       |
       |
+------+------+
shard0 shard1 shard2
```

可根据用户 ID 分配 Shard：

```go
shard = uid % shardCount
```

| 能力 | gRPC | Kafka |
| --- | --- | --- |

> <h3 id="关键结论">关键结论</h3>

对于千万级连接，不要采用层层同步 gRPC 调用：

```text
Gateway
   |
 gRPC
   |
 Room
   |
 gRPC
   |
Gateway
```

应采用消息总线与内部推送组合：

```text
Gateway
   |
 Kafka
   |
Room Service
   |
Kafka / Internal Push
   |
Gateway
   |
Client
```

各组件职责如下：

- **Gateway：**维护连接并完成最终推送。
- **Room Service：**维护房间逻辑与路由关系。
- **Kafka：**承载跨节点消息流、削峰和故障恢复。
- **Redis：**负责状态发现与订阅关系存储。
- **ClickHouse：**存储历史消息和分析数据。

**核心原则：控制面使用 gRPC 与 Redis，数据面使用 Kafka；普通房间使用 Owner 模式，热门房间通过 Shard 分摊压力。**该架构可扩展到千万级 WebSocket 连接与亿级弹幕数据。


## <span id="代码实现后的-V7目标与准确结论">代码实现后的-V7 目标与准确结论</span>

参考 `/Users/ganghuang/Desktop/Temp.md` 中“Gateway 负责最终发送”“Local Room 使用 SendQueue 和 AsyncWrite”的原则，本轮继续优化 Gateway 最终推送层，不改变 Redis Pub/Sub、Kafka Outbox 或 ClickHouse 历史链路。

V6 已对房间广播使用 `MaxPendingBytes` 隔离慢连接，但以下 WebSocket 帧仍直接调用 `AsyncWrite`，没有共享同一个每连接预算：

- `danmaku.ack`。
- 命令 Error。
- Ping 请求对应的 Pong。
- 服务端心跳 Ping。
- Protocol、Unsupported Data、Normal Closure 和 Going Away Close 帧。

gnet 的固定 `WriteBufferCap` 超过后可以转入弹性缓冲，因此只限制房间广播不能形成完整的连接级硬边界。热门房间广播、命令响应和客户端 Ping 同时发生时，旁路帧仍可继续增加慢连接的待发送内存。

V7 将 Upgrade 后所有 WebSocket 帧收口到一个出站入口：

```text
Broadcast / ACK / Error / Pong / Heartbeat Ping / Close
                         |
                   hgWriteFrame
                         |
             atomic reserve pending bytes
                   /             \
              超过上限          预算内
                |                 |
             拒绝并关闭       gnet.AsyncWrite
                                  |
                         callback release bytes
```

准确结论是：**V7 在当前 Gateway 进程内为 Upgrade 后的全部 WebSocket 帧建立了统一、原子、每连接的待发送字节上限；已通过业务测试、20 次 race 检查、vet 和统一入口搜索，但尚未用真实慢速客户端和大规模热门房间压测验证断连速率、内存曲线与尾延迟。**

## <span id="统一WebSocket出站预算">统一 WebSocket 出站预算</span>

### 准确代码入口

实现文件：

```text
internal/modules/video_danmaku/realtime/hg_gnet_server.go
```

所有 Upgrade 后帧统一调用：

```go
func (s *Server) hgWriteFrame(c gnet.Conn, state *hgConnection, frame []byte) error {
	if c == nil || state == nil {
		return errors.New("danmaku connection state cannot be nil")
	}
	frameBytes := int64(len(frame))
	if !state.hgReservePendingWrite(frameBytes, int64(s.config.MaxPendingBytes)) {
		return hgErrPendingWriteLimit
	}
	err := c.AsyncWrite(frame, func(conn gnet.Conn, writeErr error) error {
		state.hgReleasePendingWrite(frameBytes)
		if writeErr != nil {
			_ = conn.Close()
		}
		return nil
	})
	if err != nil {
		state.hgReleasePendingWrite(frameBytes)
	}
	return err
}
```

预算预占与回滚：

```go
func (state *hgConnection) hgReservePendingWrite(frameBytes, maxPendingBytes int64) bool {
	if frameBytes <= 0 || maxPendingBytes <= 0 {
		return false
	}
	for {
		pendingBytes := state.pendingBytes.Load()
		if frameBytes > maxPendingBytes-pendingBytes {
			return false
		}
		if state.pendingBytes.CompareAndSwap(pendingBytes, pendingBytes+frameBytes) {
			return true
		}
	}
}

func (state *hgConnection) hgReleasePendingWrite(frameBytes int64) {
	state.pendingBytes.Add(-frameBytes)
}
```

### 为什么使用帧字节而不是消息条数

不同类型帧大小差异明显：心跳 Ping 只有少数字节，弹幕广播和 ACK 包含完整 JSON，Error 也受文案和 requestId 长度影响。使用消息条数会让同样的阈值对应完全不同的内存占用。

V7 继续使用已有：

```yaml
max_pending_bytes: 65536
```

该值表示单连接已提交到 gnet 异步写队列、但尚未由回调确认完成的 WebSocket 帧总字节预算。它不是房间级预算，也不是 Gateway 全局预算。

### 覆盖范围

代码搜索确认 realtime 包内 `AsyncWrite` 只剩 `hgWriteFrame` 内部一处。当前纳入预算的帧包括：

| 帧 | 调用位置 | 超限行为 |
| --- | --- | --- |
| `danmaku.created` | 房间广播 worker | 记录为慢连接并关闭 |
| `danmaku.ack` | 创建命令 worker | 关闭连接，客户端按既有 requestId 幂等回退 |
| Error | event-loop 或创建命令 worker | 关闭连接 |
| Pong | event-loop | 返回 `gnet.Close` |
| 心跳 Ping | 时间轮后台线程 | 关闭连接 |
| Close | 协议错误、客户端关闭、服务端关闭 | 尝试在预算内写出后关闭 |

HTTP `101 Switching Protocols` 握手不属于 Upgrade 后 WebSocket 帧，仍在连接所属 event-loop 内同步写出，不计入该预算。

## <span id="V7并发与失败语义">并发与失败语义</span>

### 原子预算边界

`pendingBytes` 是 `atomic.Int64`。广播 worker、命令 worker、心跳 goroutine 和 event-loop 可以同时为同一连接发送帧，预占操作必须跨这些执行上下文原子化。

每次发送遵循：

```text
pendingBytes += frameBytes
        |
是否超过 MaxPendingBytes
   /                 \
 是                   否
 |                    |
立即回滚          提交 AsyncWrite
返回超限错误       /          \
                 同步失败      异步完成
                    |             |
                 立即释放       回调释放
```

预占使用 CAS 循环，不先写入超限值再回滚，因此其他 writer 不会观察到瞬时越界，也不会因为另一个 writer 的临时越界而误拒绝本来可以容纳的小帧。每个成功预占恰好对应一次释放：

- `AsyncWrite` 同步返回错误时，由调用线程释放。
- `AsyncWrite` 成功接收后，只由异步回调释放。
- 超限时先回滚本次预占，不改变之前已排队帧的计数。

### 为什么命令携带 state

`gnet.Conn.Context()` 明确不是并发安全 API，只能在 EventHandler 中调用。ACK 和创建失败 Error 由后台命令 worker 发送，因此不能在 worker 中重新读取 `Context()`。

V7 在 event-loop 投递命令时同时保存已有连接状态：

```go
type hgCommand struct {
	conn      gnet.Conn
	state     *hgConnection
	userID    string
	requestID string
	request   VideoDanmakuDtoPackage.CreateRequest
}
```

`state` 的预算字段是原子值；worker 不修改 `videoID`、`userID`、限流字段或 event-loop 私有协议状态。

### 慢连接策略

V7 采用“单连接超限即关闭”，不阻塞发送方等待缓冲恢复：

- 不让 broadcast worker 被一个慢客户端拖住。
- 不让命令 worker 因写队列积压占满数据库任务并发。
- 不在 event-loop 中等待网络写。
- 不为每连接新增 channel、goroutine 或定时器。
- 连接关闭后由既有 `OnClose` 幂等释放房间成员、Redis 房间引用、心跳和连接计数。

对于 ACK 超限导致断线，结果可能已经成功写入 MySQL。客户端沿用既有 requestId 通过 HTTP 或重连后重试，数据库唯一键和幂等逻辑负责返回同一业务结果，不能生成新的 requestId 重复提交。

> <h2 id="grpc-go-与-Kitex-的架构差异">grpc-go 与 Kitex 的架构差异</h2>

## grpc-go

```text
Application
    |
 grpc-go
    |
HTTP/2 Transport
    |
 net.Conn
    |
Linux TCP
```

`grpc-go` 基于标准 HTTP/2 协议，跨语言能力较好。典型请求处理路径为：

```text
HTTP2 Stream
      ↓
  goroutine
      ↓
    codec
      ↓
   handler
```

## Kitex

```text
Application
    |
  Kitex
    |
  Codec
    |
 Netpoll
    |
Epoll/Kqueue
    |
   TCP
```

Kitex 配合 Netpoll，可减少 HTTP 层、Header 解析和部分 syscall 开销。

---
<br/>

## 为什么 Netpoll 更适合实时系统

原文将 Go 默认网络模型概括为：

```text
net.Conn
    |
goroutine per connection
    |
blocking read/write
```

百万连接可能对应大量 goroutine，从而增加 scheduler、goroutine stack 和 GC 压力。

Netpoll 使用 EventLoop 模型：

```text
EventLoop
    |
epoll/kqueue
    |
connection callback
```

其思路类似 Nginx Event Loop 和 Redis Reactor，更适合需要集中处理大量网络事件的场景。

## <span id="代码实现后的-V8目标与准确结论">代码实现后的-V8 目标与准确结论</span>

参考 `/Users/ganghuang/Desktop/Temp.md` 中 gnet Reactor、gobwas/ws 协议解析和 Gateway 最终维护 WebSocket 连接的设计，本轮继续补齐 Gateway 入站协议层，不引入 Kitex、Room Service 或新的数据面依赖。

V7 之前的入站校验包含：

```go
if ws.CheckHeader(header, ws.StateServerSide) != nil ||
    !header.Fin ||
    header.Length > int64(s.config.MaxFrameBytes) {
    // close
}
```

这会拒绝所有 `FIN=0` 的标准 WebSocket 数据帧，因此浏览器或中间库只要将一条文本消息拆成 `Text + Continuation`，即使命令内容和总长度都合法，也会收到 Protocol Error。同时，如果只删除 `!header.Fin` 而不保存协议状态和累计长度，攻击者可以通过大量小分片绕过单帧限制，持续占用每连接内存。

V8 实现：

```text
Text(FIN=0)
     |
保存 opcode 和首段 payload
     |
Ping / Pong / Close 可穿插
     |
Continuation(FIN=0)...
     |
累计长度不得超过 MaxFrameBytes
     |
Continuation(FIN=1)
     |
完整消息 UTF-8 校验、JSON 解析、限流和入队
```

准确结论是：**V8 已支持 RFC 6455 文本消息的 Fragment/Continuation 有界重组，使用 gobwas/ws 的 `StateFragmented` 校验分片顺序，允许控制帧穿插，并让单帧及完整重组消息共享现有 `MaxFrameBytes` 上限。新增协议状态只由连接所属 event-loop 访问，已通过业务测试、20 次 race、vet 和差异检查；尚未使用真实 TCP/WebSocket 分片客户端进行大规模网络压测。**

## <span id="Fragment与Continuation有界重组">Fragment 与 Continuation 有界重组</span>

### 连接状态

实现文件：

```text
internal/modules/video_danmaku/realtime/hg_gnet_server.go
```

每个连接新增两个仅由所属 event-loop 访问的字段：

```go
type hgConnection struct {
	upgraded, pending bool
	videoID, userID   string
	handshake         []byte
	fragmentPayload   []byte
	fragmentOpCode    ws.OpCode
	// 其他字段省略
}
```

- `fragmentOpCode == 0` 表示当前没有等待 Continuation 的消息。
- `fragmentOpCode == ws.OpText` 表示已收到文本首分片。
- `fragmentPayload` 只保存尚未完成的文本消息，不跨连接共享。
- 当前 JSON 命令协议不接受 Binary，因此 Binary 继续返回 Unsupported Data，不为未来未定义的二进制协议保留无效状态。

### gobwas 协议状态

V8 不自行复制完整 RFC 6455 Header 校验，而是将连接重组状态传给 gobwas/ws：

```go
func (state *hgConnection) hgWebSocketState() ws.State {
	webSocketState := ws.StateServerSide
	if state.fragmentOpCode != 0 {
		webSocketState = webSocketState.Set(ws.StateFragmented)
	}
	return webSocketState
}
```

OnTraffic 使用：

```go
if ws.CheckHeader(header, state.hgWebSocketState()) != nil {
	_ = s.hgWriteFrame(c, state, ws.CompiledCloseProtocolError)
	return gnet.Close
}
```

因此 gobwas/ws 负责保证：

- 客户端帧必须带 Mask。
- RSV 位在未协商扩展时必须为零。
- 控制帧必须 `FIN=1` 且 payload 不超过 125 字节。
- 没有分片消息时禁止无前序的 Continuation。
- 等待 Continuation 时禁止新的 Text 或 Binary 数据帧。
- 等待 Continuation 时允许 Ping、Pong 和 Close 控制帧穿插。

### 有界重组准确代码

```go
func (state *hgConnection) hgAcceptDataFrame(
	header ws.Header,
	payload []byte,
	maxMessageBytes int,
) ([]byte, error) {
	switch header.OpCode {
	case ws.OpBinary:
		return nil, hgErrUnsupportedData
	case ws.OpText:
		if header.Fin {
			return payload, nil
		}
		state.fragmentOpCode = header.OpCode
		// OnTraffic 已复制出独立 payload，直接接管首分片，避免重复复制。
		state.fragmentPayload = payload
		return nil, nil
	case ws.OpContinuation:
		if state.fragmentOpCode == 0 {
			return nil, ws.ErrProtocolContinuationUnexpected
		}
		if len(payload) > maxMessageBytes-len(state.fragmentPayload) {
			state.fragmentPayload = nil
			state.fragmentOpCode = 0
			return nil, hgErrFragmentMessageTooBig
		}
		state.fragmentPayload = append(state.fragmentPayload, payload...)
		if !header.Fin {
			return nil, nil
		}
		message := state.fragmentPayload
		state.fragmentPayload = nil
		state.fragmentOpCode = 0
		return message, nil
	default:
		return nil, ws.ErrProtocolOpCodeReserved
	}
}
```

`len(payload) > maxMessageBytes-len(state.fragmentPayload)` 使用减法比较，避免先做长度加法产生整数溢出边界。生产调用在进入该函数前已经保证每一个物理帧的 `header.Length <= MaxFrameBytes`；重组函数再保证所有数据分片的累计 payload 不超过同一上限。

`OnTraffic` 在解除 Mask 后已将当前 payload 从 gnet 入站缓冲复制为独立 slice，首分片由连接状态直接接管，不进行第二次同字节复制；后续 Continuation 才按累计长度扩展该 slice。

完成最终 Continuation 后，代码先把 slice 返回给本次 event-loop 调用，再将连接字段设为 `nil`，因此：

- 本次调用仍可完成 UTF-8 和 JSON 解析。
- 连接不再长期持有已经完成消息的 backing array。
- 超限时也立即清空重组状态，然后发送 Close 1009 并关闭连接。

## <span id="V8协议与内存边界">V8 协议与内存边界</span>

### 配置语义

V8 不新增配置，继续使用：

```yaml
max_frame_bytes: 4096
```

配置名和默认值不变。其准确语义扩展为：

1. 任意单个客户端 WebSocket 帧的 payload 上限。
2. 一条完整客户端 WebSocket 数据消息在 Fragment/Continuation 重组后的 payload 上限。

这保证客户端不能通过以下方式绕过 4096 字节限制：

```text
4096 个 1 字节分片
或
多个各自小于 4096 字节、累计远大于 4096 字节的分片
```

分片重组会给正在发送分片消息的连接增加最多 `MaxFrameBytes` 级别的长期连接状态。帧解析过程中仍存在当前入站帧 payload 副本，因此瞬时应用层内存不能简单表述为“每连接严格只有 4096 字节”；还需要计入 gnet read buffer、当前帧副本、结构体、出站预算和内核 socket buffer。

### 完整消息处理顺序

只有收到最终分片后才执行：

```text
完整 payload
    |
UTF-8 校验
    |
JSON Unmarshal
    |
command type 校验
    |
连接令牌桶
    |
有界 command queue
```

这避免对半条 JSON 重复解析，也不会让一个逻辑命令按分片数量重复消耗令牌或重复进入数据库 worker。

### Close 状态码映射

| 场景 | Close 帧 | 含义 |
| --- | --- | --- |
| Mask、RSV、Continuation 顺序或控制帧规则错误 | `CompiledCloseProtocolError` | 1002 Protocol Error |
| Binary 数据消息 | `CompiledCloseUnsupportedData` | 1003 Unsupported Data |
| 完整文本不是合法 UTF-8 | `CompiledCloseInvalidFramePayloadData` | 1007 Invalid Payload |
| 单帧或重组总消息超过 `MaxFrameBytes` | `CompiledCloseMessageTooBig` | 1009 Message Too Big |

所有 Close 帧继续经过 V7 的 `hgWriteFrame`，共享 `MaxPendingBytes` 出站预算。当前实现仍是尝试异步写 Close 后立即关闭 TCP，因此状态码在极端网络条件下不保证送达；V8 没有扩大这项结论。

### 并发边界

`fragmentPayload` 和 `fragmentOpCode` 只在 `OnTraffic` 及其直接调用函数中读写。gnet 保证同一连接的 EventHandler 由所属 event-loop 串行执行，因此该状态不使用 mutex 或 atomic。

后台执行上下文仍只访问已有安全字段：

- 命令 worker 使用 event-loop 传入的 `hgConnection`，只操作原子出站预算。
- 心跳线程读取原子活动时间、时间轮元数据和原子出站预算。
- 广播 worker 使用房间锁读取连接并操作原子出站预算。
- 后台线程不读取或修改分片重组状态。

## <span id="滚动发布与优雅下线">滚动发布与优雅下线</span>

### 滚动策略

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

该策略先创建额外新 Pod，新 Pod 通过 startup 和 readiness 后，Deployment 才开始淘汰旧 Pod。它能避免发布过程主动减少 ready 副本数，但不能阻止节点故障、资源不足、依赖故障或 Ingress 配置错误造成容量下降。

### 探针职责

| 探针 | 路径 | 语义 |
| --- | --- | --- |
| startup | `/healthz` | 给进程和依赖初始化最多约 60 秒，不在启动完成前执行其他探针 |
| readiness | `/readyz` | 检查 MySQL、Redis、Kafka、Kafka runtime 和弹幕 realtime readiness |
| liveness | `/healthz` | 只检查进程能响应，不因外部依赖抖动重启容器 |

探针通过容器内 loopback 执行：

```yaml
exec:
  command:
    - /bin/sh
    - -c
    - wget -q -T 2 -O /dev/null http://127.0.0.1:9091/readyz
```

这样不会依赖 kubelet 探针源地址是否被当前 CNI 的 NetworkPolicy 放行。Alpine 3.20 自带 BusyBox `wget`；该结论通过最终镜像构建和容器 shell 验证了镜像可运行，但未连接真实基础设施执行 readyz。

### 终止时间线

```text
Pod 进入 Terminating
        |
EndpointSlice / Ingress 开始摘流
        |
preStop sleep 10s
        |
Kubernetes 发送 SIGTERM
        |
应用 Shutdown 最多 10s
├── HTTP server.Shutdown
├── management server.Shutdown
└── realtime.Close
        |
剩余约 20s 调度与网络安全余量
        |
40s 总 grace period 到期后才可能 SIGKILL
```

准确清单：

```yaml
terminationGracePeriodSeconds: 40
lifecycle:
  preStop:
    exec:
      command:
        - /bin/sh
        - -c
        - sleep 10
```

现有应用收到 SIGTERM 后会停止 HTTP、管理端口和 gnet 网关；gnet 会尝试发送 Going Away Close 后关闭连接。WebSocket 连接不会迁移到新 Pod，客户端仍必须实现带抖动和退避的重连。`preStop` 只为负载均衡配置传播留出时间，不等于无损连接迁移。

### PDB

```yaml
kind: PodDisruptionBudget
spec:
  minAvailable: 2
```

当前 Deployment 默认 3 个副本，PDB 对节点排空等 voluntary disruption 至少保留两个可用副本。PDB 不防止进程崩溃、节点突然断电等 involuntary disruption；若副本数调整到 1 或 2，必须同步调整 `minAvailable`。

> <h2 id="Gateway服务优雅上下线">Gateway 服务优雅上下线</h2>

Gateway 使用 `gnet + gobwas/ws` 承载 WebSocket 长连接时，Kubernetes 发布的核心目标是：**旧 Pod 先停止接收新连接，再通知客户端重连、等待存量连接退出，最后关闭进程；新 Pod 负责承接新流量。**

```text
SIGTERM
   ↓
Readiness 失败，Service 摘除 Endpoint
   ↓
停止接受新连接
   ↓
通知客户端重连到可用 Gateway
   ↓
等待存量连接退出
   ↓
超时后关闭剩余连接并退出
```

> **注意：** WebSocket/TCP 连接不能直接从旧 Pod 搬到新 Pod。本文中的 `Connection Migration` 指旧 Gateway 下发 `redirect/drain` 指令，由客户端重新连接新 Gateway，并通过 Redis、Kafka 等外部状态恢复会话。

> <h3 id="普通RollingUpdate的问题">普通 RollingUpdate 的问题</h3>

普通 Deployment 在删除旧 Pod 时，进程收到 `SIGTERM` 后直接退出，现有 WebSocket 连接会同时断开：

```text
旧版本:

gateway-v1
    |
    |
 100000 websocket

kubectl rollout
    ↓
删除 Pod
    ↓
SIGTERM
    ↓
进程退出
    ↓
100000 用户断线
```

这会引发用户重连风暴、登录压力暴涨、Redis 压力增加、Kafka 消息乱序，以及热门直播间大量连接瞬间丢失。因此，Gateway 下线前必须进入 **Drain** 阶段。

> <h3 id="优雅下线实现">优雅下线实现</h3>

### 定义生命周期状态

目录：

```text
gateway/internal/lifecycle
└── state.go
```

```go
package lifecycle

import "sync/atomic"

type State int32

const (
	StateStarting State = iota
	StateReady
	StateDraining
	StateStopped
)

var current int32

func Set(s State) {
	atomic.StoreInt32(&current, int32(s))
}

func Get() State {
	return State(atomic.LoadInt32(&current))
}
```

`atomic` 保证生命周期状态可被信号处理、健康检查和连接处理逻辑并发读取。

---
<br/>

### Readiness Probe 主动摘流

Drain 时必须让 Kubernetes 停止向旧 Pod 发送新连接。Gateway 进入 `StateDraining` 后，`/health/readiness` 返回 `503`：

```go
func readiness(w http.ResponseWriter, r *http.Request) {
	if lifecycle.Get() == lifecycle.StateDraining {
		w.WriteHeader(http.StatusServiceUnavailable)
		return
	}

	w.WriteHeader(http.StatusOK)
}
```

启动健康检查服务：

```go
http.HandleFunc("/health/readiness", readiness)
http.ListenAndServe(":8080", nil)
```

Deployment 配置：

```yaml
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: gateway
          readinessProbe:
            httpGet:
              path: /health/readiness
              port: 8080
            periodSeconds: 5
```

发布时的摘流过程：

```text
Pod 收到 SIGTERM
        ↓
Gateway 进入 DRAINING
        ↓
Readiness 返回 503
        ↓
Service 删除 Endpoint
        ↓
不再向旧 Pod 分配新连接
```

Readiness 变更到 Endpoint 摘除并非瞬时完成，因此应用层仍需拒绝新连接，形成双重保护。

---
<br/>

### 监听 SIGTERM

```go
func waitShutdown(server *GatewayServer) {
	sig := make(chan os.Signal, 1)
	signal.Notify(sig, syscall.SIGTERM, syscall.SIGINT)

	<-sig
	server.Drain()
}
```

Kubernetes 删除 Pod 时会先发送 `SIGTERM`，应用收到信号后进入 Drain，而不是立即退出。

---
<br/>

### Drain 流程

```text
SIGTERM
   |
   |
停止 accept
   |
   |
通知客户端
   |
   |
等待连接迁移
   |
   |
关闭剩余连接
```

```go
func (s *Server) Drain() {
	lifecycle.Set(lifecycle.StateDraining)

	// 1.停止新连接
	s.gnet.StopAccept()

	// 2.通知客户端
	s.connections.Range(func(_, v any) bool {
		conn := v.(*Connection)
		conn.Send([]byte("server_draining"))
		return true
	})

	// 3.等待
	time.Sleep(60 * time.Second)

	// 4.关闭
	s.Close()
}
```

生产实现通常还应在全部连接提前退出时立即结束等待，而不是固定休眠完整的 `60s`；Drain 总时长必须小于 `terminationGracePeriodSeconds`，否则 Kubernetes 最终会发送 `SIGKILL`。

---
<br/>

### 停止接受新连接

如果当前 `gnet` 封装没有直接关闭监听器的能力，可维护 `accepting` 状态，在 `OnOpen` 中拒绝 Drain 期间到达的新连接：

```go
type Server struct {
	accepting atomic.Bool
}

func (s *Server) StopAccept() {
	s.accepting.Store(false)
}
```

```go
func OnOpen(c gnet.Conn) {
	if !accepting.Load() {
		c.Close()
		return
	}
}
```

该方式不会阻止 TCP 握手本身，只会在连接进入应用后立即关闭；是否能真正停止监听，应以所用 `gnet` 版本提供的 API 为准。

> <h3 id="客户端重连迁移">客户端重连迁移</h3>

### Redirect 协议

旧 Gateway 不应只等待连接被动断开，而应通知客户端主动重连：

```text
gateway-v1
  user100
     |
     | redirect
     ↓
gateway-v2
```

旧 Gateway 下发控制消息：

```json
{
  "type": "redirect",
  "server": "gateway-v2"
}
```

可使用 Protobuf 定义 WebSocket 控制协议：

```protobuf
message ServerCommand {
  enum Type {
    DRAIN = 0;
    REDIRECT = 1;
  }

  string endpoint = 2;
}
```

客户端收到 `DRAIN/REDIRECT` 后，应建立新连接并完成鉴权、订阅恢复，再关闭旧连接。为避免迁移期间消息重复或丢失，业务协议还需要配合消息序号、幂等处理或断点续传机制。

---
<br/>

### 查找可用 Gateway

Gateway 可将实例信息注册到 Redis：

```text
gateway:list
```

```json
[
  {
    "id": "gw1",
    "addr": "10.0.0.1"
  },
  {
    "id": "gw2",
    "addr": "10.0.0.2"
  }
]
```

客户端收到 `redirect` 后请求 Gateway Router：

```text
GET gateway-router
```

返回新的可用节点：

```text
gateway-v3
```

客户端通常不应直接访问 Pod IP，Router 应返回可路由的域名、端口或接入层地址。

### Gateway 注册与心跳

Gateway 启动时注册实例，并设置较短 TTL：

```go
func Register() {
	redis.Set(
		ctx,
		"gateway:"+id,
		addr,
		10*time.Second,
	)
}
```

每 `5s` 续期，超过 `10s` 未续期的节点自动失效：

```go
for {
	redis.Expire(ctx, key, 10*time.Second)
	time.Sleep(5 * time.Second)
}
```

进入 Drain 后应停止续期或把实例标记为 `DRAINING`，避免 Router 继续把客户端分配到旧 Gateway。

### 连接状态外置

用户状态不能只保存在 Gateway 内存中，否则客户端连接新 Gateway 后无法恢复。

错误方式：

```text

```

正确方式是将会话状态外置到 Redis：

```text

  room:888,
  token:xxx

```

用户加入、离开等事件可写入 Kafka：

```text

```

新 Gateway 在客户端重连后读取外部状态，恢复鉴权信息、房间关系和订阅。Redis/Kafka 只能提供状态恢复基础，具体一致性仍需由业务协议保证。

> <h3 id="Kubernetes发布流程">Kubernetes 发布流程</h3>

执行发布：

```bash

```

完整流程：

1. Kubernetes 创建新 Pod，状态为 `STARTING`。
2. 新 Pod 健康检查通过，进入 `READY` 并加入 Service。

5. 旧 Gateway 停止接收新连接。
6. 旧 Gateway 通知客户端重新连接，新 Gateway 恢复外置状态。
7. 存量连接清空或超时后，旧 Gateway 关闭并退出。

```text
    |
Helm upgrade
    |
Kubernetes
    |
New Gateway Pod
    |
Readiness OK
    |
Traffic Shift
    |
Old Gateway Drain
    |
Connection Migration
    |
Shutdown
```

### 连接数量保护

每个 Gateway 设置连接上限，避免单个 Pod 过载：



### Pod 驱逐保护

使用 `PodDisruptionBudget` 限制自愿中断时同时不可用的 Pod 数量：

```yaml

metadata:
  name: gateway-pdb
spec:
  minAvailable: 90%
  selector:
    matchLabels:
      app: gateway
```

这可防止节点维护等自愿驱逐一次下线大量 Gateway，但不保证节点故障、资源耗尽等非自愿中断不发生。

> <h3 id="最终生产架构">最终生产架构</h3>

```text
                   LoadBalancer
                         |
              Kubernetes Service
                         |
        +----------------+----------------+
        |                                 |
   Gateway-v2                       Gateway-v1
   READY                            DRAINING
        |                                 |
   New Users                       Old Users
        |                                 |
        +-------------+-------------------+
                      |
              Redis Session State
                      |
                 Room/Kafka
```

核心原则：

1. **Kubernetes 删除 Gateway 时，应用不能收到信号后立即退出。**
2. **收到 `SIGTERM` 后先进入 Drain，并通过 Readiness 主动摘流。**
3. **应用层停止接受新 WebSocket，处理 Endpoint 更新期间的时间窗口。**
4. **客户端必须支持 `DRAIN/REDIRECT` 后重连，而不是依赖连接跨 Pod 转移。**
5. **用户会话和业务状态必须外置到 Redis、Kafka 或其他共享系统。**
6. **Drain 必须有超时兜底，并小于 `terminationGracePeriodSeconds`。**
7. **无损发布是多层协作结果，仍需结合客户端重试、协议幂等和容量冗余。**

这套流程可显著降低百万至千万级 WebSocket 系统发布时的集中掉线风险，但“零中断”仍取决于客户端迁移协议、消息一致性设计和基础设施配置。

> <h2 id="代码实现后的-Prometheus+OpenTelemetry实现B站级弹幕系统链路监控">代码实现后的-Prometheus + OpenTelemetry 实现 B 站级弹幕系统链路监控</h2>

在千万连接实时系统中，只监控 CPU 和内存无法定位业务问题，还需要回答：当前有多少 WebSocket 在线、哪个 Gateway 延迟升高、弹幕从发送到展示用了多久、Kafka 是否积压、哪个 Room 是热点，以及一条弹幕经过了哪些服务。

## <span id="代码实现后的-V10目标与准确结论">代码实现后的-V10 目标与准确结论</span>

V10 的目标是补齐弹幕实时链路的低开销、固定基数 Prometheus 指标和可执行告警规则，使运维能够回答：

1. 每个 Pod 当前有多少已认证 WebSocket。
2. 本地有多少活跃房间。
3. 命令队列和广播队列是否持续饱和。
4. Redis 发布是否失败。
5. 实时广播是否因本地队列满而丢弃。
6. 慢客户端是否持续触发出站预算。
7. 本地房间扇出调度 P99 是否升高。

准确结论：

- 已实现的是进程内实时链路 Metrics，不是完整分布式 Trace。
- `/metrics` 只读取原子计数和有界 channel 的瞬时长度，不访问 MySQL、Redis、Kafka，也不扫描全量连接或成员。
- 没有任何指标使用 `video_id`、`user_id`、`request_id`、连接 ID、IP 或错误文本标签。
- `AsyncWrite` 成功只表示 gnet 接受异步调度，不表示客户端已经收到或渲染。
- `broadcast_duration_seconds` 是本机扇出调度耗时，不是端到端展示耗时。
- 本轮没有证明支撑千万连接；它补齐了容量和过载观测能力，真实容量仍需分布式压测与基础设施验证。

## <span id="真实可观测链路">真实可观测链路</span>

## <span id="V10Prometheus指标设计">Prometheus 指标设计</span>

### Gauge

| 指标 | 准确含义 |
| --- | --- |
| `mlc_video_danmaku_websocket_connections` | 当前进程中票据、Redis 订阅和 Upgrade 均成功的连接数 |
| `mlc_video_danmaku_websocket_connection_limit` | 当前进程配置的原始 TCP admission 上限 |
| `mlc_video_danmaku_active_rooms` | 当前 Pod 中至少有一个 Upgrade 连接的本地房间数 |
| `mlc_video_danmaku_command_queue_size` | 命令 channel 抓取瞬间的近似长度 |
| `mlc_video_danmaku_command_queue_capacity` | 命令 channel 固定容量 |
| `mlc_video_danmaku_broadcast_queue_size` | 所有广播 worker channel 的近似长度之和 |
| `mlc_video_danmaku_broadcast_queue_capacity` | 所有广播 worker channel 容量之和 |
| `mlc_video_danmaku_outbound_pending_bytes` | 当前进程所有已预占、尚未完成的 gnet 异步写字节总量 |

连接数与连接上限不是完全相同口径：前者只统计 Upgrade 成功连接，后者限制从 `OnOpen` 开始的 TCP 连接。二者比值用于容量预警，不替代 admission 的真实原子计数。

`active_rooms` 是本地值。若同一视频的观众分布在三个 Pod，Prometheus 对三个 Pod 求和会重复计算该视频，不能把结果称为全局去重视频数。

| 指标 | 固定标签 | 准确含义 |
| --- | --- | --- |
| `mlc_video_danmaku_commands_received_total` | 无 | 完整文本消息进入命令解析的次数 |
| `mlc_video_danmaku_command_rejections_total` | `reason=invalid_command/rate_limited/queue_full` | 持久化前拒绝次数 |
| `mlc_video_danmaku_command_create_failures_total` | 无 | `Service.Create` 失败次数 |
| `mlc_video_danmaku_broadcast_publish_total` | `result=success/failure` | MySQL 提交后 Redis 发布结果 |
| `mlc_video_danmaku_broadcast_queue_dropped_total` | 无 | 本地广播队列满导致实时副本丢弃次数 |
| `mlc_video_danmaku_broadcasts_total` | 无 | 本进程处理的本地广播事件数 |
| `mlc_video_danmaku_broadcast_recipient_writes_total` | `result=queued/failed` | 接收者写入被 gnet 接受或调度失败的次数 |
| `mlc_video_danmaku_outbound_write_failures_total` | `reason=pending_budget/async_write/callback` | 出站预算、同步投递、异步回调失败次数 |

所有固定标签即使为零也会输出，便于 Dashboard 和告警从进程启动时保持稳定时序。

### Histogram

```text
mlc_video_danmaku_broadcast_duration_seconds
```

桶边界：

```text
1ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, +Inf
```

计时边界从 `hgBroadcastLocal` 开始，到以下操作完成为止：

1. JSON 编码。
2. WebSocket Frame 编译。

应用自身每个 target 约 34 条固定时序，不随用户数、连接数、视频数或消息数增长。抓取目标添加的 `instance`、`service`、`environment` 属于 Prometheus 服务发现维度，不由业务消息动态生成。

## <span id="V10并发与性能边界">并发与性能边界</span>

### WebSocket 一次计数

`hgConnection.websocketCounted` 使用 `atomic.Bool`：

```go
func (s *Server) hgCountWebSocketConnection(state *hgConnection) {
	if state != nil && state.websocketCounted.CompareAndSwap(false, true) {
		s.metrics.websocketConnections.Add(1)
	}
}

func (s *Server) hgReleaseWebSocketConnection(state *hgConnection) {
	if state != nil && state.websocketCounted.CompareAndSwap(true, false) {
		s.metrics.websocketConnections.Add(-1)
	}
}
```

只有 Upgrade 成功后增加，关闭路径只释放一次。它不复用 `upgraded bool` 做跨生命周期同步，避免异步升级和连接关闭重叠时重复扣减。

### 活跃房间切换

房间 gauge 在已有 directory 锁内更新：

- `room == nil` 创建首个本地房间时 `+1`。
- `memberCount` 从 1 降到 0、删除房间时 `-1`。

抓取 `/metrics` 不需要遍历 room map 或 member map，不会让监控抓取成本随连接规模线性增长。

### 出站字节精确释放

`hgWriteFrame` 只有在连接预算预占成功后才增加进程级 pending bytes，并保持单一释放所有权：

- `AsyncWrite` 接受：由 callback 释放连接和进程两级字节。
- `AsyncWrite` 同步返回错误：调用方立即释放，callback 不拥有该预占。
- 预算拒绝：不增加 pending bytes，只增加 `reason="pending_budget"`。

该设计避免同步错误与 callback 双重释放造成负 gauge。

### Histogram 热路径

直方图使用固定数组和原子计数，不引入第三方 registry、锁或后台 goroutine。每次广播只增加 sum、count 和一个非累计桶；抓取时再转换为 Prometheus 累计 bucket。

## <span id="V10告警规则与多副本语义">告警规则与多副本语义</span>

新增六条规则：

1. `MLCVideoDanmakuWebSocketCapacityHigh`：单 Pod 已认证连接与 admission limit 比值持续 5 分钟超过 90%。
2. `MLCVideoDanmakuCommandQueueHigh`：任一 Pod 命令队列持续 5 分钟超过 80%。
3. `MLCVideoDanmakuBroadcastQueueHigh`：任一 Pod 广播队列持续 5 分钟超过 80%。
4. `MLCVideoDanmakuBroadcastDrops`：多 Pod 合计丢弃速率持续 2 分钟大于零，触发 critical。
5. `MLCVideoDanmakuOutboundBackpressure`：出站预算拒绝持续 5 分钟出现，触发 warning。
6. `MLCVideoDanmakuBroadcastSchedulingLatencyHigh`：本地广播调度 P99 持续 10 分钟超过 100ms。

容量与队列规则使用 `max by (service, environment)`，不能用跨 Pod 平均值，否则一个饱和 Pod 会被其他空闲 Pod 掩盖。Counter 规则先对每个实例执行 `rate()`，再按服务和环境求和。Histogram 必须先按 `le`、`service`、`environment` 聚合 bucket，再计算 `histogram_quantile`。

CI 从只测试一个评论规则文件改为遍历 `deployments/monitoring/tests/*.yml`，后续新增行为测试不会被静默遗漏。

## <span id="V10OpenTelemetry取舍">OpenTelemetry 取舍</span>

V10 没有直接引入 OpenTelemetry，原因不是技术上不可行，而是当前仓库尚缺少一组必须一起确定的语义：

1. HTTP request 与 WebSocket 单命令的 Trace Context 创建方式。
2. Redis Pub/Sub payload 的上下文传播或 span link。
3. Outbox 落库后跨时间异步 dispatch 的 trace metadata 保留。
4. Kafka producer/consumer propagation。
5. Collector、Tempo/Jaeger、采样率、属性白名单和 shutdown flush。
6. 客户端渲染回执、时钟偏差和采样防滥用。

如果只在 Gateway 收到消息时创建一个 span，却不解决 Redis、Outbox 和 Kafka 的异步边界，会得到看似完整但实际错误的链路。因此本轮先建立 Metrics 基线，后续把 tracing 作为跨模块独立版本处理。

># <h1 id="B站级弹幕系统设计V11">B站级弹幕系统设计 V11</h1>

V11 按照 `/Users/ganghuang/Desktop/Temp.md` 的 Kubernetes Graceful Shutdown、Drain 和 Zero Downtime Deployment 方向继续优化。当前工程不是独立 Gateway 微服务，而是一个 `mlc-go` 进程同时承载业务 HTTP、gnet WebSocket 和管理端口，因此本版本只实现与真实架构一致、能够验证的两阶段 Drain，不虚构透明连接迁移。

## <span id="V11目标与准确结论">V11 目标与准确结论</span>

目标生命周期：

```text
STARTING
   |
   v
SERVING
   |
   | SIGTERM / listener failure
   v
DRAINING
   |
   | existing WebSocket reaches zero or drain_timeout expires
   v
STOPPED
```

准确结论：

- SIGTERM 后 realtime 先进入 `DRAINING`，`/readyz` 立即因 realtime `Ready()` 失败而返回 503。
- 新 TCP 连接在 `OnOpen` 被关闭；已经开始 Redis 票据校验但尚未激活的迟到握手也会被拒绝。
- 已存在 WebSocket 收到 RFC 6455 `1001 Going Away` Close Frame；发送 Close 后不再调度业务数据帧，服务端等待最多 `drain_timeout`，再强制关闭残余连接。
- Drain 期间业务 HTTP 先执行标准库 `Shutdown`，management 最后关闭，因此 `/healthz`、`/readyz` 和 `/metrics` 可持续观察。
- management Service 使用 `publishNotReadyAddresses: true`，防止 Pod NotReady 后 Prometheus 同时失去 Drain 指标。
- 这不是 TCP/WebSocket 透明迁移。客户端仍需收到 `1001` 后带随机抖动重连稳定 WebSocket 入口，并重新申请一次性 ticket。
- 没有新增 `redirect` 消息、Gateway 注册中心或具体 Pod 地址，避免在客户端协议和新票据流程未确定时制造不可用的伪迁移能力。

## <span id="V11两阶段Drain实现">V11 两阶段 Drain 实现</span>

### 生命周期状态

`internal/modules/video_danmaku/realtime/hg_gnet_server.go` 使用固定原子枚举：

```go
type hgLifecycleState int32

const (
	hgLifecycleStarting hgLifecycleState = iota
	hgLifecycleServing
	hgLifecycleDraining
	hgLifecycleStopped
)
```

`OnBoot` 只允许 `STARTING -> SERVING`，已经进入 Drain 的 Server 不能重新回到 Serving。`Ready()` 只有在 `SERVING` 且 Redis room router 可用时成功。

### BeginDrain

```go
func (s *Server) BeginDrain() {
	// 原子切换为 DRAINING；重复调用不重复发送 Close Frame 或增加指标。
	// 随后获取当前已激活 WebSocket 快照，发送 1001 Going Away。
}
```

`BeginDrain` 的行为：

1. 幂等切换 `SERVING -> DRAINING`。
2. 记录 Drain 开始时间与次数。
3. 使 readiness 立即失败。
4. 阻止新 `OnOpen` 连接进入。
5. 阻止异步票据校验的迟到 Upgrade 激活。
6. 向当前已激活 WebSocket 调度 `1001 Going Away`，但不立即关闭 TCP。
7. 连接进入 closing 后停止业务广播、ACK/error 和 heartbeat 数据帧，避免违反 RFC 6455 Close 语义。

### 握手与 Drain 竞态

异步握手必须处理以下时序：

```text
event-loop 收到握手
        |
Redis ConsumeTicket
        |
SIGTERM -> DRAINING
        |
runnable 返回 event-loop
```

V11 使用只覆盖“生命周期切换与握手激活”的短 `RWMutex`：

- `hgActivateWebSocket` 持读锁检查 Serving 并完成本地状态、房间、连接 gauge 和心跳注册。
- `BeginDrain` 持写锁切换到 Draining，确保切换完成后不会再出现新的成功激活。
- 房间全量快照和网络写不持有该锁，避免连接规模放大临界区。

同时把 HTTP `101 Switching Protocols` 的实际写出移动到 `hgActivateWebSocket` 成功之后。Drain 期间迟到 runnable 不会出现“客户端收到 101，但服务端没有注册房间”的半激活连接。

### 等待与强制关闭

```go
func (s *Server) WaitForDrain(ctx context.Context) error
func (s *Server) Close(ctx context.Context) error
```

`WaitForDrain` 每 100ms 读取原子 WebSocket gauge，不扫描连接或房间；连接归零立即返回。deadline 到期只增加 timeout counter，随后 `Close`：

1. 获取仍存在的已激活连接。
2. 累计强制关闭数量。
3. 关闭残余连接。
4. 取消 worker、Redis room router 和 heartbeat。
5. 等待后台 goroutine。
6. 停止 gnet engine 并进入 `STOPPED`。

## <span id="V11应用关闭顺序">V11 应用关闭顺序</span>

`main_mlc_project.go` 的准确关闭顺序：

```text
SIGTERM
  |
realtime.BeginDrain()
  |  /readyz -> 503, existing management remains observable
business HTTP Shutdown (10s independent deadline)
  |
realtime.WaitForDrain (configured 30s)
  |
realtime.Close (10s independent deadline)
  |
management HTTP Shutdown (10s independent deadline)
  |
deferred application Close: jobs -> Kafka -> Redis/MySQL -> logger
```

与 V10 前的顺序相比：

- 不再让 business、management 和 realtime 顺序共享同一个 10 秒 context。
- 某一阶段失败不会跳过后续 listener 的关闭；错误通过 `errors.Join` 汇总。
- management 不会在 Drain 开始时立即关闭。
- 任一 listener 非预期退出时，也会触发同一套关闭流程并等待其余 Serve goroutine 返回。
- Serve goroutine 的最终等待也有 10 秒上限；listener 未按时退出会返回剩余数量，不会无限阻塞到 kubelet SIGKILL。

## <span id="V11配置与Kubernetes预算">V11 配置与 Kubernetes 预算</span>

新增配置：

```yaml
video_danmaku:
  drain_timeout: 30s
```

配置缺失时兼容默认 `30s`，校验范围为 `5s-30s`。上限必须与当前 120 秒 Kubernetes 硬终止预算一起约束，不能允许配置为 2 分钟后再叠加 HTTP、gnet、management 和资源关闭时间。Deployment 调整为：

```yaml
terminationGracePeriodSeconds: 120
automountServiceAccountToken: false
```

当前预算：

```text
10s preStop Endpoint/Ingress 传播
30s WebSocket Drain
10s business HTTP Shutdown
10s realtime final Close
10s management Shutdown
20s timeout 指标抓取窗口（仅 Drain 超时时启用）
20s 调度、Kafka/资源关闭和安全余量
= 120s
```

这些阶段并不保证全部耗满，也不是严格串行最坏值证明；120 秒是当前清单给 kubelet 的硬上限。真实生产仍需测量目标 Ingress 的 EndpointSlice 收敛 P99 和 Kafka flush 时间后校准。

Pod 不访问 Kubernetes API，因此关闭 ServiceAccount Token 自动挂载，减少容器失陷后的凭据暴露面。

ServiceMonitor 新增固定标签：

```yaml
relabelings:
  - targetLabel: service
    replacement: mlc-go
  - targetLabel: environment
    replacement: prod
```

这与现有按 `service/environment` 聚合的告警规则一致，避免依赖 Operator 生成且可能变化的发现标签。

### 兼容性与潜在影响

- HTTP API、WebSocket 路径、ticket API、`danmaku.create`、ACK/error 和广播 payload 未改变。
- 发布时旧连接不再立即 TCP Close，而是先收到标准 `1001` 并获得最多 30 秒关闭窗口。
- 现有客户端若不响应 Close，连接会在窗口后强制关闭；因此仍依赖客户端重连能力。
- Drain 开始后尚未完成的一次性 ticket 校验会被拒绝，该 ticket 已可能被 Redis 消费，客户端必须重新申请 ticket，这是有意的安全边界。
- Drain 不停止 Redis Pub/Sub、命令 worker 或 heartbeat，已有连接在窗口内仍可完成控制帧和在途工作；最终 Close 才取消后台 goroutine。
- 已发送 Close 的连接不再发送业务数据帧；已进入 worker 的命令仍可完成持久化，但 ACK 若因连接 closing 无法发送，客户端必须按原有 requestId 幂等语义处理结果未知。
- Drain 超时后 management 额外保留 20 秒，至少跨过一个 15 秒 ServiceMonitor 周期，使 timeout、force-close 和最终耗时有机会被抓取；正常连接归零不增加该等待。
- management Service 发布 NotReady 地址只影响管理服务发现，不会让 business/realtime Service 继续向 Draining Pod 发送流量。
- `terminationGracePeriodSeconds: 120` 会让异常无法退出的 Pod 最长保留更久，但正常进程完成后会立即退出，不固定等待 120 秒。
- 本轮仍不是无感连接迁移，也没有证明零掉线；准确能力是 readiness-first、有界 Graceful Drain 和可观测强制回收。
