> <h2 id="B站级弹幕系统设计V1">B站级弹幕系统设计V1</h2>

目标：使用 Go 实现仿 B 站、斗鱼、虎牙的弹幕系统，支撑**千万并发连接和亿级弹幕数据**。

核心不在于单个 WebSocket 库，而在于：**连接模型、房间广播模型、消息削峰、冷热数据分离**。

***
<br/>

> <h3 id="Redis的用途">Redis 的用途</h3>

Redis 不保存全部弹幕，主要用于热门房间状态和最近弹幕等热数据。

## 热门房间状态

例如，使用 `room:10001` 保存房间在线人数和最后消费位置：

```text
room:10001

{
 online:5000000,
 last_cursor:123456
}
```

## 最近弹幕

可使用 `ZSET` 保存最近一段时间的弹幕：

```text
danmaku:10001

score=time
value=json
```

写入示例：

```text
ZADD danmaku:10001 1720000000 msg
```

只保留最近 5 分钟的数据，历史弹幕交给持久化存储。

***
<br/>

> <h3 id="亿级弹幕存储">亿级弹幕存储</h3>

不要使用 MySQL 单表保存十亿级弹幕。例如：

```text
danmaku

id
danmu_id // 字符串
video_id
user_id
content

10亿行
```

单表达到该规模后，查询和维护成本会非常高。推荐进行冷热数据分离：

- **热数据：** Redis。
- **历史数据：** ClickHouse。

ClickHouse 历史表：

```text
danmaku_history
```

主要字段：

```text
video_id
user_id
content
create_time
```

按月份分区：

```sql
PARTITION BY month(create_time)
```

按视频和创建时间排序：

```sql
ORDER BY
(
 video_id,
 create_time
)
```

该结构适合查询视频回放弹幕。

***
<br/>

> <h3 id="网络模型">网络模型</h3>

B 站级弹幕系统可采用以下网络与消息链路：

```text
Linux

epoll
 |
gnet
 |
gobwas/ws
 |
Room Engine
 |
Kafka
```

Go WebSocket 接入层选择：

```text
gnet + gobwas/ws
```

- `gnet` 提供基于 Reactor 模型的高性能事件驱动网络能力。
- `gobwas/ws` 负责 WebSocket 协议处理。
- `Room Engine` 负责房间管理和广播。
- `Kafka` 负责消息削峰和异步解耦。

***
<br/>

> <h3 id="千万连接的机器规模">千万连接的机器规模</h3>

单机经过系统参数和程序优化后，可承载约 `10万~50万` WebSocket 连接，实际容量取决于消息频率、内存占用、广播模型和硬件配置。

千万连接需要 Gateway 集群。例如使用 100 台 Gateway，每台承载 10 万连接：

```text
10,000,000 users

        |

100 gateway

每台:
100,000 connections
```

> <h3 id="推荐方案">推荐方案</h3>

| 模块 | 技术选型 |
| --- | --- |
| WebSocket 层 | `gobwas/ws` |
| 网络模型 | `gnet` |
| 消息队列 | `Kafka` |
| 热状态 | `Redis Cluster` |
| 历史弹幕 | `ClickHouse` |
| 服务发现 | `Nacos` / `Consul` |
| RPC | `gRPC` |

完整架构：

```text
                 User

                  |
              WebSocket
                  |
          +---------------+
          | Danmaku GW    |
          +---------------+

                  |
              Kafka
                  |
        +----------------+
        | Room Service   |
        +----------------+

          |          |

       Redis     ClickHouse
```

对于“B 站级弹幕、千万并发、亿级数据、Go 工程”这一目标，推荐选择 **`gnet + gobwas/ws`**。

> <h3 id="Go工程设计">Go 工程设计</h3>

## 弹幕入口

```text
gnet
+
gobwas/ws
```

主要负责：

- TCP 网络通信。
- WebSocket 协议处理。
- 心跳检测。
- 长连接管理。

## 内部 RPC

```text
Kitex
+
netpoll
```

主要用于服务间调用，包括用户服务、视频服务和推荐服务。

## 消息队列

```text
Kafka
```

Kafka 用于消息削峰、异步处理和服务解耦。

## 存储

- **实时热数据：** `Redis Cluster`。
- **历史弹幕：** `ClickHouse`。

## 最终架构

```text
                 Client

                   |
              WebSocket
                   |
        +----------------+
        | gnet Gateway  |
        +----------------+

                   |
              Kafka
                   |
        +----------------+
        | Room Service  |
        +----------------+

          |             |

       Redis       ClickHouse


内部服务：

Kitex
 |
netpoll
```

最终选择：`gnet + gobwas/ws`。

主要原因：

- 采用 Reactor 模型。
- 编程模型接近 Netty。
- 长连接承载能力强。
- 适合房间广播场景。
- 对网络层的控制粒度高。

**最终结论：WebSocket 库只是接入层的一部分，系统能否支撑千万并发，取决于连接承载、房间广播、消息削峰以及冷热数据分离的整体设计。**

未声称当前实现已经实测支撑千万连接。千万并发仍需要多实例网关、房间亲和路由、Kafka 分区、Redis Cluster、内核与网络调优以及分阶段压测共同完成。

**1. 修改了哪些文件**

- `config/base/app.yaml`
- `internal/pkg/config/hg_env_config.go`
- `internal/pkg/config/hg_video_danmaku_config_test.go`
- `internal/modules/video_danmaku/realtime/hg_gnet_server.go`
- `internal/modules/video_danmaku/realtime/hg_gnet_server_test.go`
- `internal/modules/video_danmaku/repository/hg_video_danmaku_repository.go`
- `internal/modules/video_danmaku/repository/hg_video_danmaku_repository_test.go`
- `internal/pkg/mysql/queries/hg_video_danmaku_queries.go`

前端仓库未修改。本轮保持现有 WebSocket 消息格式和前端发送行为兼容。

**2. 做了什么改动**

- 将全局房间锁拆成默认 `256` 个房间目录分片。
- 每个目录分片设置默认 `64` 个共享成员分片。
- 移除每次广播创建全房间 `[]target` 快照的逻辑。
- 广播只锁定对应视频的一个目录分片，并逐成员分片发送。
- 成员分片资源固定，不再为每个长尾视频预分配 64 个 map 和锁。
- 保留每连接出站积压统计，并将硬编码的 `64 KiB` 改为可配置。
- 慢客户端超过出站预算后主动关闭，防止热门房间广播导致 OOM。
- 慢客户端关闭延后到成员锁释放后执行，避免潜在锁重入。
- 新增 event-loop 内无锁令牌桶，在进入共享 worker 队列和 MySQL 前拒绝单连接突刺。
- 默认限流为每连接每秒 `5` 条、突发 `10` 条。
- ACK、error 和房间广播改为具体结构体序列化，移除 `map[string]any`。
- 房间路由使用内联 FNV-1a，避免每次查找创建哈希对象。
- 单连接限流时间改为 `int64` 纳秒时间戳，降低连接常驻状态体积。
- 新弹幕插入后使用 `LastInsertId()` 按聚簇主键回读。
- 不再通过 `danmaku_id` 二级唯一索引回读刚插入的亿级热表记录。
- 增加配置边界、房间分布、限流和主键回读测试。
- 增加 ACK 序列化分配基准。

新增配置：

```yaml
room_shard_count: 256
member_shard_count: 64
max_pending_bytes: 65536
command_rate_per_second: 5
command_burst: 10
```

房间和成员分片数必须是二次幂，并有明确上下限，避免错误配置制造过多锁、map 或内存常驻对象。

**3. 为什么这样改**

原实现的主要风险是：

- 所有视频共享一把 `roomsMu`。
- 热门房间每次广播都会遍历房间并复制完整目标列表。
- 百万连接房间会产生与在线人数线性增长的短命切片。
- 热门房间广播会阻塞其他视频的加入和离开。
- 慢客户端的积压预算不可配置。
- 单个恶意或异常客户端可以持续占用共享命令队列和数据库连接。
- 新记录插入后还需要经过宽字符串二级索引回读。

修改后：

- 不同视频大概率落入不同目录锁，跨视频竞争显著降低。
- 广播不再创建 O(N) 目标快照，降低大房间的 GC 和内存带宽压力。
- 长尾视频不会因每房间预分配大量分片对象产生反向内存放大。
- 限流在 gnet event-loop 内完成，不访问 Redis、MySQL，也不创建额外 goroutine。
- 过载压力不会无条件传导到 worker 队列和 MySQL。
- `LastInsertId()` 回读命中 InnoDB 聚簇主键，更适合亿级热表。

**4. 准确性检查结果**

- 保留现有 `danmaku.create`、`danmaku.ack`、`danmaku.created` 和 `error` JSON 字段。
- 保留 `requestId` 幂等与请求关联语义。
- 保留 MySQL 提交成功后才广播的语义。
- 保留 Redis 跨实例广播和 MySQL 历史恢复机制。
- 保留视频公开状态和 `close_danmaku` 校验。
- 保留 `(user_id, request_id)` 唯一键幂等。
- 保留 64 个统计分片及原事务边界。
- 房间空闲后仍会从目录中删除。
- 房间删除、立即重建和并发广播由同一个目录分片锁保护。
- 慢连接不会在成员锁持有期间直接关闭。
- `git diff --check`：通过。

**5. 潜在影响**

- 单连接超过默认发送频率时将收到：

```json
{
  "type": "error",
  "requestId": "...",
  "data": {
    "code": "rate_limited",
    "message": "弹幕发送过于频繁，请稍后重试"
  }
}
```

- 这是明确的 WebSocket 业务拒绝，现有前端不会继续 HTTP 回退。
- 配置缺少新增字段时，应用会因资源边界校验失败而拒绝启动。项目基础配置已补齐；独立覆盖整个 `video_danmaku` 配置块的外部环境需要同步增加这些字段。
- 广播仍然必须执行 O(N) 连接写入，这是向 N 个客户端推送数据本身不可消除的成本。
- 当前每连接仍调用一次 `AsyncWrite`。下一阶段需要按 gnet event-loop 建立有界批量出站队列，进一步减少跨 event-loop 调度。
- Redis 仍使用单个全局 Pub/Sub 频道，网关实例数增加后会产生全量消息放大。
- MySQL 统计分片更新仍在创建事务内，热门视频极端写入时仍可能出现行锁竞争。
- 没有执行真实百万或千万连接压测，不能将代码设计优化等同于容量验证。

**7. 后续生产级优化建议**

1. 将 Redis 单一全局频道改为本地活跃房间动态订阅，避免每台网关接收全平台所有弹幕。
2. 按 gnet event-loop 建立有界广播队列，一次唤醒批量写多个连接，减少每连接一次 `AsyncWrite` 调度。
3. 增加命令队列深度、拒绝数、慢客户端关闭数、广播接收人数、锁等待和房间数量指标。
4. 修复现有 Outbox 每秒实际约 8 条的吞吐限制，再接入 `video.danmaku.created.v1` Kafka 事件。
5. 将计数更新移出弹幕创建事务，由 Kafka consumer 批量维护 Redis/MySQL 投影。
6. 为视频可弹幕状态增加短 TTL 本地加 Redis 缓存，降低创建和列表接口的重复 JOIN。
7. 引入按 `video_id` 的 Kafka partition 和网关 room affinity，避免广播全网扩散。
8. 亿级以上历史数据采用 MySQL 热数据分片、ClickHouse 冷历史和有界归档，不依赖单张 InnoDB 表无限增长。
9. 使用 10 万、50 万、100 万连接分阶段压测，采集单连接内存、广播 P99、GC、mutex/block profile、Redis 带宽和 MySQL 锁等待，再决定单机安全连接上限。
