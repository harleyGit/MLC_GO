## [BiliBili接口采集API](https://gitea.s1f.ren/shiran/bilibili-API-collect/src/commit/fecc790b9ee2dae90dd13e12198fccb1f209a48b/docs/video/info.md?utm_source=chatgpt.com)

针对现在的 Go 爬虫工程，建议采用 Go + Kafka + Redis + MySQL + ClickHouse + 对象存储 的技术架构。

目标不是简单地把 B 站视频详情保存到 MySQL，而是建立一套类似 B 站、字节跳动的 视频数据采集、清洗、存储、更新与查询系统，能够逐步扩展到千万级视频、亿级统计记录及高并发访问。

需要先明确三个概念：

- 视频元数据：标题、BV号、UP主、简介、发布时间、时长、封面等。
- 视频互动数据：播放量、点赞量、投币量、收藏量、分享量、评论量、弹幕量、UP主粉丝数等。
- 视频媒体数据：视频流、音频流、清晰度、编码格式、播放地址等。

其中，播放地址通常是有时效性的 CDN 地址，并不等于永久的视频文件地址。采集媒体地址与下载、存储、再分发视频文件也是两种不同的业务。

## 一、整体技术架构

推荐使用以下分层架构：

```
                B站推荐列表
                     |
                     v
          Go 推荐列表采集器
                     |
                     v
           提取 BV号 / aid
                     |
                     v
               Kafka
           video.discovered
                     |
                     v
          Go 视频详情采集器
              /      |      \
             v       v       v
         基础详情  互动统计  评论/UP主
             \       |       /
              v      v      v
             Kafka 原始数据
              video.raw
                     |
                     v
           Go 数据清洗服务
          (校验、去重、标准化)
                     |
                     v
              Kafka
           video.cleaned
                     |
          +----------+----------+
          |          |          |
          v          v          v
        MySQL      Redis     ClickHouse
       视频主数据   热点缓存    历史统计
          |          |          |
          +----------+----------+
                     |
                     v
               Go API 服务
                     |
                     v
            React / App 前端
```

各组件职责：

| 技术                   | 主要用途               |
| -------------------- | ------------------ |
| Go                   | 采集器、数据清洗、API 服务    |
| Kafka                | 任务解耦、缓冲、削峰         |
| MySQL                | 视频、UP主、评论等业务数据     |
| Redis                | 去重、缓存、限流           |
| ClickHouse           | 播放量、点赞量等历史趋势分析     |
| S3/MinIO             | 合规保存的原始 JSON、封面等对象 |
| Prometheus + Grafana | 采集成功率、积压、延迟监控      |

核心设计原则： 采集服务不直接操作业务主表，而是先将原始数据发送到 Kafka，再由独立的清洗服务和入库服务处理。

这样即使 B 站接口暂时失败、MySQL 写入变慢，也不会直接阻塞整个采集流程。

## 三、Go 采集器的具体实现

第一阶段先完成最重要的功能：通过 BV 号获取详情并转换成统一的数据结构。

### 1. 定义视频详情模型

```
type BiliVideoResponse struct {
    Code    int    `json:"code"`
    Message string `json:"message"`

    Data struct {
        BVID     string `json:"bvid"`
        AID      int64  `json:"aid"`
        Title    string `json:"title"`
        Desc     string `json:"desc"`
        Pic      string `json:"pic"`
        Duration int64  `json:"duration"`
        PubDate  int64  `json:"pubdate"`

        Owner struct {
            MID  int64  `json:"mid"`
            Name string `json:"name"`
        } `json:"owner"`

        Stat struct {
            View     int64 `json:"view"`
            Like     int64 `json:"like"`
            Coin     int64 `json:"coin"`
            Favorite int64 `json:"favorite"`
            Share    int64 `json:"share"`
            Reply    int64 `json:"reply"`
            Danmaku  int64 `json:"danmaku"`
        } `json:"stat"`
    } `json:"data"`
}
```

### 2. 编写 Go HTTP 请求

下面是一个最小可运行的请求函数，适合你现有 Go 工程中的 `crawler` 模块。

```
func FetchVideoDetail(
    ctx context.Context,
    client *http.Client,
    bvid string,
) (*BiliVideoResponse, error) {

    endpoint := "https://api.bilibili.com/x/web-interface/view"

    u, err := url.Parse(endpoint)
    if err != nil {
        return nil, err
    }

    q := u.Query()
    q.Set("bvid", bvid)
    u.RawQuery = q.Encode()

    req, err := http.NewRequestWithContext(
        ctx, http.MethodGet, u.String(), nil,
    )
    if err != nil {
        return nil, err
    }

    resp, err := client.Do(req)
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        return nil, fmt.Errorf(
            "upstream status: %d", resp.StatusCode,
        )
    }

    var result BiliVideoResponse

    err = json.NewDecoder(
        io.LimitReader(resp.Body, 2<<20),
    ).Decode(&result)
    if err != nil {
        return nil, err
    }

    if result.Code != 0 {
        return nil, fmt.Errorf(
            "bilibili code=%d message=%s",
            result.Code, result.Message,
        )
    }

    if result.Data.BVID == "" {
        return nil, errors.New("empty video data")
    }

    return &result, nil
}
```

使用：

```
client := &http.Client{
    Timeout: 10 * time.Second,
}

video, err := FetchVideoDetail(
    context.Background(),
    client,
    "BV1GJ411x7h7",
)

if err != nil {
    log.Println("采集失败:", err)
    return
}

fmt.Println(video.Data.Title)
fmt.Println(video.Data.Stat.View)
fmt.Println(video.Data.Stat.Like)
```

注意：这是公开接口的演示客户端，不保证接口始终对未授权请求开放。生产环境需要补充全局限流、重试退避、响应分类和授权管理。对 `403/429` 等限制性响应应停止或降低采集，不应持续重试。

## 四、数据清洗方案

采集得到的数据不要原封不动写入业务数据库。

例如：

```
B站返回数据
      |
      v
字段校验
      |
      v
数据标准化
      |
      v
数据去重
      |
      v
数据关联
      |
      v
MySQL / ClickHouse
```

建议设计统一的视频数据模型：

```
type HGVideo struct {
    ID         uint64
    Platform   string
    ExternalID string
    AuthorID   string

    Title      string
    Description string
    CoverURL   string

    Duration   int64
    PublishedAt time.Time
    CollectedAt time.Time
}

type HGVideoStats struct {
    VideoID       uint64
    ViewCount     int64
    LikeCount     int64
    CoinCount     int64
    FavoriteCount int64
    ShareCount    int64
    CommentCount  int64
    DanmakuCount  int64
    CollectedAt   time.Time
}
```

清洗规则：

| 场景     | 清洗方式                          |
| ------ | ----------------------------- |
| 重复视频   | `platform + external_id` 唯一约束 |
| 标题存在空格 | `strings.TrimSpace`           |
| 标题为空   | 标记无效，进入异常队列                   |
| 时间戳    | 转换成统一 UTC 时间                  |
| 计数为负数  | 标记异常，不直接归零                    |
| 重复统计消息 | 使用采集批次 ID 去重                  |
| 字段缺失   | 根据字段重要性决定丢弃或保留空值              |
| 超长文本   | 按数据库字段长度校验                    |
| 视频已删除  | 标记状态，不直接物理删除                  |

还需要特别处理一种情况：

```
第一次采集：播放量 10000
第二次采集：播放量 15000
第三次采集：播放量 14000
```

第三次不能简单认定为无效数据。可能是平台统计调整，也可能是旧消息乱序到达。

建议以 `collected_at` 判断消息新旧，保留有效历史快照，异常下降进入质量检测，而不是直接覆盖或累加。

尤其注意：B站返回的播放量、点赞量属于累计值，不能每采集一次就执行 `view_count = view_count + 新播放量`。

## 五、MySQL 数据库设计（亿级数据方向）

建议至少拆成 5 张核心表，不要把所有数据塞进一张表。

| 表名                   | 用途     | 唯一标识           |
| -------------------- | ------ | -------------- |
| `video`              | 视频基本信息 | 内部 `id`、平台+BV号 |
| `video_part`         | 视频分P信息 | 视频ID+CID       |
| `video_author`       | UP主信息  | 平台+UP主ID       |
| `video_stats_latest` | 最新互动统计 | 视频ID           |
| `video_comment`      | 评论信息   | 平台+评论ID        |

### 1. 视频主表

```
CREATE TABLE video (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    platform VARCHAR(32) NOT NULL,
    external_id VARCHAR(64) NOT NULL,
    author_id BIGINT UNSIGNED DEFAULT NULL,
    title VARCHAR(512) NOT NULL,
    description TEXT,
    cover_url VARCHAR(1024),
    duration INT UNSIGNED DEFAULT 0,
    published_at DATETIME(3),
    collected_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,

    PRIMARY KEY (id),
    UNIQUE KEY uk_platform_video (
        platform, external_id
    ),
    KEY idx_author_id (author_id),
    KEY idx_published_at (published_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

其中：

- `id`：你自己系统的视频主键，建议使用 `BIGINT UNSIGNED`。
- `external_id`：B站的 BV 号。
- `platform`：数据来源，例如 `bilibili`，以后可以扩展其他平台。
- `author_id`：你自己系统中的 UP 主内部 ID。

对于亿级数据，`AUTO_INCREMENT` 可以用于单个 MySQL 分片。未来多分片时，可以引入 Snowflake 等全局 ID 方案。

### 2. 视频统计表

```
CREATE TABLE video_stats_latest (
    video_id BIGINT UNSIGNED NOT NULL,
    view_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    like_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    coin_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    favorite_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    share_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    comment_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    danmaku_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    collected_at DATETIME(3) NOT NULL,

    PRIMARY KEY (video_id)
) ENGINE=InnoDB;
```

这里采用一对一关系：

```
video
  id = 10001
       |
       | 1 : 1
       v
video_stats_latest
  video_id = 10001
  view_count = 100000
  like_count = 8000
```

视频标题可能长期不变，但点赞量、播放量会持续变化，因此需要拆表。

对于历史统计，则使用 ClickHouse 单独存储：

```
CREATE TABLE video_stats_history
(
    video_id UInt64,
    view_count UInt64,
    like_count UInt64,
    favorite_count UInt64,
    share_count UInt64,
    collected_at DateTime64(3, 'UTC')
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(collected_at)
ORDER BY (video_id, collected_at);
```

这样就能分析：

- 某视频最近 7 天播放量变化。
- 哪些视频点赞增长最快。
- 某 UP 主的视频平均播放量。
- 每天新增多少热门视频。

ClickHouse 的历史记录要配置合理的保留周期和数据降采样策略，避免无限增长。

## 六、Kafka 如何设计

建议按业务划分 Topic：

| Kafka Topic        | 用途        |
| ------------------ | --------- |
| `video.discovered` | 新发现的视频    |
| `video.raw`        | 采集的原始数据   |
| `video.cleaned`    | 清洗后的标准数据  |
| `video.stats`      | 统计数据快照    |
| `video.comment`    | 评论数据      |
| `video.dlq`        | 失败消息、异常数据 |

消息示例：

```
{
  "event_id": "evt_100001",
  "platform": "bilibili",
  "external_id": "BV1GJ411x7h7",
  "event_type": "video.discovered",
  "collected_at": "2026-10-17T04:00:00Z"
}
```

Kafka 的消息 Key 建议使用：

```
platform:external_id
```

这样同一个视频的消息可以进入同一个分区，便于维持分区内顺序。

但 Kafka 消费端仍然必须实现幂等处理：

```
Kafka 消息
     |
     v
检查 event_id 是否已处理
     |
     +--- 已处理 ---> 跳过
     |
     +--- 未处理
             |
             v
         数据库事务
             |
             v
        写入业务数据
             |
             v
        写入去重记录
             |
             v
       提交事务后确认消息
```

实际工程中建议采用数据库唯一约束和事务保证幂等，而不是只依赖 Redis 去重。最新统计更新还应添加采集时间条件，避免旧快照覆盖新数据。

## 七、千万并发、亿级数据如何设计

首先区分：

千万并发访问能力 ≠ 千万并发爬虫请求。

爬虫请求能力受数据源授权、接口限流及上游容量限制，不能按照自有 API 的并发规模去压测第三方平台。

真正要重点扩展的是自己的数据存储、消费和查询能力。

| 规模        | 推荐架构                     |
| --------- | ------------------------ |
| 10万视频     | Go + MySQL + Redis       |
| 100万视频    | 增加 Kafka、批量写入            |
| 1000万视频   | 增加 ClickHouse、分布式 Worker |
| 1亿视频      | MySQL 分库分表、对象存储、冷热分层     |
| 千万级并发访问目标 | CDN、多级缓存、水平扩容、限流、容量压测    |

以上是演进参考，并非达到某个数据量就必须引入相应组件。是否分库分表，要依据真实 QPS、磁盘容量、索引大小和查询延迟决定。

对于自有服务，推荐：

```
客户端请求
     |
     v
CDN / WAF
     |
     v
API Gateway
     |
     v
Go API 服务集群
     |
     v
Redis 缓存
     |
     +--- 命中 ---> 返回
     |
     +--- 未命中
             |
             v
         MySQL 查询
             |
             v
         回填 Redis
             |
             v
           返回
```

需要进一步增加热点 Key 保护、缓存失效控制、读写分离、弹性扩容和故障降级。千万级并发是否能实现，必须结合具体的并发连接数、QPS、响应体大小和延迟指标进行压测，不能仅凭技术选型保证。

## 九、具体实施顺序

建议按以下顺序执行，先验证完整数据链路，再逐步扩大规模。

实施进度以文末“工程落地记录”为准；以下六项是演进顺序，不代表六项均已完成验收。

阶段一：详情采集

根据 BV 号获取视频详情、解析 JSON、处理错误响应

阶段二：清洗入库

创建 MySQL 表，实现去重、字段校验和 Upsert

阶段三：消息解耦

接入 Kafka，拆分采集 Worker 和清洗 Consumer

阶段四：统计分析

增加 ClickHouse，存储历史统计快照

阶段五：评论采集

实现授权范围内的评论分页、游标续采与去重

阶段六：高并发服务

增加 Redis 缓存、监控、分片和压力测试

### 最终建议

你已经有 Go 推荐列表采集器，因此不建议立即重构整个项目。

最优先实现这条最小闭环：

```

     |
     v
提取 bvid
     |
     v
Go 详情采集
     |
     v
字段清洗
     |
     v
MySQL video + video_stats_latest
     |
     v
GET /api/videos
GET /api/videos/{id}
     |
     v
```

### 10.2 已实现的消息流水线

```text
任务解析 / 周期推荐
  → MySQL短事务：推荐 + 任务关联 + collection + discovered Outbox
  → 现有Outbox dispatcher
  → mlc.crawler.video.discovered.v1
  → crawler_fetch：固定view接口，安全HTTP、限速、有界响应
  → MySQL短事务：阶段raw + raw Outbox
  → mlc.crawler.video.raw.v1
  → crawler_clean：身份/字段校验及标准化
  → MySQL短事务：阶段cleaned + cleaned Outbox
  → mlc.crawler.video.cleaned.v1
  → crawler_store：基础详情 + 最新统计 + 阶段stored + stored Outbox
  → mlc.crawler.video.stored.v1
  → crawler_history：ClickHouse批量历史摄入
```

四个阶段独立消费组，复用 `internal/infrastructure/kafka/hg_runtime.go` 管理关闭、健康与 lag。Kafka key 固定为 `bilibili:{bvid}`。每条发现生成 `collection_id` UUID，阶段 eventId 由 collection UUID 和事件名稳定派生为 UUID，满足既有 Outbox `VARCHAR(64)` 限制。

阶段检查、状态推进和下一阶段 Outbox 在同一短事务，数据库失败不确认消息；事务内没有 HTTP、Kafka 或 ClickHouse I/O。消费者成功后才由通用运行器提交 offset。抓取成功但提交前崩溃可能再次访问上游；一旦 raw 阶段提交，重复 discovered 不再抓取。保证至少一次与业务幂等，不宣称端到端 exactly-once。

正式任务 `succeeded` 仍表示推荐及发现事件提交，**不表示所有详情已经入库**。每次详情采集另有 `pending → raw → cleaned → stored` 或 `failed` 状态，页面展示最新状态；失败刷新时仍可展示上一次成功快照。`stored` 表示MySQL完成，ClickHouse投影进度通过独立消费组 lag 判断。
