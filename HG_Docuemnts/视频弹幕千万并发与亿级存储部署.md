# 视频弹幕千万并发与亿级存储部署

## 已实现链路

```text
Client
  -> gnet WebSocket Gateway
  -> local sharded room broadcast
  -> Redis room channel, only gateways with local members subscribe

MySQL transaction
  -> video_danmaku hot authoritative row
  -> outbox_events
  -> Kafka topic mlc.video.danmaku.created.v1, key=video_id
  -> partition batch consumer
  -> ClickHouse video_danmaku_history
  -> Redis recent Stream, MAXLEN ~ 1000
```

现有 JSON、HTTP、WebSocket ACK 和 MySQL 幂等语义保持不变。Redis Pub/Sub 只负责低延迟实时副本，Kafka、MySQL 和 ClickHouse 负责可恢复历史。

## 上线顺序

1. 创建 Kafka Topic：

```bash
./scripts/kafka_init.sh
```

默认创建：

- `mlc.domain.events`：12 partitions
- `mlc.video.danmaku.created.v1`：96 partitions
- replication factor：3

同一视频使用 `video_id` 作为 Kafka key，因此默认保持分区内顺序。单个超级热门视频达到单 partition 上限后，应单独评估 lane 分片，不能直接增加消费者解决同 key 热点。

2. 执行 ClickHouse DDL：

```bash
clickhouse-client --multiquery < deployments/clickhouse/002_video_danmaku_history.sql
```

表按月分区，排序键为 `(video_id, progress_ms, created_at, danmaku_id)`，适合视频回放时间窗和复合游标查询。默认保留 1825 天，生产应按合规、磁盘容量和备份策略调整 TTL。

3. 配置 ClickHouse：

```yaml
clickhouse:
  enabled: true
  danmaku_history_table: video_danmaku_history
```

密码通过 `CLICKHOUSE_PASSWORD` 注入，不写入仓库。

4. 灰度启用消费者：

```yaml
kafka:
  business:
    consumers:
      danmaku:
        enabled: true
        group_id: mlc-go-prod-danmaku-history
        client_id: mlc-go-prod-danmaku-history
        topics:
          - mlc.video.danmaku.created.v1
```

5. 先单副本观察 Kafka lag、ClickHouse insert latency、Redis latency 和 DLQ，再逐步增加消费者副本。消费者数量不应高于 Topic 有效 partition 数。

## Gateway 部署

千万连接不能由单实例承担。应使用多个 Gateway Pod，并按实测单 Pod 安全连接数计算副本：

```text
required_pods = ceil(target_connections / verified_connections_per_pod) * safety_factor
```

建议安全系数至少 `1.3`，并预留滚动发布、AZ 故障和热点视频倾斜容量。

Ingress/LB 应满足：

- 支持 WebSocket upgrade 和长连接。
- 空闲超时大于应用心跳超时。
- 默认应用心跳为每 `20s` 发送一次 WebSocket Ping，连接连续 `60s` 没有任何有效入站帧时关闭；Ingress/LB 空闲超时应至少高于 `60s`，建议配置为 `90s` 以上。
- 心跳由网关固定 ticker 扫描房间成员完成，不为每条连接创建 goroutine 或 timer。调整 `heartbeat_interval` 时，`heartbeat_timeout` 必须至少为其 2 倍。
- 使用 `videoId` 或票据绑定的房间路由键做 consistent hash。
- 扩缩容迁移期间允许同一房间暂时分布到多个 Pod；动态 Redis 房间订阅保证跨 Pod 广播。
- 暴露业务端口 `8080`、实时端口 `8081`，管理端口 `9091` 仅内网探针访问。
- Pod `terminationGracePeriodSeconds` 必须覆盖连接排空、Kafka consumer 退出和 producer flush。

操作系统至少检查：

```text
nofile
somaxconn
tcp_max_syn_backlog
ip_local_port_range
conntrack capacity
NIC queue/RSS
pod PID and memory limits
```

不能只提高 `nofile` 后宣称支持百万连接，必须同时验证每连接内存、GC、网络带宽和 event-loop CPU。

## 数据一致性

- MySQL 弹幕和 Outbox 在同一事务提交，不会出现 MySQL 成功但事件永久缺失。
- Outbox dispatcher 有积压时持续以固定 64 并发排空；空队列时才按 1 秒退避。
- Kafka consumer 成功写 ClickHouse 和 Redis recent 后才提交 offset。
- ClickHouse 使用 `ReplacingMergeTree(ingested_at)`，Kafka 重放不会改变查询主键语义。
- Redis recent 使用 `topic:partition -> offset` 水位，重复投递不会重复追加 Stream。
- Redis Pub/Sub 可瞬时丢失，但不作为权威存储；客户端通过时间窗历史恢复。

## 查询边界

ClickHouse 客户端已实现：

- 单次时间窗最大 5 分钟。
- 单页最大 1000 条。
- `(progress_ms, created_at, danmaku_id)` 复合游标。
- 禁止 OFFSET 深分页。

现有 HTTP 查询仍读取 MySQL 热数据，避免未经灰度直接改变对外语义。完成双写对账、历史回灌和读取压测后，再将旧时间窗路由到 ClickHouse。

## 回滚

1. 将 `kafka.business.consumers.danmaku.enabled` 改为 `false` 并滚动发布。
2. 不删除 Kafka Topic，不重置 consumer group offset，保留后续重放能力。
3. 不删除 ClickHouse 表，避免历史数据丢失。
4. Gateway 动态房间订阅与 MySQL 同步写路径可独立运行，不依赖弹幕历史消费者启用。
5. Redis recent 故障不会影响 MySQL 权威写入和实时 Pub/Sub 广播。

## 验收

分阶段执行 10 万、50 万、100 万连接压测，再按实际部署副本数推演千万连接。至少采集：

- 单连接常驻内存和总 RSS。
- gnet event-loop CPU、GC pause、mutex/block profile。
- 广播 P50/P95/P99 和慢连接关闭率。
- command queue、broadcast queue 高水位和丢弃量。
- Redis Pub/Sub 带宽、命令延迟、Stream 内存。
- Kafka producer buffer、consumer lag、partition 热点和 DLQ。
- ClickHouse batch size、insert latency、parts 数量、merge 压力和磁盘增长。
- MySQL transaction latency、Outbox pending/dead 数量、redo/binlog 和锁等待。

当前交付表示已完成面向千万连接、亿万级历史的横向扩展代码路径，不表示已经在本机或当前集群真实验证千万同时在线。最终生产容量必须以压测和故障演练结果为准。
