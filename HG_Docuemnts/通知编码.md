# Go 后端工程：通知系统 + 消息中心 + 即时通信（IM）完整技术设计方案

目标：对标字节跳动、B站、抖音等大型互联网平台的功能形态，设计一套支持千万级用户、亿级消息存储、可横向扩展的统一消息系统。

结合你目前的 Go 后端工程（商城、视频、评论、点赞、关注、钱包、爬虫、运维管理），建议采用：

统一消息事件 + 通知模板中心 + 多渠道投递 + 站内消息中心 + WebSocket 即时通信 + Kafka 异步处理。

需要先明确：以下是参考大型互联网平台常见架构模式设计的可落地方案，不代表字节或 B站公开确认的内部实现。

## 一、总体架构设计

首先需要区分三个概念：

| 模块                  | 主要职责                  | 典型业务            |
| ------------------- | --------------------- | --------------- |
| 通知中心 Notification   | 业务事件触发通知，按模板生成内容并投递   | 订单支付成功、审核结果、验证码 |
| 消息中心 Message Center | 保存和展示用户收到的通知、未读数、历史记录 | 点赞、评论、关注、系统通知   |
| 即时通信 IM             | 用户与用户实时收发消息           | 私信、图片、文字、聊天记录   |

三者应该共享部分基础设施，但不建议把所有消息放在同一张表，也不建议使用同一套投递逻辑。

### 1.1 总体架构图

```
                 业务服务层
                       |
       +---------------+---------------+
       |               |               |
    用户服务         视频服务         商城服务
       |               |               |
    注册登录       点赞/评论/关注     订单/支付
       |               |               |
       +---------------+---------------+
                       |
                 业务事件 Outbox
                       |
                    Kafka
                       |
          +------------+------------+
          |                         |
      通知服务                  消息服务 IM
    Notification               Messaging
          |                         |
    +-----+------+           +------+------+
    |            |           |             |
  模板中心     路由引擎     会话管理      消息存储
    |            |           |             |
    +-----+------+           +------+------+
          |                         |
      渠道投递                 WebSocket Gateway
          |                         |
   +------+------+           +------+------+
   |      |      |           |             |
  站内   短信   邮件        Web端         App端
   |
  消息中心
   |
  MySQL / Redis

公共基础设施：
MySQL + Redis + Kafka + 对象存储 + Metrics
```

核心原则：

- 业务服务只负责产生事件，不直接发送短信或推送。
- 通知服务决定发送什么、发给谁、通过什么渠道发送。
- IM 服务负责实时消息、会话、顺序、离线同步和已读回执。
- 消息中心负责通知历史、分类、未读数。
- 图片、视频等附件存对象存储，数据库只保存元数据和引用。

## 三、通知模板中心设计

### 3.1 为什么要有模板？

例如用户支付成功后，系统需要发送：

```
站内通知：
您购买的商品【小米电视】支付成功，
订单号：202610300001。

短信通知：
【MLC商城】您的订单202610300001
已支付成功。

邮件通知：
主题：订单支付成功
正文：您好，您购买的商品已经支付成功……
```

三个渠道的内容不同，但来源是同一个业务事件：

```
order.paid
```

因此建议把事件、模板、渠道解耦。

### 3.2 模板表示例

`notification_template`

| 字段                   | 类型           | 说明            |
| -------------------- | ------------ | ------------- |
| id                   | BIGINT       | 自增主键          |
| template_code        | VARCHAR(100) | 业务模板编码        |
| channel              | VARCHAR(32)  | 站内、短信、邮件、Push |
| locale               | VARCHAR(16)  | 语言            |
| version              | INT          | 模板版本          |
| title                | VARCHAR(255) | 标题            |
| content              | TEXT         | 内容            |
| variables_schema     | JSON         | 变量定义          |
| status               | TINYINT      | 草稿、已发布、停用     |
| provider_template_id | VARCHAR(128) | 短信供应商模板ID     |
| created_at           | DATETIME(3)  | 创建时间          |
| updated_at           | DATETIME(3)  | 更新时间          |

建议唯一索引：

```
UNIQUE KEY uk_template_version
(template_code, channel, locale, version)
```

模板版本发布后应不可变，修改时创建新版本，避免历史通知重试时内容发生变化。

### 3.3 Go 模板定义

```
type HGNotificationTemplate struct {
    ID                 uint64
    TemplateCode       string
    Channel            string
    Locale             string
    Version            int
    Title              string
    Content            string
    VariablesSchema    json.RawMessage
    ProviderTemplateID string
    Status             int
}
```

模板示例：

```
{
  "templateCode": "ORDER_PAID",
  "channel": "in_app",
  "title": "订单支付成功",
  "content": "您购买的{{productName}}已支付成功",
  "variables": {
    "productName": "小米电视"
  }
}
```

模板渲染后：

```
您购买的小米电视已支付成功
```

生产环境需要对模板变量进行类型、长度和必填校验；站内富文本还需要防止 XSS。

## 四、通知渠道中心设计

建议采用策略模式 + Provider Adapter（供应商适配器）。

### 4.1 渠道类型

```
type HGNotifyChannel string

const (
    HGChannelInApp HGNotifyChannel = "in_app"
    HGChannelSMS   HGNotifyChannel = "sms"
    HGChannelEmail HGNotifyChannel = "email"
    HGChannelPush  HGNotifyChannel = "push"
)
```

### 4.2 统一渠道接口

```
type HGNotifyMessage struct {
    MessageID   string
    ReceiverID  string
    Destination string
    Title       string
    Content     string
    Data        map[string]any
}

type HGNotifyProvider interface {
    Channel() HGNotifyChannel

    Send(
        ctx context.Context,
        message HGNotifyMessage,
    ) (HGSendResult, error)
}

type HGSendResult struct {
    ProviderMessageID string
    Status            string
}
```

分别实现：

```
HGNotifyProvider
       |
       +-- HGInAppProvider
       |
       +-- HGSMSProvider
       |       |
       |       +-- AliyunSMS
       |       +-- TencentSMS
       |
       +-- HGEmailProvider
       |
       +-- HGPushProvider
               |
               +-- APNs
               +-- FCM
```

供应商密钥通过环境变量或密钥管理服务管理，不存储在普通模板表中。

### 4.3 通知投递任务表

`notification_delivery`

| 字段                  | 类型           | 说明      |
| ------------------- | ------------ | ------- |
| id                  | BIGINT       | 自增ID    |
| delivery_id         | VARCHAR(64)  | 投递业务ID  |
| event_id            | VARCHAR(64)  | 来源事件ID  |
| receiver_id         | VARCHAR(64)  | 接收用户    |
| channel             | VARCHAR(32)  | 渠道      |
| template_code       | VARCHAR(100) | 模板编码    |
| template_version    | INT          | 使用版本    |
| status              | TINYINT      | 投递状态    |
| retry_count         | INT          | 重试次数    |
| next_retry_at       | DATETIME(3)  | 下次重试    |
| provider_message_id | VARCHAR(128) | 供应商消息ID |
| last_error          | VARCHAR(512) | 最后一次错误  |
| created_at          | DATETIME(3)  | 创建时间    |

需要增加：

```
UNIQUE KEY uk_delivery_id (delivery_id),
UNIQUE KEY uk_event_receiver_channel
(event_id, receiver_id, channel)
```

第二个索引适用于一个事件向同一用户同一渠道只发送一次的场景；若允许多模板投递，需要把模板或通知规则ID纳入唯一键。

### 4.4 重试策略

```
发送任务
   |
   v
调用渠道 Provider
   |
   +-- 成功 --> 更新 sent
   |
   +-- 可重试失败
   |       |
   |       +-- 1分钟
   |       +-- 5分钟
   |       +-- 15分钟
   |       +-- 1小时
   |       |
   |       +-- 超过上限 --> 死信/人工处理
   |
   +-- 永久失败 --> failed
```

重试要使用指数退避和随机抖动，防止供应商恢复时瞬间涌入大量请求。

短信等外部渠道尤其要注意：超时不等于发送失败。如果供应商已经受理，但本地没有收到响应，盲目重试可能造成重复短信。应优先使用供应商支持的幂等键或状态查询能力。

### 5.3 点赞通知示例

假设用户 A 点赞了用户 B 的视频：

```
用户A点赞视频
      |
      v
视频服务写入点赞记录
      |
      v
Outbox 记录 video.liked
      |
      v
Kafka
      |
      v
通知消费者
      |
      +-- 查询接收用户 B
      |
      +-- 判断通知偏好
      |
      +-- 渲染点赞通知
      |
      +-- 写入 notification_inbox
      |
      +-- 更新未读计数
      |
      +-- WebSocket 实时提醒
```

如果一分钟内 100 人点赞同一个视频，建议做聚合通知：

```
张三、李四等100人赞了你的视频
```

而不是直接向用户发送100条提醒。

点赞通知可使用 Redis 聚合窗口，但聚合状态必须具备持久化或可重建机制，不能仅依赖易丢失的 Redis 临时计数。

## 六、即时通信 IM 设计

IM 是整套系统中技术复杂度最高的部分。

建议第一期支持：

- 单聊
- 文字消息
- 图片消息
- 文件消息
- 会话列表
- 未读消息
- 已读回执
- WebSocket 实时通信
- 离线消息补拉

第二期再增加群聊、撤回、禁言、消息搜索、音视频等能力。

### 6.1 IM 架构

```
                  Web / iOS / Android
                         |
                         |
                  WebSocket / HTTPS
                         |
                 +-------+-------+
                 |               |
              API Gateway    WS Gateway
                 |               |
                 |          用户连接管理
                 |               |
                 +-------+-------+
                         |
                     IM Service
                         |
          +--------------+--------------+
          |              |              |
       会话服务        消息服务        权限风控
          |              |              |
          +--------------+--------------+
                         |
                      MySQL
                         |
                     Outbox
                         |
                       Kafka
                         |
                 消息分发消费者
                         |
                 Redis 用户路由
                         |
                   WS Gateway
                         |
                      接收端
```

这里的 Redis 用户路由用于查询用户在线连接所在的 Gateway 节点。Kafka 负责可靠的跨节点消息分发，不能简单地把 Redis Pub/Sub 当作持久化消息队列。

### 6.2 会话表

`im_conversation`

| 字段              | 类型          | 说明       |
| --------------- | ----------- | -------- |
| id              | BIGINT      | 自增ID     |
| conversation_id | VARCHAR(64) | 会话ID     |
| type            | TINYINT     | 1单聊，2群聊  |
| last_seq        | BIGINT      | 会话最后消息序号 |
| last_message_id | VARCHAR(64) | 最新消息ID   |
| created_at      | DATETIME(3) | 创建时间     |

`im_conversation_member`

| 字段                 | 类型          | 说明    |
| ------------------ | ----------- | ----- |
| id                 | BIGINT      | 自增ID  |
| conversation_id    | VARCHAR(64) | 会话ID  |
| user_id            | VARCHAR(64) | 成员ID  |
| last_read_seq      | BIGINT      | 已读位置  |
| last_delivered_seq | BIGINT      | 已送达位置 |
| is_muted           | TINYINT     | 是否免打扰 |
| is_pinned          | TINYINT     | 是否置顶  |
| joined_at          | DATETIME(3) | 加入时间  |

唯一约束：

```
UNIQUE KEY uk_conversation_member
(conversation_id, user_id)
```

单聊创建时，还需要对排序后的两个用户ID建立唯一关系，避免重复创建多个相同单聊。

### 6.3 IM 消息表

`im_message`

| 字段              | 类型          | 说明                     |
| --------------- | ----------- | ---------------------- |
| id              | BIGINT      | 自增主键                   |
| message_id      | VARCHAR(64) | 服务端消息ID                |
| client_msg_id   | VARCHAR(64) | 客户端幂等ID                |
| conversation_id | VARCHAR(64) | 会话ID                   |
| seq             | BIGINT      | 会话内消息序号                |
| sender_id       | VARCHAR(64) | 发送者                    |
| message_type    | VARCHAR(32) | text/image/file/system |
| content         | JSON        | 消息内容                   |
| status          | TINYINT     | 正常、撤回、删除               |
| created_at      | DATETIME(3) | 创建时间                   |

核心索引：

```
UNIQUE KEY uk_message_id (message_id),

UNIQUE KEY uk_conversation_seq
(conversation_id, seq),

UNIQUE KEY uk_sender_client_msg
(sender_id, client_msg_id),

KEY idx_conversation_history
(conversation_id, seq)
```

其中 `client_msg_id` 用于客户端发送重试的幂等控制。

注意：会话序号必须由服务端分配，不能依赖消息时间戳排序。 第一版可以通过事务锁定 `im_conversation` 行并递增 `last_seq`，但对于超高频热点会话，需要进一步采用专用序号分配或分区架构。

## 七、图片、文字消息如何设计？

建议采用统一消息信封，按 `messageType` 区分内容。

### 7.1 文字消息

```
{
  "type": "im.send",
  "requestId": "req_001",
  "data": {
    "clientMsgId": "client_10001",
    "conversationId": "conv_001",
    "messageType": "text",
    "content": {
      "text": "你好，请问商品还有货吗？"
    }
  }
}
```

### 7.2 图片消息

```
{
  "type": "im.send",
  "requestId": "req_002",
  "data": {
    "clientMsgId": "client_10002",
    "conversationId": "conv_001",
    "messageType": "image",
    "content": {
      "mediaId": "media_001",
      "width": 1080,
      "height": 1920
    }
  }
}
```

图片上传流程：

```
客户端选择图片
       |
       v
调用上传凭证接口
       |
       v
获取预签名上传URL
       |
       v
上传到对象存储
       |
       v
服务端校验文件/归属/安全状态
       |
       v
获取 mediaId
       |
       v
发送 IM 图片消息
       |
       v
接收端通过授权媒体接口加载图片
```

不要直接将图片 Base64 放进 WebSocket 消息，也不要在数据库保存图片二进制。

服务端需要校验 MIME、文件大小、图片真实格式、媒体归属和访问权限。私信图片不能默认使用永久公开 URL。

### 7.3 Go 消息结构体

```
type HGIMMessageType string

const (
    HGIMText  HGIMMessageType = "text"
    HGIMImage HGIMMessageType = "image"
    HGIMFile  HGIMMessageType = "file"
)

type HGIMSendCommand struct {
    ClientMsgID    string          `json:"clientMsgId"`
    ConversationID string          `json:"conversationId"`
    MessageType    HGIMMessageType `json:"messageType"`
    Content        json.RawMessage `json:"content"`
}

type HGIMTextContent struct {
    Text string `json:"text"`
}

type HGIMImageContent struct {
    MediaID string `json:"mediaId"`
    Width   int    `json:"width"`
    Height  int    `json:"height"`
}
```

`sender_id` 必须从已验证的登录身份中获取，而不是信任客户端传来的发送者ID。

## 八、消息发送完整流程

这是 IM 最核心的业务链路。

用户 A 向用户 B 发送一条图片消息

```
用户 A
   |
   | 1. WebSocket发送消息
   v
WS Gateway
   |
   | 2. 验证登录身份、限流
   v
IM Service
   |
   | 3. 校验会话成员、图片权限
   | 4. 检查clientMsgId幂等
   v
MySQL事务
   |
   | 5. 分配会话seq
   | 6. 插入im_message
   | 7. 更新会话状态
   | 8. 插入Outbox事件
   v
事务提交成功
   |
   +----> ACK给用户A（已持久化）
   |
   v
Outbox Relay -> Kafka
   |
   v
IM Dispatch Consumer
   |
   | 9. 查询用户B在线路由
   v
WS Gateway
   |
   +----> 在线：实时推送
   |
   +----> 离线：等待重新登录补拉
   |
   v
用户 B
   |
   | 10. 收到并处理消息
   | 11. 上报已送达/已读位置
   v
更新回执状态
```

这里需要明确区分三个状态：

| 状态        | 含义          |
| --------- | ----------- |
| Sent      | 服务端已经成功持久化  |
| Delivered | 接收端已确认收到并处理 |
| Read      | 接收端已上报阅读    |

WebSocket `WriteMessage()` 成功不等于对方已经收到，更不等于已读。

### 8.1 幂等设计

假设用户 A 因网络抖动连续发送两次：

```
clientMsgId = abc123
clientMsgId = abc123
```

服务端应只生成一条消息：

```
messageId = msg_001
seq       = 101
```

第二次请求返回第一次成功创建的消息。

需要校验同一 `clientMsgId` 对应的请求内容一致，防止不同消息意外复用同一个幂等键。

## 九、Kafka Topic 设计

你目前已经使用 Kafka 和 franz-go，可以继续复用现有基础设施。

建议不要把所有通知、IM 消息都塞进一个 Topic。

| Topic                     | 作用          | 分区 Key            |
| ------------------------- | ----------- | ----------------- |
| `business_events_v1`      | 业务领域事件      | aggregate_id      |
| `notification_tasks_v1`   | 通知投递任务      | receiver_id       |
| `notification_results_v1` | 投递结果        | delivery_id       |
| `im_message_events_v1`    | IM 已持久化消息事件 | conversation_id   |
| `im_receipt_events_v1`    | 已送达、已读事件    | conversation_id   |
| `im_dead_letter_v1`       | 无法自动处理的消息   | original_event_id |

设计重点：

1. 同一会话的 IM 消息采用相同 `conversation_id` 作为分区 Key，以利用 Kafka 分区内顺序。
2. Kafka 默认至少一次处理语义，消费者必须幂等。
3. Kafka 分区内有序不等于客户端最终严格有序；客户端还需要依据 `seq` 去重、排序、补洞。
4. 业务事务与 Kafka 发布之间采用 Transactional Outbox，避免数据库提交成功但事件丢失。
5. 通知任务消费与实际供应商发送要分离，避免短信接口阻塞整个 Kafka 消费组。

## 十、Redis 设计

Redis 主要用于在线状态、未读计数、限流和热点数据，不应作为唯一权威消息存储。

| Key                      | 数据结构     | 作用               |
| ------------------------ | -------- | ---------------- |
| `im:route:{userId}`      | Hash/Set | 用户所在 Gateway 和连接 |
| `im:presence:{userId}`   | String   | 在线状态与TTL         |
| `im:unread:{userId}`     | Hash     | 各会话未读数缓存         |
| `notify:unread:{userId}` | Hash     | 各通知分类未读数         |
| `im:send:limit:{userId}` | String   | 发送频率限制           |
| `notify:aggregate:{key}` | Hash     | 通知聚合窗口           |

注意：

- 一个用户可能同时登录手机、网页、平板，在线路由要支持多连接。
- Redis 在线状态应由心跳和租约维护。
- 未读计数需要提供从 MySQL 权威状态重建的能力。
- IM 消息的持久化确认不能依赖 Redis 写入成功。


## 十三、千万级用户、亿级消息如何扩展？

需要区分三个不同指标：

- 注册用户数：1000万
- 同时在线连接数：例如10万、100万
- 每秒消息写入量：例如1万、10万条

这三者对架构的影响完全不同。不能仅根据注册用户数量确定分片数或 Kafka 分区数。

### 13.1 存储容量示例

假设每天新增1000万条 IM 消息，平均每条数据库逻辑数据约1KB：

每天新增

# 1,000万

条消息

一年新增

# 36.5亿

条消息

一年逻辑数据

# 3.65 TB

按1KB/条估算

仅为容量模型，未包含索引、数据库副本、备份、Binlog、附件及存储引擎额外开销。

### 13.2 分阶段演进

| 阶段   | 数据库           | IM 网关 | 消息队列       |
| ---- | ------------- | ----- | ---------- |
| 初期   | MySQL 单主库     | 单节点   | Kafka      |
| 成长期  | MySQL 主从、读写分离 | 多节点   | 多分区、多消费者   |
| 大规模  | 按会话分片、冷热分层    | 网关集群  | 分区规划、独立消费组 |
| 超大规模 | 分布式存储、归档      | 跨机房部署 | 多地域容灾      |

当消息量进入亿级以后，重点不只是分库分表，还包括：

- 会话历史按 `(conversation_id, seq)` 游标查询，禁止深度 OFFSET 分页。
- 读写热点隔离，防止大群聊或高频会话成为单行锁热点。
- 历史消息冷热分层和归档。
- 按租户、用户和会话实施限流与配额。
- 建立 P95/P99 延迟、消息积压、重复投递、补拉失败率等监控。
- 设计消息保留期限、个人信息删除、内容审核和审计策略。

## 十四、生产环境必须补充的关键能力

这些能力容易在初版中遗漏，但后续补救成本很高。

| 能力     | 设计要求                     |
| ------ | ------------------------ |
| 通知偏好   | 用户可关闭营销、点赞等可选通知；安全通知独立处理 |
| 通知规则   | 事件与渠道映射，支持优先级、静默时段、频控    |
| 运营群发   | 审批、灰度、定时、取消、分批发送         |
| 短信合规   | 签名、模板审核、营销退订、发送限制        |
| IM 反垃圾 | 敏感内容审核、举报、拉黑、陌生人私信限制     |
| 媒体安全   | 私有对象存储、授权下载、恶意文件扫描       |
| 权限隔离   | 普通运维不能任意查看私人聊天内容         |
| 消息删除   | 区分仅自己删除、全局撤回、保留策略        |
| 消息同步   | 多设备独立游标、断线补拉、重复去重        |
| 灾难恢复   | 数据备份、恢复演练、Kafka 重放、投递对账  |

其中，运营群发与私信 IM 需要严格隔离权限和发送路径，防止营销系统绕过用户私信权限或发送频率限制。

## 十五、推荐的编码实施顺序

建议分四期实施，确保每一期都有可测试、可交付的业务闭环。

第一期：通知基础平台（P0）

完成模板管理、渠道接口、站内通知、短信验证码、Outbox、Kafka 消费、幂等和重试。

验收：用户注册、订单支付、视频审核都能触发相应通知。

第二期：消息中心（P0）

完成消息分类、未读计数、批量已读、历史查询、通知偏好、点赞聚合。

验收：用户能够查看点赞、评论、关注、交易等消息，未读状态正确。

第三期：单聊 IM（P1）

完成 WebSocket Gateway、会话管理、文本图片消息、消息序号、ACK、已读回执、断线同步。

验收：两个用户在不同设备上实时聊天，断网重连后不丢消息、不产生重复消息。

第四期：平台化与高可用（P2）

完成多节点 IM、消息审核、运营群发、供应商容灾、存储分片、全链路监控与压测。

验收：按目标峰值完成故障注入、负载测试、数据一致性和恢复测试。

## 十六、最终推荐架构

对于你当前的 MLC_GO 工程，我推荐：

| 技术领域    | 技术选型                            |
| ------- | ------------------------------- |
| 服务端     | Go 1.24+                        |
| HTTP    | `net/http` + 自定义路由封装            |
| 实时通信    | WebSocket                       |
| 业务数据库   | MySQL 8                         |
| 缓存与在线路由 | Redis                           |
| 消息队列    | Kafka + franz-go                |
| 图片文件    | S3 兼容对象存储                       |
| 短信      | Provider Adapter                |
| 邮件      | SMTP / 第三方邮件 API                |
| 移动推送    | APNs / FCM                      |
| 鉴权      | JWT + RBAC/ABAC                 |
| 监控      | Prometheus + OpenTelemetry      |
| 一致性     | Transactional Outbox + Inbox 幂等 |
| 历史消息分页  | 基于 `seq` 的游标分页                  |

最终应形成三个业务边界清晰的模块：

```
MLC_GO
   |
   +-- Notification
   |     模板、规则、渠道、投递、重试
   |
   +-- MessageCenter
   |     站内通知、分类、聚合、未读
   |
   +-- IM
         会话、私信、图片、实时通信、
         回执、离线同步、多设备
```

最重要的架构决策是：通知属于业务事件驱动的多渠道投递系统；IM 属于以会话和消息序号为核心的实时通信系统。两者可以共享 Kafka、Redis、MySQL、鉴权、对象存储和监控，但必须独立建模。

按照这个设计，可以先在现有 Go 工程内编码实现，再根据实际并发量逐步拆分和扩容，而不需要一开始就引入过度复杂的微服务体系。
