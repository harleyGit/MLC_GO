# 08-performance.md

## 目标
- 面向高并发与大流量场景，优先保障稳定性、延迟与资源成本。
- 当用户明确提出“大厂标准”“百万级并发”“高并发”“生产级”时，本文件规则优先级提升为最高工程约束：不能只满足功能可用，必须处理容量边界和失败模式。

## 优先级
- 先消除重复计算：重复鉴权、重复 panic 恢复、重复 body 读取
- 再做链路治理：超时、限流、熔断、降级
- 最后做深度优化：缓存命中、批处理、连接池、热点拆分
- 对高成本接口优先做削峰：限流、幂等、异步队列、对象存储直传、批处理或后台任务，不把重 I/O 全压在同步请求链路

## 规则
- 不改变对外接口语义前提下，优先做低风险高收益优化
- 请求期避免动态分配与重复拼接，拦截链在启动期装配
- CPU 密集逻辑（签名、哈希、序列化）优先减少重复执行
- I/O 密集逻辑（日志、DB、Redis）优先削峰和异步化
- 高并发链路必须正确传递 `context.Context`，避免超时、取消和链路追踪失效
- 缓存优化必须同步考虑单体缓存、列表分页缓存和 total 缓存的一致性
- 所有性能优化必须带验证结论（压测或关键指标）
- 限流必须同时评估实现原子性和算法突刺边界；固定窗口只适合低成本接口，高成本接口优先令牌桶、漏桶或滑动窗口
- 队列必须有容量上限和满队列策略；禁止无界 channel、无界 goroutine、无界内存缓存
- 大文件/大请求体链路必须限制 body 大小，优先流式处理，避免临时文件、内存、磁盘 I/O 放大
- 所有“百万级并发”结论必须区分已验证、理论可扩展和仍需基础设施支持三类，不得把理论设计说成已压测通过

## 验证
- 至少提供受影响包编译/测试结果
- 若无法全量压测，明确说明未验证项与风险
- 高并发声明必须给出验证方式：单元测试、集成测试、压测脚本、关键指标或未验证原因；缺少压测时只能说明“已做高并发设计优化”，不能说明“已支撑百万级并发”
