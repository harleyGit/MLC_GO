# 03-api-rules.md

## Handler
- 请求处理风格与当前项目一致
- 不在 handler 中堆过多业务逻辑
- 参数解析、校验、响应方式统一
- 错误码、响应结构、状态码沿用现有规范
- 高并发链路避免重复鉴权与重复恢复，统一在拦截器层做一次
- 大文件、流式上传、高并发接口不得默认使用会缓存完整 body 或产生临时文件放大的解析方式；必须优先流式读取、限制 body 大小并正确处理取消
- 对外写接口必须考虑重复提交、幂等 token、用户/IP 限流和错误快速返回，不能仅依赖前端按钮禁用

## Service
- service 负责流程组织，边界清晰
- 不过度拆分
- 不擅改业务顺序
- 事务、幂等、回滚、重试沿用现有模式
- Redis 验证码等字符串校验时，若存在 JSON 序列化入库路径，先做解码兼容再比较
- 会影响列表查询结果的写操作后，及时清理对应列表缓存（分页 key + total key）
- 高成本同步操作（上传、转码、审核、批处理、外部 I/O）必须评估是否异步化；用户要求大厂标准/百万级并发时，默认采用元数据同步落库 + 异步任务削峰的设计
- 限流算法必须匹配业务成本：高成本接口不得默认使用固定窗口；需评估令牌桶、漏桶、滑动窗口，并说明选择理由和突刺边界

## Request / Response
- 保持现有定义方式
- 不改 response 结构
- 不改对外字段名
- 不为“更优雅”破坏兼容
- DTO / Request / Response 结构体必须写清晰注释：导出结构体说明用途、调用场景和关键约束；导出字段说明业务含义、来源、单位、枚举值、默认值或前后端映射关系
- 对外接口字段新增、删除、改名或 tag 变更时，必须同步检查注释、前端调用、handler 解析、service 校验和 repository 写入

## 校验与错误
- 参数校验风格一致
- 错误返回格式、错误码、错误信息风格一致
