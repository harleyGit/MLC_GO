# 订单与账户基础

## 交付边界

本次采用方案 B：平台币唯一余额权威为 `account`，不可变流水为 `account_ledger`，事件表为 `outbox_event`。迁移文件只准备、不自动执行。新订单域目前是 DDL、数据库模型和仓储契约，不是已上线的下单、支付或退款服务。

| 迁移 | 作用 |
| --- | --- |
| `000035_rename_outbox_event` | 将既有 `outbox_events` 原地改名，保留消息、索引、租约和重试状态 |
| `000036_account_authority` | 将既有余额和权威流水原地改名，增加账户扩展列和变更前余额生成列 |
| `000037_order_foundation` | 创建交易、明细、充值、支付、退款、商品与商品 SKU 七张表 |

继续复用 `payment_recharge_sku`。不新建空余额表，不复制历史流水，不改变既有流水 ID；`coin_asset_requests`、`coin_asset_lots`、`coin_asset_allocations`、合并来源和任务游标继续参与资金事务。旧 `user_coin_commands`、`user_coin_ledger` 留作历史兼容，不成为新的写入权威。

## 与原方案的差异

- 实际用户业务标识是字符串，不采用示例中的 BIGINT user_id。
- `account` 保留 `user_id` 聚簇主键和 `balance` 字段，不重建亿级账户表来增加示例中的自增主键、account_id 或 available_balance。目前一用户一个 `MLC_COIN` 账户。
- `account_ledger` 保留原始自增 ID、request_id、operation、signed_delta 和业务关联字段，不新造 ledger_id。变更前余额为 `balance_after - signed_delta` 的 VIRTUAL DECIMAL，仅作精确整数运算，不引入浮点金额。
- 账户时间沿用既有 TIMESTAMP 精度；新订单表使用 UTC DATETIME(3)。应用及数据库会话必须使用 UTC。
- `frozen_balance` 仅预留，当前写入路径不支持冻结、解冻或多币种，不得直接启用这些字段改变余额语义。
- 现有 coin service/repository 仍是统一记账引擎，其 SQL 已指向新表。account 目录提供只读适配，不复制第二套记账逻辑。
- 现有 wallet API 仍使用 `wallet_recharge_orders`；其资产写入通过统一引擎进入新账户表。新的 `payment_recharge_order` 尚未替换钱包订单 API，不对旧订单进行隐式搬迁。
- 新目录未机械建立空 service、wechat、alipay 或第二个 Outbox worker。真实支付适配必须另行实现验签、商户/金额/币种校验、查询补偿及对账。

## 正确性边界

新表金额为整数最小单位；充值付款限 CNY，平台币到账单位为 MLC_COIN，不定义隐式汇率。充值目录快照需检查 uint64 到 int64 的边界。订单总额和明细乘法使用精确 DECIMAL CHECK 避免整数表达式溢出。

订单幂等键为用户加请求 ID。仓储实现必须对比规范化 request_hash，不能把任何重复键都当作成功。状态列目前只定义存储枚举，不代表状态机已实现。创建订单、明细及充值关联须共用短事务；支付成功更新及 Outbox 须共用短事务。事务内不得调用支付渠道或 Kafka。

支付单代表一次尝试，支持同币种全额重试，不支持混合支付。多个尝试成功或超时后回调成功必须进入实收核实和退款/对账，不能重复履约。退款累计金额需锁定原支付/交易后验证，DDL 不负责跨行退款上限。当前不是复式会计或清结算系统。

现有资产幂等请求、余额、流水、lot、分配及 Outbox 原子性不变。消费者仍需幂等，Outbox 至少一次投递不是端到端恰好一次。旧投币请求的重放兼容不能删除。

## 容量与性能

亿级数据、千万并发是设计风险基线，不是本次验证结论。没有运行压测，单个 MySQL 主库或一条账户热点行不可能仅靠索引就获得该容量保证。

- 用户订单按 `(created_at DESC,id DESC)` 游标查询，索引同向；列表最多100条，不使用深 OFFSET 或在线全表 COUNT。
- 一单明细最多100行，依靠 line_no 范围及订单内唯一键约束；超时任务按状态、截止时间和 ID 索引有界扫描。
- 同一用户账户写入仍由行锁串行化。入口应按用户限流，限制总在途请求、连接池、队列和重试预算；热点账户不能通过任意拆余额解除资金一致性约束。
- 本次没有实际分库分表路由。后续按稳定用户路由将账户、流水、幂等和 lot 同置分片；同事务关联必须在同一实例，不能先独立分 ledger 库再声称本地原子提交。
- 回调仅携带 payment_id 时需要可路由订单号或持久化路由索引，禁止广播所有分片查单。路由版本与扩容搬迁需要独立方案，不硬编码 `user_id % N` 后随意改 N。
- 不直接按 created_at 做 MySQL RANGE 分区：所有唯一键需含分区键，盲目增加时间列会破坏订单号、请求幂等和支付渠道号的唯一范围。
- 历史归档应有界、可恢复，先处理最终状态和对账，保留幂等记录及关联可追溯性。跨用户报表下沉分析存储，不在交易库做大表联查。
- 现有 Outbox 保留共享队列表结构；按域隔离容量、分片领取、死信告警和已发布归档仍需后续实现。严禁删除 pending 或未完成重试的数据。
- 现有 FEFO 查询虽然限制返回行数，失效/耗尽 lot 多时扫描量仍可能放大；账户锁等待、lot 扫描及对账聚合必须纳入真实执行计划验证。

验收至少记录代表性数据规模、索引大小、EXPLAIN、扫描/返回行数、吞吐、P95/P99、锁等待、连接池等待、复制延迟、Outbox 积压和故障恢复。需要分别测试正常用户、热点用户、重复请求、回调乱序与提交结果未知。

## 发布与恢复

1. 授权隔离环境验证 MySQL CHECK、INSTANT 加列和 VIRTUAL 生成列能力；不满足算法要求不得悄悄降级 COPY。
2. 发布前核对实际表结构、迁移版本、目标表名、外部报表/CDC/备份引用，按游标对账并检查流水到 lot、订单、幂等结果的关联；未知生产索引不能假设已存在。
3. 停止所有资金写入方、事件写入方、dispatcher 及相关后台任务，排空事务后再进入获批迁移窗口。不能让旧表名版本与新表名版本混跑。
4. 依序执行审核后的迁移，再部署对应代码。RENAME 会等待元数据锁；三份迁移及其中的多条 DDL 不构成一个可整体回滚事务，失败需确认已执行步骤，不得盲目重跑或清理 dirty 标记。
5. 验证余额、重复入账防护、退款、过期、Outbox 重放和历史订单查询后再恢复流量。本次未执行这些真实验收。

`000035.down` 可恢复旧表名；`000036.down` 仅恢复旧表名且保留新增列，因此不能直接 down 后重新 up，必须人工审核恢复步骤。启用冻结或资金扩展后禁止直接降级不识别这些字段的旧程序。`000037.down` 有意不删除交易事实，迁移版本回退不代表结构删除；不要再盲目运行 CREATE。优先向前修复，任何资金数据清理需单独授权。
