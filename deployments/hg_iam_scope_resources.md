# IAM 作用域：类型、资源与权限生效边界

## 为什么以前只有三种可分配

`iam_scope_types` 是**类型字典**，不是具体资源清单。迁移 `000076` 已登记
`global/shop/org/creator/organization/environment/crawler_project/content_channel/region`。
前 3 种原本可授权：`global` 无资源 ID；`shop` 来自已登记店铺或审核通过的商家；
`org` 来自已启用的 `iam_organizations`。其余 6 种初始为 `status=0`，
既无资源登记，也不在即时授权与 `Authorize` 允许列表中；只将字典状态改为 1 并不会让业务 API 受控。
`org` 是旧编码，`organization` 是新编码，两者不共用 ID。

## 第一阶段（迁移 `000080`；本机 debug 已确认应用）

六类新类型在迁移后状态为 1，新增 `iam_scope_resources` 登记表；
其它环境是否应用不能由本机 debug 推断。
只有活动管理员同时持有全局 `iam:role:grant` 和 `iam:role:grant_direct`
才可通过 `POST /api/v1/iam/scope-resources` 传入 `{scopeType,name}` 登记。
服务端生成不可变随机 ID，审计登记行为；`created_by + request_id` 保证同一次请求幂等。
`GET /api/v1/iam/scope-resources/list?scopeType=...&cursor=...&pageSize=...`
分页返回已启用资源的 `id/name/nextCursor/hasMore`，最多 50 条/页。
编辑用户页只展示启用且服务端已支持的类型；选中后从候选目录选择 ID，
仅有一个候选时自动填充。没有候选时不能通过构造 ID 授权。
第二阶段 `000082` 之后，人工创建的 IAM 占位记录不再出现在六类业务候选中；
须走下述业务实体创建接口才有可授权资源。

即时授权在入参校验及写入事务内复核类型状态和资源存在性，继续保持角色权限委派、
禁止自授、禁止直接授予超管、MFA 与审计等原有约束。显式调用
`Authorize(ctx,userID,permission,HGResource{ScopeType:...,ScopeID:...})`
时还会拒绝不存在或停用的新登记资源；**仅角色绑定或前端显示并不等于业务操作可用**。

## 尚未接入的业务语义

登记的是 IAM 候选资源，而非创作者账号、企业组织、运行环境、爬虫项目、
内容频道或区域的实际业务实体。本阶段不凭登记推断资源归属、业务状态或租户资格；
现有视频、爬虫、运维等接口仍按原有规则鉴权，不因新增绑定自动改权。
逐模块上线前必须确定真实业务实体与 IAM 资源 ID 的映射、创建/停用同步、
用户归属/跨租户边界、服务端传入的可信 `HGResource` 及负向测试；不能把客户端 ID 当作来源。
新增资源当前不提供停用接口，避免在尚无业务生命周期规则时误撤销已绑定的资源。

## 发布与回退

在其它环境先审阅并运行 `000080`、`000081`、`000082`，再部署新服务与前端；
混合新旧服务实例时，旧实例仍会拒绝六类绑定，不能视为完成切换。
`000080` 必须使用迁移工具连接时选定的数据库，不能通过 `USE HG_MLC_DB`
跳到共享库。迁移包含建表和字典更新：MySQL DDL 不保证整体事务回滚，
若迁移中途失败须先检查 `schema_migrations.dirty`、实际表与六类字典状态，
不可盲目重跑或直接 `force`。运行前须确认目标已有 `000079` 且 `dirty=false`。
迁移下行脚本主动拒绝自动回滚：若已登记资源或产生绑定，必须先按受控流程
核对业务影响并撤销，不能直接删除表或静默停用类型。验收不得直接写生产依赖。

### 真实授权与业务接口验收的前置条件（尚未执行）

1. 已在本机 debug 执行 `000081`、`000082`，不能再把迁移文件存在或版本已到位
   视为真实授权验收。开展有身份数据的验收前，须确认测试库独占、可丢弃或有
   可恢复快照，并确定恢复责任人和时间窗；不要发送口令、令牌或完整连接串。
   不运行会启动依赖并自动迁移的 `scripts/ensure_debug_deps.sh debug` 代替确认。
2. 明确专用测试账号/角色及写入范围：创建六类**业务实体**、MFA 批量授权另一
   专用测试用户、读取与必要的撤销/停用。实体停用保留历史授权和审计，
   不能通过下行迁移自动清除；共享 debug 库不适合随意登记测试资源。
3. 测试环境 IAM 操作账号是活动管理员，具有全局 `iam:role:read`、
   `iam:role:grant`、`iam:role:grant_direct` 和本人可用 MFA；目标是另一名专用测试用户。
   角色必须是可委派的非 `super_admin` 角色，角色权限已生效，操作者持有其完整可委派权限；
   不提供真实用户 ID、验证码或身份凭据给自动化脚本。前后端都须部署支持
   `000080` 至 `000082` 的版本，不能混用仍信任占位记录的旧实例。
4. 核验顺序：只读检查目标数据库身份、迁移版本、表和索引 →
   用专用测试账号创建业务实体 →
   候选接口有界分页回填 → 授权另一测试用户并确认绑定及伪造 ID 拒绝路径；
   在隔离测试数据上通过停用接口验证拒绝路径，不直接修改共享数据的 `status` →
   由责任人恢复数据库快照并核对授权、审计和迁移状态。验收不得操作真实用户、商家、
   运行环境或生产依赖；客户端成功提示不替代服务端权威检查。

### 第二阶段：现有业务对象与接口的待接入映射

以下是仓库当前可定位的**邻近数据**，不是自动映射；在业务负责人明确 ID、
所有者/租户、有效状态、创建和停用同步及逐个受控接口前，不把它们绑定到 IAM：

| IAM 类型 | 现有相近数据 | 不能直接映射的原因 |
| --- | --- | --- |
| `creator` | `video_submissions.user_id` | 表示投稿用户，不是可独立授权的创作者空间资源 ID；上传目前按 `global` + 本人归属判定。 |
| `organization` | `iam_organizations` 的旧 `org` 类型 | 旧编码与新编码独立；未定义企业组织实体、成员/租户关系或迁移对应关系。 |
| `environment` | debug/pre/prod 运行配置 | 部署环境不是数据库里的有界业务实体；无可给用户分配的权威 ID、状态及运维审批边界。 |
| `crawler_project` | `crawler_task_definitions.id` | 表示单个任务定义，不是项目；无项目与任务关系、项目归属或项目状态。 |
| `content_channel` | 稿件 `category` 和视频标签 | 分类/标签字符串不是有状态的内容频道实体；也不能据此推断频道管理员。 |
| `region` | 用户收货地址省市 | 收货地址不代表运营区域或商家归属；不能用个人地址划分管理员权限。 |

业务接入前必须逐类确认：权威表/创建 API、稳定 ID 和唯一性、owner/tenant 来源、
允许状态、哪些读写 API 受控、原有 `global` 授权与自有资源规则如何组合，
以及撤销/停用后已发 IAM 绑定与缓存如何失效。落实后由业务服务从权威表读取 ID，
以该值构造 `HGResource`，覆盖跨用户、跨租户、停用、越权及失败场景。

## 第二阶段进度（部分实施，业务操作尚未接通）

`000081` 已新增六类权威实体与明确关联表，`000082` 已给 IAM 目录增加
`business_verified` 默认 0 和有界候选索引；**没有从旧数据自动猜测归属**。
`POST /api/v1/iam/business-scopes` 会在一个短事务中创建业务实体与同 ID 的 IAM 资源：
`creator` 必填已有 `ownerUserId`，`environment/region` 必填唯一小写 `code`，
`crawler_project/content_channel` 可指定已启用的 `organizationId`。
当前管理入口创建 `creator` 时只允许本人 `ownerUserId`；不可由管理员冒充他人建空间，
其他创作者的本人开通与同意流程尚未接入。
创建权限目前为活动管理员全局 `iam:role:grant` + `iam:role:grant_direct`。
`POST /api/v1/iam/business-scopes/disable` 在同事务停用权威实体与 IAM 候选并推进策略版本；
有活动项目或频道的组织不能停用，历史绑定保留审计；管理页只支持停用本页刚创建的资源，
其他资源需通过受控管理接口指定准确 ID。
原 `POST /api/v1/iam/scope-resources` 保留旧客户端协议，仅登记占位 IAM 资源；
**占位记录不能通过新候选查询、授权点查和 `Authorize` 的业务实体复核**，
原有绑定若指向占位 ID 须审计后人工处理，不能自动转换。

本机 debug 已只读确认 `127.0.0.1:3306/HG_MLC_DB` 迁移为 80、`dirty=false`，
本轮按项目迁移入口依次执行 `000081`、`000082`，每次都只读复核版本，
最终确认 `migration_version=82 dirty=false`。
另以显式启用的只读测试在同一 debug 库验证六类授权/候选 SQL 的 MySQL
解析、表列和组织状态查询；未发起真实管理员 MFA 授权、浏览器验收或其它环境迁移。
部署新服务前必须先应用 `000081`、`000082`；混合旧实例时旧实例仍只查 IAM
占位表，可能接受尚无业务实体的资源，不能将该状态视为安全灰度。

### 后续业务接入与兼容边界

1. 审阅现有 debug 的 `schema_migrations` 和数据库身份；若低于 `000079`，
   **先核查中间迁移**：例如 `000076` 也含 `USE HG_MLC_DB`，不能仅因为
   `000080` 已移除硬编码库名就整批迁移。只读核查无须启动服务或基础设施。
2. `000081` 已通过新表增加权威实体、所需关联和索引；亿级表不做无保护回填、非空列改写或全表扫描。
   旧数据先保留旧授权规则；按稳定主键有界批次迁移，校验计数和关联冲突后再切读。
   无法验证归属的旧行保持未关联，不用默认区域/频道/项目伪造所有权。
3. 新实体创建与 `iam_scope_resources` 登记已在**同一个 MySQL 短事务**
   内使用同一随机 ID；候选目录和 IAM 授权点查已复核业务实体状态。
   仍需成员和对象关联写入的服务端校验及审计，
   并确保状态变更后缓存和后续请求一律失败关闭。
   原有手工 `POST /api/v1/iam/scope-resources` 创建的孤立记录只能保留 IAM
   管理语义，不能取得新业务权限；既有授权须审计并由管理员决定对应实体，
   **不自动转换**。对于业务接通的类型，候选列表及新授权应排除无业务实体的 ID。
4. 业务服务从可信数据库取归属、状态和 ID 后调用 `Authorize`；路由 Guard
   的全局权限检查不替代逐对象校验。现有 `Authorize` 对指定作用域还会尝试
   `global` 授权，`RequireOwner` 则优先拒绝非本人：两者是否继续适用于每个接口，
   必须先明确；不能为接入作用域静默移除本人限制，或把平台管理员等同于租户成员。
   列表按服务端可见边界分页过滤，不能先返回全部再逐条鉴权。
5. 停用、撤销与缓存失效使用同一权威状态；测试覆盖伪造/跨租户/停用 ID、
   无绑定、全局角色、本人/受委托用户、事务失败和跨环境请求。预发灰度与回退
   不能让旧实例继续按客户端资源 ID 放行。

后续有身份数据的真实授权和业务写入验收还须提供：非敏感目标别名与库名、
是否独占/可丢弃、当前迁移版本（含 `dirty`）、快照与恢复责任人/时间及写入范围。
已执行本机 debug 迁移和只读 SQL 检查，不构成真实授权或生产验收。
